HealthLog reads Fitbit and Pixel data through the **Google Health API**
(`health.googleapis.com`), the successor to the classic Fitbit Web API. Google
retires that older API in **September 2026**, so this connection is the path
forward for Fitbit and Pixel Watch accounts; it runs alongside the classic
Fitbit connection until then, and every account eventually re-consents through
Google OAuth.

The OAuth app is therefore a **Google Cloud** OAuth client — not a Fitbit
developer-console app. Credentials are brought **per user**: Google's
restricted-scope verification is tied to each OAuth client, so a shared,
instance-wide app is not workable. Each user pastes their own client ID and
secret in Settings.

:::note[Beta]
The connection imports live data since v1.27.4; daily activity totals (steps,
distance, floors, active energy) read correctly since v1.27.12. The Google
Health API itself is young — individual values can still be missing or shift as
Google publishes more of the wire format.
:::

## Set it up

<Steps>

1. **Create a Google Cloud OAuth client.** In
   [console.cloud.google.com](https://console.cloud.google.com) pick (or
   create) a project, enable the **Google Health API** under **APIs & Services
   → Library** (not the Fitness API, not Health Connect), configure the OAuth
   consent screen, then create an **OAuth 2.0 Client ID** of type **Web
   application**.

   On the consent screen, leave the publishing status on **Testing** — the
   deliberate choice for a self-hoster, since a Testing-mode client avoids
   Google verification and the annual CASA security assessment entirely. On
   the **Audience** page, add every account that will connect as a **test
   user** (**+ Add users**); an account not on that list is refused at the
   consent screen. An unverified client is capped at **100 users** — staying
   at or below that ceiling keeps you verification-free.

   - **Authorized redirect URI** — copy it exactly, with your own hostname:

     ```
     https://your-instance.example.com/api/google-health/callback
     ```

   The path is pinned: HealthLog refuses to start the OAuth flow if the
   resolved redirect URI does not target exactly `/api/google-health/callback`.
   Google issues a **Client ID** and **Client Secret**.

2. **Confirm the scopes.** HealthLog requests exactly these four read-only
   scopes:

   ```
   https://www.googleapis.com/auth/googlehealth.activity_and_fitness.readonly
   https://www.googleapis.com/auth/googlehealth.health_metrics_and_measurements.readonly
   https://www.googleapis.com/auth/googlehealth.sleep.readonly
   https://www.googleapis.com/auth/googlehealth.profile.readonly
   ```

   ECG, location, and intraday scopes are deliberately omitted to keep the
   Restricted-scope review surface minimal. The authorize request sends
   `access_type=offline` + `prompt=consent` so Google issues a refresh token.

3. **Wire the credentials in Settings.** Sign in as the target user, open
   **Settings → Integrations → Google Health**, and paste the client ID and
   secret. They are stored on your user record, encrypted AES-256-GCM at rest —
   not in `.env`.

4. **Connect.** Click **Connect with Google Health**. HealthLog exchanges the
   returned code for tokens, stores them encrypted, and queues a full-history
   backfill. There is **no webhook** — Google Health syncs on an hourly poll.

5. **Test the connection.** The card's connection test does a single profile
   read and reports latency. It can also run a **structure probe**: one sample
   request per data type, reduced to field names and value kinds — never actual
   readings, timestamps, or IDs. That redacted shape is safe to paste into a
   support thread when a data type imports nothing.

</Steps>

## What imports

Activity (steps, distance, active energy, floors, VO₂ max), health metrics
(weight, body fat, height, SpO₂, resting heart rate, HRV, respiratory rate,
spot heart rate), per-stage sleep, and exercise workouts.

Two limits are stated plainly up front: **stress and readiness scores are not
offered** by the Google Health API, and **skin/wrist temperature** is exposed
only as a nightly deviation, so neither imports. Google may also ask you to
reconnect from time to time — the connection shows a clear prompt when it does.

## Sync cadence and backfill

- **Hourly poll.** A background job walks every connected account once an hour
  (staggered against the other integrations). New readings appear on the next
  tick; the Settings card offers a manual sync for impatience.
- **Full-history backfill.** On first connect, a serial background job pulls up
  to **five years** of history, chunked into ≤ 90-day windows (with a 14-day
  fallback when Google rejects the larger window). Large histories take a
  while; the connection status shows when the backfill has completed.

## Redirect URI is validated strictly

The resolved `redirect_uri` is asserted at connect time to be absolute, `https`
(or `http` on localhost), to target exactly `/api/google-health/callback`, and
— when `GOOGLE_HEALTH_REDIRECT_URI` is set alongside `NEXT_PUBLIC_APP_URL` — to
share its origin. A misconfigured value fails closed rather than redirecting
elsewhere. The integration card can warn about a callback origin that differs from the address in the browser; [troubleshooting](/self-hosting/troubleshooting/#oauth-callbacks-land-on-localhost-or-the-wrong-host) says when that check works.

```env
# Only when the callback origin differs from NEXT_PUBLIC_APP_URL:
GOOGLE_HEALTH_REDIRECT_URI="https://your-instance.example.com/api/google-health/callback"
```

`GOOGLE_HEALTH_REDIRECT_URI` is not on the compose `environment:` whitelist by
default; variables not listed there never reach the container, so add it to the
`environment:` block when you set it.

For everyone else, no environment variable is involved: the redirect URI
resolves from `NEXT_PUBLIC_APP_URL`, and the client ID and secret live in the
per-user Settings card.

## Caveats

- Each operator's OAuth client needs Google brand verification plus an annual
  CASA assessment before it can leave Testing mode. In Testing mode the client
  works for the test users you list in the consent screen — fine for a
  self-host — but Google **expires the refresh token after 7 days**. When
  that happens the sync stops with a soft "needs reconnect" state rather
  than a hard error, and the Google Health card shows a **Reconnect**
  banner: click it, complete the Google consent once more, and syncing
  resumes. This is the price of avoiding CASA — expected, not a bug.
  (Publishing the client past verification removes the 7-day expiry but
  triggers the verification + CASA requirements.)
- Access tokens live one hour (the classic Fitbit API's were eight), so token
  refresh is routine; a failed refresh surfaces as a reconnect prompt, not a
  silent stall.
- If Google Health and another source both supply the same vital, the
  per-metric [source priority](/guides/source-priority/) decides which reading
  is canonical.

## Disconnect

The Settings **Disconnect** button revokes the stored tokens and removes the
connection. Previously synced measurements stay in the database.

## Garmin owners

There is no direct Garmin connector for a self-hosted instance, and there
cannot be one: Garmin's data-sharing program is business-partner-only —
approval-gated and not the "register your own app, paste a key" model the
other wearable integrations rely on. Instead, HealthLog reads Garmin data
through the phone health platform the Garmin already feeds:

- **Android:** since Garmin Connect 5.14.1 (July 2025) the app writes to
  **Google Health Connect**, so this integration is how Garmin data reaches
  HealthLog on Android.
- **iOS:** Garmin Connect writes to Apple Health automatically — use the
  [Apple Health import](/guides/import-apple-health/).

Everything Garmin shares with the platform flows in: steps, heart rate, sleep
stages, calories, distance, weight and body composition, cadence, and —
partially — blood-oxygen saturation. Garmin's **proprietary scores** (Body
Battery, HRV Status, VO₂ max, Training Load / Training Effect, Recovery Time,
Intensity Minutes, Stress score, running dynamics) are not shared with Apple
Health or Health Connect, so no self-hosted integration can obtain them — they
remain visible only inside Garmin Connect itself.
