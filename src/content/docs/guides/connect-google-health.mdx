HealthLog reads Fitbit and Pixel data through the **Google Health API**
(`health.googleapis.com`), the successor to the classic Fitbit Web API. Google
retires that older API in **September 2026**, so this connection is the path
forward for Fitbit and Pixel Watch accounts; it runs alongside the classic
Fitbit connection until then, and every account eventually re-consents through
Google OAuth.

The OAuth app is therefore a **Google Cloud** OAuth client — not a Fitbit
developer-console app. Credentials are brought **per user**: Google's
restricted-scope verification is tied to each OAuth client, so a shared,
instance-wide app is not workable. Each user pastes their own client ID and
secret in Settings.

:::note[Beta]
The connection imports live data since v1.27.4; daily activity totals (steps,
distance, floors, active energy) read correctly since v1.27.12. The Google
Health API itself is young — individual values can still be missing or shift as
Google publishes more of the wire format.
:::

## Set it up

<Steps>

1. **Create a Google Cloud OAuth client.** In
   [console.cloud.google.com](https://console.cloud.google.com) pick (or
   create) a project, enable the **Google Health API** under **APIs & Services
   → Library** (not the Fitness API, not Health Connect), configure the OAuth
   consent screen, then create an **OAuth 2.0 Client ID** of type **Web
   application**.

   On the consent screen, leave the publishing status on **Testing** — the
   deliberate choice for a self-hoster, since a Testing-mode client avoids
   Google verification and the annual CASA security assessment entirely. On
   the **Audience** page, add every account that will connect as a **test
   user** (**+ Add users**); an account not on that list is refused at the
   consent screen. An unverified client is capped at **100 users** — staying
   at or below that ceiling keeps you verification-free.

   - **Authorized redirect URI** — copy it exactly, with your own hostname:

     ```
     https://your-instance.example.com/api/google-health/callback
     ```

   The path is pinned: HealthLog refuses to start the OAuth flow if the
   resolved redirect URI does not target exactly `/api/google-health/callback`.
   Google issues a **Client ID** and **Client Secret**.

2. **Confirm the scopes.** HealthLog requests exactly these four read-only
   scopes:

   ```
   https://www.googleapis.com/auth/googlehealth.activity_and_fitness.readonly
   https://www.googleapis.com/auth/googlehealth.health_metrics_and_measurements.readonly
   https://www.googleapis.com/auth/googlehealth.sleep.readonly
   https://www.googleapis.com/auth/googlehealth.profile.readonly
   ```

   ECG, location, and intraday scopes are deliberately omitted to keep the
   Restricted-scope review surface minimal. The authorize request sends
   `access_type=offline` + `prompt=consent` so Google issues a refresh token.

3. **Wire the credentials in Settings.** Sign in as the target user, open
   **Settings → Integrations → Google Health**, and paste the client ID and
   secret. They are stored on your user record, encrypted AES-256-GCM at rest —
   not in `.env`.

4. **Connect.** Click **Connect with Google Health**. HealthLog exchanges the
   returned code for tokens, stores them encrypted, and queues a full-history
   backfill. There is **no webhook** — Google Health syncs on an hourly poll.

5. **Test the connection.** The card's connection test does a single profile
   read and reports latency. It can also run a **structure probe**: one sample
   request per data type, reduced to field names and value kinds — never actual
   readings, timestamps, or IDs. That redacted shape is safe to paste into a
   support thread when a data type imports nothing.

</Steps>

## What imports

Activity (steps, distance, active energy, floors, VO₂ max), health metrics
(weight, body fat, height, SpO₂, resting heart rate, HRV, respiratory rate,
spot heart rate), per-stage sleep, and exercise workouts.

Two limits are stated plainly up front: **stress and readiness scores are not
offered** by the Google Health API, and **skin/wrist temperature** is exposed
only as a nightly deviation, so neither imports. Google may also ask you to
reconnect from time to time — the connection shows a clear prompt when it does.

Daily totals are stored at noon of their day in your own time zone, so they
land on the right day wherever you live (since v1.39.3; see
[the timezone model](/explanation/timezone-model/#cumulative-daily-aggregates)).

## Sync cadence and backfill

- **Hourly poll.** A background job walks every connected account once an hour
  (staggered against the other integrations). New readings appear on the next
  tick; **Sync now** in the card's menu fetches them right away.
- **Full-history backfill.** On first connect a background job reads the
  account's whole history. Daily totals go back up to five years, in windows
  of up to 90 days (14 days when Google refuses the larger window).

Only one sync runs per account at a time. While the backfill that follows a
connect is running, **Sync now** says that a sync is already in progress and
shows its progress instead of starting a second one. The card says "Older
history is loading in the background" until the backfill is done.

### The backfill runs in slices

For a watch that records heart rate every minute, the history is a
thousand-odd pages per year. Since v1.42.4 the backfill reads it in slices: a
slice reads for up to five minutes or 500 pages, writes what it read, notes
how far it got and lets go of the account. The next slice starts a minute
later where the last one stopped.

Two kinds of note are kept. A data type read to the end is not read again.
A data type read page by page (heart rate, weight, body fat, blood glucose,
core temperature) keeps the time of the oldest reading it has written, so the
next slice asks Google only for what is older. A restart or an update in the
middle loses at most the page that was being read.

Asking for "what is older" uses an upper bound on the sample time. Google's
filter grammar allows it, but a given account may still refuse it. If Google
answers the first resumed request with `400`, the slice reads that data type
again without the bound, passes over the readings it already has without
writing them, and carries on writing from there. The refusal is noted per data
type, so later slices read without the bound straight away. Passing over stops
after three minutes at most, and wherever a walk stops, the slice keeps
Google's page token for the last page it read, so the next slice continues
from that page instead of passing over everything again.

The hourly sync waits for a running slice (up to eight minutes) instead of
skipping the account, so recent data keeps arriving while an old history is
still coming in. It stays inside its own fifteen-minute limit: when time runs
low the wait is cut short, and an account the hourly job reaches too late
waits for the next hour.

### Rate limits and retries

Google limits how many requests one account may make per minute. When a sync
reaches that limit Google answers `429`, and HealthLog waits and repeats the
request. If Google asks for a wait longer than a minute, the slice ends there
and the next one starts five minutes later.

A server error (`500`, `502`, `503`, `504`), a request that times out and a
dropped connection are repeated three times before they count as a failure.
None of these mark the connection as needing a reconnect. Access tokens last
an hour, and a long backfill renews its token as it goes.

A slice that moved nothing forward (no data type finished, no reading older
than before) is a real failure: the job fails with the reason, the job queue
retries it a few times, and after that the next restart of the container
offers the backfill again. Everything already written stays.

If an older version left the card asking for a reconnect after a backfill,
the first sync after updating checks the stored grant and resumes on its own
when the grant is still valid.

### Reading the backfill in the logs

Every slice writes one log line when it ends, with
`"background":{"task_name":"job.integration_backfill"}`. The parts worth
reading:

- `meta.kind` is `google-health-backfill`, `meta.slice` the slice number (0
  for the first), `meta.job_id` the job.
- `external_calls` lists the requests the slice made to Google, one entry per
  request: `method` names the data type and page (`fetchHeartRate(page=212)`),
  `status` the HTTP status, `duration_ms` how long it took. A request that was
  repeated carries a `note`:

  | `note` | Meaning |
  | --- | --- |
  | `rate_limited_retrying_in_ms=4000` | Google answered `429`; the request is repeated after the wait |
  | `server_error_retrying_in_ms=2000` | Google answered with a server error |
  | `no_response_retrying_in_ms=2000` | Timeout or dropped connection |
  | `token_rejected_retrying_with_fresh_token` | The access token was refused and renewed |
  | `edge_filter_rejected_reading_without_it` | Google refused the upper-bound filter for this data type |

  A request that failed for good carries an `error`. Successful requests are
  listed up to 60 per line and everything up to 200;
  `external_calls_omitted` counts the rest.
- `meta["googleHealth.backfill.slice"]` sums the slice up:
  - `pages`, `elapsedMs` and `imported`: what the slice read, how long it
    took and how many readings it wrote. `skippedPages` is the part of
    `pages` read only to pass over readings already written.
  - `stopReason`: why it ended. `time_budget` and `page_budget` are the
    normal end of a slice, `rate_limited` means Google would not take more
    requests for now, `job_budget` that the job itself ran out of time.
    `null` means the slice read everything it started.
  - `collectionsDone` of `collectionsTotal`: data types read to the end so
    far.
  - `collections`: one entry per data type the slice touched, with its
    `status` (`done`, `stopped` on a budget or a rate limit, `deferred` to
    the next slice, or `failed`) and its `pages`. Page-by-page types also
    carry `edgeFrom` and `edgeTo`, the oldest reading written before and
    after the slice.
  - `edges`: where every unfinished page-by-page data type stands now.
- `meta["googleHealth.backfill.edgeFilterUnsupported"]` appears on the slice
  where Google refused the upper-bound filter and lists the data types it was
  noted for.
- `action.name` is `google_health.backfill.continued` for a slice that made
  progress and queued the next one, `google_health.backfill.complete` for the
  one that finished the history, and `google_health.backfill.stuck` for one
  that moved nothing. A stuck slice also fails the job with a message that
  names each unfinished data type and its status, for example
  `no progress in slice 4, stopped on rate_limited; fetchHeartRate:stopped`.

While a slice runs, the `job.progress` line for the
`integration-backfill-admission` queue reports
`google_health_backfill_slice`, `google_health_backfill_pages` and
`google_health_backfill_collections_done` every two minutes.

### If the backfill seems stuck

A long history takes hours, sometimes a day or more, and most of that time is
spent waiting for Google's rate limit. Before you do anything:

1. Look at the newest slice lines. As long as `action.name` says
   `google_health.backfill.continued` and `edgeTo` keeps moving back in time
   from one slice to the next, the backfill is working, only slowly.
   `stopReason: "rate_limited"` on several slices in a row is normal for a
   large account.
2. Check that recent data still arrives. The hourly sync runs between slices,
   so the card should stay on **Working** with new readings.
3. If you see `google_health.backfill.stuck`, read the job's failure message:
   it names the data type that did not move and why. The job is retried a few
   times on its own. After that, restart the container to offer the backfill
   again; it resumes from its notes and does not start over.
4. If it stays stuck, copy the card's
   [details for a bug report](/guides/integrations/#details-for-a-bug-report)
   and the `meta["googleHealth.backfill.slice"]` part of the last few slice
   lines (they contain no health values or tokens) into an issue.

**Sync all data** does not unstick a running backfill. While a slice
holds the account it answers that a sync is already running, and between
slices it only competes with the backfill for the same rate limit.

## Redirect URI is validated strictly

The resolved `redirect_uri` is asserted at connect time to be absolute, `https`
(or `http` on localhost), to target exactly `/api/google-health/callback`, and
— when `GOOGLE_HEALTH_REDIRECT_URI` is set alongside `NEXT_PUBLIC_APP_URL` — to
share its origin. A misconfigured value fails closed rather than redirecting
elsewhere. The integration card can warn about a callback origin that differs from the address in the browser; [troubleshooting](/self-hosting/troubleshooting/#oauth-callbacks-land-on-localhost-or-the-wrong-host) says when that check works.

```env
# Only when the callback origin differs from NEXT_PUBLIC_APP_URL:
GOOGLE_HEALTH_REDIRECT_URI="https://your-instance.example.com/api/google-health/callback"
```

`GOOGLE_HEALTH_REDIRECT_URI` is already on the compose `environment:`
whitelist — set it in `.env` and restart.

For everyone else, no environment variable is involved: the redirect URI
resolves from `NEXT_PUBLIC_APP_URL`, and the client ID and secret live in the
per-user Settings card.

## Caveats

- Each operator's OAuth client needs Google brand verification plus an annual
  CASA assessment before it can leave Testing mode. In Testing mode the client
  works for the test users you list in the consent screen — fine for a
  self-host — but Google **expires the refresh token after 7 days**. When
  that happens the sync stops with a soft "needs reconnect" state rather
  than a hard error, and the Google Health card shows **Action needed** with
  a **Reconnect** button: click it, complete the Google consent once more,
  and syncing resumes. This is the price of avoiding CASA: expected, not a bug.
  (Publishing the client past verification removes the 7-day expiry but
  triggers the verification + CASA requirements.)
- Access tokens live one hour (the classic Fitbit API's were eight), so token
  refresh is routine; a failed refresh surfaces as a reconnect prompt, not a
  silent stall.
- If Google Health and another source both supply the same vital, the
  per-metric [source priority](/guides/source-priority/) decides which reading
  is canonical.

## Disconnect

The Settings **Disconnect** button revokes the stored tokens and removes the
connection. Previously synced measurements stay in the database.

## Garmin owners

There is no direct Garmin connector for a self-hosted instance, and there
cannot be one: Garmin's data-sharing program is business-partner-only —
approval-gated and not the "register your own app, paste a key" model the
other wearable integrations rely on. Instead, HealthLog reads Garmin data
through the phone health platform the Garmin already feeds:

- **Android:** since Garmin Connect 5.14.1 (July 2025) the app writes to
  **Google Health Connect**, so this integration is how Garmin data reaches
  HealthLog on Android.
- **iOS:** Garmin Connect writes to Apple Health automatically — use the
  [Apple Health import](/guides/import-apple-health/).

Everything Garmin shares with the platform flows in: steps, heart rate, sleep
stages, calories, distance, weight and body composition, cadence, and —
partially — blood-oxygen saturation. Garmin's **proprietary scores** (Body
Battery, HRV Status, VO₂ max, Training Load / Training Effect, Recovery Time,
Intensity Minutes, Stress score, running dynamics) are not shared with Apple
Health or Health Connect, so no self-hosted integration can obtain them — they
remain visible only inside Garmin Connect itself.
