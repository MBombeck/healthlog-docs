You want to set up how you and the people on your instance sign in, and know
what happens when something goes wrong. This page covers the password and
passkey paths, second factors, the admin's enrolment policy, single sign-on
through an OpenID Connect provider, the native app's sign-in leg, and password
reset. The account-side controls all live under **Settings, Security**; the
session, trusted-device and activity cards are under **Settings, Data &
Privacy**.

## Passwords

Registration asks for an email address, a username and a password. The
password must be at least 12 characters and score well on a strength check
that knows your username and email, and it is checked against a breach
corpus (by hashed prefix, so the password itself is never sent; the operator
can switch that check off with `PASSWORD_BREACH_CHECK_DISABLED`). Passwords are
stored as Argon2id hashes. Sign-in accepts email or username, case-insensitive,
and is limited to five attempts per 15 minutes per address. Failed attempts are
audited without the typed identifier.

Since v1.39.3 there is also a limit per account: after ten wrong passwords for
one account within fifteen minutes, password sign-in for that account pauses
until the fifteen minutes are over, whichever networks the attempts came from.
A passkey and single sign-on still work while it is paused, and entering the
right password does not use up an attempt.

Registration is open by default. The admin can close it under Admin, General;
a closed instance still accepts a valid invite link, and a fresh instance with
no accounts always allows the first signup, which becomes the admin.

To change your password, open Settings, Security and use the password card.
It asks for the current password, and for a fresh second factor if you have
one enrolled. Each attempt counts toward the same limit as every other
confirmation (five in fifteen minutes per account, see
[Confirming it is you](#confirming-it-is-you)). Changing the password ends every
other way into the account, as
[Sign out everywhere else](#sessions-devices-and-activity) does with share
links included; the browser you changed it on stays signed in with a fresh
session.

### Signing in over plain http

With `SESSION_COOKIE_SECURE=true` (or unset in production), a browser on an
`http://` address drops the sign-in cookie. Since v1.40.0 the sign-in page says
so before you start ("Signing in cannot complete on this page"), and the server
refuses such a sign-in before it checks a password or uses up a second-factor
code, so a code is no longer burnt on a sign-in that could never stick. Use
https, or set `SESSION_COOKIE_SECURE=false` for a server you only reach on your
own network. See
[Troubleshooting](/self-hosting/troubleshooting/#signing-in-cannot-complete-on-this-page).

## Passkeys

A passkey is a primary sign-in method, not a second factor: it replaces the
password at sign-in and counts as a satisfied second factor for the session it
creates. Add one under Settings, Security. Before the browser can start the
enrolment you must re-prove an existing factor: a password, a code from an
authenticator you have already confirmed, or an existing passkey or security
key. Re-proving with a password
authorises that one enrolment only; re-proving with a strong factor also
refreshes the session's step-up window. Removing a passkey asks for a fresh
factor as well, and the last passkey on an account with no password cannot be
removed.

An account can end up with a passkey and no password (for example one
provisioned through single sign-on that later adds a passkey). Sign-in then
offers the passkey directly. Self-registration always requires a password, so
there is no passkey-only signup.

## Second factors

Two kinds of second factor exist, both managed under Settings, Security:

- **Authenticator app (TOTP).** Scan the QR code and confirm one code. On
  confirmation you receive ten recovery codes in the form `XXXXX-XXXXX`. Each
  works once, they are stored hashed, and you can regenerate the whole set
  later (which asks for a fresh factor).
- **Security keys.** Hardware or platform WebAuthn keys registered as a
  second factor. These are kept separately from passkeys.

Adding either kind needs more than being signed in. Within five minutes of
signing in, or of completing a second factor, the setup starts straight away.
Later, HealthLog first asks you to confirm it is you, with your password, an
authenticator you have already confirmed, a passkey or a security key, and then
continues. An authenticator whose setup you started but never confirmed with a
code is not a second factor anywhere: its codes are refused at sign-in, at every
step-up and when confirming another change. Turning on your first second factor
signs out your other sessions and leaves tokens, connected assistants and share
links alone.

With a second factor enrolled, a correct password no longer creates a session
on its own. Sign-in returns a short-lived ticket and the second-factor step
offers the methods you have: authenticator code, recovery code, or security
key. That step allows five attempts per sign-in, counted before each one is
checked, however quickly they arrive. At that step you can tick **remember this device**. A remembered device
skips the second factor for 30 days, but only the second factor: the password
is still required, and a session that came in through a remembered device
does not count as freshly verified. A recovery-code sign-in never remembers
the device.

Disabling the second factor, removing a security key, and regenerating
recovery codes are step-up actions. Each asks for confirmation in a dialog, and
the dialog closes once the server has answered, whichever way it went, so a
refusal (usually a step-up that has gone stale) is readable on the card instead
of painting underneath the overlay.

### Step-up (fresh factor)

Some actions ask you to confirm a second factor again even though you are
signed in. The window is five minutes. Actions behind it, for accounts with a
second factor: disabling the second factor, regenerating recovery codes,
removing a security key or passkey, changing the password, deleting the
account, resetting all data, the passphrase-encrypted export, creating an
access invite, and creating, editing or deleting a managed profile or its
guardians.
Encryption-key rotation in the admin console is behind the same gate. An
account with no second factor passes these gates without a prompt; the
confirmation described under [Confirming it is you](#confirming-it-is-you) is
separate and applies to every account.

The native app can satisfy a step-up through a short-lived elevation minted
from a re-proved factor; a recovery code is deliberately not accepted there,
so an app-only user who lost the authenticator uses the web.

### Confirming it is you

Since v1.39.3 some actions ask you to confirm it is you even when no second
factor is involved, because they hand your record, or a way into it, to
someone else or change how you sign in:

- downloading the full backup, plain or encrypted;
- making a doctor share link;
- creating an assistant (MCP), measurement or document token;
- adding a passkey, an authenticator or a security key;
- changing your password or your email address.

If you signed in within the last five minutes they go straight through; with a
second factor, that means a sign-in that included it, or a passkey sign-in (a
sign-in through a remembered device does not count). Otherwise the app asks you
to confirm first:

- With a second factor turned on, use your authenticator code, your security
  key or a passkey. Your password alone is not enough, just as it is not
  enough to sign in.
- Without a second factor, enter your password or use a passkey.

One confirmation covers five minutes, so a download followed by a share link
asks once. If you signed in through single sign-on and have no password or
passkey in the app, sign in again and repeat the action within five minutes.

Every one of these confirmations, and the native app's step-up, shares one
limit per account: five attempts in fifteen minutes. Each wrong attempt is
recorded and shows in **Security activity** under Settings, Data & Privacy.

Changing the email address needs your current password unless you signed in,
completed a second factor or confirmed within the last five minutes. The
profile form shows the password field as soon as the address differs from the
saved one. Without it, the rest of the form is saved and the address stays as
it was.

The admin actions that move or replace data ask the same of the admin: see
[Admin overview](/guides/admin-overview/).

### Forced enrolment

The admin can require a second factor for the whole instance (Admin, General)
or for one account (Admin, Users). The effective requirement is either one.
An account under the policy that signs in on the web without a factor is sent
to `/enroll-mfa`, a page that shows the same security cards plus a sign-out
link, and cannot reach the rest of the app until it enrols. A primary passkey
satisfies the policy, as does an authenticator or a security key.

This is a nudge for web sessions, not an API wall. A native client or an
automation using a long-lived token keeps working until the user enrols; there
is no server-side way to mint a factor on someone's behalf, and locking a
native client out of its own data would leave it no path to enrol. To hard-gate
one account, disable it or revoke its tokens instead. The redirect clears the
moment enrolment completes.

## Single sign-on (OIDC)

HealthLog can delegate sign-in to a self-hosted OpenID Connect provider such
as Authentik, Keycloak, Authelia or Pocket-ID, using the authorization-code
flow with PKCE against one env-configured provider. By default SSO is
additive: the button appears next to password and passkey sign-in.

1. Register a confidential client at your provider with the redirect URI
   `${NEXT_PUBLIC_APP_URL}/api/auth/oidc/callback`. The comparison at the
   provider is byte-exact, including scheme, port and trailing slash.
2. Set all three of `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID` and
   `OIDC_CLIENT_SECRET`. Anything less keeps SSO fully off. The issuer must
   serve `<issuer>/.well-known/openid-configuration` and must equal the
   `issuer` inside that document.
3. Optionally set `OIDC_SCOPES` (default `openid email profile`) and
   `OIDC_BUTTON_LABEL` (default `Single Sign-On`).
4. Make sure every `OIDC_*` variable is on the compose `environment:`
   whitelist; the shipped file lists them. `pnpm check-env` flags a
   half-configured group.

How identities are matched: the first SSO sign-in either provisions a new
account (subject to the registration setting) or links to an existing account
with the same email, and only when the provider asserts
`email_verified: true`. Since v1.39.3 an existing account is never linked on
the email alone, because HealthLog never verified the address on it: anyone
could have registered with it or typed it into their profile. Instead the
sign-in page explains that the account exists, and the person signs in to it
once with its own password (and second factor) or passkey within ten minutes.
That sign-in makes the link. Either way the account is pinned to the provider's issuer and subject, and every later
sign-in matches on that pair alone. An email change at the provider updates
the displayed email but can never re-point the login. An email that already
belongs to an account pinned to a different identity is refused and audited.
There is no unlink or relink flow; moving an account to a new identity is an
operator's manual database edit.

An SSO session never satisfies a step-up gate, because the app did not see
whatever the provider checked. Accounts with their own second factor keep it:
after the provider round-trip they land in the same second-factor step
password sign-in uses. Enforce MFA at the provider for SSO-provisioned
accounts; the app's own factor remains available on top.

### `OIDC_ONLY`

`OIDC_ONLY="true"` disables password and passkey sign-in and registration
server-side: those routes return 403 with `oidc_only`, so hiding the buttons
is not the boundary. Before turning it on:

- Existing sessions survive; the flag gates new sign-ins only.
- It takes effect only while the three provider variables are fully set, so a
  typo cannot lock everyone out.
- The native app needs a build that ships the SSO handoff (below). Older
  password-only builds are locked out.
- The token exchange that completes a native SSO sign-in, the second-factor
  verify step and the refresh route are deliberately not blocked.
- Linking an existing account still works: after the provider round-trip the
  sign-in page shows the password form for that one step, and it accepts only
  the account the provider's email matched. An account that has only a
  passkey cannot be confirmed while `OIDC_ONLY` is on; turn it off for the
  first sign-in or have an operator link it.

### Break-glass

If the provider is down or misconfigured: unset `OIDC_ONLY` (or set it to
`"false"`) and `docker compose up -d`. Password and passkey sign-in are live
again immediately. Accounts that were provisioned through SSO have no
password; set one from the host as described under
[Password reset](#password-reset).

Troubleshooting for discovery mismatches, redirect-URI errors, clock skew
and the `email_verified` refusal is in the app repository's
[SSO runbook](https://github.com/MBombeck/HealthLog/blob/main/docs/self-hosting/sso.md).

## The native app

The iOS app signs in with password or passkey, or through the SSO handoff.
For SSO it opens `GET /api/auth/oidc/login?client=native` with a PKCE
challenge in a system web session; the callback returns to the fixed
`healthlog://oidc-callback` scheme with a one-time `hlh_` code (or a
second-factor ticket when the account has one), valid for 90 seconds. The app
exchanges the code at `POST /api/auth/oidc/native/token` for its normal token
bundle. A PKCE mismatch burns the code. The token pair never rides a URL, the
redirect target is compiled in (there is no `redirect_uri` parameter to
abuse), and the resulting session is never marked as freshly verified. When
the provider's email matches an account that is not linked yet, the app
receives `oidc_link_required`; confirm the account once on the web and SSO in
the app works from then on. Device setup is in [Connect the iOS app](/getting-started/connect-ios-app/).

## Sessions, devices and activity

Web sessions last 30 days and slide: after a day of use the expiry is
extended back to a full 30 days. Under Settings, Data & Privacy you can see
every session with device label, masked IP, location and last activity, sign
one out, or use **Sign out everywhere else**. Since v1.39.3 that ends every way
into your account except the device you press it on:

- every other browser and phone sign-in, with the native app's refresh
  tokens, remembered devices and step-up elevations;
- every AI assistant you connected (it has to be connected again);
- every API token: Home Assistant, scale bridges, document importers, and
  connector tokens you created by hand;
- every doctor share link, unless you untick **Also end the doctor share
  links** in the confirmation.

Share links are ended by default because a link made by someone who had your
session would keep opening your record without a sign-in. If you are sure your
links are yours, keep them.

The same page lists remembered devices and a read-only feed of security events
(**Security activity**): sign-ins, factor changes, password changes, session
revocations, exports and deletions.

## Password reset

There is no self-service "forgot password" flow. Recovery paths are:

- **Recovery codes** for a lost authenticator, as above.
- **An admin reset.** Under Admin, Users, the reset action sets a new password
  (subject to the same strength and breach checks), asks the admin to confirm
  it is them first, and in one transaction destroys the user's sessions, API
  tokens, refresh tokens, trusted devices, connected assistants and share
  links, then writes an audit row. It is a cookie-only admin call
  (`POST /api/admin/users/{id}/reset-password`); an API token cannot invoke
  it.
- **The operator CLI**, for when no admin can sign in. It runs under plain
  `node` inside the image and uses the app's own Argon2id parameters:

  ```sh
  docker compose exec app node scripts/reset-password.mjs <username-or-email>
  ```

  It prompts for the new password without echoing it. The identifier matches
  username or email case-insensitively and must resolve to exactly one user;
  the password must be at least 12 characters. Prefer the prompt over passing
  the password as a second argument, which would land in shell history.

  The script ships in the image from v1.39.3. On v1.39.2 and earlier the
  command fails with "Cannot find module"; update first, or run it from a
  source checkout of the same release (after `pnpm install`) with
  `DATABASE_URL='postgres://…' node scripts/reset-password.mjs <username-or-email>`.
