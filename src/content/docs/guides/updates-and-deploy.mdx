HealthLog ships releases roughly weekly. Each release's notes, including its
upgrade notes, are in the
[CHANGELOG](https://github.com/MBombeck/HealthLog/blob/main/CHANGELOG.md).
Read them before you pull, and pin a tag if you want to choose when an update
happens.

## The update sequence

Migrations land **before** the new app container takes traffic. On a
single-instance host the sequence is:

```bash
# 1. Get the new compose file (git pull in your checkout) and pull the new
#    image. If you pin a version with HEALTHLOG_IMAGE_REF, set it first.
git pull
docker compose pull

# 2. Optional: run the migrations with the new image before it takes
#    traffic. The one-off container starts inside the stack, so it reaches
#    the database as `db`. Its entrypoint applies the migrations and exits;
#    a failed migration stops here.
docker compose run --rm app sh -c 'exit 0'

# 3. Recreate the containers so they pick up the new image.
docker compose up -d
```

The entrypoint applies pending migrations on every start, so step 2 is only
for seeing the result before the new container serves. Use `docker compose run`
rather than a plain `docker run`: outside the stack's network `db` does not
resolve, and the entrypoint gives up after thirty seconds with "Database not
reachable".

A migration is not undone by going back to the previous image, so the way
back is a dump taken before it, and the container takes that dump itself.
When the new image brings migrations, the entrypoint first writes
`healthlog-<time>-pre-migration.dump` into the `backups` volume (the newest
always stays, an older one until it is older than every nightly dump kept) and logs `HealthLog: 2 database migrations pending. Unless
DB_BACKUP_BEFORE_MIGRATE=false, a pg_dump of the database is written ...`, or
`HealthLog: Database schema is up to date.` A dump that fails on a writable
directory, usually a full disk, stops the start before anything is migrated.
Without a volume at `DB_BACKUP_DIR` the dump lands inside the container and is
lost when the container is next recreated; take one by hand first then.
Restoring it is under
[Going back to before a migration](/guides/backups/#going-back-to-before-a-migration).
Keep the encryption key with your dumps: a dump without the key cannot be
read.

:::caution[Do not run the old and new image side by side]
Some releases drop a column the previous image still reads (v1.44.0 and
v1.46.0 do). An old container left running against the new schema then fails
on ordinary reads. Stop the old container before the new one migrates; the
sequence above does that on a single host. With a
[web/worker split](/self-hosting/scaling/), stop both roles before the first
new container starts.
:::

## Releases that need a step of their own

Most releases need nothing beyond the sequence above. These do:

| Release | What to do |
| --- | --- |
| v1.46.0 | The compose file moves the bundled database to Postgres 18 on the first `docker compose up -d`. Needs free disk about the size of the database. See [Moving to Postgres 18](/self-hosting/postgres-upgrade/). Also check: a proxy that reaches the app from a public address has to be listed in [`TRUSTED_PROXY_CIDRS`](/guides/reverse-proxy/#trusted_proxy_cidrs), or every user shares one sign-in rate limit; deletions now wait 14 days before they are final (`ACCOUNT_DELETION_GRACE_DAYS=0` keeps them immediate, see [The grace window](/account/data-deletion/#the-grace-window)). |
| v1.45.0 | With a web/worker split, start the new worker first and the web containers after its log shows `"reminder_worker": "started"`. Add `stop_grace_period: 45s` to a forked compose file. |
| v1.43.0 | Run v1.42.x first and let it finish its location backfill. A host that skips it stops at migration 0409; see [below](#migration-0409-stops-the-upgrade). |
| v1.42.0 | The database container restarts once (it now loads `pg_stat_statements`). Background jobs repair and clean up folded Apple Health data; afterwards start the maintenance run (see [Database maintenance](/self-hosting/database-maintenance/)). Behind PgBouncer set `DATABASE_SESSION_OPTIONS_DISABLED=1` first. |

### Migration 0409 stops the upgrade

v1.42 seals home locations, location periods and daily locations, and its
encryption backfill clears the readable copies account by account. Migration
`0409_drop_plaintext_location` first counts the rows that still hold a
readable location. If any count is above zero it stops, and the container
exits during the migration step with:

```text
Migration name: 0409_drop_plaintext_location
Database error code: P0001
ERROR: HealthLog migration 0409 stopped: 3 home location(s), 0 location period(s) and 12 daily location(s) are still stored in plaintext. ...
```

Every later start refuses with `P3009` until the failed attempt is cleared.
Nothing was dropped: the check runs before any other statement of the
migration. The migrations before it did apply; they only add tables, columns
and enum values, and v1.42.4 runs on top of them unchanged.

This happens on a host that went from v1.41 straight to v1.43, or that was
stopped soon after updating to v1.42, so the backfill never reached every
account. To recover, clear the failed attempt first, because v1.42.4 also
runs the migrations on start and refuses to boot while one is recorded as
failed:

```bash
# 1. Mark the failed attempt as rolled back. The entrypoint is replaced so
#    the container does not try to migrate first.
docker compose run --rm --entrypoint sh app -c \
  'NODE_PATH=/opt/prisma-cli/node_modules node /opt/prisma-cli/node_modules/prisma/build/index.js migrate resolve --rolled-back 0409_drop_plaintext_location'

# 2. Start the previous release: set HEALTHLOG_IMAGE_REF=:v1.42.4 in the
#    compose .env (or your platform's environment), then recreate.
docker compose up -d app
```

v1.42.4 starts the encryption backfill about three minutes after boot and
again once a day, one account at a time. Watch the three counts the
migration checks until all three are 0:

```bash
docker compose exec -T db psql -U healthlog healthlog -c "
  SELECT
    (SELECT count(*) FROM users WHERE home_lat IS NOT NULL) AS home,
    (SELECT count(*) FROM environment_travel_locations WHERE lat IS NOT NULL) AS periods,
    (SELECT count(*) FROM environment_contexts WHERE lat IS NOT NULL) AS days;"
```

Each pass logs `[free-text-encryption-backfill] user=...` lines. If the counts
stop going down, look for a line ending in `failed`; the error on the line
after it names the cause. Once all three are 0, dump the database again,
remove the pin (or set it to the new version), pull and recreate. Migration
0409 then runs through.

:::danger[Two shortcuts that lose data]
Do not set the readable columns to `NULL` by hand to get past the check:
those values have no sealed copy yet, so the location is gone for good. Do
not run `migrate resolve --applied 0409_drop_plaintext_location` either; it
records the migration as done while the columns are still there, and the
v1.43 schema no longer matches the database.
:::

The same steps are in the app repository as
[`docs/ops/migration-0409-plaintext-location.md`](https://github.com/MBombeck/HealthLog/blob/main/docs/ops/migration-0409-plaintext-location.md).

## Rolling back

Migrations are forward-only, and the previous image is not guaranteed to read
the newer schema. Rolling back therefore means restoring the dump the
container took before it migrated, with the previous image pinned; the steps
are under
[Going back to before a migration](/guides/backups/#going-back-to-before-a-migration).
A dump you took by hand restores as described in
[Restore a database dump](/guides/backups/#restore-a-database-dump).

Anything written after the dump is lost, so roll back early or not at all.
From v1.46.0 back to v1.45 the old Postgres 16 volume is the way back instead;
see [Going back](/self-hosting/postgres-upgrade/#going-back).

## Verify the served version

The deploy status of your platform is not the source of truth; the version the
server answers is. `/api/version` needs no sign-in and returns `version`,
`buildSha` and `builtAt`:

```bash
curl -s https://your-instance.example.com/api/version
```

Probe it twice, a few seconds apart: during the container swap a single probe
can be answered by the outgoing container. If the version is old, check the
image the container really runs
(`docker inspect healthlog-app --format '{{.Config.Image}}'`) and that the
compose file still has `pull_policy: always`.

## Pin the image by digest

Tags (`:latest`, `:v1.46.0`) are mutable aliases. The digest is the image's
only immutable identity, and it is what the release signature covers. The
compose file's `app` image is `ghcr.io/mbombeck/healthlog${HEALTHLOG_IMAGE_REF:-:latest}`,
so set `HEALTHLOG_IMAGE_REF` in the `.env` next to the compose file (or in the
deployment platform's env vars) to change the reference without editing the
file: `:v1.46.0` pins a tag, `@sha256:<digest>` pins the digest. Resolve a
release's digest with

```bash
docker buildx imagetools inspect ghcr.io/mbombeck/healthlog:vX.Y.Z | grep -m1 Digest
```

which returns the manifest-list digest covering both architectures.

Every release image is signed keyless through Sigstore by the release
workflow, so a digest can be verified before it is pinned:

```bash
cosign verify \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp 'https://github.com/MBombeck/HealthLog/\.github/workflows/docker-publish\.yml@refs/tags/v.*' \
  ghcr.io/mbombeck/healthlog:vX.Y.Z
```

:::caution[A pin is sticky, and a stale pin is silent]
A pinned instance never follows a release on its own. Every later deploy ships
the pinned reference until somebody changes it, and the deploy still reports
success. If you pin, bumping the pin is part of shipping. After any deploy
check two things: `/api/version` reports the version and commit you shipped,
and the running container's image is the one you expect
(`docker inspect <container> --format '{{.Config.Image}}'`). Probe
`/api/version` more than once a few seconds apart: during the container swap a
single probe can be answered by the outgoing container.
:::
