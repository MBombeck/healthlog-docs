Each release's notes, including its upgrade notes, are in the
[CHANGELOG](https://github.com/MBombeck/HealthLog/blob/main/CHANGELOG.md).
Read them before you pull, and pin a tag if you want to choose when an update
happens.

## Release schedule

HealthLog ships on a calendar. A feature release comes out on the first
Saturday of every month. On the other Saturdays there is a patch release with
fixes, if there is anything to fix; a week with nothing worth shipping has no
release. Nothing else ships in between, with one exception: a security
problem, lost data or an install that does not start gets a fix as soon as it
is ready, and the release notes say why in their first sentence.

For a self-hoster that means one update a month to read about, a small one on
some Saturdays, at the weekend when there is time for it, and no reason to pull
images every day. 1.49.0 is the last release before the calendar; the first
scheduled feature release is 1.50.0.

| Release | When | What it may contain |
| --- | --- | --- |
| Minor, `X.Y.0` | first Saturday of the month | features, new settings, API additions, compose and environment changes, removals announced one minor ahead |
| Patch, `X.Y.Z` | other Saturdays, when needed | fixes and security fixes only, and a migration only when a fix needs it |
| Out of schedule | as soon as the fix is ready | one fix for a security problem, lost data or a broken install |

Minor releases are the ones that can drop a column or retire a route, always
announced in the notes of the minor before; read their notes first. A patch
never needs more than the update sequence below, unless its notes say a fix
needed an additive migration.

The `:edge` image is built from every push to `main` and carries fixes that are
merged but not yet released. It is amd64 only and there to check a fix before
its Saturday, not to run on: take a backup first, because migrations do not run
backwards. Production installs track a release tag or `:latest`. The full rule
is in the repository's
[release policy](https://github.com/MBombeck/HealthLog/blob/main/docs/contributing/release-policy.md).

## The update sequence

Migrations land **before** the new app container takes traffic. On a
single-instance host the sequence is:

```bash
# 1. Get the new compose file (git pull in your checkout) and pull the new
#    image. If you pin a version with HEALTHLOG_IMAGE_REF, set it first.
git pull
docker compose pull

# 2. Optional: run the migrations with the new image before it takes
#    traffic. The one-off container starts inside the stack, so it reaches
#    the database as `db`. Its entrypoint applies the migrations and exits;
#    a failed migration stops here.
docker compose run --rm app sh -c 'exit 0'

# 3. Recreate the containers so they pick up the new image.
docker compose up -d
```

The entrypoint applies pending migrations on every start, so step 2 is only
for seeing the result before the new container serves. Use `docker compose run`
rather than a plain `docker run`: outside the stack's network `db` does not
resolve, and the entrypoint gives up after thirty seconds with "Database not
reachable".

A migration is not undone by going back to the previous image, so the way
back is a dump taken before it, and the container takes that dump itself.
When the new image brings migrations, the entrypoint first writes
`healthlog-<time>-pre-migration.dump` into the `backups` volume (the newest
always stays, an older one until it is older than every nightly dump kept) and logs `HealthLog: 2 database migrations pending. Unless
DB_BACKUP_BEFORE_MIGRATE=false, a pg_dump of the database is written ...`, or
`HealthLog: Database schema is up to date.` A dump that fails on a writable
directory, usually a full disk, stops the start before anything is migrated.
Without the `backups` volume no dump is kept: the log says so and the
migrations run anyway, so run `pg_dump` yourself before step 1 (see
[Dumps taken by hand](/guides/backups/#dumps-taken-by-hand)).
Restoring it is under
[Going back to before a migration](/guides/backups/#going-back-to-before-a-migration).
Keep the encryption key with your dumps: a dump without the key cannot be
read.

:::caution[Do not run the old and new image side by side]
Some releases drop a column the previous image still reads (v1.44.0 and
v1.46.0 do). An old container left running against the new schema then fails
on ordinary reads. Stop the old container before the new one migrates; the
sequence above does that on a single host. With a
[web/worker split](/self-hosting/scaling/), stop both roles before the first
new container starts.
:::

Most releases need nothing beyond the sequence above. These do:

Check for accounts that differ only in case first, or migration 0517 stops the start. The push relay is new and off until an admin turns it on; `PUSH_RELAY_MODE`, `PUSH_RELAY_URL`, `PUSH_RELAY_KEYS`, `PUSH_RELAY_LIVE_ACTIVITY` and `HEALTH_CONNECT_WEBDAV_PRIVATE_ORIGINS` are optional and on the compose whitelist, so pull the new compose file. See [The v1.49.0 update](#the-v1490-update). |
| v1.48.0 | Eleven migrations run on the first start (0499 to 0509: nutrient targets, lab result identities, provider chains, the Fitbit cleanup, the seizure diary, an index for deleted readings, GLP-1 step ids and the hypertension event type); on a large instance give the first start a minute or two. The index is built without locking the table. The Fitbit integration is gone, so `FITBIT_REDIRECT_URI` is no longer read and can be removed from your environment. Upload an Apple Health export once more to pick up lab results from Health Records. The Fitbit tables stay in the database for this release, so going back to v1.47.6 works; the steps are in `docs/ops/deploy.md` in the app repository. |

### The v1.49.0 update

v1.49.0 brings twenty-seven migrations, `0514` to `0545` (the numbers `0516`,
`0523`, `0527`, `0528` and `0541` do not exist), so the boot log says
`27 database migrations pending`. Most add tables and columns. Four touch
data you already have:

- `0515` merges doses that two sources recorded for the same slot (a take wins
  over a skip, and a merged take gives its units back to the pack), clears the
  missed mark on doses that were taken or skipped, and stores the dose window
  of older single-time schedules.
- `0517` makes e-mail addresses and usernames unique regardless of case. If two
  accounts share one, it stops and the container does not start; see
  [Accounts that differ only in case](#accounts-that-differ-only-in-case).
  While it runs, writes to the accounts table wait, so an old container that
  still serves cannot add a clashing account halfway through.
- `0529` stores Apple push tokens in lower case. Where two devices held the same
  token in different case, the one seen most recently keeps it, and the other
  registers again on its next launch. Device writes wait while it runs.
- `0543` records where each symptom on a cycle day came from: a symptom on a
  day imported from Apple Health or another import takes that day's source,
  every other one counts as entered by hand. An Apple Health import then
  replaces only the symptoms it wrote, and the ones you logged yourself on the
  same day stay.

Two more change data only on an instance that ran a 1.49 pre-release; coming
from 1.48 they find nothing to change:

- `0539` stores the pregnancy state encrypted. It drops the plaintext columns
  `0533` added (the state, the start, due and delivery dates) and their enum.
  A state set under a pre-release is cleared and has to be set again.
- `0540` records who made a care calendar feed or an emergency card link, so a
  link a guardian made for a managed profile ends with the guardian's access.
  Existing links count as made by their owner.

`0542`, `0544` and `0545` add one column each with no effect on existing rows.
`0518` builds an index on `measurements` without locking the table while the
container starts. On a large instance the first start takes longer than usual;
let it finish rather than restarting the container.

Before you update:

<Steps>

1. Make sure the `backups` volume is mounted (it is in the published compose
   file), or take a dump by hand. Copy the pre-migration dump off the host once
   it is written: it is the way back.

2. Run the query under
   [Accounts that differ only in case](#accounts-that-differ-only-in-case) and
   resolve any pair it lists.

3. Follow [the update sequence](#the-update-sequence).

</Steps>

If `0517` stops the start anyway, that is not a reason to go back: nothing was
changed. Resolve the pairs as described in
[Accounts that differ only in case](#accounts-that-differ-only-in-case) and
start again.

**Going back to 1.48.5.** Switching the image back alone does not work: after
`0515`, `0517` and `0529` the old image writes rows the new indexes refuse
(after `0517`, an address or username that differs from another account's only
in case). Restore the pre-migration dump with the 1.48.5 image instead, as
described in
[Going back to before a migration](/guides/backups/#going-back-to-before-a-migration),
with `HEALTHLOG_IMAGE_REF=:v1.48.5` in the `.env` next to the compose file (the
leading colon is part of the value; `@sha256:<digest>` pins the digest
instead). Anything written since the update is lost, so decide early.

Only the dump undoes these:

- `0515`: merged doses, refunded packs, cleared missed marks and rewritten
  schedules stay as they are; the previous values are not kept.
- `0529`: tokens stay in lower case, and the device that lost a clash keeps no
  token.
- `0514` and `0519`: the new measurement types cannot be removed from the
  database, and the old image fails on a reading of one of them.

No other migration needs the dump. If the dump is gone, the operator notes for
[v1.49.0](https://github.com/MBombeck/HealthLog/blob/main/docs/ops/deploy.md#v1490-notes)
list the three statements that let the old image run on the migrated database,
and what stays changed.

### The v1.47.0 image

v1.47.0 moves the app image from Alpine to the official Node 22 image on
Debian slim. The runtime is glibc now, and the native page renderer, password
hashing and the Prisma engine run their glibc builds. The published arm64
image renders PDF pages on a Raspberry Pi 4 again. Node security releases
reach the image with the official Node image, usually within days. Inside the
container:

- **No package manager.** npm, npx, corepack and yarn are removed. The
  operator scripts still run with `node`, for example
  `docker compose exec app node scripts/reset-password.mjs <username-or-email>`.
- **No `psql` in the app container.** Run it in the `db` container:
  `docker compose exec db psql -U healthlog`. `pg_dump` and `pg_restore` are
  still in the app image, at PostgreSQL 18.6, the bundled database's version.
- **Health checks.** The current `docker-compose.yml` probes `/api/health`
  with Node directly. A compose file copied before this release, or a platform
  template, that still health-checks with `wget` keeps working: the image
  carries a small `wget` that answers health checks and nothing else. Switch
  to the probe in the current compose file when you next update yours.

### Accounts that differ only in case

From 1.49.0 an e-mail address and a username are unique regardless of case,
because sign-in already treats `Name@host` and `name@host` as the same
address. Migration `0517_case_insensitive_identity_and_retention_indexes`
first counts the addresses and names that two accounts on the instance share
when case is ignored. When there are any, it stops with

```text
HealthLog 0517: 1 e-mail address(es) and 0 username(s) belong to more than one account when case is ignored; no account was changed.
```

and the container does not start. Nothing is merged or renamed for you. List
the accounts:

```bash
docker compose exec -T db psql -U healthlog healthlog -c "
  SELECT id, username, email, created_at FROM users
   WHERE lower(email) IN (SELECT lower(email) FROM users WHERE email IS NOT NULL
                           GROUP BY 1 HAVING count(*) > 1)
      OR lower(username) IN (SELECT lower(username) FROM users
                              GROUP BY 1 HAVING count(*) > 1)
   ORDER BY lower(email), lower(username), created_at"
```

Decide which account of each pair keeps the address or name, and give the
other one a different one
(`UPDATE users SET email = '…' WHERE id = '…'`, or `username`). The migration
runs as one transaction, so the failed attempt changed nothing, but Prisma
keeps it on record as failed. Mark it rolled back, then start the container
again:

```bash
docker compose run --rm --entrypoint sh app -c \
  'NODE_PATH=/opt/prisma-cli/node_modules node /opt/prisma-cli/node_modules/prisma/build/index.js migrate resolve --rolled-back 0517_case_insensitive_identity_and_retention_indexes'
docker compose up -d
```

The same migration drops six indexes that only repeated another one in
descending order, adds the indexes the retention clean-ups need, and checks
the shape of the dates stored as text (`YYYY-MM-DD`). A column that already
holds a row in another shape gets the check for new writes only, and the
count is logged.

### How a migration runs

Every start runs `prisma migrate deploy` before the server starts. A
migration file with a `DO` block, which is almost all of them, runs as one
transaction: it applies whole or not at all. A file that bounds its wait for
a table lock is marked for retry, and when it times out waiting for a lock that
another session holds, the start retries it after 15, 30, 60, 120 and 240
seconds and goes on as soon as an attempt gets the lock. A file that builds an
index without locking the table (such as 0518) is retried the same way, after
the half-built index is dropped. Any other failure stops the start. The retries fit inside the container's ten-minute start period. The
details for operators are in the app repository's
[`docs/ops/migrations/README.md`](https://github.com/MBombeck/HealthLog/blob/main/docs/ops/migrations/README.md)
and [`docs/ops/deploy.md`](https://github.com/MBombeck/HealthLog/blob/main/docs/ops/deploy.md).

### Migration 0409 stops the upgrade

v1.42 seals home locations, location periods and daily locations, and its
encryption backfill clears the readable copies account by account. Migration
`0409_drop_plaintext_location` first counts the rows that still hold a
readable location. If any count is above zero it stops, and the container
exits during the migration step with:

```text
Migration name: 0409_drop_plaintext_location
Database error code: P0001
ERROR: HealthLog migration 0409 stopped: 3 home location(s), 0 location period(s) and 12 daily location(s) are still stored in plaintext. ...
```

Every later start refuses with `P3009` until the failed attempt is cleared.
Nothing was dropped: the check runs before any other statement of the
migration. The migrations before it did apply; they only add tables, columns
and enum values, and v1.42.4 runs on top of them unchanged.

This happens on a host that went from v1.41 straight to v1.43, or that was
stopped soon after updating to v1.42, so the backfill never reached every
account. To recover, clear the failed attempt first, because v1.42.4 also
runs the migrations on start and refuses to boot while one is recorded as
failed:

```bash
# 1. Mark the failed attempt as rolled back. The entrypoint is replaced so
#    the container does not try to migrate first.
docker compose run --rm --entrypoint sh app -c \
  'NODE_PATH=/opt/prisma-cli/node_modules node /opt/prisma-cli/node_modules/prisma/build/index.js migrate resolve --rolled-back 0409_drop_plaintext_location'

# 2. Start the previous release: set HEALTHLOG_IMAGE_REF=:v1.42.4 in the
#    compose .env (or your platform's environment), then recreate.
docker compose up -d app
```

v1.42.4 starts the encryption backfill about three minutes after boot and
again once a day, one account at a time. Watch the three counts the
migration checks until all three are 0:

```bash
docker compose exec -T db psql -U healthlog healthlog -c "
  SELECT
    (SELECT count(*) FROM users WHERE home_lat IS NOT NULL) AS home,
    (SELECT count(*) FROM environment_travel_locations WHERE lat IS NOT NULL) AS periods,
    (SELECT count(*) FROM environment_contexts WHERE lat IS NOT NULL) AS days;"
```

Each pass logs `[free-text-encryption-backfill] user=...` lines. If the counts
stop going down, look for a line ending in `failed`; the error on the line
after it names the cause. Once all three are 0, dump the database again,
remove the pin (or set it to the new version), pull and recreate. Migration
0409 then runs through.

:::danger[Two shortcuts that lose data]
Do not set the readable columns to `NULL` by hand to get past the check:
those values have no sealed copy yet, so the location is gone for good. Do
not run `migrate resolve --applied 0409_drop_plaintext_location` either; it
records the migration as done while the columns are still there, and the
v1.43 schema no longer matches the database.
:::

The same steps are in the app repository as
[`docs/ops/migration-0409-plaintext-location.md`](https://github.com/MBombeck/HealthLog/blob/main/docs/ops/migration-0409-plaintext-location.md).

## Rolling back

Migrations are forward-only, and the previous image is not guaranteed to read
the newer schema. Rolling back therefore means restoring the dump the
container took before it migrated, with the previous image pinned; the steps
are under
[Going back to before a migration](/guides/backups/#going-back-to-before-a-migration).
A dump you took by hand restores as described in
[Restore a database dump](/guides/backups/#restore-a-database-dump).

Anything written after the dump is lost, so roll back early or not at all.
From v1.46.0 back to v1.45 the old Postgres 16 volume is the way back instead;
see [Going back](/self-hosting/postgres-upgrade/#going-back).

## Verify the served version

The deploy status of your platform is not the source of truth; the version the
server answers is. `/api/version` needs no sign-in and returns `version`,
`buildSha` and `builtAt`:

```bash
curl -s https://your-instance.example.com/api/version
```

Probe it twice, a few seconds apart: during the container swap a single probe
can be answered by the outgoing container. If the version is old, check the
image the container really runs
(`docker inspect healthlog-app --format '{{.Config.Image}}'`) and that the
compose file still has `pull_policy: always`.

## Pin the image by digest

Tags (`:latest`, `:v1.46.0`) are mutable aliases. The digest is the image's
only immutable identity, and it is what the release signature covers. The
compose file's `app` image is `ghcr.io/mbombeck/healthlog${HEALTHLOG_IMAGE_REF:-:latest}`,
so set `HEALTHLOG_IMAGE_REF` in the `.env` next to the compose file (or in the
deployment platform's env vars) to change the reference without editing the
file: `:v1.46.0` pins a tag, `@sha256:<digest>` pins the digest. Resolve a
release's digest with

```bash
docker buildx imagetools inspect ghcr.io/mbombeck/healthlog:vX.Y.Z | grep -m1 Digest
```

which returns the manifest-list digest covering both architectures.

Every release image is signed keyless through Sigstore by the release
workflow, so a digest can be verified before it is pinned:

```bash
cosign verify \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp 'https://github.com/MBombeck/HealthLog/\.github/workflows/docker-publish\.yml@refs/tags/v.*' \
  ghcr.io/mbombeck/healthlog:vX.Y.Z
```

:::caution[A pin is sticky, and a stale pin is silent]
A pinned instance never follows a release on its own. Every later deploy ships
the pinned reference until somebody changes it, and the deploy still reports
success. If you pin, bumping the pin is part of shipping. After any deploy
check two things: `/api/version` reports the version and commit you shipped,
and the running container's image is the one you expect
(`docker inspect <container> --format '{{.Config.Image}}'`). Probe
`/api/version` more than once a few seconds apart: during the container swap a
single probe can be answered by the outgoing container.
:::
