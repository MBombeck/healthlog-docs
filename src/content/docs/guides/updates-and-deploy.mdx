HealthLog ships releases roughly weekly. Pin a tag, back up before upgrades, and
skim the [changelog](https://github.com/MBombeck/HealthLog/blob/main/CHANGELOG.md)
before pulling `latest`.

## Migration ordering

Migrations land **before** the new app container takes traffic. On a
single-instance host the canonical sequence is:

```bash
# 0. Dump the database first. A migration is not undone by going back to
#    the previous image; the dump is the way back.
docker compose exec -T db pg_dump -U healthlog healthlog \
  | gzip > healthlog-before-update-$(date +%F).sql.gz

# 1. Pull the new image. If you pin a version with HEALTHLOG_IMAGE_REF,
#    set it to the new one first.
docker compose pull app

# 2. Run the migrations with the new image before it takes traffic. The
#    one-off container starts inside the stack, so it reaches the database
#    as `db` and gets the same environment as the app. Its entrypoint
#    applies the migrations and exits; a failed migration stops here.
docker compose run --rm app sh -c 'exit 0'

# 3. Recreate the app container so it picks up the new image.
docker compose up -d app
```

Use `docker compose run` rather than a plain `docker run` for step 2. A plain
`docker run` starts outside the stack's network, where `db` does not resolve,
and the entrypoint gives up after thirty seconds with "Database not reachable".
The entrypoint also runs the migrations on every boot, so step 2 is optional; it
is there for when you want to see the migration result before the new container
takes traffic.

Keep the dump until the new version has run for a few days, and keep your
encryption key with it: a dump without the key cannot be read. The command
assumes the bundled `db` service; with an
[external Postgres](/self-hosting/external-postgres/) run `pg_dump` against
that server instead.

### The pending-migrations line

Since v1.42.4 the container says what is about to happen before it applies
migrations:

```text
HealthLog: 2 database migrations pending. Back up the database before updating (pg_dump, see the Updates section of docs/self-hosting/getting-started.md); a migration is not undone by going back to the previous image.
HealthLog: Running database migrations...
```

or `HealthLog: Database schema is up to date.` when the image brings none.
If the count cannot be read, the line says so and the start continues. The
line is a reminder and does not pause anything: the migrations run right
after it. That is why the dump belongs before the pull, in step 0, and not
after you have seen the count.

:::caution[Do not start the app before migrations run]
If the new container starts against the old schema, Prisma throws
`P2022 column does not exist` on the first query that touches the new shape, the
request 500s, and the dispatcher logs fill with the same error. `/api/version`
does not exercise the affected tables, so the container stays "healthy" and a
naïve load balancer routes real traffic into the broken shell.
:::

## Migrations in the v1.30 line

Three migrations shipped between v1.30.15 and v1.30.34. All three are additive
and need no operator action beyond the normal `migrate deploy`:

| Migration | Release | What it adds |
| --- | --- | --- |
| `0254_document_summary_state` | v1.30.31 | A state column on documents so the four summary outcomes can be told apart. Documents that already hold a summary are moved to `READY`; every other pre-existing row is truthfully "not attempted". |
| `0255_session_token_hash` | v1.30.33 | A nullable hash column on sessions for the new cookie shape. |
| `0256_medication_inventory_pen_labelling` | v1.30.34 | Manufacturer and printed strength on an inventory container, both nullable. |

:::note[v1.30.33 does not sign anyone out]
`0255` is nullable on purpose. Every session that exists when you deploy keeps a
`NULL` hash and stays resolvable the old way, so nobody is logged out. Those rows
cannot have their sliding expiry extended, so the old scheme drains itself within
the normal 30-day session lifetime with no operator action. Every sign-in from
v1.30.33 onward uses the new scheme.

What *does* sign everyone out is rotating `API_TOKEN_HMAC_KEY`, which now keys
session cookies as well as API tokens — see
[environment variables](/reference/environment-variables/).
:::

## Migration 0339 in v1.38.18

Take a backup before deploying v1.38.18, and expect no image rollback without
one. Migration `0339_retire_wizard_columns` drops `users.onboarding_step` and
`users.onboarding_goals`, two columns the v1.38.16 and v1.38.17 images select
on every session load. An older image against a migrated database therefore
fails at login, not only on the retired wizard.

Rolling the image back means restoring the database, or re-adding the two
columns with their defaults. The second is loss-free, because nothing at
v1.38.18 writes them:

```sql
ALTER TABLE users
  ADD COLUMN onboarding_step integer NOT NULL DEFAULT 0,
  ADD COLUMN onboarding_goals text[] NOT NULL DEFAULT '{}';
```

`onboarding_completed_at` stays; it gates the first-run redirect and the
needs-based flow keeps stamping it.

## Migrations 0343, 0344 and 0345 in v1.39.0

Take a backup before deploying v1.39.0. Two of the migrations remove data, and
one of them changes settings for some accounts.

`0343_ai_capability_switches` reshapes the assistant switches on the admin
Coach page:

- It adds the **Reading documents** switch, on by default.
- Where the Coach module was switched off under module availability, it turns
  the **Coach** switch off instead, and removes the Coach entry from module
  availability.
- For every account that had hidden the Coach, it switches **AI analysis** off
  (the `insights` module). Hiding the Coach used to stop the nightly briefing and
  status notes as well; from this release it hides the Coach and nothing else,
  so these accounts keep the privacy they chose. They can switch AI analysis
  back on under Settings, Modules.
- It drops the column behind the retired **Correlations** switch.

`0344_insight_status_cache` moves the per-metric status notes out of the audit
log into their own table, encrypted at rest, one row per metric and language.
It deletes the old rows from the audit log and copies nothing, because a
migration cannot encrypt. Expect one night in which every note is written again,
which costs about one normal night of model use on top.

`0345_cycle_absorbed_start` only adds a column. It remembers which period start
was folded into an earlier one, so deleting a start tapped by mistake brings
the later one back.

Restoring an instance backup taken before v1.39.0 applies the same Coach change
as `0343`: a Coach switched off under module availability comes back as the
**Coach** switch turned off.

An older image against the migrated database still reads the dropped
Correlations column. Rolling back means restoring the backup, or re-adding the
column with its old default:

```sql
ALTER TABLE app_settings
  ADD COLUMN assistant_correlations_enabled boolean NOT NULL DEFAULT true;
```

Re-adding the column does not bring back the deleted status notes or undo the
AI analysis change; the older image writes the notes again on its next nightly
run.

### Migration 0409 stops the upgrade

v1.42 seals home locations, location periods and daily locations, and its
encryption backfill clears the readable copies account by account. Migration
`0409_drop_plaintext_location` first counts the rows that still hold a
readable location. If any count is above zero it stops, and the container
exits during the migration step with:

```text
Migration name: 0409_drop_plaintext_location
Database error code: P0001
ERROR: HealthLog migration 0409 stopped: 3 home location(s), 0 location period(s) and 12 daily location(s) are still stored in plaintext. ...
```

Every later start refuses with `P3009` until the failed attempt is cleared.
Nothing was dropped: the check runs before any other statement of the
migration. The migrations before it did apply; they only add tables, columns
and enum values, and v1.42.4 runs on top of them unchanged.

This happens on a host that went from v1.41 straight to v1.43, or that was
stopped soon after updating to v1.42, so the backfill never reached every
account. To recover, clear the failed attempt first, because v1.42.4 also
runs the migrations on start and refuses to boot while one is recorded as
failed:

```bash
# 1. Mark the failed attempt as rolled back. The entrypoint is replaced so
#    the container does not try to migrate first.
docker compose run --rm --entrypoint sh app -c \
  'NODE_PATH=/opt/prisma-cli/node_modules node /opt/prisma-cli/node_modules/prisma/build/index.js migrate resolve --rolled-back 0409_drop_plaintext_location'

# 2. Start the previous release: set HEALTHLOG_IMAGE_REF=:v1.42.4 in the
#    compose .env (or your platform's environment), then recreate.
docker compose up -d app
```

v1.42.4 starts the encryption backfill about three minutes after boot and
again once a day, one account at a time. Watch the three counts the
migration checks until all three are 0:

```bash
docker compose exec -T db psql -U healthlog healthlog -c "
  SELECT
    (SELECT count(*) FROM users WHERE home_lat IS NOT NULL) AS home,
    (SELECT count(*) FROM environment_travel_locations WHERE lat IS NOT NULL) AS periods,
    (SELECT count(*) FROM environment_contexts WHERE lat IS NOT NULL) AS days;"
```

Each pass logs `[free-text-encryption-backfill] user=...` lines. If the counts
stop going down, look for a line ending in `failed`; the error on the line
after it names the cause. Once all three are 0, dump the database again,
remove the pin (or set it to the new version), pull and recreate. Migration
0409 then runs through.

:::danger[Two shortcuts that lose data]
Do not set the readable columns to `NULL` by hand to get past the check:
those values have no sealed copy yet, so the location is gone for good. Do
not run `migrate resolve --applied 0409_drop_plaintext_location` either; it
records the migration as done while the columns are still there, and the
v1.43 schema no longer matches the database.
:::

The same steps are in the app repository as
[`docs/ops/migration-0409-plaintext-location.md`](https://github.com/MBombeck/HealthLog/blob/main/docs/ops/migration-0409-plaintext-location.md).

- **For API clients.** Request timestamps need seconds, the legacy integration

**The database restarts once.** The bundled `docker-compose.yml` now loads

minute without the app. Reading the statistics is optional and needs one

you keep your own compose file, nothing changes until you add the same lines.

New optional variables, all on the compose whitelist:

| Variable | What it does |
| --- | --- |
| `DATABASE_WORK_MEM` | Postgres `work_mem` per app session, `16MB` by default |
| `DATABASE_SESSION_OPTIONS_DISABLED` | `1` behind PgBouncer, which refuses the session settings otherwise |
| `ENVIRONMENT_AIR_QUALITY_DISABLED` | `1` turns air quality and pollen off for the whole instance |
| `OPENMETEO_AIR_QUALITY_URL` | Points the air-quality requests at a self-hosted Open-Meteo |

If your database sits behind PgBouncer without `options` in its
`ignore_startup_parameters`, set `DATABASE_SESSION_OPTIONS_DISABLED=1` before
updating. Setting the statement timeout to `0` no longer keeps the app from
sending session settings. With the variable set, the measurement maintenance
job applies its own settings with `SET` after it connects, and its concurrent
index rebuild needs a whole session: run it through a session-mode pool or a
direct connection, not a transaction-mode pool. See
[Session settings](/self-hosting/database-maintenance/#session-settings-work_mem-and-pgbouncer).

`IP_GEO_LOOKUP_URL` is now read as a decision. With the variable set, the geo
row under **Admin, System status** shows green for the provider you named.
Without GeoLite2 databases and without the variable, the default online
provider still receives every login IP, and the row shows a warning. Mount the
databases, name a provider, or set `IP_GEO_LOOKUP_DISABLED`; see
[Offline geolocation](/self-hosting/geolite2/).

All requests to Open-Meteo, weather and air quality alike, share one instance
budget: 500 calls a minute, 4,000 an hour and 8,000 a day, below the free
limits of the hosted service, and 5 % of the daily budget per account. The
budget is built in, not a variable, and applies to a self-hosted Open-Meteo as
well. A refused request ends the night's run, and the next night continues
where it stopped. See
[Switches](/explanation/environmental-module/#switches).

### After the update, in this order

1. **The fold repair runs by itself.** Once per account, a background job
   recomputes hourly and daily means that an earlier fold computed from part
   of a day, and writes only values that differ. It checks only the window in
   which every sample of a day is still stored: the last 75 days for daily
   means, and for hourly means the 75 days before the raw window. Older days
   stay as they are, and the job counts them as
   `windowsSkippedBeyondHorizon`. The nightly mean and dense folds follow the
   same rule and leave a day beyond that horizon that already has a mean
   untouched.
2. **The cleanup follows by itself.** The compaction tombstone purge removes
   the folded Apple Health samples older releases kept as deleted rows. It
   waits for the repair account by account and starts on an account only once
   its repair has finished. On an instance that has synced Apple Health for a
   while the measurements table shrinks a lot.

- **Single sign-on** links to an existing account with the same email only after
  one sign-in to that account with its own password or passkey. Accounts
  already linked are not affected.
- **The password reset script** ships in the image from this release.

## Migrations 0352 to 0355 in v1.39.2

`0353_document_import_source` and `0354_condition_body_site` only add columns
and tables: the source key and the held-back AI reading of imported documents,
the memory of imported documents you deleted (see
[Import documents](/guides/import-documents/#running-it-again-duplicates-and-deletions)),
and the body site and side of a condition.

`0355_checkup_stays_due` adds the column that keeps the repeat of an open
reminder to once a week, and changes existing data in two places. It puts
reminders repeating less often than weekly, or on their last date, that had moved on to
their next date after notifying in the previous 90 days back to the day they
notified, unless they were done, skipped, snoozed past that day or edited
since, or were a course whose end date had passed before it (see
[When a reminder is due](/guides/checkups-and-practitioners/#when-a-reminder-is-due)).
And it adds **Appointments** to every saved choice of start-page items that
lacks it, so visits show on the start page again for layouts saved before they
existed (see [The Today view](/insights/today/#the-worth-a-look-rail)).
Nothing is deleted.

`0352_data_backup_chunks` adds the `data_backup_chunks` table and makes
`data_backups.data` optional, because from v1.39.2 a stored backup is kept as
pieces in the new table (see
[Backups kept in the database](/guides/backups/#backups-kept-in-the-database)).
Existing copies are not touched. Going back to the v1.39.1 image is not
supported: that version reads only the single value, so it finds a copy stored
in pieces empty, and if it writes a weekly copy into such a row, the row holds
both forms. v1.39.2 then refuses to read that row ("This backup holds both a
single stored value and pieces"), and the next weekly backup replaces it. Take
a database dump before deploying; if you must go back, restore that dump.

## Rolling back

Rolling back **migrations** is generally one-way (Prisma's `down` step is not
auto-generated; most HealthLog migrations are forward-only). To revert:

1. Roll the **app container** back to the previous image tag.
2. Leave the **database schema** at the newer migration — the previous app
   version reads forward-compatible shapes for nearly every release pair.
3. If a column-drop shipped in the rollback target, hand-roll the column back via
   a fresh forward migration. Never `migrate resolve --rolled-back` against
   production without a fresh `pg_dump` first.

## Verify the served version

The queued-deploy status is **not** the source of truth — the version
`/api/version` actually answers is. A BuildKit layer-cache hit can re-ship the
prior image even when the dashboard reports a clean deploy. `/api/version`
returns `version` + `buildSha` + `builtAt`; the published image carries its build
SHA so a deployment can prove what is running. Always confirm after a deploy:

```bash
# Asserts the targets serve the expected version, prints each buildSha,
# exits non-zero on mismatch after a bounded retry loop.
pnpm dlx tsx scripts/assert-deploy.ts <version>   # e.g. the tag you deployed
```

Pass `--only=prod` / `--only=demo` for a single target, or
`--attempts=N --interval=ms` to widen the retry window while a slow pull settles.

## Walk the synthetic journey

The version check proves the instance serves the right build. It does not prove
a person can use it. `scripts/synthetic-journey.mjs` warms the instance, checks
`/api/version` against the tag you deployed, signs in, writes a reading with an
idempotency key, reads it back and deletes it again, printing one line per leg
with its elapsed time and stopping at the first failure:

```bash
BASE_URL=https://your-instance.example.com \
SYNTHETIC_USERNAME=<probe account> \
SYNTHETIC_PASSWORD=<its password> \
EXPECTED_VERSION=vX.Y.Z \
  node scripts/synthetic-journey.mjs
```

It is plain Node 22 with no dependencies, so it runs from a workstation, a
runner or the deploy host. Two preconditions on the probe account: it must be
password-only, because the password flow stops at the MFA ticket for an account
with a second factor, and the target must not be a demo instance, where every
mutation is blocked and the write leg would be red for a reason that has nothing
to do with the deploy.

A red leg names the layer. `version` means the instance serves a different build
than the tag; check the image digest and `pull_policy` first. `sign in` means
sessions are broken, or the probe account gained a second factor. `write` means
the database, the encryption keys or a migration that did not run. `read back`
means a value was written and cannot be read back; roll back. `delete` means the
reversible delete is broken and the probe reading is still on the account.

The same journey runs by hand as the **Synthetic journey** workflow in the
server repository. Nothing calls it from the deploy path. Full runbook:
[Ops → Deploy](https://github.com/MBombeck/HealthLog/blob/main/docs/ops/deploy.md).

## Pin the image by digest

Tags (`:latest`, `:v1.38.0`) are mutable aliases. The digest is the image's
only immutable identity, and it is what the release signature covers. The
compose file's `app` image is `ghcr.io/mbombeck/healthlog${HEALTHLOG_IMAGE_REF:-:latest}`,
so set `HEALTHLOG_IMAGE_REF` in the `.env` next to the compose file (or in the
deployment platform's env vars) to change the reference without editing the
file: `:v1.38.0` pins a tag, `@sha256:<digest>` pins the digest. Resolve a
release's digest with

```bash
docker buildx imagetools inspect ghcr.io/mbombeck/healthlog:vX.Y.Z | grep -m1 Digest
```

which returns the manifest-list digest covering both architectures.

Every release image is signed keyless through Sigstore by the release
workflow, so a digest can be verified before it is pinned:

```bash
cosign verify \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  --certificate-identity-regexp 'https://github.com/MBombeck/HealthLog/\.github/workflows/docker-publish\.yml@refs/tags/v.*' \
  ghcr.io/mbombeck/healthlog:vX.Y.Z
```

:::caution[A pin is sticky, and a stale pin is silent]
A pinned instance never follows a release on its own. Every later deploy ships
the pinned reference until somebody changes it, and the deploy still reports
success. If you pin, bumping the pin is part of shipping. After any deploy
check two things: `/api/version` reports the version and commit you shipped,
and the running container's image is the one you expect
(`docker inspect <container> --format '{{.Config.Image}}'`). Probe
`/api/version` more than once a few seconds apart: during the container swap a
single probe can be answered by the outgoing container.
:::

## Web/worker split for scale

The default container runs both the Next.js server and the pg-boss worker
(`HEALTHLOG_PROCESS_TYPE=all`). The same image deploys in three modes:

| `HEALTHLOG_PROCESS_TYPE` | Web | Worker | Use when |
| --- | --- | --- | --- |
| `all` (default) | ✅ | ✅ | single-host self-hosting |
| `web` | ✅ | ❌ | scaling HTTP horizontally |
| `worker` | ❌ | ✅ | dedicated job worker |

To split: set `HEALTHLOG_PROCESS_TYPE=web` on `app`, uncomment the `app-worker`
service in the compose file, ensure both see the same `DATABASE_URL`,
`ENCRYPTION_KEY`, and `API_TOKEN_HMAC_KEY`, then
`docker compose up -d --build`. pg-boss claims jobs atomically via row-level
locking (`FOR UPDATE SKIP LOCKED`), so a duplicate worker replica is safe but
only doubles DB load — run one worker and scale the web containers, as the
[scaling page](/self-hosting/scaling/) recommends. A startup gate refuses to
boot the reminder worker when `HEALTHLOG_PROCESS_TYPE=web`, so a cross-mode
misconfiguration aborts instead of doubling cron load.

### Connection-pool sizing

Each container opens its own pool, capped at **20 connections by default**. Plan
total Postgres slots as **container_count × pool_max**. A stock Postgres 16 ships
`max_connections = 100`:

| Web | Worker | Containers | Slots used | Headroom |
| --- | --- | --- | --- | --- |
| 1 | 0 | 1 | 20 | 80 |
| 1 | 1 | 2 | 40 | 60 |
| 2 | 1 | 3 | 60 | 40 |
| 3 | 1 | 4 | 80 | 20 |
| 4 | 1 | 5 | 100 | 0 (do not exceed) |

Override per container with `DB_CONNECTION_LIMIT`, which the bundled compose
folds into `DATABASE_URL`; `DATABASE_POOL_MAX` is still read but is not on the
compose whitelist, so setting it in `.env` alone does nothing. Past the
"0 headroom" row, every other client (`psql`, backups, the Prisma CLI during a
migration) gets `FATAL: sorry, too many clients already`. Either raise
`max_connections`, lower `DB_CONNECTION_LIMIT`, or front Postgres with PgBouncer
in transaction-pooling mode.
