HealthLog connects to WHOOP via OAuth2 plus HMAC-signed webhooks for
near-real-time sync of recovery, strain, sleep, and the underlying
heart-rate / HRV signals. Unlike Withings, WHOOP credentials are brought **per
user**: each user (or the operator on their behalf) registers their own WHOOP
developer app and pastes the client id/secret into Settings.

## Why bring your own keys

WHOOP caps the number of users a single developer app may authorise. Per-user
BYO-keys sidestep that cap: every user authorises against their own WHOOP app,
so a shared HealthLog instance never hits one app's user ceiling. It also keeps
each user's grant scoped to credentials they control.

## Set it up

<Steps>

1. **Register a WHOOP developer app** at
   [developer.whoop.com](https://developer.whoop.com/).

   - **Redirect URI:**
     `https://your-instance.example.com/api/whoop/callback`.
   - **Scopes** (the exact set HealthLog requests):

     ```
     offline read:recovery read:sleep read:workout read:cycles read:profile read:body_measurement
     ```

     `offline` is **mandatory** — without it WHOOP issues no refresh token and
     the connection dies when the first access token expires (~1 hour). The
     `read:*` scopes are read-only.

2. **Wire the credentials in Settings.** Sign in as the target user, open
   **Settings → Integrations → WHOOP**, and paste the client ID and secret. They
   are AES-256-GCM-encrypted at rest. There is no `WHOOP_CLIENT_ID/SECRET` env
   var.

3. **Connect.** Click **Connect WHOOP**. The flow redirects to WHOOP, exchanges
   the code for an access + refresh token, registers the webhook, and triggers
   an initial sync of recent history. Subsequent syncs run on every webhook
   delivery plus a safety-net cron pull.

</Steps>

## Optional instance env vars

```env
WHOOP_REDIRECT_URI="https://your-instance.example.com/api/whoop/callback"
WHOOP_WEBHOOK_SECRET="$(openssl rand -hex 32)"
```

- `WHOOP_REDIRECT_URI` — overrides the derived
  `${NEXT_PUBLIC_APP_URL}/api/whoop/callback` when the public URL differs.
- `WHOOP_WEBHOOK_SECRET` — used twice: as the **trailing path segment** of the
  webhook URL you register in the WHOOP console, and as the key HealthLog
  verifies the WHOOP HMAC body signature against. Set the WHOOP console webhook
  to:

  ```
  https://your-instance.example.com/api/whoop/webhook/<WHOOP_WEBHOOK_SECRET>
  ```

  WHOOP signs each body (`X-WHOOP-Signature` + `X-WHOOP-Signature-Timestamp`,
  HMAC-SHA256); the handler rejects deliveries older than five minutes and
  validates the signature before processing. Without a webhook, WHOOP still
  syncs on the safety-net cron pull — only the near-real-time push is lost.

Add both to the compose `environment:` whitelist if you set them.

## The signals it brings

WHOOP is the canonical source for recovery, strain, and the HRV / resting-heart-rate
inputs that feed the [health scores](/explanation/health-scores/). When two
sources report the same vital, the [source ladder](/guides/source-priority/)
decides display; a recovery strap leads the sleep and HRV ladders.

## Disconnect

The Settings **Disconnect** button revokes the stored tokens and removes the
connection. Measurements already synced from WHOOP stay in the database —
disconnect does not delete data. A **Resume** control recovers a connection
after a revoked grant.
