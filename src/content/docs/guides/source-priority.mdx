When two providers report the same metric — a Withings scale and an Apple Watch
both logging weight, or HealthKit and Fitbit both reporting steps — HealthLog
keeps every row as an audit trail but applies a per-metric **source priority** to
decide which reading is canonical for display and analytics.

This is the practical guide to adjusting that ladder. For the reasoning behind
the two-ladder design, see
[Why source priority works the way it does](/explanation/source-priority/).

## The default ladders

HealthLog ranks sources differently depending on the metric class, because the
right answer differs. The defaults are per metric and wearable-aware; a few
representative ones:

- **Point measurements from a dedicated sensor** (weight, blood pressure, body
  fat, body temperature) put the primary device first. Weight defaults to
  **`WITHINGS ≻ APPLE_HEALTH ≻ MANUAL ≻ WHOOP ≻ FITBIT ≻ GOOGLE_HEALTH`**; blood
  pressure to **`WITHINGS ≻ APPLE_HEALTH ≻ MANUAL`**. A dedicated cuff or scale
  outranks a wrist estimate.
- **Cumulative activity metrics** (steps, active energy, distance, flights) pick
  exactly **one source per day** so they are never double-counted. Steps default
  to
  **`APPLE_HEALTH ≻ WITHINGS ≻ FITBIT ≻ GOOGLE_HEALTH ≻ OURA ≻ POLAR ≻ STRAVA ≻ MANUAL`**:
  HealthKit folds multiple sensors into one canonical daily stream, so it is the
  most complete cumulative source.
- **Recovery inputs** (sleep, HRV, resting heart rate, respiratory rate) are led
  by the worn-all-night wearables:
  **`WHOOP ≻ FITBIT ≻ GOOGLE_HEALTH ≻ OURA ≻ POLAR ≻ APPLE_HEALTH ≻ WITHINGS`**.
- **SpO₂** ranks the ScanWatch pulse-ox first, then the straps and rings:
  **`WITHINGS ≻ WHOOP ≻ FITBIT ≻ GOOGLE_HEALTH ≻ OURA ≻ POLAR ≻ APPLE_HEALTH ≻ MANUAL`**.

A source that is not listed in a metric's ladder is never silently dropped: when
none of the colliding sources appear in the ladder, every row is kept. The full
per-metric defaults live in `src/lib/validations/source-priority.ts`.

## Adjust the ladder

Open **Settings → Source priority** (`/settings/sources`). For each metric (or
metric class) you can:

- Reorder the source ladder with the up/down arrow buttons.
- Set an optional **device-type tie-break** so two devices reporting under the
  same source resolve deterministically.

Changes are per user and audit-logged. The API surface is
`GET` / `PUT /api/auth/me/source-priority`.

## What happens to the losing rows

Nothing is deleted. A reading that loses the priority contest stays in the
`Measurement` table tagged with its source and drops out of the active display
and analytics. If you later disconnect the winning source or reorder the ladder,
the previously-hidden rows resurface — no data was lost.

## Worked example

You sync a Withings scale and also import Apple Health (which received the same
weighing second-hand via the Health Mate app):

- **Weight** (point): Withings wins for display; the Apple Health row stays as
  audit trail.
- **Steps** (cumulative): if a ScanWatch feeds HealthKit, the Apple-Health-
  aggregated day wins; the Withings step rows stay in the database.

Override either default under **Settings → Source priority** if your setup
differs — for instance, if you trust a Fitbit's resting heart rate over a
Withings estimate.
