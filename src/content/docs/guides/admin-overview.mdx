You are the admin of an instance and want to know which console section
controls a given thing. This page walks the Admin navigation top to bottom, in
its five groups — System, Connectivity, AI, Account, Your data. Each entry says
what the section does, what it needs, and which environment variable or stored
setting stands behind it.

One rule applies to the whole console. Admin routes accept a browser session
only. The admin check resolves the session cookie and nothing else; a Bearer
token, even one with full scope, is refused. The native app is not an admin
client and cannot become one. On the web, the console is visible only to
accounts with the admin role, and the first account registered on a fresh
instance gets that role.

A few admin actions also require a fresh second factor (confirmed within the
last five minutes); those are marked "step-up" below. The actions that move or
replace data ask the admin to confirm it is them unless they
signed in within the last five minutes: downloading, uploading or restoring a
backup, wiping all data, and setting another account's password. An admin with
a second factor confirms with it; one without uses the password or a passkey.
See [Confirming it is you](/guides/sign-in-and-security/#confirming-it-is-you).

## System status

Host metrics chart and a status card: database, heap limit, start time, user
and measurement counts, active tokens and sessions, worker state, last reminder
check, and the state of Umami, GlitchTip, Web Push, and the offline geo
databases. Each row carries its state on the indicator beside it rather than in
the colour of the text, so the wording stays readable in every state, including
the worker-absent one a split deployment shows on the page served from the web
process.

The **Heap limit** row shows how much memory the app may use. It turns amber
when the container's memory limit is below the supported floor of 1536 MB
("Container 1024 MB, below the supported floor of 1536 MB. Set
APP_MEMORY_LIMIT=1536m in .env"), or when the heap is low for another reason.
Raise `APP_MEMORY_LIMIT` and recreate the container; never lower it below the
floor. See
[Requirements](/getting-started/self-host-in-10-minutes/#requirements).

A separate card lists failing background jobs, but only when a queue has
actually given up. A job that ran out of time says what its limit was and that
either the run was too slow for it or the app restarted while it ran; a restart
shows in the container's restart count and log. The geo row reflects
`GEOLITE2_DIR`, `MAXMIND_LICENSE_KEY`, `IP_GEO_LOOKUP_URL` and
`IP_GEO_LOOKUP_DISABLED`. It warns only when no database is mounted and the
default online provider is in use; a provider you named in
`IP_GEO_LOOKUP_URL` shows green. See
[Offline geolocation](/self-hosting/geolite2/).

Two more cards sit on this page.

**Support report** creates a text summary of the instance for a bug report,
with **Copy** and **Download**. It is built when you press the button and
shown first, so you can read it before you share it. Accounts appear as
"Account 1", "Account 2" in the order they were created; the report holds no
email address, username, account id, recorded value or token. See
[Report a problem](/self-hosting/troubleshooting/#report-a-problem-with-an-error-id)
for what it contains.

**Pulse day mean** decides how hours with only a few heart-rate readings count
toward a day's pulse. **Dry run** compares the current method with the
weighted one for every account and day and writes nothing but its result: how
many days were compared, how many would move by more than 1 bpm, the largest
change and how the changes spread, per account by number only. **Apply**
needs a dry run that finished in the last seven days; it switches the method
and recalculates the stored pulse days in the background.
**Recalculate again** repeats that recalculation, for example when another
run was still busy at the time. See
[Sparse hours](/insights/intraday-pulse/#sparse-hours).

## General

Instance-wide settings stored in the database: registration on or off,
require a second factor for everyone, default display language, default
timezone for new accounts, and the document vault's per-file size limit and
per-user quota. The second-factor policy redirects a web sign-in without a
factor to enrolment; it does not block API or native access for an account
that has not enrolled yet. Registration can be closed and reopened here; with
registration closed, an invite still admits a signup.

## Services

Four global kill-switches: Telegram, ntfy, Web Push, and the API. Each is a
stored setting. Turning a channel off here hides its card for every user;
turning the API off refuses ingest and every MCP route regardless of the
tokens users hold.

## About

The same version card users see under Settings, About this app: running
version, an update check, and links to the repository, changelog, docs and
credits.

## Integrations

Three cards. Umami analytics (enable, script URL, website id, test action),
GlitchTip error reporting (enable, DSN, environment, test action), and Web
Push VAPID keys, which you can generate here or supply through
`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT`. Umami and
GlitchTip are stored settings, not environment variables. The GlitchTip badge
tracks delivery, not intent: it is green only while a report has actually left
this host inside the last fourteen days, amber while a target is set and
nothing has come back from it, and it names the reason when the last attempt
was refused (a wrong key, a wrong project id and a host that stopped answering
all parse). The card names the host reports go to and never the key. Press
**Test** to prove the target; that send is recorded like any other. There is
no default target: reports leave the host only after somebody typed a DSN
here.

Page views go to Umami through the HealthLog server, so the browser only talks
to this host. That also works with an Umami whose tracker was built with a
custom collect endpoint: the server reads the endpoint from the tracker script
and forwards the events to the configured Umami host.

The users' own connections (Withings, Oura, Apple Health and the rest) are
not configured here. A watchdog tells every admin when one of
them goes quiet or keeps failing; see
[The watchdog](/guides/integrations/#the-watchdog-for-the-instance-admin).

## API tokens

A read-only, instance-wide list of every personal API token with owner,
scope, and status (active, expired, revoked). There is deliberately no create
action here; users mint their own tokens under Settings, API & tokens.

## Coach

Seven cards for everything AI-related at the instance level: the
**Assistant** card, **AI usage levels**, the server key, the central Codex
connection, provider health, and the two feedback-quality tables. The server
key drives OpenAI, or Anthropic when its base URL is Anthropic's; it sits at
the end of every user's chain and needs each user's consent before it is used
(its base URL is HTTPS-only with an allowlist you can extend through
`ADMIN_AI_BASE_URL_ALLOWLIST`). The central Codex connection uses the
device-code flow and is off until connected. Provider health shows, per
provider type, how many chains are failing and which providers are paused and
until when. User-side setup is in [AI providers](/guides/ai-providers/).

The Assistant card has a master switch and four switches under it:

| Switch | What it covers |
| --- | --- |
| **Assistant enabled** | Every AI feature. Off means nothing is sent to a model, and the four below are off with it. |
| **Coach** | The Coach chat, upkeep of the Coach's memory, and AI-written nudges. |
| **Daily Briefing** | The daily briefing, its opening lines elsewhere in the app, and period summaries written by a model. |
| **Status notes** | The short notes a model writes per reading and metric, workout notes and reaction lines. The largest share of token use. |
| **Reading documents** | AI reading of stored documents, lab report scans, and turning a typed medication description into a schedule. The largest share of data leaving the server. |

A switch stops the work it covers, not just the text. With a
switch off, nothing it covers is sent to a model, including background work
that was queued before you flipped it, and text a model wrote earlier is not
shown. Nothing is deleted: turn the switch back on and the stored notes come
back. Readings, charts, scores and correlations load the same whatever these
switches say. If the server cannot read the switches for a moment, every AI
feature stays off for that request rather than every one turning on.

**Reading documents** is on by default. Correlations have no switch: they are
statistics that no model writes, so they always load.

With the master switch off, **Test connection** in a user's AI settings says
AI is off on this server instead of calling the model.

The **AI usage levels** card sets the highest level an account
may choose and the level accounts without a choice run at (both standard by
default), and the hours between status card refreshes after a sync at
standard (1 to 48; empty uses `AI_SYNC_REGEN_GAP_HOURS`, else 6). The default
cannot be above the highest level. The provider health card counts accounts
per level. See [AI usage levels](/guides/ai-providers/#ai-usage-levels).

### Thinking

The Assistant card also decides whether models may think before
they answer. **Allow deeper thinking** is on by default and covers the Coach,
the daily briefing and the weekly and monthly summaries. Status notes,
workout notes, reaction lines, nudges and document reading never think,
whatever this says. Switched off, no request asks a model to reason, and each
person's **Thinking depth** in the Coach settings is locked with a sentence
saying so.

**Highest thinking depth** (**Low**, **Medium** or **High**; **High** by
default, which means no limit) is the deepest level anyone on the server may
choose. A person who picked more runs at this level, and the higher options in
their settings say **(limited by the admin)**.

When the model is yours to pay for, through the server's shared key or the
shared ChatGPT connection, the Coach thinks at **Medium** at most, whatever
the two controls allow, and an answer gets a smaller budget: 55,000 tokens, 120
seconds and eight rounds instead of 165,000 tokens, 200 seconds and sixteen on
a person's own provider. The background jobs ask for **Low** on your budget. See
[Thinking depth](/guides/coach-conversations/#thinking-depth) and
[AI providers](/guides/ai-providers/#reasoning).

## Module availability

One switch per optional module, applied server-wide above each user's own
preference. Only an explicit off disables a module; the core domains (weight,
blood pressure, pulse) cannot be switched off and the write path
refuses the attempt. A user whose module is disabled here sees the switch
greyed out under [Settings, Modules](/guides/settings-overview/#modules), and a
page of that module tells them it is not available on this server.

The Coach has one operator switch, the one on the Assistant card. Its row here
shows that switch's state, cannot be flipped, and links to the Assistant card.

## Reminders

The two medication-reminder thresholds, late and missed, in minutes (defaults
120 and 240), a send-test-notification action, a manual reminder check, and a
notification health panel showing the last 24 hours of push attempts by
channel and result plus the count of channels the dispatcher has auto-disabled.
The console button sweeps the whole instance and dispatches into every account
with an overdue dose and a configured channel, which is what you want when the
worker has been down. Debugging one account is a different job: send `userId` on
`POST /api/admin/notifications/reminder-check` and the sweep narrows to that
account instead of becoming a second writer for everybody else. The selector
narrows the query only and never the authorisation. Channel setup for users is in
[Reminder channels](/guides/reminder-channels/).

## Users

The account table with role and status, and three actions per row: edit
(username, email, document quota, and the per-user second-factor override),
reset password, and force logout. A password reset sets a new password that
must pass the strength and breach checks, then destroys the user's sessions,
API tokens, refresh tokens, trusted devices, connected assistants and share
links in one transaction, and writes an audit row. None of these actions is
step-up gated; the password reset asks the admin to confirm it is them. See
[Sign-in and security](/guides/sign-in-and-security/#password-reset).

An account or managed profile whose deletion is pending shows its erasure
date and **Undo deletion**. Undoing keeps the account and everything in it as
it was; API tokens, share links and trusted devices stay revoked. See
[The grace window](/account/data-deletion/#the-grace-window).

## Invites

Mint invite links with a maximum number of uses, reveal the link and a QR
code, see status and redemptions, and revoke. Invites are how people join an
instance whose registration is closed under General. See
[Invites](/guides/invites/).

## Login overview

The audit log with an action filter, a date-range preset (24 hours, 7 days,
30 days, all), page size, CSV download, and IP and location columns per row.
Location comes from the geo resolver described in
[Offline geolocation](/self-hosting/geolite2/). Client IP resolution behind a
proxy honours `TRUST_PROXY_HOPS`, `TRUSTED_PROXY_CIDRS` and `TRUST_CF_CONNECTING_IP`; see
[Reverse proxy](/guides/reverse-proxy/).

## App logs

The wide-event log with a level filter (debug, info, warn, error), a time
preset (15 minutes, 1 hour, 6 hours, all), refresh, and a detail dialog per
event. Optional shipping to Loki is configured with `LOKI_USERNAME` and
`LOKI_PASSWORD`.

Long background jobs leave a trace in the app log (the
container's output, Loki if configured, and this page when the jobs run in the
same container as the web app). A job that runs for more than a minute writes `job.finished` naming its
queue when it ends, and `job.progress` every two minutes while it runs, with
how far it has got and how much memory the app is using. A job that passes its
time limit writes a `job.expired` warning. After a restart, the worker writes
`worker.boot.jobs_cut_off`, naming every job the restart cut off.

The page has an **Error ID** filter. Type the id a person read
off an error message, or its first eight characters, and the page finds the
event behind it. That search reads a second buffer that keeps the last 1,000
warnings and errors of the process, so ordinary traffic cannot push them out
the way it turns over the main buffer of 500 events. Both buffers live in memory: a restart empties them, and a split
web and worker deployment has one per process. See
[Report a problem](/self-hosting/troubleshooting/#report-a-problem-with-an-error-id).

## Backups

The page opens with the
[Recovery readiness](/guides/backups/#recovery-readiness) card, which also sits
on the admin overview, and the **Database dump** card: the newest good dump,
whether it is kept on this server, off-host or both, the newest failed run,
and how long deleted accounts stay in the dumps. Then the backup table with
run now, upload, download, a summary, and restore. A
backup is a database row, not a file on disk, and the payload never reaches
the browser except through the download action. Restore asks you to type
`RESTORE` and replaces rather than merges: every row the account gained after
the snapshot was taken is removed with the rest of its class. The restore runs in
the background and the page shows its progress, also after a reload; one
restore per account runs at a time. A restore never runs beside a backup or
another large job (an import, a nightly pass). While it waits, the page says
which of the two it waits for and since when; it starts about a minute after
that job finishes. The upload takes a `.json`
or `.json.gz` file of up to 512 MB and compresses a plain file in the browser
first. Beside the typed confirmation sits a **Restore instance settings** checkbox, off by default. Off,
the restore touches the snapshot owner's data only and leaves registration, the
second-factor requirement, the default language and timezone, module
availability, the notification and AI configuration and the document caps
exactly as they are. Tick it only when you are rebuilding a host from a
snapshot, because those settings apply to every account on the installation.
The restore is credential-free by design: API tokens, trusted devices, step-up
elevations, known devices and clinician share links are excluded. A restore on
the same server leaves them as they are; onto another server none of them
comes along. Optional off-site copies use
`BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY`,
`BACKUP_S3_SECRET_KEY` and `BACKUP_ENCRYPTION_KEY`. Full procedure in
[Backups](/guides/backups/).

Below the table, **Off-host copies**: one row per account with
the state of its newest object in your bucket (fresh, due, stale, never, or no
record yet), the size, and when the nightly run last checked it, stale first.
It reads the worker's ledger, not the bucket, and says plainly when off-host
backup is not configured. It also reads the bucket's lifecycle
rule and says when there is none (every nightly copy is then kept forever) or
when the credential may not read it, and it lists deleted or wiped accounts
whose copies are still in the bucket, with the bucket's answer when it refused
to delete them. See
[Which account has no copy](/guides/backups/#which-account-has-no-copy).

## Encryption

Encryption coverage, rotation status with a **Rotate now** trigger, the
per-column key-id breakdown and **Keys the backups still need**: per key id, the stored copies that need it with the oldest date, and
when the last off-host copy that needs it expires under the bucket's lifecycle
rule. Rotation is behind a step-up gate; a 401 here means you need a fresh
second factor, or have none enrolled, in which case the rotation script from a
source checkout is the way. Backed by `ENCRYPTION_KEYS`, `ENCRYPTION_ACTIVE_KEY_ID`, or the
legacy `ENCRYPTION_KEY`; a key is 64 hex characters or 32 bytes of base64, and
anything else stops the container at startup. Procedure in
[Encryption key rotation](/guides/encryption-key-rotation/).

The section opens with the **Recovery kit**: every key a restore of this
server needs, by id and fingerprint, where the keys are set on your platform,
an optional **Check my copy** that compares a pasted key and discards it, and
**I have a copy of every key**. Admins see a dashboard reminder until the kit
is confirmed, and again when it lists a key the confirmation did not cover.
See [The recovery kit](/explanation/encryption-at-rest/#the-recovery-kit).

## Danger zone

One action: wipe all data on the instance. It requires typing `DELETE ALL`,
which the server checks as well, and the response reports a count per table
that held rows. It is not step-up gated, but it asks the admin to
confirm it is them unless they signed in within the last five minutes. It
deletes nothing in the off-host bucket: those copies are the way back from a
wipe pressed by mistake.
