HealthLog encrypts sensitive at-rest data — provider tokens, AI keys,
notification configs, web-push secrets, VAPID keys — with AES-256-GCM under a
per-deployment key. A versioned key format lets you rotate the key **without
downtime** and without re-encrypting every row by hand. For the design rationale,
see [Encryption at rest](/explanation/encryption-at-rest/).

## The versioned format

| Layout | Marker | Where |
| --- | --- | --- |
| Versioned (new) | `<keyId>.<base64(iv ‖ tag ‖ ciphertext)>` | All new writes |
| Legacy (≤ v1.3.x) | `<base64(iv ‖ tag ‖ ciphertext)>` | Existing rows until rotated |

`<keyId>` matches `[A-Za-z0-9_-]{1,32}` and indexes into the `ENCRYPTION_KEYS`
JSON map. Decryption tries the versioned format first; a value with no `.` is
treated as legacy and decrypted under `v1` (the synthetic id for the existing
`ENCRYPTION_KEY`).

:::caution[Keep the old key until rotation completes]
Legacy ciphertexts have no key id, so the only way to identify them is "no `.`
in the value". If you remove the `v1` entry from `ENCRYPTION_KEYS` before every
legacy row has rotated, those rows can no longer be decrypted. The decrypt path
refuses to silently fall back to the active key and throws a clear error instead.
:::

## Rotate from a single key to a new one

<Steps>

1. **Generate the new key:**

   ```bash
   openssl rand -hex 32
   ```

2. **Update the environment.** Keep the existing `ENCRYPTION_KEY` in place — it
   still decrypts legacy rows during the transition:

   ```env
   ENCRYPTION_KEY="<old key, unchanged>"
   ENCRYPTION_KEYS='{"v1":"<old key>","v2":"<new key>"}'
   ENCRYPTION_ACTIVE_KEY_ID="v2"
   ```

   Restart. New writes encrypt under `v2`; existing `v1`-keyed and legacy rows
   still decrypt.

3. **Re-encrypt the stored data under the new key.** Open **Admin →
   Encryption** and press **Rotate now**. The button needs an admin account
   with a second factor, confirmed within the last five minutes. It queues one
   background run on the app's own worker, so it works on the published image
   with nothing else installed, and the same page shows the per-column counts
   and the last run's result.

   Without a second factor on any admin account, run the rotation script from a
   source checkout of the same release; the image does not contain it. It needs
   the app's `ENCRYPTION_KEYS`, `ENCRYPTION_ACTIVE_KEY_ID` and a `DATABASE_URL`
   that reaches the database. The bundled `db` service publishes no port, so
   publish 5432 for the duration or run the checkout in a throwaway `node:22`
   container on the compose network:

   ```bash
   git checkout vX.Y.Z
   pnpm install && pnpm db:generate
   pnpm dlx tsx scripts/rotate-encryption-key.ts v2
   ```

   Both paths are idempotent: re-running is a no-op for rows already prefixed
   `v2.`. They rotate every encrypted column across the schema, from the
   connection credentials and notification channels through Coach content,
   mood entries, lab results, documents and the search index, so a new
   release's encrypted columns ride along. The script's summary reports
   `scanned` / `rotated` / `errors` per table and field; treat `errors > 0` as a
   hard failure and re-run after fixing the cause.

4. **Drop the old key (optional, recommended)** once **Admin → Encryption**
   reports zero rows outside the active key (or a full script run reports
   `rotated=0`, `errors=0` and every column walked) **and no backup you may
   still restore needs it**. Rotation re-encrypts every row, and every stored
   backup's outer layer, but not the content inside a backup: a restore writes
   that content back as it was stored, so a copy taken before the rotation
   still needs the old key. The same goes for every copy in the off-host bucket
   and every backup file you downloaded. Since v1.39.3 **Admin → Encryption →
   Keys the backups still need** lists, per key id, the stored copies that need
   it with the oldest date, and when the last off-host copy that needs it
   expires under your bucket's lifecycle rule. The weekly copy replaces itself
   within a week; delete old uploaded copies you no longer want, and wait out
   the off-host retention. Copies written before v1.39.3 did not record their
   keys and are listed as such; treat them as needing every key that existed
   when they were written. The coverage badge only says the old key is safe to
   drop when both the rows and the backups are clear.

   ```env
   ENCRYPTION_KEYS='{"v2":"<new key>"}'
   ENCRYPTION_ACTIVE_KEY_ID="v2"
   # ENCRYPTION_KEY can now be removed
   ```

</Steps>

Adding a third key (v2 → v3) is the same procedure with shifted labels — keep
`v2` in the map until the rotation reports zero `v2.`-prefixed rows and no
backup still needs it.

## Rollback

Once the script runs, ciphertexts start with `v2.`. The pre-rotation image
expects bare base64 and will throw on that prefix. So:

- **Prefer keeping the new image.** The new code reads both formats, so most
  rollbacks need no undo.
- If you must run old code, **restore a database backup taken before the
  rotation**. There is no script to convert `v2.`-prefixed rows back — rotation
  is forward-only by design.

Run rotation in a window where you have a fresh DB snapshot and the new image has
been smoke-tested in production for at least 24 hours.

If you drop a key too early, nothing is lost for good and nothing is changed by
mistake. A stored copy sealed under the removed key is refused on restore,
download and preview with `422` and
`meta.errorCode: backup.payload.undecryptable`. A copy whose content needs the
removed key is refused on preview and upload with `422` and
`meta.errorCode: backup.key.missing`, naming the key, and its restore fails with
the same reason. Put the key back into `ENCRYPTION_KEYS` and restart, and both
copies restore.

Stored backups rotate like every other column. A copy stored in pieces
(v1.39.2 on) is re-sealed piece by piece in small batches without reading the
backup inside. A copy still in the older single-value form, uploaded copies
included, is converted into pieces under the new key, one copy at a time and a
few megabytes at a time, and keeps its date. Each conversion is one
transaction, so a copy that fails its check is left exactly as it was and
counted as an error.

Up to v1.39.1 the script counted every stored backup written by v1.38.6 to
v1.39.1 as an error and never reported clean. After updating to v1.39.2, run
the rotation again before retiring the old key.

## Troubleshooting

- `Encryption key id 'v1' is not configured` — the DB still has `v1.`-prefixed
  rows but `v1` was removed. Re-add it, run the script, then remove again.
- `Found a legacy-format ciphertext but no v1 key is configured` — same cause
  for legacy bare-base64 rows. Restore `ENCRYPTION_KEY` (or add a `v1` entry)
  and run the script before removing it.
- `Refusing to rotate: argv key id ... does not match the currently active id` —
  pass the same id you set in `ENCRYPTION_ACTIVE_KEY_ID`.
