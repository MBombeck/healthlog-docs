HealthLog fans medication reminders and proactive coach nudges out to whichever
channels a user has enabled. One dispatcher drives the cascade and keeps a
record of every delivery attempt per channel for 90 days.

Each user sets up their channels under **Settings → Integrations → Delivery
channels** (`/settings/integrations#channels`). Which reminders exist is set
under **Settings → Notifications**.

The single message to take away: **you do not need an Apple Developer account
or APNs to get push.** Five of the six channels are free and cover every
platform a self-hoster runs; an APNs-less instance degrades gracefully —
urgent events still escalate on ntfy (max priority), Web Push (raised
urgency), and the webhook (urgent flag). Web Push is the recommended default:
it needs no third-party account, just a keypair you generate once.

## The cascade

The dispatcher tries channels in this order: **APNs → Telegram → ntfy →
Webhook → Email → Web Push**. Each user's preferences are a per-channel ×
per-event matrix
(`GET` / `PUT /api/notifications/preferences`), so a user can route medication
reminders to Telegram while keeping the daily briefing on Web Push only.

Every attempt writes a `push_attempts` row (channel, event type, result, reason,
timestamp). A hard reject — an unregistered APNs token, a revoked Telegram chat —
is classified so the dispatcher stops retrying a dead endpoint instead of
hammering it.

## Apple Push (APNs)

For the [native iOS app](/getting-started/connect-ios-app/). Reminders arrive
with taken / skip / snooze action buttons that work without opening the app.
APNs needs the all-or-none env set (`APNS_KEY_ID`, `APNS_TEAM_ID`,
`APNS_BUNDLE_ID`, and one key source — `APNS_KEY_B64` is the recommended
form: the base64-encoded `.p8` survives env-file round-trips that mangle
literal newlines; `APNS_KEY` / `APNS_KEY_FILE` remain accepted). See the
[iOS connect guide](/getting-started/connect-ios-app/#push-notifications-apns)
for the `.p8` gotchas.

One thing worth stating plainly: APNs binds a push to a specific Apple
Developer team + bundle ID + signing key, and the published iOS app is signed
under the maintainer's team. A self-hosted server has no way to mint that
team's key, so it **cannot** send APNs pushes to the published app — native
push on your own infrastructure means building and signing your own copy of
the open iOS client under your own Apple identity. Everyone else gets the
same reminders through Web Push (install the PWA), Telegram, ntfy, webhook,
or email; only the lock-screen Live Activity is APNs-exclusive.

## Telegram

Configured **per user** under Delivery channels: each user saves their own
bot token and chat id via `PUT /api/settings/telegram` (the token is stored
encrypted in the database, not in `.env`). Setup: create a bot with
**@BotFather** and copy the token, send `/start` to the bot so it can message
you, read your chat ID from **@userinfobot**, and fill both into the Telegram
card under **Settings → Integrations → Delivery channels**. One bot can serve every user on the
instance; each user pairs their own chat ID. Telegram reminders carry inline
action buttons (taken / snooze / skip); the button callback lands on
`POST /api/telegram/webhook`, which is secret-authenticated.

## ntfy

Self-hostable push. Configured per user under Delivery channels. Point it at a
public `ntfy.sh` topic or your own ntfy server. Good for a no-account,
no-vendor push channel. Pick a hard-to-guess topic name: on public `ntfy.sh`
the topic **is** the access control — anyone who knows the string can read it,
so treat it like a secret. Urgent events are published at ntfy's top priority
(`5`) so they bypass batching and surface on the lock screen.

HealthLog publishes each message as JSON to the server's root
URL, with the topic in the body (ntfy's
[publish as JSON](https://docs.ntfy.sh/publish/#publish-as-json)), so titles
and button labels in any language arrive as written. If your own ntfy sits
behind a reverse proxy, the proxy has to pass `POST /` through, not only
`POST /<topic>`. The mood reminder on ntfy carries three
[quick answers](#quick-answers-on-the-mood-reminder).

## Webhook

A generic outbound POST for chat services and homelab relays: Discord,
Slack, Gotify, Home Assistant, n8n. You supply the URL and optionally one
custom header, such as an auth token. Step-by-step setup for each target and
the errors they answer are in
[Notifications via webhook](/guides/webhook-notifications/). Outbound goes through the SSRF-guarded
fetch path with the DNS-rebinding pin, since the host is user-supplied. A
relay on your own network needs the operator grant described in the next
section.

### What the webhook sends

Every event is one `POST` with `Content-Type: application/json` and the one
header you configured, to the URL exactly as you saved it. The body depends
on the **Payload format** you choose on the Webhook card. The examples are
what the Test button sends.

**Generic JSON** is the default, and what every webhook saved before the
choice existed keeps sending:

```json
{
  "title": "HealthLog Test",
  "message": "HealthLog: Connection successful! Webhook notifications are active.",
  "eventType": "SYSTEM_ALERT",
  "priority": "default",
  "content": "HealthLog Test\nHealthLog: Connection successful! Webhook notifications are active.",
  "text": "HealthLog Test\nHealthLog: Connection successful! Webhook notifications are active.",
  "allowed_mentions": { "parse": [] }
}
```

`title` and `message` are plain text. `content` (for Discord, cut to 2000
characters) and `text` (for Slack) repeat both on two lines, and
`allowed_mentions` stops Discord from resolving mentions, so a Discord or
Slack webhook URL works with the generic format. `eventType` is the event name for
routing rules; with discreet cycle notifications on, a cycle event arrives
as `reminder` with its title and message masked. `priority` is a word:
`urgent` for an event flagged urgent, `high` for medication reminders,
`default` for everything else. The body also carries `url`, the
page the notification leads to, when `APP_URL` is set (see
[What tapping a notification opens](#what-tapping-a-notification-opens)).

**Gotify** sends the body Gotify's `POST /message` endpoint expects:

```json
{
  "title": "HealthLog Test",
  "message": "HealthLog: Connection successful! Webhook notifications are active.",
  "priority": 5,
  "extras": {
    "client::display": { "contentType": "text/plain" },
    "healthlog::event": { "type": "SYSTEM_ALERT" }
  }
}
```

`priority` is an integer: `5` for most events, `8` for medication reminders,
`10` for urgent events. The Gotify Android app plays a sound from 4 and
shows a heads-up banner from 8, so routine events are audible and reminders
pop up on screen. The generic body does not work with Gotify: Gotify reads
`priority` as a number and answers `400 Bad Request` to the word `default`.

### Sending to Gotify

1. In Gotify, create an application and copy its token.
2. On the Webhook card, set **URL** to your Gotify address ending in
   `/message`, for example `https://gotify.example.com/message`.
3. Set **Header name** to `X-Gotify-Key` and **Header value** to the
   application token. Gotify also accepts `?token=` on the URL, but in a
   header the token stays out of proxy access logs.
4. Set **Payload format** to **Gotify**, save, and press Test.

If the test fails, the card shows the status Gotify answered and, when it is
short, Gotify's own error text. A `401` means the token is wrong. A `400`
means Gotify could not read the body, so check that the format is set to
Gotify. A Gotify on your own network also needs the operator grant below.

### When a test fails

The Test buttons on the webhook, ntfy and email cards show why a test
failed: the status the other end answered, and for webhook and ntfy the
start of its error message. Anything that looks like a token or contains one
of your saved secrets is left out. The detail travels inside the server's
`502` response, so a reverse proxy that replaces 5xx pages, such as
Traefik's `errors` middleware or nginx with `proxy_intercept_errors on`,
hides it and the card can only say "Test failed". Exclude the `/api/` paths
from that rule to keep the detail.

## Targets on a private network

Every webhook and ntfy target is resolved at send time and refused when the
answer is a private, loopback, link-local or CGNAT address. That is the
DNS-rebinding defence, and it applies to a public-looking name with a LAN A
record (a Gotify behind a reverse proxy with a DNS-01 certificate) exactly as
it applies to `http://192.168.1.20`. The operator can open a
target by listing its exact origin in `NOTIFICATION_PRIVATE_ORIGINS`, the
same grammar as `NIGHTSCOUT_PRIVATE_ORIGINS`; the rules are on the
[environment-variables reference](/reference/environment-variables/#notification-targets-on-a-private-network-optional).

What you see on the card:

- Saving a private target that is not listed answers `422` with
  `meta.errorCode: private_origin_not_approved`; the message names the
  variable to list it in. Nothing is stored.
- Saving a link-local, metadata or unspecified target answers
  `private_origin_not_grantable` instead. No grant can open it, so the
  message says so rather than sending you to the operator.
- The **Test** button answers the same code for the same reason, instead of a
  bare `500` that sent the operator to the log. The save, the test and the
  scheduled delivery take one decision, so a test that fails on this means
  nothing would have arrived either.
- A DNS name the save cannot classify (a `.lan` name, a Docker service name,
  a public name with a private A record) is accepted at save and refused
  when the test or a reminder dials it, unless its origin is listed.

The resolved address is never shown to the user. Telegram, email and Web Push
are not affected: their hosts are not user-supplied.

## Email

Rendered plain-text email over an operator-supplied SMTP transport. The
channel only appears when the operator sets `SMTP_HOST`, `SMTP_PORT`, and
`SMTP_FROM` (plus optional `SMTP_USER` / `SMTP_PASS` / `SMTP_SECURE`);
without them the dispatcher skips it silently.

## Web Push (VAPID)

Browser-native push for the PWA. The easiest path is the admin panel's **Web
Push VAPID** card: **Generate keys** mints a keypair server-side, stores the
private key encrypted at rest, and only asks you to set the `mailto:` subject
— no shell, no `.env`. Regenerating an existing pair invalidates every
browser subscription (each device must re-subscribe), so the card asks for
confirmation first. Alternatively set `VAPID_PUBLIC_KEY` /
`VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` as env vars — the database values win
when both are present.

A browser registers via `POST /api/notifications/web-push` after the user
grants notification permission; `GET /api/notifications/vapid` hands the
client the public key. Test a registration with
`POST /api/notifications/web-push/test`.

On an iPhone, Safari supports Web Push only from **iOS 16.4** and only for a
site installed to the Home Screen as a PWA — a regular Safari tab cannot
subscribe. Share → **Add to Home Screen**, launch from the icon, then
subscribe under **Settings → Integrations → Delivery channels**. Android and desktop browsers need
no such step.

## Tap targets, content and quick answers

Every notification leads somewhere, a setting decides how much
it may say on a lock screen, and the mood reminder on ntfy can be answered
from the notification.

### What tapping a notification opens

The server decides the target once per event type, and every channel carries
the same one:

| Notification | Opens |
| --- | --- |
| Mood reminder | `/mood`, with the mood entry sheet already open |
| Morning briefing | the dashboard |
| Medication reminder, low supply, shared dose | `/medications` (low supply opens the medication) |
| Check-up and measurement reminders | `/checkups` |
| Proactive Coach nudge | the Coach conversation it started |
| Cycle reminders | `/cycle` (the dashboard with discreet notifications on) |
| New sign-in | Settings, Security |
| Integration sync failing | Settings, Integrations (an admin alert about another account opens the admin page) |
| Illness red flag | the illness episode |
| Other system alerts | the dashboard, or the admin status page for operator alerts |

How each channel carries it:

- **ntfy**: the message's `click` field, so tapping the notification opens
  the page.
- **Telegram**: an **Open in HealthLog** button under the message, below any
  action buttons. Telegram only accepts `https` button links on a public
  host, so a plain-HTTP instance gets a text link instead, and an instance
  on `localhost` gets no link.
- **Web Push**: the service worker opens the page, or focuses an open
  HealthLog tab and navigates it there.
- **APNs**: the path rides the payload as `url`. The iOS app follows it from
  its next update on.
- **Webhook**: the generic body gains a `url` field; the Gotify body gains
  `extras["client::notification"].click.url`, which the Gotify app opens.
- **Email**: a link line under the message.

ntfy, Telegram, the webhook and email need an absolute link, built from
`APP_URL` (or `NEXT_PUBLIC_APP_URL`). Without one those channels deliver
without a link. A notification about a profile
you look after as a guardian opens the dashboard rather than the profile's
page, because your session opens on your own record and the record switcher
lives there. A discreet notification opens the dashboard as well, so its link
names nothing. The silent background sync push for medication intake is the
only notification without a link.

### Health figures in notifications

Settings, Notifications, **Health figures in notifications** decides what a
notification may show on a lock screen:

- **Off**, the default: a notification says what it is about and shows no
  health figure. The morning briefing reads "Your morning briefing".
- **On**: notifications add their figures. The morning briefing becomes
  "Morning score 78" with the day's one-line summary underneath.

Tap targets and quick answers work the same either way. The setting is
stored as `content.detail` (`generic` or `detailed`) in the notification
preferences (`PATCH /api/auth/me/notification-prefs`) and travels with the
account backup.

### Quick answers on the mood reminder

On **ntfy** the mood reminder carries three buttons, **Good**, **Okay** and
**Bad**. Tapping one logs a mood entry straight from the notification,
without opening the app. They map onto the five-point mood scale as
Good = 4, Okay = 3, Bad = 2; the outer points stay in the app. The entry is
marked with the source **Notification**.

Each button calls `POST <APP_URL>/api/notifications/action/<token>`. The
token is the only credential, so it is built to be harmless on its own:

- it is signed with `API_TOKEN_HMAC_KEY` and names one account and one
  answer, so it cannot be moved to another account or another answer;
- it expires six hours after the reminder was sent;
- the three answers of one reminder are one use between them: the first
  tap logs, every later tap on that reminder is refused, and that stays
  true when the logged entry is deleted and purged from the trash within
  the six hours;
- the route is rate-limited before it reads the token, refuses when the
  mood module is switched off, and the token is scrubbed from logs.

The buttons need `APP_URL`, because the ntfy app calls the URL from your
phone, and your phone has to reach the instance at that address.

:::caution[The topic is the weak point]
The button URLs, token included, travel through your ntfy server inside the
message, and the message reaches everyone subscribed to the topic. For the
six hours a token is valid, anyone who can read the topic can log that one
answer for you. On the public `ntfy.sh` the topic name is the only access
control, so:

- use a long, random topic name and do not share it;
- better, run your own ntfy server with access control and give HealthLog
  an access token that may only publish to your topic;
- to invalidate every quick-answer token at once, rotate
  `API_TOKEN_HMAC_KEY`. The same key hashes API tokens and session cookies,
  so rotating it also invalidates every issued API token and signs out every
  browser session and the iOS app. See
  [Environment variables](/reference/environment-variables/).
:::

### When a quick answer does nothing

The ntfy app sends the answer from your phone, outside the browser, so it
carries no session cookie and cannot pass a sign-in page. Two things have to
hold:

- **`APP_URL` is the exact public https address** of the instance, the one
  your phone reaches. An `http://` address or an old hostname gets
  redirected, and an HTTP client follows a redirect with a `GET`, so the
  `POST` never arrives.
- **A sign-in gateway lets the route through.** If Authelia, Authentik,
  Cloudflare Access or any other forward-auth layer sits in front of
  HealthLog, add a bypass rule for `POST /api/notifications/action/*`. The
  link carries its own short-lived credential, so the route needs no
  session. See [Reverse proxy](/guides/reverse-proxy/#a-sign-in-gateway-in-front-of-healthlog).

Every refusal on that route writes a log line with the action
`notification.action.refused` and a `reason`: `method_not_allowed` (a
request other than `POST` arrived, which almost always means a redirect
rewrote it; the answer is `405` with `Allow: POST`), `rate_limited`,
`expired`, `bad_signature`, `malformed`, `already_used`, `module_disabled`
or `unknown_user`, and `worker_only` or `demo_mode` when the request reached
a worker-only container or a demo instance. The token itself is never logged.

**Telegram** keeps its own keyboard on the mood reminder: the full 1 to 5
scale, a note and a "later" button.

**Web Push** offers no buttons. Most browsers show at most two actions,
which cannot carry a three-way answer, and Safari on iPhone shows none.
Tapping the notification opens the mood entry sheet instead.

**APNs**: the iOS app draws its own buttons from the notification category
it registers for the mood reminder.

## Proactive coach nudges

Separate from dose reminders, a daily pass can send at most one gentle coach
nudge per rolling window through the same channels: 7 days by default, 14 when
you pick the biweekly preference. It watches seven triggers (low 7-day
adherence, blood pressure above its target band, a falling recovery trend, a
stale self-context, weight drifting away from its green range, accumulating
sleep debt, and an abrupt measurement gap), grouped under three opt-out
toggles — medication, vitals, routine. It is off whenever the coach is disabled. See
[Health scores](/explanation/health-scores/) for what the signals mean.

## Client-managed reminders

A client that manages its own local reminders can suppress server-side
`MEDICATION_REMINDER` APNs by setting `clientManaged: true` on
`PATCH /api/auth/me/notification-prefs`. Only the APNs send is skipped; every
other enabled channel (Telegram, ntfy, webhook, email, Web Push) still
delivers.

`GET /api/auth/me` publishes the resolved preference as
`notificationPrefs.medication.clientManaged`, so the medication notification
card can say so on screen. With it on, the card marks the server-side medication
reminder as decided by your phone rather than by the switch in front of you,
which is the honest reading: flipping that switch changes nothing for a paired
device that reminds you itself.

## Diagnostics

`/api/admin/notifications/diagnostic` surfaces masked device tokens, per-channel
state, and the last 20 attempts for the calling user — the fastest way to see
whether a token registered and a push actually left.
