HealthLog connects to an Oura account over [OAuth 2.0](https://datatracker.ietf.org/doc/html/rfc6749) against the Oura API v2. You bring your own developer app: the Oura **Client ID** and **Client Secret** are pasted into Settings (or set as server env vars) and stored AES-256-GCM-encrypted at rest. HealthLog never ships a shared credential.

Once linked, the ring's sleep (with stage hypnogram), heart rate through the day, respiratory rate, activity, workouts, blood-oxygen and **daily readiness** flow in. Oura readiness ranks below WHOOP but above Polar and the computed proxy as a recovery source — see [Recovery and readiness](/methodology/recovery/).

## What gets synced

HealthLog reads the Oura v2 user collections and maps:

- **Sleep** — the `sleep` detail records carry a 5-minute hypnogram; light maps to HealthLog's CORE stage, plus efficiency, HRV and resting (lowest) heart rate.
- **Daily readiness** — the headline readiness score with its temperature-deviation and balance contributors.
- **Daily activity** — steps, energy, distance.
- **Daily SpO₂** — average overnight blood-oxygen saturation.
- **Daily sleep** — the headline Sleep Score (distinct from the `sleep` detail).
- **VO₂ max** — the dedicated `vO2_max` collection.
- **Cardiovascular age** — Oura's daily estimate, stored as vascular age.
- **Daily resilience** — the resilience level, encoded on a 1 to 5 scale.
- **Workouts** — each Oura workout, recorded or auto-detected, becomes a workout. The same walk from another source is shown once, by your [source priority](/guides/source-priority/).
- **Heart rate through the day** — the ring's readings every few minutes, stored as pulse readings.
- **Cycle phases** — a best-effort import of `daily_cycle_phases` for Cycle Insights, where the ring provides it.

Imported rows are tagged `source = OURA` and pass through the [source-priority](/explanation/source-priority/) resolver. Naps are kept distinct from the main sleep so a nap's segments never collide with the night's. Periods you dismissed in the Oura app (Oura marks them as `rest`) and periods you deleted are not imported: they are not sleep. Daily totals are stored at noon of their day in your own time zone, so they land on the right day wherever you live (see [the timezone model](/explanation/timezone-model/#cumulative-daily-aggregates)).

After connecting, HealthLog imports the account's whole history in the background, a slice at a time, starting with the newest days. A slice that stops (a rate limit, a failed window) is picked up where it left off.

## OAuth scopes

HealthLog requests:

```
daily spo2 heart_health stress workout heartrate personal
```

`daily` covers sleep, readiness and activity; `personal` is the profile information used to anchor the sync. `spo2` covers the daily blood-oxygen average, `heart_health` covers VO₂ max and cardiovascular age, `stress` covers resilience, `workout` the workouts and `heartrate` the heart rate through the day. All are read-only. Cycle phases are read when Oura allows it, without a scope of their own.

Oura enforces these per data type: a grant without one of them is refused on exactly those types while everything else syncs.

### Existing connections: reconnect once

A connection made before HealthLog asked for a scope holds a grant without it. HealthLog notices when Oura refuses only those data types, keeps syncing everything else and does not count it as a broken connection. The Oura card in **Settings → Integrations** then shows a short hint naming what is missing (for example resilience, workouts or heart rate) with a **Reconnect Oura** button. Reconnect once and approve the new permissions; the hint goes away with the new grant.

If authorization fails after you approve, or Oura's consent screen does not offer the new permissions, open your application in Oura's developer portal and check that every scope above is enabled for it, then connect again.

## 1. Register an Oura developer app

1. Sign in at [cloud.ouraring.com/oauth/applications](https://cloud.ouraring.com/oauth/applications) and **create a new application**.
2. **Redirect URI:** `https://your-instance.example.com/api/oura/callback`. It must match exactly.
3. Save. Oura issues a **Client ID** and **Client Secret**.

## 2. Wire the credentials into HealthLog

```env
OURA_CLIENT_ID="your-client-id"
OURA_CLIENT_SECRET="your-client-secret"
OURA_REDIRECT_URI="https://your-instance.example.com/api/oura/callback"
```

`OURA_REDIRECT_URI` is optional — when unset it is derived from `NEXT_PUBLIC_APP_URL` as `<app-url>/api/oura/callback`. Restart the `app` container after saving. A per-user credential override is also available from the Settings UI.

## 3. Connect from Settings

1. Sign in as the target user and open **Settings → Integrations → Oura**.
2. Click **Connect Oura** and grant the requested scopes.
3. Oura redirects back to `/api/oura/callback`; HealthLog exchanges the code, stores the token encrypted, and runs an initial sync.

### Which token endpoint HealthLog uses

Oura moved its sign-in to a new authorization server. Apps created in Oura's current developer portal get their codes from that server, and the older documented token endpoint refuses them. HealthLog exchanges every code at the current endpoint (`moi.ouraring.com/oauth/v2/ext/oauth-token`) and never sends a code from the new server to the old endpoint, since a code works only once. Refreshing a token falls back to the older endpoint (`api.ouraring.com/oauth/token`) once, for apps that still live there. The callback also checks the `iss` parameter Oura sends ([RFC 9207](https://datatracker.ietf.org/doc/html/rfc9207)) and stops the connection when it does not name one of Oura's own servers.

Nothing changes in your setup: the redirect URI and the credentials stay the same.

## Readiness as a recovery source

Oura's daily readiness is read as a recovery source. The resolver ranks recovery **WHOOP ≻ Oura ≻ Polar ≻ computed proxy**, so an Oura reading wins over the server-computed proxy and over a Polar device on the same day, but yields to a WHOOP strap. The eight readiness contributors are the *why* behind the headline number. See [Recovery and readiness](/methodology/recovery/).

## Troubleshooting

### Sleep stages do not appear

The hypnogram comes from the `sleep` detail collection. A night that only produced a `daily_sleep` summary has no per-stage timeline — the breakdown shows once the detail record syncs.

### Connecting fails right after you approve access

If the integration card says the sign-in answer did not come from Oura's own authorization server, start the connection again; that message means the callback named an issuer HealthLog does not accept.

### SpO2, VO2 max, cardiovascular age, resilience, workouts or heart rate are missing

The grant does not cover the matching scope. Reconnect Oura once from the integration card (see [Existing connections: reconnect once](#existing-connections-reconnect-once)). If the authorization then fails, enable the scopes for your application in Oura's developer portal and try again.

### Callback URI mismatch

The redirect URI in the Oura application must match the one HealthLog sends exactly, including the `/api/oura/callback` path. The integration card can warn about a callback origin that differs from the address in the browser; [troubleshooting](/self-hosting/troubleshooting/#oauth-callbacks-land-on-localhost-or-the-wrong-host) says when that check works.
