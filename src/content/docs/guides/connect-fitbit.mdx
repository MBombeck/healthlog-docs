The classic Fitbit connection reads a Fitbit account through the Fitbit Web
API with a per-user app from [dev.fitbit.com](https://dev.fitbit.com). Google
switched that API off on **30 October 2026**.

:::caution[Move to Google Health]
Google Health reads the same Fitbit and Pixel devices. Connect it with the
[Google Health guide](/guides/connect-google-health/). Google asks for your
consent once more, because a Fitbit connection cannot be carried over.
Everything the Fitbit connection already imported stays in HealthLog.
:::

## What happened on 30 October

Until the date, the Fitbit card showed a **Shutting down** badge with a link to
the Google Health card. Since the start of 30 October (midnight UTC, still the
evening before in the Americas) HealthLog makes no further Fitbit call: no
sync, no backfill, no token refresh and no new connection. The badge now
reads **Retired**. The connection stops counting as broken, so the watchdog
does not report it and nobody is asked to reconnect.

Self-serve app registration at dev.fitbit.com closed before that, so no new
Fitbit connection could be set up in the last months either.

## Before 30 October (existing app holders)

For reference, this is how an app registered earlier worked until the date:

- Its redirect URL had to be exactly
  `https://your-instance.example.com/api/fitbit/callback`.
- The Fitbit **Client ID** (a short numeric id, not a Google Cloud id) and
  **Client Secret** went on the Fitbit card under **Settings → Integrations**.
  They are stored encrypted; there are no `FITBIT_CLIENT_ID` /
  `FITBIT_CLIENT_SECRET` env vars.
- The connection polled hourly and had a manual sync button. There was no
  webhook.
- `FITBIT_REDIRECT_URI` overrode the callback only when its origin differed
  from `NEXT_PUBLIC_APP_URL`.
