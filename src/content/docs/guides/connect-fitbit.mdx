HealthLog's classic Fitbit connection reads a Fitbit account through the
Fitbit Web API with a per-user app registered at
[dev.fitbit.com](https://dev.fitbit.com). It coexists with the newer
[Google Health connection](/guides/connect-google-health/) — same devices,
different API.

:::caution[New registrations are closed; the API retires in September 2026]
Fitbit has **discontinued self-serve app registration** — the form at
`dev.fitbit.com/apps/new` is disabled for new applications — and Google
retires the classic Fitbit Web API in **September 2026**. An app you
registered before the shutdown keeps working until the sunset, and this page
still applies to it. Connecting Fitbit data for the first time? Use the
[Google Health connection](/guides/connect-google-health/) instead — Fitbit
devices sync into Google's health stack, which HealthLog reads directly.
:::

## Set it up (existing app holders)

<Steps>

1. **Check your existing Fitbit app.** Sign in at
   [dev.fitbit.com](https://dev.fitbit.com/apps) and open the application you
   registered before the shutdown. The **Personal** OAuth application type is
   the right one for a single-person self-host — it only ever sees the
   owner's own Fitbit account and gets intraday (per-minute) heart-rate and
   steps automatically. **Server** (or **Client**) is only needed when the
   instance connects other people's accounts; intraday access is then granted
   case by case via Fitbit's Intraday Data Access request form.

   - **Redirect URL** — copy it exactly, with your own hostname:

     ```
     https://your-instance.example.com/api/fitbit/callback
     ```

   The path is pinned: HealthLog refuses to start the flow if the resolved
   redirect URI does not target exactly `/api/fitbit/callback`. The app's
   settings page shows its **Client ID** and **Client Secret**.

2. **Paste the credentials in Settings.** Sign in as the target user, open
   **Settings → Integrations → Fitbit**, and paste the client ID and secret.
   They are stored AES-256-GCM-encrypted — there are no
   `FITBIT_CLIENT_ID` / `FITBIT_CLIENT_SECRET` env vars.

   A common mistake: the field wants a **Fitbit** Client ID (a short numeric
   id from dev.fitbit.com), **not** a Google Cloud client id ending in
   `.apps.googleusercontent.com`. A Google Cloud client fails at the Fitbit
   consent screen with `unauthorized_client — Invalid client_id`, because
   Fitbit and Google Cloud are separate client registries.

3. **Connect.** Click **Connect Fitbit**. The flow uses Authorization Code
   with PKCE and requests these read scopes:

   ```
   activity cardio_fitness heartrate oxygen_saturation profile respiratory_rate sleep weight
   ```

   The `temperature` scope is deliberately omitted — Fitbit exposes skin
   temperature only as a nightly deviation, not an absolute reading. On
   success, a full-history backfill is queued.

</Steps>

## Sync behaviour

There is **no webhook**: the classic connection polls hourly, staggered
against the other integrations, and a manual sync button lives on the
Settings card. The Web API's rate budget (~150 requests per hour per user)
paces the backfill. Values import in metric units regardless of the Fitbit
account's display locale. Classic Fitbit refresh tokens rotate (one-time
use); HealthLog replaces the stored token on every refresh, so the connection
stays healthy without re-authorising.

## Redirect URI override

Only when the callback origin differs from `NEXT_PUBLIC_APP_URL`:

```env
FITBIT_REDIRECT_URI="https://your-instance.example.com/api/fitbit/callback"
```

Unlike the Polar, Oura, Strava and WHOOP redirect overrides, this variable is
not on the compose `environment:` whitelist by default. Add it there when you
set it; the Withings and Google Health overrides share this caveat.
