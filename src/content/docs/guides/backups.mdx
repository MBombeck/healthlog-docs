HealthLog ships an optional daily off-host backup: every user's JSON dump,
encrypted with AES-256-GCM under a **separate** key (`BACKUP_ENCRYPTION_KEY`),
shipped to any S3-compatible bucket — Cloudflare R2, AWS S3, Backblaze B2, MinIO.

The backup runs at **02:30 Europe/Berlin** daily from the worker container
(queue `data-backup-offhost`). Object key layout:

```
<bucket>/YYYY-MM-DD/user-<userId>.json.enc
```

## Required env vars

| Var | Required | Notes |
| --- | --- | --- |
| `BACKUP_ENCRYPTION_KEY` | yes | 64 hex chars or 32-byte base64. **Must differ from `ENCRYPTION_KEY`.** |
| `BACKUP_S3_ENDPOINT` | yes | e.g. `https://<account>.r2.cloudflarestorage.com` |
| `BACKUP_S3_BUCKET` | yes | |
| `BACKUP_S3_ACCESS_KEY` | yes | |
| `BACKUP_S3_SECRET_KEY` | yes | |
| `BACKUP_S3_REGION` | no | defaults to `auto` (Cloudflare R2) |
| `BACKUP_RETENTION_DAYS` | no | Not read by the app. The number you set your bucket's lifecycle rule to. |

These are **all-or-none**: setting some but not all disables backups silently.
The set is on the compose `environment:` whitelist. If you run a
[web/worker split](/guides/updates-and-deploy/), the backup job runs in the
worker, but the admin smoke test runs in the web container — set `BACKUP_*` on
**both**.

## Wire format

```
magic   = "HLBK"           (4 bytes, ASCII)
version = 0x03             (1 byte)
iv      = 12 random bytes  (AES-GCM nonce)
ciphertext = N bytes       (AES-256-GCM over gzip(JSON dump), key = BACKUP_ENCRYPTION_KEY)
authTag = 16 bytes         (AES-GCM tag, trailing)
```

The trailing tag is what lets the object be written as a stream: GCM only
produces the tag once the last block is in, so a leading tag means the whole
object has to exist before its first byte can be sent. Versions `0x01` (JSON
encrypted directly) and `0x02` (gzipped first, tag in front) are still read, so
older objects restore unchanged and the restore script needs no flag to tell
them apart.

## Smoke test

After deploying, hit `POST /api/admin/backup/test` (admin-only). It performs a
1-byte PUT + GET round-trip and returns the endpoint, bucket, region, and PUT/GET
latencies. Credentials are never returned.

```json
{
  "data": {
    "endpoint": "https://...r2.cloudflarestorage.com",
    "bucket": "healthlog-backups",
    "region": "auto",
    "putLatencyMs": 142,
    "getLatencyMs": 38,
    "ok": true
  },
  "error": null
}
```

## Which account has no copy

The run reports counts, never names. An account whose object has failed every
night for a month reads as `99 uploaded, 1 failed` each time, which looks like
weather.

**Admin → Backups → Off-host copies** answers it per account: when this host
last put that account's encrypted copy in the bucket, how big it was, and how
that compares with the nightly schedule. **Fresh** is inside one run, **due**
means one run produced nothing for that account, **stale** means two did not,
**never** means a run walked the account and no object has ever landed for it,
and **no record yet** means no run has recorded the account at all (`unknown`
on the wire). Stale rows sort first. On a host without `BACKUP_S3_*` the card
says off-host backup is not configured and stops there.

The ledger starts empty on the release that adds it, so on a host that has
been uploading nightly for months every account reads **no record yet** until
the first run after the upgrade. That is the ledger having no history, not the
bucket being empty, which is why it is a separate word from **never**.

Each verdict carries six hours of slack on top of the schedule's own 24 hours,
for the DST fall-back night when two 02:30 Europe/Berlin runs are 25 hours
apart and for a cohort walked one account at a time. Without it a healthy host
would paint its whole cohort **due** once a year.

The verdicts come from a ledger the worker writes when the object lands
(`offhost_backup_state`), not from a listing of the bucket, so the worker's
grant stays PutObject, GetObject and AbortMultipartUpload and the card still
tells the truth. The row is wiped with the account and is not part of the
backup itself: it describes this host's relationship with this bucket, and a
restore elsewhere must not assert a copy that host never wrote.

## Bucket lifecycle

The worker never deletes a backup object — its grant is `PutObject`,
`GetObject` and `AbortMultipartUpload` only — so the provider's lifecycle rule
is the only thing that expires them, and nothing in the app reads
`BACKUP_RETENTION_DAYS`. Set the rule to the number of days you want the
history to survive, and set the variable to the same number so the two agree
on paper. For Cloudflare R2, add it from the bucket's
**Settings → Lifecycle**.

## Restore

Pick a key from the bucket and run the restore script with the same backup
credentials and **the encryption key the backup was written under**. Never
generate a fresh `BACKUP_ENCRYPTION_KEY` for a restore — a new key cannot
decrypt any existing object. If you rotated the backup key at some point,
pre-rotation objects are only readable with the retired key, so keep retired
backup keys somewhere durable for as long as their objects live.

```bash
BACKUP_S3_ENDPOINT=https://...r2.cloudflarestorage.com \
BACKUP_S3_BUCKET=healthlog-backups \
BACKUP_S3_ACCESS_KEY=... \
BACKUP_S3_SECRET_KEY=... \
BACKUP_S3_REGION=auto \
BACKUP_ENCRYPTION_KEY=<the key the backup was written under> \
pnpm dlx tsx scripts/restore-backup.ts \
  2026-05-08/user-clx123.json.enc \
  /tmp/restored.json
```

The script downloads the object, decrypts it, and writes the JSON dump to disk
with owner-only permissions (`0600`), since the file is decrypted health data
in plaintext (v1.37.33). An output name ending in `.gz` writes the dump
compressed, which is the form to use for a large account: the JSON of 1.25
million readings is about 660 MB, the compressed file about a tenth of that.
To bring the dump back into an instance, upload it on the admin backups page
and restore it from there, as described next.

:::caution[Run the restore from a source checkout]
The script imports the full application dependency graph, which the minimal
production image does not carry, and the image strips `tsx` as well. Run it
from a checkout of the repository with the backup variables exported, through
`pnpm dlx tsx` as above, not inside the container.
:::

## Restore from the console

The bucket object is the disaster path. The routine one is the backup table
under `/admin/backups`, which holds each account's stored snapshots as database
rows. Pick a row, choose **Restore**, and type `RESTORE`.

To restore a file you hold (a dump from the restore script, or an export),
upload it on the same page first; it becomes a row of its own. The upload
takes a `.json` or a `.json.gz` file. Since v1.39.1 the page compresses a
plain JSON file in the browser before sending it and the server reads the file
as a stream, so a file of several hundred megabytes goes up. The limit is 512
MB as sent. A file whose encrypted copy is too large for this server to store
is refused with `413` (`backup.upload.too_large`), and nothing of it is kept.

Since v1.39.1 the restore runs in the background. Above the table the page
shows which step it is on (checking the file, clearing the account's current
data, writing the readings, writing the other records, rebuilding the charts)
and how many readings it has written, then whether it finished. You can leave
the page or reload it; the progress is still there when you come back. A large
account takes a while: two to three minutes for 1.25 million readings. Because
the request only starts the restore, a reverse proxy that closes requests after
60 seconds no longer shows an error for a restore that is still running.

While it runs, the account keeps showing its current data. The restore is
written in one go, so nothing changes for the account until the data is
written, and a restore that fails before that leaves the account exactly as it
was. Only one restore per account runs at a time; starting a second one while
the first is queued or running is refused, and the page says a restore is
already in progress.

If a restore fails, the page says why and what to do: the file is incomplete,
the backup was replaced by a newer copy while the restore waited, the file is
too large to restore within the background job's time limit, the worker is not
running, and so on. The backup stays in the table, so you can start the restore
again from its row without uploading the file again. A restore interrupted by a
server restart before its data was written starts again by itself once the
server is back; if it stops a second time, it is marked as failed, and the
server most likely ran out of memory. A restore that stops after the data was
written, while the charts are being rebuilt, is never run again, so nothing
written to the account since is lost. The page says the data was restored and
that the charts may take until the next nightly run to catch up.

Medications keep their creation date through a restore. A portable export
written from v1.39.1 on carries it. An older portable export does not, so the
restore dates each medication by the earliest thing the file records for it
(its first dose, the start of its first schedule, its course start and the
like), never later than the restore itself. Before, the restore date was used,
and missed doses in the restored history dropped out of the adherence rate.

Two things to know before you do.

**A restore replaces, it does not merge.** Every row the account gained after
the snapshot was taken is removed along with the rest of its class, so a reading
entered this morning is gone if the snapshot is from last night. That is the
point of the action, and it is why the typed confirmation is there.

**The instance settings stay put unless you ask.** The checkbox beside the
confirmation, **Restore instance settings**, is off by default. Off, the restore
touches one account's data. On, it also rewrites the singleton settings row:
registration, the second-factor requirement, the default language and timezone,
module availability, notification and AI configuration, and the document size
cap and quota. Those apply to every account on the installation, so tick it only
when you are rebuilding a host.

A stored copy the instance cannot open is refused rather than reported as a
crash. Restore, download and preview each answer `422` with
`meta.errorCode: backup.payload.undecryptable` straight away, and nothing is
changed. There are two ways to earn it: the key that wrote the copy is no
longer in `ENCRYPTION_KEYS`, which is a rotation that dropped the legacy entry
too early, or the stored bytes are not the ones that were written. A copy that
decrypts and then fails its checks (the file is not a valid backup, its
manifest names a section it does not carry, it belongs to another account) is
reported on the page as a failed restore with the reason, and nothing is
changed either.

## Large accounts

An account with years of imported Apple Health data can hold more than a
million readings. Since v1.39.1 every backup path handles that inside the
standard 1 GB container. The full export is sent while it is being written,
with or without a passphrase. The weekly and manual backups are stored piece by
piece, and if a run fails partway the previous backup stays in place. Stored
backups are read in small parts, so a large one can be previewed, downloaded
and restored. On an account with 1.25 million readings the export takes about
25 seconds and the restore about two and a half minutes. The off-host run
continues with the accounts it had not reached when it is retried, instead of
starting again from the first.

## What a backup does not carry

Every credential-shaped row is left out, and this is a decision rather than an
oversight: API tokens, trusted devices, step-up elevations, known devices,
clinician share links, and the account grants behind
[shared record access](/guides/shared-access/). Restoring data rolls a record
back to a known state. Restoring an authorization is different in kind, because
a grant the owner revoked on Tuesday would come back alive out of Monday's file
with nobody deciding it and neither person told.

What that means in practice depends on where you restore.

- **Onto the same instance.** Nothing changes. The restore replaces the
  account's data tables and does not touch grants, tokens or devices, so shared
  access carries on exactly as it was, now over the restored data.
- **Onto a fresh instance.** None of it comes with the file. Nobody has access
  to anybody's record, every API token has to be reissued, every device
  re-trusted, and both people have to invite and accept again before sharing
  works. That is the fail-safe direction, and re-consenting is the right amount
  of ceremony for handing somebody your health record a second time. Plan for it
  rather than discovering it.

The per-model reasoning lives in `src/lib/export/backup-plan.ts`, where every
excluded model carries a written reason, and a new one cannot be left out
without getting one.

## Monthly restore drill (automatic)

A pg-boss job (`data-restore-drill`, 04:11 on the 1st of each month) exercises
the read path end to end: it fetches the most recent backup object, decrypts
it under the current `BACKUP_ENCRYPTION_KEY`, JSON-parses it, and sanity-checks
the payload shape. It performs **no database restore** — it validates the
artefact, not the import path. Outcomes:

- **Success** — record counts, object age, and sizes land in the wide-event
  meta (`job.restore_drill`).
- **Stale chain** — the newest object is older than 3 days: the nightly
  uploader has stalled, or the lifecycle rule is too aggressive. The drill
  pages via the worker error reporter.
- **Failure** — empty bucket, fetch error, decryption failure, or malformed
  JSON pages the same way. A decryption failure right after a
  `BACKUP_ENCRYPTION_KEY` change means the new key cannot read the existing
  objects — re-encrypt, or accept that pre-rotation backups are only readable
  with the retired key.
- **Not configured** — deployments without the `BACKUP_S3_*` vars skip
  silently.

The drill needs no IAM grant beyond the uploader's existing `GetObject` +
`ListBucket`.
