HealthLog has three kinds of backup. Two run by themselves; the database dump
is yours to take. This page says which one covers which loss, then how to
restore each.

## Which backup covers what

| Backup | What it holds | Covers | Does not cover |
| --- | --- | --- | --- |
| **Database dump** (`pg_dump`, or a snapshot of the database volume) | The whole instance: every account, the instance settings, sign-ins, tokens and grants | A failed update, a lost disk or host (when the file is kept off the host), a move to a new server | Nothing, as long as you keep the encryption key with it |
| **Weekly copy in the database** (automatic) | One encrypted copy per account, inside the same database | A bad import or a mistaken delete in one account | A lost disk: it lives on the same disk |
| **Nightly off-host copy** (optional, S3-compatible bucket) | One encrypted copy per account, every night | Bringing one account back to last night, on an instance where that account exists | Sign-ins, tokens, devices and sharing grants (see [below](#what-a-backup-does-not-carry)); a fresh instance, where the account does not exist yet |

The account copies restore one account at a time under **Admin → Backups**.
An uploaded copy is refused when its account does not exist on the instance,
so they cannot rebuild a lost host on their own. For that, restore the latest
database dump first, then bring single accounts forward to a newer off-host
copy if you need to.

Every one of them is unreadable without its keys. Keep `ENCRYPTION_KEY` (or
`ENCRYPTION_KEYS` with `ENCRYPTION_ACTIVE_KEY_ID`), `API_TOKEN_HMAC_KEY` and,
for the off-host copy, `BACKUP_ENCRYPTION_KEY` somewhere other than the server
([why](/explanation/encryption-at-rest/#keep-a-copy-of-the-key)).

## Take a database dump

```bash
docker compose exec -T db pg_dump -U healthlog healthlog \
  | gzip > healthlog-$(date +%F).sql.gz
```

Run it before every update (see [Updates](/guides/updates-and-deploy/)) and on
a schedule of your own, and copy the file off the host. With an
[external Postgres](/self-hosting/external-postgres/), run `pg_dump` against
that server. A snapshot of the database volume or dataset (ZFS, TrueNAS,
Unraid) works too, taken with the app stopped or as an atomic snapshot.

## Restore a database dump

A restore replaces the whole database with the state in the file. Anything
written after the dump is lost.

```bash
# 1. Stop the app (and app-worker, if you run one) so nothing writes.
docker compose stop app

# 2. Replace the database with an empty one.
docker compose exec -T db dropdb -U healthlog healthlog
docker compose exec -T db createdb -U healthlog -O healthlog healthlog

# 3. Load the dump and gather the planner statistics, which a dump does
#    not carry.
gunzip -c healthlog-2026-10-25.sql.gz \
  | docker compose exec -T db psql -U healthlog -d healthlog -v ON_ERROR_STOP=1 -q
docker compose exec -T db vacuumdb -U healthlog -d healthlog --analyze-in-stages

# 4. Start the app. To go back to the release the dump came from, pin it
#    first with HEALTHLOG_IMAGE_REF=:vX.Y.Z in .env.
docker compose up -d app
curl -s http://localhost:3000/api/version
```

The app needs the encryption key the data was written with. With a different
key it starts but refuses to serve, with "HealthLog cannot open its data" (see
[Troubleshooting](/self-hosting/troubleshooting/#healthlog-cannot-open-its-data)).
A dump in Postgres' custom format (`pg_dump -Fc`) loads with `pg_restore
--no-owner -d healthlog` instead of `psql`.

## Move to a new server

1. On the old server, note the running version (`/api/version`), stop the app
   and take a dump as above.
2. Copy the dump and the `.env` file to the new server. The `.env` carries the
   keys the data needs: `ENCRYPTION_KEY` (or `ENCRYPTION_KEYS` and
   `ENCRYPTION_ACTIVE_KEY_ID`), `API_TOKEN_HMAC_KEY` and, if you use it,
   `BACKUP_ENCRYPTION_KEY` with any `BACKUP_ENCRYPTION_PREVIOUS_KEYS`. A new
   `API_TOKEN_HMAC_KEY` signs everyone out and invalidates every API token.
3. On the new server, clone the repository, put the `.env` in place and pin the
   same version with `HEALTHLOG_IMAGE_REF`, so the move and an update do not
   happen at once.
4. Start only the database with `docker compose up -d db`, then follow
   [Restore a database dump](#restore-a-database-dump) from step 2.
5. Check `/api/version`, sign in, and only then update to a newer release.

If the address changes, set `APP_URL` and `NEXT_PUBLIC_APP_URL` to the new one,
update the callback addresses registered at each connected provider, and expect
passkeys to stop working: a passkey belongs to the domain it was created on.

## Backups kept in the database

The app keeps an encrypted copy of every account in its own database, under
`ENCRYPTION_KEY` / `ENCRYPTION_KEYS`. The weekly run (Sunday 03:00
Europe/Berlin, and **Backup now** on the admin backups page) replaces each
account's weekly copy, and every file an admin uploads is kept as a copy of
its own. These are the copies the console restores, previews and downloads.

A copy is written as ordered pieces of about a megabyte, each encrypted on its
own, so its size does not depend on the app's memory. A new copy is written in
one transaction, and the previous one stays readable until it is complete. A
restore checks every piece before it deletes anything; a missing, altered or
foreign piece stops it and leaves the account as it was. While a restore of an
account is queued or running, backups skip that account and back up everyone
else.

### Limits

| Limit | Value | What happens past it |
| --- | --- | --- |
| Stored copy of one account | `BACKUP_MAX_STORED_MB`, default `2048` MB of encrypted copy | That account's backup stops, its previous copy stays, the run continues with the other accounts. An upload is refused with `413` (`backup.upload.too_large`). |
| Writing one account's copy | 90 minutes | That account's backup fails and its previous copy stays. |
| The weekly run for all accounts | 2 hours | The run is marked failed ("job timed out"). Copies already written stay. |
| An upload | 512 MB as sent; the page compresses a plain `.json` in the browser first | Refused with `413`. |
| A restore | Two minutes, plus a second per 1,000 readings in the file and a second per 10,000 readings the account holds now, within 4.5 hours: roughly 14 million readings | Refused before anything is deleted. See [How long a restore may take](#how-long-a-restore-may-take). |

For scale, an account with 2.6 million readings stores a copy of about 100 MB.
To store larger copies, set `BACKUP_MAX_STORED_MB` in `.env` and run
`docker compose up -d`. Keep room on the database volume for a second copy of
that size, because the old copy stays until the new one is complete.

### When a backup fails

- **"The weekly backup has stopped" or "The last scheduled backup run
  failed".** The first means the newest weekly copy is more than ten days old;
  the second quotes the run's own reason. Press **Backup now** and check that
  fresh rows appear.
- **One account's row keeps an old date.** Its backup failed, or it was skipped
  because a restore of it was running. The app log's `job.data_backup` line
  names the reason per account. If it names `BACKUP_MAX_STORED_MB`, raise the
  limit.
- **A preview, download or restore answers `409` `backup_changed`.** The copy
  was replaced by a newer one while it was being read. Nothing was changed;
  start again.
- **"A run stopped partway and never came back".** The process died under the
  run, usually a restart or the container running out of memory. The page
  names each account whose copy was started and not finished, and the next run
  takes those accounts last. The same account showing up twice points at
  memory: check the container's restart count and that `APP_MEMORY_LIMIT` is
  at least the [supported floor](/getting-started/self-host-in-10-minutes/#requirements).

In every case the account's previous copy is still there and can be restored.

## Restore from the console

Under **Admin → Backups**, pick a row, choose **Restore**, and type `RESTORE`.
Before you confirm, the dialog shows what the copy contains: how many
readings, medications, mood entries, lab results, documents, workouts and so
on.

To restore a file you hold (a copy from the restore script, or an export),
upload it on the same page first; it becomes a row of its own. The upload
takes a `.json` or `.json.gz` file of up to 512 MB as sent, and is refused when
the account it belongs to does not exist on this instance.

The restore runs in the background. The page shows which step it is on and how
many readings it has written; you can leave or reload it. A restore never runs
beside a backup or another large job such as an import; while it waits, the
page says which of the two it is waiting for and since when. Only one restore
per account runs at a time.

While it runs, the account keeps showing its current data. The restore is
written in one transaction, so a restore that fails leaves the account exactly
as it was, and the page says why. The copy stays in the table, so you can start
again from its row. A restore interrupted by a server restart before its data
was written starts again by itself; if it stops a second time it is marked as
failed, and the server most likely ran out of memory. A restore that stops
while the charts are being rebuilt is not run again; the charts catch up by
the next nightly run.

Two things to know before you start one.

**A restore replaces, it does not merge.** Every row the account gained after
the copy was taken is removed, so a reading entered this morning is gone if
the copy is from last night.

**The instance settings stay put unless you ask.** **Also restore instance
settings** is off by default. On, the restore also rewrites the instance-wide
settings: registration, the second-factor requirement, the default language
and time zone, module availability, notification and AI configuration, and the
document size cap and quota. Tick it only when you are rebuilding a host.

A copy the instance cannot open is refused straight away and nothing changes:
`422` with `backup.payload.undecryptable` when the key that wrote the copy is
no longer in `ENCRYPTION_KEYS` or the stored bytes were altered, and `422` with
`backup.key.missing` naming the key id when the copy's encrypted fields need a
key this server does not hold. Put the key back and the copy restores;
[Key rotation](/guides/encryption-key-rotation/) explains how long to keep an
old key. A file that would attach the account's records to another account's
(`backup.foreign_reference`) is refused too.

### How long a restore may take

A restore deletes the readings the account holds now and writes the ones in the
file, in one transaction. Writing is the slower half, because every reading
goes into several indexes. Measured on an account of 1.89 million readings, a
restore took about 3 minutes on a fast database host and about 15 minutes on
one held to half a processor core and 40 MB/s of disk writes.

The transaction gets its own time limit: two minutes, plus a second per 1,000
readings in the file and a second per 10,000 readings the account holds now.
A restore whose limit, plus ten minutes for rebuilding the charts, would run
past 4.5 hours is refused before anything is deleted. On a disk that manages
only a few hundred writes a second a restore of a million readings or more can
still run out of time; the page then says so, and nothing is changed.

Deleted readings stay in a backup until they are 75 days old, so a paired app
that was offline can still learn about the deletion. A restore leaves out the
older ones, which the nightly clean-up would remove anyway.

### When the database refuses a restore

The restore is rolled back whole, and the page names the cause:

| The page says | What to do |
| --- | --- |
| The restore ran longer than the database allowed | Start again when the database host is quieter. The server log names the step |
| The restore waited on records another process was changing | Start the restore again |
| The database rejected a record in the backup | The server log names the table and the rule |
| The database ran out of disk space or memory | Free up space on the database host, then start again |
| The connection to the database was lost | Check that the database is running, then start again |

The full error is in the server log and the audit log.

### Paired apps after a restore

An app that keeps its own copy of your data and catches up through the change
feed holds a position in that feed, and a restore makes it meaningless. The
server records when an account was restored, wiped with **Delete all data**,
or cleared by the admin's global wipe, and an app asking with an older position
is told to start over (`cursorExpired`). See
[Sync](/reference/sync/#cursorexpired--clean-re-init).

## What a backup carries

Besides the record, an account copy carries how the account is set up: units,
language, time zone, date and time format, modules, thresholds, layouts,
notification and reminder preferences, health score configuration, source
priority, AI choices without their keys, the profile (height, date of birth,
name, picture, home location) and which imported documents were deleted, so an
automatic import does not bring them back after a restore. Each value is
checked the way the settings page checks it; a value this server does not
accept is skipped, the account keeps its own, and the restore result names it.

### What a backup does not carry

Every credential-shaped row is left out on purpose: the password, passkeys,
two-factor secrets, API tokens, integration tokens and connection state,
trusted and known devices, single sign-on links, clinician share links, the
Telegram bot connection, and the account grants behind
[shared record access](/guides/shared-access/). Restoring data rolls a record
back to a known state; restoring an authorization would bring a grant the
owner revoked on Tuesday back to life out of Monday's file.

- **Onto the same instance**, nothing changes: the restore replaces the
  account's data and does not touch grants, tokens or devices.
- **Onto another instance**, none of it comes with the file. Tokens have to be
  issued again, devices trusted again, providers reconnected, and sharing set
  up again by both people.

A database dump is different: it carries all of this, because it is the whole
database.

## Off-host copies

The optional nightly off-host backup writes every account's copy, encrypted
with AES-256-GCM under a **separate** key (`BACKUP_ENCRYPTION_KEY`), to any
S3-compatible bucket (Cloudflare R2, AWS S3, Backblaze B2, MinIO). It runs at
02:30 Europe/Berlin from the process that runs the worker, and writes
`<bucket>/YYYY-MM-DD/user-<userId>.json.enc`. Each object names the key that
wrote it and is bound to its own object key, so a copy moved under another
account's name or date does not decrypt.

| Variable | Required | Notes |
| --- | --- | --- |
| `BACKUP_ENCRYPTION_KEY` | yes | 64 hex chars or 32-byte base64. **Must differ from `ENCRYPTION_KEY`.** |
| `BACKUP_S3_ENDPOINT` | yes | e.g. `https://<account>.r2.cloudflarestorage.com` |
| `BACKUP_S3_BUCKET` | yes | |
| `BACKUP_S3_ACCESS_KEY` | yes | |
| `BACKUP_S3_SECRET_KEY` | yes | |
| `BACKUP_S3_REGION` | no | defaults to `auto` (Cloudflare R2) |
| `BACKUP_RETENTION_DAYS` | no | Not read by the app. The number you set your bucket's lifecycle rule to. |
| `BACKUP_ENCRYPTION_PREVIOUS_KEYS` | no | Retired off-host keys, comma-separated. Read only, never written with. |

The set is all or none: with one missing, off-host backup is off. All are on
the compose whitelist. With a [web/worker split](/self-hosting/scaling/), set
them on both containers: the worker writes the copies, the web container runs
the connection test and records deleted accounts' copies for deletion.

**Connection test.** `POST /api/admin/backup/test` (admin only) writes and
reads back one byte and returns the endpoint, bucket, region and latencies,
never the credentials.

**Bucket permissions.** The worker needs `PutObject`, `GetObject`,
`ListBucket`, `DeleteObject` and `AbortMultipartUpload`; on Cloudflare R2 the
**Object Read & Write** token covers them. Add `GetLifecycleConfiguration` if
you want the admin page to confirm your lifecycle rule. The app deletes
objects only when an account's data goes (account deleted, managed profile
deleted, **Delete all data**), retried every night while the bucket refuses,
and its own connection-test object. The admin's global wipe deletes nothing in
the bucket: those copies are how you get back from a wipe pressed by mistake.

**Lifecycle.** The app does not expire copies by age. Set a lifecycle rule on
the bucket (on R2 under the bucket's **Settings → Lifecycle**) and set
`BACKUP_RETENTION_DAYS` to the same number. Without a rule every nightly copy
is kept forever.

### Which account has no copy

**Admin → Backups → Off-host copies** shows per account when this host last
wrote its copy and how big it was: **fresh** is inside one run, **due** means
one run produced nothing for that account, **stale** means two did not,
**never** means no object has ever landed for it, and **no record yet** means
no run has recorded the account so far. Stale rows sort first. The card also
says when the bucket has no lifecycle rule, and lists deleted accounts whose
copies the bucket refused to delete.

### Restore from the bucket

Decrypt an object with the restore script, from a checkout of the repository
(the production image does not carry the script's dependencies), with the
backup credentials and **the key the copy was written under**. A freshly
generated key cannot decrypt anything; after a rotation, put the old key into
`BACKUP_ENCRYPTION_PREVIOUS_KEYS`.

```bash
BACKUP_S3_ENDPOINT=https://...r2.cloudflarestorage.com \
BACKUP_S3_BUCKET=healthlog-backups \
BACKUP_S3_ACCESS_KEY=... \
BACKUP_S3_SECRET_KEY=... \
BACKUP_S3_REGION=auto \
BACKUP_ENCRYPTION_KEY=<the key the backup was written under> \
pnpm dlx tsx scripts/restore-backup.ts \
  2026-05-08/user-clx123.json.enc \
  /tmp/restored.json.gz
```

The file is decrypted health data, written with owner-only permissions; an
output name ending in `.gz` writes it compressed. Upload it under
**Admin → Backups** and restore it from its row as described
[above](#restore-from-the-console).

### Rotating the off-host key

Put the new key into `BACKUP_ENCRYPTION_KEY`, move the old one into
`BACKUP_ENCRYPTION_PREVIOUS_KEYS`, and restart. New copies use the new key and
older ones stay readable. Remove the old key once your lifecycle rule has
retired every copy written under it, and keep a copy of every retired key for
as long as its objects live.

### Monthly restore drill

On the 1st of each month at 04:11 a job reads the newest copy of every account
from the bucket, decrypts it with the keys the server holds and checks its
shape. It restores nothing into the database. It reports through the worker's
error reporting when the newest copy is older than three days (the nightly
upload stalled or the lifecycle rule is too short), when the bucket is empty,
when an object fails to decrypt (after a key change, the old key is missing
from `BACKUP_ENCRYPTION_PREVIOUS_KEYS`), or when a copy needs an application
key this server does not hold.
