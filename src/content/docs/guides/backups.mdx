HealthLog ships an optional daily off-host backup: every user's JSON dump,
encrypted with AES-256-GCM under a **separate** key (`BACKUP_ENCRYPTION_KEY`),
shipped to any S3-compatible bucket — Cloudflare R2, AWS S3, Backblaze B2, MinIO.

The backup runs at **02:30 Europe/Berlin** daily from the worker container
(queue `data-backup-offhost`). Object key layout:

```
<bucket>/YYYY-MM-DD/user-<userId>.json.enc
```

## Required env vars

| Var | Required | Notes |
| --- | --- | --- |
| `BACKUP_ENCRYPTION_KEY` | yes | 64 hex chars or 32-byte base64. **Must differ from `ENCRYPTION_KEY`.** |
| `BACKUP_S3_ENDPOINT` | yes | e.g. `https://<account>.r2.cloudflarestorage.com` |
| `BACKUP_S3_BUCKET` | yes | |
| `BACKUP_S3_ACCESS_KEY` | yes | |
| `BACKUP_S3_SECRET_KEY` | yes | |
| `BACKUP_S3_REGION` | no | defaults to `auto` (Cloudflare R2) |
| `BACKUP_RETENTION_DAYS` | no | defaults to `30` |

These are **all-or-none**: setting some but not all disables backups silently.
The set is on the compose `environment:` whitelist. If you run a
[web/worker split](/guides/updates-and-deploy/), the backup job runs in the
worker, but the admin smoke test runs in the web container — set `BACKUP_*` on
**both**.

## Wire format

```
magic   = "HLBK"           (4 bytes, ASCII)
version = 0x01             (1 byte)
iv      = 12 random bytes  (AES-GCM nonce)
authTag = 16 bytes         (AES-GCM tag)
ciphertext = N bytes       (AES-256-GCM, key = BACKUP_ENCRYPTION_KEY)
plaintext  = JSON dump (UTF-8)
```

## Smoke test

After deploying, hit `POST /api/admin/backup/test` (admin-only). It performs a
1-byte PUT + GET round-trip and returns the endpoint, bucket, region, and PUT/GET
latencies. Credentials are never returned.

```json
{
  "data": {
    "endpoint": "https://...r2.cloudflarestorage.com",
    "bucket": "healthlog-backups",
    "region": "auto",
    "putLatencyMs": 142,
    "getLatencyMs": 38,
    "ok": true
  },
  "error": null
}
```

## Bucket lifecycle

The worker prunes objects older than `BACKUP_RETENTION_DAYS`, but the provider's
own lifecycle rule is the canonical safety net. For Cloudflare R2, add from the
bucket's **Settings → Lifecycle**: expire all objects after 30 days.

## Restore

Pick a key from the bucket and run the restore script with the same backup
credentials and **the encryption key the backup was written under**. Never
generate a fresh `BACKUP_ENCRYPTION_KEY` for a restore — a new key cannot
decrypt any existing object. If you rotated the backup key at some point,
pre-rotation objects are only readable with the retired key, so keep retired
backup keys somewhere durable for as long as their objects live.

```bash
BACKUP_S3_ENDPOINT=https://...r2.cloudflarestorage.com \
BACKUP_S3_BUCKET=healthlog-backups \
BACKUP_S3_ACCESS_KEY=... \
BACKUP_S3_SECRET_KEY=... \
BACKUP_S3_REGION=auto \
BACKUP_ENCRYPTION_KEY=<the key the backup was written under> \
pnpm dlx tsx scripts/restore-backup.ts \
  2026-05-08/user-clx123.json.enc \
  /tmp/restored.json
```

The script downloads the object, decrypts it, and writes the JSON dump to disk
with owner-only permissions (`0600`), since the file is decrypted health data
in plaintext (v1.37.33). Importing the dump back into an instance is left to
the operator (`prisma db seed` or a custom script).

:::caution[Run the restore from a source checkout]
The script imports the full application dependency graph, which the minimal
production image does not carry, and the image strips `tsx` as well. Run it
from a checkout of the repository with the backup variables exported, through
`pnpm dlx tsx` as above, not inside the container.
:::

## What a backup does not carry

Every credential-shaped row is left out, and this is a decision rather than an
oversight: API tokens, trusted devices, step-up elevations, known devices,
clinician share links, and the account grants behind
[shared record access](/guides/shared-access/). Restoring data rolls a record
back to a known state. Restoring an authorization is different in kind, because
a grant the owner revoked on Tuesday would come back alive out of Monday's file
with nobody deciding it and neither person told.

What that means in practice depends on where you restore.

- **Onto the same instance.** Nothing changes. The restore replaces the
  account's data tables and does not touch grants, tokens or devices, so shared
  access carries on exactly as it was, now over the restored data.
- **Onto a fresh instance.** None of it comes with the file. Nobody has access
  to anybody's record, every API token has to be reissued, every device
  re-trusted, and both people have to invite and accept again before sharing
  works. That is the fail-safe direction, and re-consenting is the right amount
  of ceremony for handing somebody your health record a second time. Plan for it
  rather than discovering it.

The per-model reasoning lives in `src/lib/export/backup-plan.ts`, where every
excluded model carries a written verdict and a structural test refuses to let a
new model land without one.

## Monthly restore drill (automatic)

A pg-boss job (`data-restore-drill`, 04:11 on the 1st of each month) exercises
the read path end to end: it fetches the most recent backup object, decrypts
it under the current `BACKUP_ENCRYPTION_KEY`, JSON-parses it, and sanity-checks
the payload shape. It performs **no database restore** — it validates the
artefact, not the import path. Outcomes:

- **Success** — record counts, object age, and sizes land in the wide-event
  meta (`job.restore_drill`).
- **Stale chain** — the newest object is older than 3 days: the nightly
  uploader has stalled, or the lifecycle rule is too aggressive. The drill
  pages via the worker error reporter.
- **Failure** — empty bucket, fetch error, decryption failure, or malformed
  JSON pages the same way. A decryption failure right after a
  `BACKUP_ENCRYPTION_KEY` change means the new key cannot read the existing
  objects — re-encrypt, or accept that pre-rotation backups are only readable
  with the retired key.
- **Not configured** — deployments without the `BACKUP_S3_*` vars skip
  silently.

The drill needs no IAM grant beyond the uploader's existing `GetObject` +
`ListBucket`.
