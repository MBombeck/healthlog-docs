HealthLog connects to Withings via OAuth2 plus a push webhook for
near-real-time sync. Once linked, every Body+ scale weighing, BPM
blood-pressure reading, ScanWatch sleep stage, and activity sample lands in
HealthLog within seconds — no polling, no third-party relay.

## What gets synced

Withings metric types map into `Measurement` rows tagged `source = WITHINGS`:

| Withings meastype | HealthLog metric |
| --- | --- |
| 1 | `WEIGHT` |
| 5 | `FAT_FREE_MASS` |
| 9 | `BLOOD_PRESSURE_DIA` |
| 10 | `BLOOD_PRESSURE_SYS` |
| 11 | `PULSE` |
| 54, 35 | `OXYGEN_SATURATION` (ScanWatch / pulse-ox) |

Plus the body-composition family (fat ratio, muscle mass, bone mass, hydration),
sleep stages, and heart-rate variability from the nightly sleep summary (the
SDNN estimate); the heart endpoints power the ECG recording import. Activity
data (steps, active energy, distance, floors) arrives through the
`user.activity` scope.

## Set it up

<Steps>

1. **Register a Withings developer app.** Sign in at
   [developer.withings.com](https://developer.withings.com/) and create a new
   **public-API application** (the free Public tier is enough).

   - **Callback URL:** `https://your-instance.example.com/api/withings/callback`.
     Withings allows multiple callbacks — add one per environment.
   - **Scopes:** request `user.metrics` **and** `user.activity`. The first
     covers weight / BP / heart-list / sleep / SpO₂ / body comp; the second is
     the steps / energy / distance / floors stream.

   Withings issues a **Client ID** and **Client Secret** — keep the secret out
   of any log; it grants read access to every linked account's full history.

2. **Paste the credentials in Settings.** Withings credentials are
   **per user**: sign in as the target user, open **Settings → Integrations →
   Withings**, and paste the client ID and secret there. They are stored
   AES-256-GCM-encrypted on your user record — there is no server-wide
   `WITHINGS_CLIENT_ID` / `WITHINGS_CLIENT_SECRET` env path. On a shared
   instance, each user brings their own Withings app.

   Two variables do go in `.env`:

   ```env
   WITHINGS_WEBHOOK_SECRET="$(openssl rand -hex 32)"
   # Only when the callback origin differs from NEXT_PUBLIC_APP_URL:
   WITHINGS_REDIRECT_URI="https://your-instance.example.com/api/withings/callback"
   ```

   `WITHINGS_WEBHOOK_SECRET` is the path-segment token the webhook handler
   validates against — a 64-char hex value keeps it indistinguishable from
   random. It is on the compose `environment:` whitelist; the
   `WITHINGS_REDIRECT_URI` override is not, so add that one to the whitelist
   if you set it. Restart the `app` container after saving.

3. **Link from the Settings page.** On **Settings → Integrations**, click
   **Connect Withings**. The flow redirects to Withings, exchanges the
   returned code for an access + refresh token (stored
   AES-256-GCM-encrypted), subscribes the webhook URL, and triggers an
   initial sync of the past 30 days. The page then shows **Connected** with
   the last-sync timestamp. Subsequent syncs run automatically on every
   webhook delivery, plus hourly safety-net cron pulls.

</Steps>

## The webhook URL

When HealthLog subscribes a newly-linked account, it hands Withings a callback:

```
https://your-instance.example.com/api/withings/webhook/<WITHINGS_WEBHOOK_SECRET>
```

Withings cannot add HTTP headers or sign webhook bodies, so the callback URL
itself is the only authenticity surface. The secret lives in a **path segment**
(not a query parameter) so it stays out of the `query_string` column most
reverse proxies log. You do not register this URL in the developer portal —
HealthLog subscribes it per-user during the OAuth callback. See
[Webhooks](/reference/webhooks/) for the verification pattern.

## Source-priority interaction

If you run Withings alongside an Apple Health import, the
[source ladder](/guides/source-priority/) decides what shows. Withings outranks
Apple Health for **point** measurements where the Withings device is the primary
sensor (weight, BP, SpO₂, body fat); Apple Health outranks Withings for
**cumulative** metrics (steps, energy, distance, sleep) because HealthKit folds
multiple sensors into one canonical daily stream. Losing rows stay in the
database as an audit trail. Override per user under **Settings → Sources**.

## Troubleshooting

- **`Withings credentials not configured`** — the signed-in user has no
  client ID / secret saved yet. Paste both under **Settings → Integrations →
  Withings**; credentials are per user, not server env vars.
- **`Callback URI mismatch`** — the redirect URL must exactly match an entry in
  the developer-portal app's callback list, including the `https://` scheme.
  The integration card can warn about a callback origin that differs from the address in the browser;
  [troubleshooting](/self-hosting/troubleshooting/#oauth-callbacks-land-on-localhost-or-the-wrong-host) says when that check works.
- **Webhook stopped firing.** Subscriptions can lapse after a token revoke.
  Disconnect and reconnect from the settings page to re-run `Notify.subscribe()`
  with a fresh URL. Test the inbound path:
  `curl -I https://your-instance.example.com/api/withings/webhook/<secret>` — a
  `200` means the secret matches, a `401` means the running container's secret
  no longer matches the URL Withings holds.
- **"Reauthorisation required".** Withings revokes refresh tokens on password
  change or extended inactivity. Click **Connect Withings** again; the next sync
  catches up the last 30 days.

## Disconnect

The Settings **Disconnect** button unsubscribes the webhook categories at
Withings, removes the connection and its stored tokens locally, and audits the
action; the OAuth grant itself is managed on the Withings side. Existing
measurements tagged `source = WITHINGS` stay in the database — disconnect does
not delete data. Re-linking the same Withings account merges back onto the same
metric timeline: the upsert path matches on `(userId, type, measuredAt,
source)`, so previously-synced rows update in place instead of duplicating.

## Connection test

`POST /api/integrations/withings/test` runs a read-only round-trip against the
signed-in user's stored credentials and returns the latency; the Settings card
exposes it, and it is rate-limited to five calls per minute. A green test plus
a stale `lastSyncedAt` usually means the webhook URL Withings holds is out of
sync — re-subscribe.
