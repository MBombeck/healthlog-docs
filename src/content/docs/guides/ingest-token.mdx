HealthLog pulls from Withings, WHOOP, Fitbit, Oura, Polar and Strava over
OAuth. A local sensor has no such door: a Bluetooth scale, a Garmin bridge or a
Zigbee thermometer lives in your own automation platform and has to push. This
page covers that path, a token you mint yourself and the two endpoints it
reaches.

Nothing here is specific to Home Assistant. Node-RED, a cron job with `curl`,
or anything else that can set a header works the same way.

For documents rather than readings, see
[Import documents from Paperless-ngx or Papra](/guides/import-documents/).

## Mint a token

**Settings → API & Tokens → Measurement tokens.** Name it after the thing you
are pasting it into, because that name is what you will be reading later when
you decide whether to revoke it.

The token is shown **once**. It is stored as an HMAC, so no page can show it to
you again. If you lose it, mint another and revoke the old one.

A token expires after a year unless you pick a shorter lifetime when minting
(1 to 365 days; a year is also the longest allowed). It appears in the token
list on the same page alongside every other credential on the account and is
revoked there.

Minting needs a browser session. `POST /api/tokens/measurements` accepts the
session cookie only, so no API token can mint one of these, not even the
wildcard token a native sign-in holds. The reason is lifetime rather than
reach: the sign-in a phone holds lasts a day, and what it could mint here lasts a year, so a credential that
leaked for an afternoon would leave behind one that outlives cancelling it.
Mints are limited to ten per minute, and if the operator has switched the API
off in the admin panel the mint is refused with `403`. You may hold ten live
tokens at once; the eleventh mint is refused with `409` and the remedy is to
revoke one, not to wait.

## What the token can and cannot do

It can add readings, on your own record, through:

- `POST /api/measurements`: one reading, or an array of up to five
- `POST /api/measurements/batch`: up to 500 entries per call

That is the whole list. It **cannot** read a reading back, change or delete
one, reach the export, or mint another token. The read, edit and delete
endpoints name no scope, so a request from this token is refused with `403`
before the handler runs. That is the point of it being a separate credential
rather than a general one: a container you do not fully trust, a Home
Assistant add-on or a script from a forum, holds something whose worst case is
junk in your own record, not your health history leaving the building.

It also cannot be pointed at somebody else's record. If an account has
[shared their record with you](/guides/shared-access/), a request carrying the
`X-HealthLog-Account` selector is refused with `403` before the sharing grant is
even read, so no future change to what sharing permits can widen what one of
these tokens reaches. Use the web app for that.

## Readings are marked as coming from an external device

Since v1.39.1, rows written with this token carry `source: EXTERNAL`. The
measurements list shows them with an **External device** badge, and the source
filter there can pick them out, so months later you can still tell which
readings came off the scale and which you typed in yourself. Three things
follow from that:

- You can correct them in the app. Readings owned by a connected provider are
  read-only because the number is the provider's; these come from your own
  hardware and stay editable.
- **The payload must not name a source.** The server decides it from the
  token. A body that carries `source` at all, whether `MANUAL`,
  `APPLE_HEALTH` or anything else, is refused with `422`
  (`measurement.create.source_not_permitted` on the single endpoint,
  `measurement.batch.source_not_permitted` on the batch endpoint) rather than
  quietly relabelled. If your automation sends a `source` field, drop it. The
  example below never sent one, so a setup copied from it needs no change.
- They never claim to be from Apple Health. That source is half the
  deduplication key the iOS app writes into, and a bridge borrowing it would
  corrupt the phone's sync rather than merely mislabel a row.

Readings pushed before v1.39.1 keep the label `MANUAL`. Nothing recorded which
of them arrived through a token, so they cannot be sorted out afterwards. If
you push through the batch endpoint, a re-push of entries you had already sent
before the upgrade can land a second copy, because a reading's identity
includes its source. Delete the older one if you see pairs.

`EXTERNAL` is on none of the [source priority](/guides/source-priority/)
ladders. On a day where you both typed a reading in and had the same kind
pushed in, and the metric's ladder ranks manual entries (the default ladders
for weight, blood pressure, steps and blood oxygen do), the typed one counts
wherever the app needs one source per day: the daily totals behind the
charts, the health score, the doctor report, correlations and personal
records. The pushed reading is still stored and still listed. A day with only
pushed readings is unaffected.

A push through this token also does not move the phone's sync checkpoint. That
checkpoint records that your phone delivered what it was holding, and a scale
advancing it could make the phone skip a window of its own samples.

## Home Assistant example

Add a `rest_command` to `configuration.yaml`. Keep the token in
`secrets.yaml`, not here.

```yaml
rest_command:
  healthlog_measurement:
    url: "https://healthlog.example.com/api/measurements"
    method: POST
    headers:
      Authorization: !secret healthlog_token
      Content-Type: "application/json"
    payload: >-
      {
        "type": "{{ type }}",
        "value": {{ value }},
        "measuredAt": "{{ now().isoformat() }}"
      }
```

```yaml
# secrets.yaml
healthlog_token: "Bearer hlk_replace_me"
```

Then call it from an automation. This one forwards a scale whenever it reports
a new weight:

```yaml
automation:
  - alias: "Push weight to HealthLog"
    trigger:
      - platform: state
        entity_id: sensor.bathroom_scale_weight
    condition:
      - condition: template
        value_template: "{{ trigger.to_state.state not in ['unknown', 'unavailable'] }}"
    action:
      - service: rest_command.healthlog_measurement
        data:
          type: WEIGHT
          value: "{{ trigger.to_state.state | float }}"
```

The `condition` is not decoration. Home Assistant sensors publish `unknown` and
`unavailable` as ordinary states, and forwarding one produces a `422` on every
restart.

## Measurement types

`type` is an enum, not free text. Some of the ones a Garmin or scale
integration tends to have:

| What the sensor reports        | `type`                   | Unit expected |
| ------------------------------ | ------------------------ | ------------- |
| Weight                         | `WEIGHT`                 | kg            |
| Body fat                       | `BODY_FAT`               | %             |
| Resting heart rate             | `RESTING_HEART_RATE`     | bpm           |
| Heart-rate variability (SDNN)  | `HEART_RATE_VARIABILITY` | ms            |
| Heart-rate variability (RMSSD) | `HRV_RMSSD`              | ms            |
| Blood oxygen                   | `OXYGEN_SATURATION`      | %             |
| VO₂ max                        | `VO2_MAX`                | ml/kg/min     |
| Respiratory rate               | `RESPIRATORY_RATE`       | breaths/min   |
| Sleep duration                 | `SLEEP_DURATION`         | minutes       |
| Steps                          | `ACTIVITY_STEPS`         | count         |
| Body temperature               | `BODY_TEMPERATURE`       | °C            |

Units are derived server-side from the type, so send the number in the unit
above and do not send a `unit` field. Each type also has a plausibility range
(a respiratory rate of 200 is refused with `422`, for instance). The full enum
is under `MeasurementType` in
[`docs/api/openapi.yaml`](https://github.com/MBombeck/HealthLog/blob/main/docs/api/openapi.yaml).

## Sending several readings at once

A bare array writes up to five readings in one request, which is the shape to
use for blood pressure, since that is two rows:

```bash
curl -X POST https://healthlog.example.com/api/measurements \
  -H "Authorization: Bearer hlk_..." \
  -H "Content-Type: application/json" \
  -d '[
        { "type": "BLOOD_PRESSURE_SYS", "value": 118, "measuredAt": "2026-03-14T07:20:00Z" },
        { "type": "BLOOD_PRESSURE_DIA", "value": 76,  "measuredAt": "2026-03-14T07:20:00Z" }
      ]'
```

For a backfill of hundreds of rows, use `/api/measurements/batch` instead. It
takes up to 500 entries and reports a per-entry status (`inserted`, `updated`,
`duplicate`, `skipped` or `failed`), so a partial failure tells you which rows
to retry. A batch of more than 500 entries is refused whole with `422`
(`measurement.batch.too_large`), and nothing from it is written.

## Sleep stages

Since v1.39.1 a bridge can send each stage of a night by name, to the same
`/api/measurements` address as every other reading. Send one request per
stage, with the stage and its start and end:

```bash
curl -X POST https://healthlog.example.com/api/measurements \
  -H "Authorization: Bearer hlk_..." \
  -H "Content-Type: application/json" \
  -d '{ "type": "SLEEP_DURATION", "sleepStage": "DEEP",
        "startDate": "2026-03-15T00:10:00Z", "endDate": "2026-03-15T00:55:00Z" }'
```

| `sleepStage` | Stage                   |
| ------------ | ----------------------- |
| `IN_BED`     | In bed                  |
| `ASLEEP`     | Asleep, stage not known |
| `AWAKE`      | Awake                   |
| `CORE`       | Core (light) sleep      |
| `DEEP`       | Deep sleep              |
| `REM`        | REM sleep               |

If your automation knows when a stage ended and how long it lasted rather than
when it started, send `measuredAt` (the end) and `value` (the length in
minutes) instead of `startDate` and `endDate`. The stored entry is the same:
a `SLEEP_DURATION` reading in minutes, dated at the end of the stage, exactly
as the iPhone app's stages are stored. Sent with this token it carries the
source `EXTERNAL`, like every other reading from it.

You do not need an id. HealthLog recognises a stage by its name, start and
end, so sending the same stage again answers `200` with `"status": "duplicate"`
and keeps one entry, and sending it again with a corrected start answers
`"status": "updated"` and replaces it. A new stage answers `201` with
`"status": "inserted"`. If your source has its own record ids, you can add one
as `externalId`; keep it the same for the same stage.

A stage that lasts more than 24 hours, ends before it starts, or ends in the
future is refused with `422` and a list of what was wrong. So is a `value`
sent together with `startDate` and `endDate` that does not match them.

### Several stages in one request

To send a whole night in one call, use `/api/measurements/batch`, one entry
per stage interval. The batch endpoint speaks the same format the iPhone app sends: every entry names the sleep
category `HKCategoryTypeIdentifierSleepAnalysis`, carries the interval's length
in minutes as its value, and says which stage it was with a number in
`sleepStage`:

| `sleepStage` | Stage                            |
| ------------ | -------------------------------- |
| `0`          | In bed                           |
| `1`          | Asleep, stage not known          |
| `2`          | Awake                            |
| `3`          | Core (light) sleep               |
| `4`          | Deep sleep                       |
| `5`          | REM sleep                        |

```bash
curl -X POST https://healthlog.example.com/api/measurements/batch \
  -H "Authorization: Bearer hlk_..." \
  -H "Content-Type: application/json" \
  -d '{ "entries": [
        { "hkIdentifier": "HKCategoryTypeIdentifierSleepAnalysis", "sleepStage": 3,
          "value": 60, "unit": "min",
          "startDate": "2026-03-14T23:10:00Z", "endDate": "2026-03-15T00:10:00Z",
          "externalId": "hc-sleep-3f2a-2026-03-14T23:10:00Z" },
        { "hkIdentifier": "HKCategoryTypeIdentifierSleepAnalysis", "sleepStage": 4,
          "value": 45, "unit": "min",
          "startDate": "2026-03-15T00:10:00Z", "endDate": "2026-03-15T00:55:00Z",
          "externalId": "hc-sleep-3f2a-2026-03-15T00:10:00Z" }
      ] }'
```

`externalId` has to stay the same when you send the same interval again, so
build it from the source record's id and the interval's start rather than from
anything that changes between runs. A repeated interval then comes back as
`duplicate` instead of a second row. The Sleep page puts the stages together
into nights, and when you have more than one sleep source it shows one of them
per night, following the order under [Settings, Source priority](/guides/source-priority/).

Android's Health Connect numbers its stages differently. If you forward sleep
sessions from Health Connect (with Tasker or a similar automation), translate
them like this:

| Health Connect stage            | By name  | Batch number |
| ------------------------------- | -------- | ------------ |
| `STAGE_TYPE_AWAKE` (1)          | `AWAKE`  | `2`          |
| `STAGE_TYPE_AWAKE_IN_BED` (7)   | `AWAKE`  | `2`          |
| `STAGE_TYPE_SLEEPING` (2)       | `ASLEEP` | `1`          |
| `STAGE_TYPE_SLEEPING_LIGHT` (4) | `CORE`   | `3`          |
| `STAGE_TYPE_SLEEPING_DEEP` (5)  | `DEEP`   | `4`          |
| `STAGE_TYPE_SLEEPING_REM` (6)   | `REM`    | `5`          |
| `STAGE_TYPE_UNKNOWN` (0)        | `ASLEEP` | `1`          |

Leave out `STAGE_TYPE_AWAKE_OUT_OF_BED` (3): time out of bed is not part of the
night. A session without any stages can go in as a single `ASLEEP` stage (or a
batch entry with `sleepStage` `1`) covering the whole session.

## Retries and duplicates

Both endpoints honour an `Idempotency-Key` header. Send a value your automation
can reproduce for the same reading, and a retry with the same key returns the
original response instead of writing a second row:

```yaml
headers:
  Authorization: !secret healthlog_token
  Content-Type: "application/json"
  Idempotency-Key: "{{ type }}-{{ now().strftime('%Y-%m-%dT%H') }}"
```

Independently of that, a reading on `/api/measurements` with the same type,
timestamp and source as an existing row is refused with `409`
(`measurement.duplicate_timestamp`), so a duplicate push is a visible error
rather than a duplicated data point. A sleep stage sent by name is the
exception: a repeat answers `200` with `"status": "duplicate"`. The batch
endpoint reports such an entry as `duplicate` instead of failing the call;
`skipped` means the entry did not pass validation. Since v1.39.1 an entry
skipped as `value_out_of_range` also carries `convertedValue` (the value after
conversion into the stored unit) and `range` (`min`, `max` and `unit`), so a
body-fat percentage sent as a fraction is easy to spot.

## When it stops working

| Response | What it means                                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `401`    | The token is wrong, revoked, or expired. Mint a new one.                                                                                                       |
| `403`    | The endpoint is outside the token's scope (check you are calling one of the two above and not a read), or the request named another account's record.       |
| `409`    | A reading with this type, timestamp and source already exists (single endpoint only).                                                                          |
| `422`    | The payload is wrong: an unknown `type` or `sleepStage`, a non-numeric or implausible `value`, an `unavailable` sensor state, a body or entry naming any `source`, or a batch over 500. On the batch endpoint `meta.errorCode` says which: `measurement.batch.invalid`, `measurement.batch.source_not_permitted` or `measurement.batch.too_large`. None of these is worth retrying unchanged. |
| `429`    | Too many requests. The batch route allows 60 calls per minute per account; the single route shares a 300-a-minute bucket with the other one-row writes and says so with `meta.errorCode: record_write.rate_limited`. The response carries `Retry-After` in whole seconds plus `X-RateLimit-Limit`, `-Remaining` and `-Reset`; wait out `Retry-After` rather than retrying on a timer of your own. |

The response envelope is `{ "data": ..., "error": null }` on success and
`{ "data": null, "error": "<message>", "meta": { "errorCode": "..." } }` on
failure, so logging `error` from the body will usually say exactly what was
wrong. The conventions are on the [API overview](/reference/api-overview/).
