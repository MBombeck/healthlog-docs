HealthLog's Coach, daily briefing, weekly report, and per-metric insights run
through a multi-provider AI client. Pick whichever provider you prefer — there is
no lock-in. The provider is resolved per user via a fallback chain, so a user
with a Claude key and an Ollama endpoint can fall back from one to the other
automatically. For what each provider sees, read
[Privacy architecture](/explanation/privacy-architecture/).

None of this is required. With no provider set up, AI switched off, or consent
not given, readings, charts, scores, correlations, ECG recordings and the
Insights page all load as usual; the parts a model would write are simply not
there. See [When AI is not available](#when-ai-is-not-available).

## Provider matrix

| Provider | Key acquisition | Default model | Endpoint | Privacy stance |
| --- | --- | --- | --- | --- |
| OpenAI | [platform.openai.com/api-keys](https://platform.openai.com/api-keys) | `gpt-4o` | `api.openai.com/v1` | Context sent to OpenAI |
| Anthropic | [console.anthropic.com](https://console.anthropic.com/settings/keys) | `claude-sonnet-4-6` | Anthropic default | Context sent to Anthropic |
| Local | none (your endpoint) | your model | OpenAI-compatible URL you control | Stays on your network |
| ChatGPT OAuth | sign in with your ChatGPT account | Codex-routed | Codex-routed | Via your ChatGPT subscription |
| OpenAI-compatible gateway | the credential your gateway issues, if it wants one | your model | the gateway URL you configure | Context sent to your gateway |

The model is overridable per provider in `/settings/ai` — e.g. a lighter
`gpt-4o-mini` trades some reasoning headroom for a lower per-token cost. Cost
expectation for BYOK: a daily briefing runs at roughly 4–8k input tokens +
~1k output, so even a heavy user generating multiple Coach turns plus a
weekly report typically spends a few dollars per month on a full-size hosted
model.

Reading a lab-report photo or a document image needs a vision-capable model.
On OpenAI that is `gpt-5*`, `gpt-4o*`, `gpt-4.1*`, `gpt-4-turbo*` and the full
`o1` / `o3` / `o4` reasoning models (their `-mini` and `-preview` variants take
no image input); on Anthropic, the Claude 3, 3.5, 3.7 and 4 families. Since
v1.38.1 a report the provider could not process is answered with `502` and a
message saying the configured provider could not process it, instead of a hint
to retake the photo, and the upstream status and model land in the request's
wide event so the operator can see which step failed.

## BYOK vs admin-shared

Two key-provisioning modes coexist:

- **BYOK (bring your own key)** — each user pastes a personal API key into
  `/settings/ai`. It is AES-256-GCM-encrypted at rest and only decrypted
  in-process. Cost falls to the user.
- **Admin-shared** — the admin panel accepts a single OpenAI key. Users without
  their own key fall back to it. It is the last entry in the chain, so it acts
  as a safety net rather than the default route. The operator can additionally
  share a subscription-based account — see
  [Operator-shared subscription access](#operator-shared-subscription-access).

## The fallback chain

`User.aiProviderChain` is a priority-ordered list, tried top to bottom. The
default:

1. **ChatGPT OAuth** (covered by a ChatGPT subscription; no per-token cost)
2. **OpenAI** (the user's own key)
3. **Anthropic** (the user's own key)
4. **Local** (self-hosted Ollama / LM Studio / vLLM)
5. **admin-shared OpenAI** (last-ditch)

Entries the user has no credential for are silently skipped. The first to return
a non-error completion wins; a 422 fires only when every entry errored. Edit the
order — or disable an entry without removing it — in `/settings/ai`.

## Local endpoints

Any OpenAI-compatible local endpoint plugs in as the **Local** provider. Data
stays on your network end to end.

- **Ollama** — `ollama pull qwen2.5:14b-instruct && ollama serve`, base URL
  `http://localhost:11434/v1`. If HealthLog runs in Docker and Ollama on the
  host, swap `localhost` for `host.docker.internal` (Mac/Windows) or the LAN IP
  (Linux).
- **LM Studio** — start the Local Server (usually `http://localhost:1234/v1`).
- **vLLM** — `vllm serve ... --api-key your-shared-secret`, base URL
  `http://<host>:8000/v1`.

:::caution[SSRF guard for local endpoints]
Local endpoints route through the same outbound-URL validation as every other
fetch. The guard rejects private-IP targets by default. To allow a private
destination, set `ALLOW_LOCAL_AI_PRIVATE_HOSTS` in the container environment —
preferably to a comma-separated host allowlist (`ollama.lan, 10.0.0.5`), which
permits exactly those hosts. The legacy value `true` opens **every** private
host and remains accepted. Leave it unset on internet-facing instances unless
you specifically run an internal endpoint.
:::

Rough model sizing: 7-8B for an 8 GB GPU / Apple Silicon base, 14-24B for
16-24 GB (the BYOK sweet spot), 70B+ for 48 GB+.

## OpenAI-compatible gateways

The **Local** provider speaks the plain OpenAI chat-completions dialect, so it
also covers gateways and routers, not just single-model servers: LiteLLM,
OpenRouter, vLLM, LM Studio, or any proxy that exposes an OpenAI-compatible
`/v1` endpoint. A gateway also has its own provider entry, **OpenAI-compatible
gateway**, with its own base URL, model and optional key, held in three
dedicated columns so neither the OpenAI base URL nor the OpenAI key can leak
into it; the OpenAI provider deliberately pins `api.openai.com`, so an OpenAI
API key is never forwarded to a custom host. Point the base URL at the gateway (it ends with `/v1` — e.g.
`https://openrouter.ai/api/v1`), pick the model name the gateway routes, and
set the API key field if the gateway expects one — the Bearer header is
optional and simply omitted when no key is configured.

Structured generations send `response_format: { type: "json_object" }` by
default. Since v1.28.28 the flag falls back **per endpoint**: a gateway that
rejects the parameter with a 400 flips that base URL to a no-flag dialect and
the request is retried, so strict gateways work without configuration.
Hosted gateways on public hosts need no `ALLOW_LOCAL_AI_PRIVATE_HOSTS` entry;
a gateway on your LAN does.

The **admin** server-key path has a separate guard: an admin-set custom base
URL must additionally be allowed via `ADMIN_AI_BASE_URL_ALLOWLIST` in the
container environment. The user-level Local provider does not read that
variable — it is governed by the SSRF guard above.

## ChatGPT OAuth (Codex)

Routes generations via the `chatgpt.com/backend-api/codex/responses` endpoint the
official Codex CLI uses — no API key, no per-token billing on top of the ChatGPT
subscription. In `/settings/ai`, set provider to **ChatGPT OAuth**, click
**Connect ChatGPT**, and complete the device-code flow (open the shown URL,
enter the short code). Tokens land AES-256-GCM-encrypted; refresh runs
automatically. The wire protocol is documented in the repo's
`docs/codex-protocol-spec.md`.

## Operator-shared subscription access

Besides the shared API key, the operator can connect a single
subscription-based AI account for the whole instance and let users opt into
it:

- **Admin side.** Under **Admin → AI** the operator runs the same device-code
  OAuth flow as the per-user ChatGPT connection. The tokens are stored
  AES-256-GCM-encrypted in the instance settings and are never returned by
  any endpoint; the admin routes sit behind the cookie-only admin boundary.
- **User side.** Each user opts in individually in `/settings/ai` — the
  opt-in is off by default.
- **Chain semantics.** The shared connection is never part of a user's
  persisted chain and never appears in the chain editor. It is appended
  **last** to the resolved chain, only when the user opted in and the
  operator has connected the account, so a user's own providers always
  resolve first.
- **Cost.** Generations through it run under the operator's account — usage
  and rate limits land on the operator, not the user.

The settings UI states this plainly: the shared access is a single signed-in
AI account the operator connected for everyone on the server, not the user's
own key. Users who want their data to reach only a provider under their own
contract should configure a personal provider instead.

## Caching and budget

Two caches sit in front of every provider call so budgets stay predictable:

1. **24-hour insight cache** keyed by the measurement snapshot hash and prompt
   version. A read within 24 hours returns the cached envelope instead of
   re-billing. Force-regen bypasses it.
2. **Snapshot LRU** caches per `(userId, scope)` for 60 seconds so a rapid-fire
   conversation reuses upstream context.

`INSIGHTS_RATE_LIMIT_PER_HOUR` (default 10) bounds `POST /api/insights/generate`
per user per hour. `INSIGHTS_MAX_TOKENS` (default 2500, clamped to 500–8000)
sets the completion-token budget per generation — raise it when a verbose
local model truncates its JSON mid-answer.

## Automatic document reading (opt-in)

The [document vault](/guides/document-vault/) is local-first by default: an
uploaded document is only read by an external AI provider when you tap a
per-document AI action, and text-layer PDFs are indexed for search locally
with no egress. AI settings carry a per-user **"Read documents automatically
with AI"** switch, **off by default**, that reads, describes, and indexes
each upload through your configured provider with no per-document
confirmation. Turning it on is standing consent for reading documents and is
recorded in the consent audit trail; a subscription connection applies its own
consumer data settings, so privacy-sensitive deployments should keep the
switch off, or pair it with a no-training BYOK key or a local model. See the
[vault guide](/guides/document-vault/#reading-documents-with-ai--automatic-search)
for how the readers are chosen.

Since v1.30.32, switching it on also catches up on documents already in your
vault instead of only applying to new uploads. The catch-up re-asserts the
consent and the daily budget per document; it grants nothing extra.

Since v1.39.0 that consent covers document reading, lab report scans and
turning typed medication text into a schedule, and nothing else. Before, the
switch recorded full AI consent, which also opened the Coach and AI analysis
without saying so. If you turned it on in an earlier version, that earlier
consent stays until you withdraw it. The other way round, your consent for the
Coach or AI analysis no longer counts for documents: the first time a document
or a lab scan would go to an AI service outside your server, you are asked
once. A self-hosted local model on your own server needs no consent for
documents. If you withdraw the document consent, reading stops at once, even
while the switch is still on.

The operator can stop all of this for the server with the **Reading documents**
switch under Admin, Coach. With it off, or with the master switch off, asking
for a summary, a lab scan or a schedule from medication text is refused with a
message that AI is off on this server, and nothing is sent. Settings, AI says
the same next to the automatic reading switch: "Reading documents with AI is
switched off on this server."

## Withdrawing AI consent

AI settings show the standing consent decision in plain words and carry the
control that changes it. Withdrawing takes effect immediately: without an active
consent, every AI feature that needs it stops on the next call.

Since v1.39.0, withdrawing also deletes the notes the app can write again once
no consent for AI analysis is left: the per-metric status notes, the daily
briefing, model-written period summaries, the lines written after a new reading,
and workout notes. Your Coach conversations, what the Coach remembers, and the
summaries of your documents are your records and stay; you can read and delete
them yourself. Nothing you recorded is deleted by a withdrawal; that is the
export and erase path under **Data & Privacy**.

Two things changed in v1.30.32 that are worth knowing if you used an earlier
release:

- **A withdrawn consent stays withdrawn.** Opening the AI settings used to grant
  consent again if you had taken it back, and recorded it as though you had done
  it yourself. A withdrawal is now a standing decision that only an explicit act
  lifts.
- **The web can withdraw at all.** The revoke endpoint has existed since
  v1.4.40, but only the native client ever called it; on the web, consent could
  be given and never taken back. Withdrawal now sits on the same surface as the
  grant.

## Connection test

`POST /api/ai/test` runs a one-shot probe against the resolved provider and
returns latency plus the model it routed to. The Settings UI surfaces a **Test
connection** button per provider; a failed probe returns a localisable
`errorCode`.

With the operator's master switch off, the test does not call the model and
answers with `assistant.disabled.enabled` instead.

## When AI is not available

Since v1.39.0 the server decides in one place whether each AI feature can run
for you, and tells the app why when it cannot. The possible reasons, from the
outside in:

1. The operator switched it off for the server, with the master switch or the
   feature's own switch under Admin, Coach.
2. Someone gave you access to their record, and the access does not allow
   AI work on it.
3. The feature's module is off: the Coach module for the Coach, **AI
   analysis** for the briefing and notes, Documents for document reading, Labs
   for lab scans.
4. You opted out: you hid the Coach, or switched **AI analysis** off under
   Settings, Modules.
5. No provider is set up that can do the job.
6. Your consent for it is missing.

Your data never depends on the answer. Readings, charts, scores and statistics
load whatever the AI settings say. What changes is that nothing new is written
by a model, and text a model wrote earlier is not shown while the feature is
unavailable. Turn it back on and the stored text returns. Only a consent
withdrawal deletes anything, as described above.

**AI analysis** is the module that covers text a model writes for you: the daily
briefing, status notes, workout notes and the line after a new reading. It used
to be called Insights. Switching it off keeps the Insights page, your scores and
your data; the morning briefing notification still arrives, with your health
score or the day's reminders instead of the written first sentence.

Hiding the Coach hides the Coach and nothing else. Until v1.39.0 it also stopped
the nightly briefing and status notes. The upgrade switched AI analysis off for
everyone who had the Coach hidden, so nothing changed for them; switch it back
on under Settings, Modules if you want the notes.

Someone you gave access to your record sees the briefing, notes and summaries
you would see, but opening your record never starts AI work on it.

## Troubleshooting

- **"No AI provider configured."** Set up at least one BYOK provider in
  `/settings/ai`, or configure an admin-shared key in the admin panel.
- **Local endpoint rejected as "internal/private host".** Set
  `ALLOW_LOCAL_AI_PRIVATE_HOSTS` to the endpoint's exact hostname
  (comma-separate several) in the container environment. Prefer the host list
  over the legacy `true`; leave it unset on internet-facing instances.
- **ChatGPT OAuth disconnects after a few weeks of inactivity.** ChatGPT
  refresh tokens lapse after extended idle periods. Reconnect via **Connect
  ChatGPT** — the device-code flow re-runs and the new tokens land in the same
  encrypted columns.
- **A shared provider is failing for everyone.** Since v1.37.31 the admin AI
  section shows a provider-health card: one row per provider type with how many
  users' chains have recorded an outcome for it, how many are currently
  failing, the longest uninterrupted failure run, and the last success and
  failure times. Operator-managed providers sort first, since their failure
  takes the shared fallback down for everyone relying on it. The card reports
  counts and timestamps, never which user a row belongs to.
- **Chain falls through every entry.** Run the per-provider connection test
  from `/settings/ai` to identify the failing step. The most common cause is a
  stale or revoked BYOK key earlier in the chain; remove or disable that entry
  to skip ahead.
