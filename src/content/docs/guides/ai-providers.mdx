HealthLog's Coach, daily briefing, weekly report, and per-metric insights run
through a multi-provider AI client. Pick whichever provider you prefer — there is
no lock-in. The provider is resolved per user via a fallback chain, so a user
with a Claude key and an Ollama endpoint can fall back from one to the other
automatically. For what each provider sees, read
[Privacy architecture](/explanation/privacy-architecture/).

None of this is required. With no provider set up, AI switched off, or consent
not given, readings, charts, scores, correlations, ECG recordings and the
Insights page all load as usual; the parts a model would write are simply not
there. See [When AI is not available](#when-ai-is-not-available).

## Provider matrix

| Provider | Key acquisition | Default model | Endpoint | Privacy stance |
| --- | --- | --- | --- | --- |
| OpenAI | [platform.openai.com/api-keys](https://platform.openai.com/api-keys) | `gpt-4o` | `api.openai.com/v1` | Context sent to OpenAI |
| Anthropic | [console.anthropic.com](https://console.anthropic.com/settings/keys) | `claude-sonnet-4-6` | Anthropic default | Context sent to Anthropic |
| Local | none (your endpoint) | your model | OpenAI-compatible URL you control | Stays on your network |
| ChatGPT OAuth | sign in with your ChatGPT account | `gpt-5.6-terra`, then a built-in fallback list | `chatgpt.com` Codex backend | Via your ChatGPT subscription |
| OpenAI-compatible gateway | the credential your gateway issues, if it wants one | your model | the gateway URL you configure | Context sent to your gateway |

The model is overridable per provider in `/settings/ai` — e.g. a lighter
`gpt-4o-mini` trades some reasoning headroom for a lower per-token cost. Cost
expectation for BYOK: a daily briefing runs at roughly 4–8k input tokens +
~1k output, so even a heavy user generating multiple Coach turns plus a
weekly report typically spends a few dollars per month on a full-size hosted
model.

Reading a lab-report photo or a document image needs a vision-capable model.
On OpenAI and ChatGPT that is every GPT from 5 on (the gpt-6 line included),
`gpt-4o`, `gpt-4.1`, `gpt-4-turbo` and the full `o1` / `o3` / `o4` models; their
`-mini` and `-preview` variants take no images. On Anthropic it is the Claude 3
family and every Claude from 4 on. A Local or gateway model is assumed to read
images; one that cannot fails with a message saying the provider could not
process the file.

## BYOK vs admin-shared

Two key-provisioning modes coexist:

- **BYOK (bring your own key)** — each user pastes a personal API key into
  `/settings/ai`. It is AES-256-GCM-encrypted at rest and only decrypted
  in-process. Cost falls to the user.
- **Admin-shared** — the operator sets one server key under **Admin → Coach**.
  It drives OpenAI by default (`gpt-4o`), or Anthropic when its base URL is
  Anthropic's (`claude-sonnet-4-6`). Users without their own key fall back to
  it. It is the last entry in the chain, so it acts as a safety net rather
  than the default route. The operator can additionally
  share a subscription-based account — see
  [Operator-shared subscription access](#operator-shared-subscription-access).

## The fallback chain

Each account has a priority-ordered list of providers, tried top to bottom.
The default:

1. **ChatGPT OAuth** (covered by a ChatGPT subscription; no per-token cost)
2. **OpenAI** (the user's own key)
3. **Anthropic** (the user's own key)
4. **Local** (self-hosted Ollama / LM Studio / vLLM)
5. **the server key** (last-ditch)

Entries the user has no credential for are silently skipped. The first to return
a non-error completion wins; a 422 fires only when every entry errored. Edit the
order — or disable an entry without removing it — in `/settings/ai`.

## Local endpoints

Any OpenAI-compatible local endpoint plugs in as the **Local** provider. Data
stays on your network end to end.

- **Ollama**: base URL `http://<host>:11434/v1`.
- **LM Studio**: start the Local Server (usually port `1234`), base URL
  `http://<host>:1234/v1`.
- **vLLM**: `vllm serve ... --api-key your-shared-secret`, base URL
  `http://<host>:8000/v1`.

:::caution[SSRF guard for local endpoints]
Any user of the instance can type a base URL, so a base URL on a private
address is refused unless the operator has listed it. List the endpoint's exact
origin in `AI_PRIVATE_ORIGINS` in the container environment, comma-separated:
`AI_PRIVATE_ORIGINS="http://ollama.lan:11434,http://10.0.0.5:4000"`. An origin
is `scheme://host[:port]` and nothing else, never a wildcard or a range. A
listed endpoint is called over a pinned connection that does not follow
redirects, and the cloud metadata address, link-local addresses and the
unspecified address stay unreachable even when listed.

The older `ALLOW_LOCAL_AI_PRIVATE_HOSTS` still works as a host list
(`ollama.lan, 10.0.0.5`), which grants those hosts on any port. Its `true`
form is deprecated: it covers only the server key and AI settings saved on an
admin account. While it is set, the admin AI settings page shows the exact
`AI_PRIVATE_ORIGINS` line to use instead.
:::

### Example: Ollama on the same host as Docker

HealthLog runs in the compose stack and Ollama runs on the host itself. Inside
the container, `localhost` is the container, not the host.

1. Make Ollama listen beyond loopback (`OLLAMA_HOST=0.0.0.0` in its service
   environment), then pull a model, for example `ollama pull qwen2.5:14b-instruct`.
2. Pick the address the container reaches the host on. On Docker Desktop (Mac,
   Windows) that is `host.docker.internal`. On Linux the bundled compose file
   does not map that name, so use the host's LAN IP, for example
   `192.168.1.20`. (Adding `extra_hosts: ["host.docker.internal:host-gateway"]`
   to the `app` service in a `docker-compose.override.yml` makes the name work
   on Linux too.)
3. Allow that origin in `.env` and recreate the app container
   (`docker compose up -d`):

   ```env
   AI_PRIVATE_ORIGINS="http://192.168.1.20:11434"
   ```

   With `host.docker.internal`, list `http://host.docker.internal:11434`
   instead; that name resolves to a private address too.
4. Under **Settings → AI provider**, choose **Local**, set the base URL to
   `http://192.168.1.20:11434/v1` (or `http://host.docker.internal:11434/v1`),
   the model name exactly as `ollama list` shows it, and leave the key empty.
5. For a thinking model, set **Reasoning** to **Off** so the answer budget goes
   to the answer. If the model is slow to load, raise the
   [response timeout](#response-timeout). If a verbose model cuts its JSON off
   mid-answer, raise `INSIGHTS_MAX_TOKENS` (default 2500, up to 8000).
6. Press **Test connection**.

Rough model sizing: 7-8B for an 8 GB GPU / Apple Silicon base, 14-24B for
16-24 GB (the BYOK sweet spot), 70B+ for 48 GB+.

### Response timeout

**Settings → AI provider → Response timeout** sets how long each AI call waits
for an answer, 10 to 600 seconds. Left empty, a call waits 60 seconds; the
daily briefing and the Coach wait 180. The setting applies to every AI job:
each call of the daily briefing, status cards, document and lab reading,
medication extraction, the Coach and background jobs. Only the line under a
new reading and Coach nudges keep their own short limit, because each has a
plain text to fall back on. A reverse proxy in front can still end a long
request earlier; see [Reverse proxy](/guides/reverse-proxy/).

Reasoning models served this way can think before they answer; see
[Reasoning](#reasoning).

## OpenAI-compatible gateways

The **Local** provider speaks the plain OpenAI chat-completions dialect, so it
also covers gateways and routers, not just single-model servers: LiteLLM,
OpenRouter, vLLM, LM Studio, or any proxy that exposes an OpenAI-compatible
`/v1` endpoint. A gateway also has its own provider entry, **OpenAI-compatible
gateway**, with its own base URL, model and optional key, kept apart from the
OpenAI entry; the OpenAI provider pins `api.openai.com`, so an OpenAI API key
is never forwarded to a custom host. Point the base URL at the gateway (it ends with `/v1` — e.g.
`https://openrouter.ai/api/v1`), pick the model name the gateway routes, and
set the API key field if the gateway expects one — the Bearer header is
optional and simply omitted when no key is configured.

Structured generations send `response_format: { type: "json_object" }` by
default. A gateway that rejects the parameter with a 400 is remembered per
base URL and asked without it, so strict gateways work without configuration.
Hosted gateways on public hosts need no entry; a gateway on your LAN needs its
origin in `AI_PRIVATE_ORIGINS`.

The **admin** server-key path has a separate guard: an admin-set custom base
URL must additionally be allowed via `ADMIN_AI_BASE_URL_ALLOWLIST` in the
container environment. The user-level Local provider does not read that
variable — it is governed by the SSRF guard above.

## ChatGPT OAuth (Codex)

Routes generations via the `chatgpt.com/backend-api/codex/responses` endpoint the
official Codex CLI uses — no API key, no per-token billing on top of the ChatGPT
subscription. In `/settings/ai`, set provider to **ChatGPT OAuth**, click
**Connect ChatGPT**, and complete the device-code flow (open the shown URL,
enter the short code). Tokens land AES-256-GCM-encrypted; refresh runs
automatically. The wire protocol is documented in the repo's
`docs/codex-protocol-spec.md`.

The ChatGPT backend accepts only some model names, and it changes them without
notice. HealthLog tries a built-in list in order, starting at `gpt-5.6-terra`,
then the gpt-6 models, and remembers the first one that answers. An operator
can steer this in the container environment: `CODEX_MODEL` puts one model
ahead of the list, and `CODEX_MODEL_FALLBACK_CHAIN` (comma-separated) replaces
the list. Use them when every model is rejected after the backend changed
again. An override set only to get past the models rejected in October 2026
can be removed; the built-in list covers that.

## Operator-shared subscription access

Besides the shared API key, the operator can connect a single
subscription-based AI account for the whole instance and let users opt into
it:

- **Admin side.** Under **Admin → Coach** the operator runs the same device-code
  OAuth flow as the per-user ChatGPT connection. The tokens are stored
  AES-256-GCM-encrypted in the instance settings and are never returned by
  any endpoint; the admin routes sit behind the cookie-only admin boundary.
- **User side.** Each user opts in individually in `/settings/ai` — the
  opt-in is off by default.
- **Chain semantics.** The shared connection is never part of a user's
  persisted chain and never appears in the chain editor. It is appended
  **last** to the resolved chain, only when the user opted in and the
  operator has connected the account, so a user's own providers always
  resolve first.
- **Cost.** Generations through it run under the operator's account — usage
  and rate limits land on the operator, not the user.

The settings UI states this plainly: the shared access is a single signed-in
AI account the operator connected for everyone on the server, not the user's
own key. Users who want their data to reach only a provider under their own
contract should configure a personal provider instead.

## Reasoning

HealthLog asks a model to think before it answers wherever that helps: in the Coach, at the depth each person picks under **Thinking depth**
(see [Coach conversations](/guides/coach-conversations/#thinking-depth)), and
in a few background jobs, namely the daily briefing (scheduled and on request),
the weekly and monthly summaries and the upkeep of the Coach's memory. Status
notes, workout notes, reaction lines, nudges and document reading never ask
for it, so they stay fast and cheap.

Every provider gets the request in its own documented form:

| Provider | How it is asked | What the Coach shows |
| --- | --- | --- |
| ChatGPT OAuth (Codex) | A reasoning effort, with summaries. **Off** really switches thinking off | Reasoning summaries while the model thinks |
| OpenAI (your key) | `reasoning_effort` for GPT-5 and the o-series; models such as `gpt-4o` do not reason. Sent only on rounds without tool calls, since this interface cannot carry the reasoning between rounds. **Off** is real from GPT-5.1 on; older reasoning models get their lowest effort | No summaries |
| Anthropic | Adaptive thinking with an effort from Claude 4.6 on, a thinking budget for 3.7 to 4.5; 3.5 and older do not think. From generation 5 the model always thinks a little, so **Off** becomes the lowest effort | Reasoning summaries once a round is done |
| OpenRouter | `reasoning` with an effort; the reasoning details go back unchanged between tool rounds | Reasoning text once a round is done |
| Other OpenAI-compatible gateways and local servers | `reasoning_effort`; the reply's `reasoning_content` or `reasoning` field, or a leading `<think>` block, is read as reasoning | Reasoning text, live from a local server |

Providers that take a budget rather than a named effort get 1,024 thinking
tokens for **Low**, 4,096 for **Medium** and 12,000 for **High**, on top of the
answer.

Some providers hand back a signed or encrypted form of their reasoning that
has to travel with the next round of the same answer. HealthLog passes it on
within that answer and never stores it. The readable summary the Coach shows is
checked like an answer and stored encrypted.

### When a model refuses

No model list has to be kept up to date. A model name HealthLog does not
recognise gets the request as if it could reason. If the endpoint answers with
a 400 that names one of the reasoning parameters, the request is sent again
without it and the answer arrives as usual. The server remembers that for an
hour, per provider, endpoint and model, so the next request goes out without
the parameter straight away, and after the hour it tries again in case the
endpoint learned it. Only such a 400 teaches anything: an authentication
error, a rate limit or a server error never does, and neither does an error
about the reasoning handed back between rounds.

### The Reasoning setting on Local and gateway providers

The **Local** and **OpenAI-compatible gateway** settings have a **Reasoning**
choice: **Default**, **Off**, **Low**, **Medium** or **High**. **Off** leaves
the whole answer budget for the answer itself, which helps a thinking model
that spends a minute deliberating over a short summary. **Default** sends
nothing; the other choices send `reasoning_effort` (`none` for Off). The
setting is stored per provider in the fallback chain and applies to everything
that provider does except the Coach, which uses the person's **Thinking
depth**. OpenAI, Anthropic and Codex pin their own models and parameters, so
the setting is not offered for them.

A reply that holds reasoning and no answer is asked once more without
reasoning. If that does not help either, the model is not asked that way again
for an hour. One AI call makes at most two requests.

### What the operator controls

Under Admin, Coach, on the Assistant card, **Allow deeper thinking**
switches reasoning off for the whole server and **Highest thinking depth** caps
it. When the operator pays for the model (the shared key or the shared ChatGPT
connection), the Coach thinks at **Medium** at most and the background jobs at
**Low**. See [Admin overview](/guides/admin-overview/#thinking).

## Caching and budget

Two caches sit in front of every provider call so budgets stay predictable:

1. **24-hour insight cache** keyed by the measurement snapshot hash and prompt
   version. A read within 24 hours returns the cached envelope instead of
   re-billing. Force-regen bypasses it.
2. **Snapshot LRU** caches per `(userId, scope)` for 60 seconds so a rapid-fire
   conversation reuses upstream context.

`INSIGHTS_RATE_LIMIT_PER_HOUR` (default 10) bounds `POST /api/insights/generate`
per user per hour. `INSIGHTS_MAX_TOKENS` (default 2500, clamped to 500–8000)
sets the completion-token budget per generation — raise it when a verbose
local model truncates its JSON mid-answer.

Each account also has a daily AI budget that the Coach, the briefing, the
summaries and document reads draw on. It resets at midnight in the account's
own time zone. Tokens spent on replies without an answer count toward it.

## AI usage levels

Every account runs at one of three AI usage levels, chosen
under **Settings, AI provider, AI usage**. A level decides how much model work
runs in the background for you. It never decides what is stored or shown, and
the Coach is the same at every level.

| | Frugal | Standard | Full |
| --- | --- | --- | --- |
| Status cards after a sync | at most once a day | the instance gap, 6 hours by default | hourly |
| Status cards after a hand entry | every 6 hours | hourly | hourly |
| Data snapshot in a prompt | 10,000 characters | 14,000 | 14,000 |
| Background reasoning | off | the job's default | the job's default |
| Daily briefing | short: the lead, today, one recommendation | full | full |
| Automatic document reading | on request only | your own switch | your own switch |
| Reading a supplement label photo | not offered | offered | offered |

A watch or an integration delivers readings all day, and each delivery
changes the day's figures. Without a gap every touched card was written again
about once an hour; **Full** keeps that behaviour. A reading you enter by hand
keeps a one-hour gap on standard, so it is still described the same day.

The short briefing keeps every field a client reads, so the iOS app shows it
unchanged. Snapshots are sent as compact JSON, and the Coach's prompt starts
with the same text on every turn of a conversation, which lets a provider
that caches prompts reuse it.

Settings shows an estimate of tokens per day for each level, scaled from your
own use over the last seven days, the Coach included. It appears after three
days of AI use.

The instance admin sets the highest level an account may choose and the level
an account without a choice runs at, both **standard** on a new or updated
instance, under **Admin, Coach, AI usage levels**. A choice above the ceiling
is refused rather than quietly lowered. If the admin lowers the ceiling later,
an account above it runs at the ceiling and keeps its choice, so raising the
ceiling again restores it. The same card sets the gap for standard (1 to 48
whole hours); left empty, `AI_SYNC_REGEN_GAP_HOURS` applies, else 6. A feature
the level does not offer answers with the reason `usage_level` and the level
it needs.

## Automatic document reading (opt-in)

The [document vault](/guides/document-vault/) is local-first by default: an
uploaded document is only read by an external AI provider when you tap a
per-document AI action, and text-layer PDFs are indexed for search locally
with no egress. AI settings carry a per-user **"Read documents automatically
with AI"** switch, **off by default**, that reads, describes, and indexes
each upload through your configured provider with no per-document
confirmation. Turning it on is standing consent for reading documents and is
recorded in the consent audit trail; a subscription connection applies its own
consumer data settings, so privacy-sensitive deployments should keep the
switch off, or pair it with a no-training BYOK key or a local model. See the
[vault guide](/guides/document-vault/#reading-documents-with-ai--automatic-search)
for how the readers are chosen.

Switching it on also catches up on documents already in your vault. That
consent covers document reading, lab report scans and turning typed medication
text into a schedule, and nothing else. Your consent for the Coach or AI
analysis does not count for documents: the first time a document or a lab scan
would go to an AI service outside your server, you are asked once. A
self-hosted local model on your own server needs no consent for documents.
Withdrawing the document consent stops reading at once, even while the switch
is still on.

The operator can stop all of this for the server with the **Reading documents**
switch under Admin, Coach. With it off, or with the master switch off, asking
for a summary, a lab scan or a schedule from medication text is refused with a
message that AI is off on this server, and nothing is sent. Settings, AI provider says
the same next to the automatic reading switch: "Reading documents with AI is
switched off on this server."

## Withdrawing AI consent

AI settings show the standing consent decision in plain words and carry the
control that changes it. Withdrawing takes effect immediately: without an active
consent, every AI feature that needs it stops on the next call.

Withdrawing also deletes the notes the app can write again once no consent
for AI analysis is left: the per-metric status notes, the daily briefing,
model-written period summaries, the lines written after a new reading, and
workout notes. Your Coach conversations, what the Coach remembers, and the
summaries of your documents are your records and stay; you can read and delete
them yourself. Nothing you recorded is deleted by a withdrawal; that is the
erase path under **Settings → Advanced**. A withdrawn consent stays withdrawn
until you give it again.

## Connection test

`POST /api/ai/test` runs a one-shot probe against the resolved provider and
returns latency plus the model it routed to. The Settings UI surfaces a **Test
connection** button per provider; a failed probe returns a localisable
`errorCode`.

With the operator's master switch off, the test does not call the model and
answers with `assistant.disabled.enabled` instead.

## When AI is not available

The server decides in one place whether each AI feature can run for you, and
tells the app why when it cannot. The possible reasons, from the
outside in:

1. The operator switched it off for the server, with the master switch or the
   feature's own switch under Admin, Coach.
2. Someone gave you access to their record, and the access does not allow
   AI work on it.
3. The feature's module is off: the Coach module for the Coach, **AI
   analysis** for the briefing and notes, Documents for document reading, Labs
   for lab scans.
4. You opted out: you hid the Coach, or switched **AI analysis** off under
   Settings, Modules.
5. No provider is set up that can do the job.
6. Your consent for it is missing.

Your data never depends on the answer. Readings, charts, scores and statistics
load whatever the AI settings say. What changes is that nothing new is written
by a model, and text a model wrote earlier is not shown while the feature is
unavailable. Turn it back on and the stored text returns. Only a consent
withdrawal deletes anything, as described above.

**AI analysis** is the module that covers text a model writes for you: the daily
briefing, status notes, workout notes and the line after a new reading.
Switching it off keeps the Insights page, your scores and
your data; the morning briefing notification still arrives, with your health
score or the day's reminders instead of the written first sentence.

Hiding the Coach hides the Coach and nothing else; the briefing and status
notes follow **AI analysis**.

Whatever the reason the Coach is unavailable, what it kept stays yours: its
conversations, remembered facts, plans and reminders can be read and deleted
under Settings, Coach, or under Settings, AI provider when the Coach page is out of
reach. Reminders are held until the Coach is available again.

Someone you gave access to your record sees the briefing, notes and summaries
you would see, but opening your record never starts AI work on it.

## Troubleshooting

- **"No AI provider configured."** Set up at least one BYOK provider in
  `/settings/ai`, or configure an admin-shared key in the admin panel.
- **Local endpoint rejected as "internal/private host".** Add the endpoint's
  exact origin to `AI_PRIVATE_ORIGINS` in the container environment (for
  example `http://ollama.lan:11434`; comma-separate several) and restart. Under
  `ALLOW_LOCAL_AI_PRIVATE_HOSTS=true` an admin account's endpoint still works
  but no other account's does; the admin AI settings page lists the origins to
  add.
- **ChatGPT OAuth disconnects after a few weeks of inactivity.** ChatGPT
  refresh tokens lapse after extended idle periods. Reconnect via **Connect
  ChatGPT** — the device-code flow re-runs and the new tokens land in the same
  encrypted columns.
- **A shared provider is failing for everyone.** **Admin → Coach** has a
  provider-health card: one row per provider type with how many users' chains
  recorded an outcome for it, how many are failing, the longest failure run,
  the last success and failure, and whether it is paused and until when. It
  never says which user a row belongs to.
- **Chain falls through every entry.** Run the per-provider connection test
  from `/settings/ai` to identify the failing step. The most common cause is a
  stale or revoked BYOK key earlier in the chain; remove or disable that entry
  to skip ahead.

### When a provider keeps failing

A provider that fails three times in a row (rate limit, server error, network
error) is skipped for five minutes. From five failures in a row it is paused
for half an hour, and the pause doubles with each further failure, up to a
day. A rejected key or sign-in is skipped for six hours. Background work
(status cards, the briefing, document indexing) leaves a skipped provider
alone; the Coach and **Re-run analysis** still try it last and show its error.
One success clears the count. Saving your AI settings, the admin AI settings
or a fresh ChatGPT sign-in ends the pause at once.
