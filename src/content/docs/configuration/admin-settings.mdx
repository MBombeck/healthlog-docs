HealthLog stores its configuration in an **AppSettings singleton** in the database. These settings are managed through the admin interface at `/admin` and take effect immediately — no restart required.

The admin console is a **status-first overview** plus a sidebar with one focused panel per section. As of v1.4.14, every panel lives at its own URL (`/admin/<section>`) so links and bookmarks point at the exact view you want, and only the section you visit ships its bundle to the browser:

| Section | Route | What's there |
|---|---|---|
| Overview | `/admin` | Recent audit-log preview + system-status snapshot (v1.4.15+; section grid now lives in the sidebar) |
| System status | `/admin/system-status` | Container, DB, queue, and external-service health, plus a host-load chart over the last 2h (v1.4.16+) |
| App logs | `/admin/app-logs` | Tail of the last hour of structured wide-events with filters + JSON inspector (v1.4.16+) |
| Audit log | `/admin/audit-log` | Filterable + paginated audit history with CSV export (v1.4.16+ filters / pagination / export) |
| AI quality | `/admin/ai-quality` | Per-(severity × provider) helpful-rate from user feedback (v1.4.16+) |
| General | `/admin/general` | Registration, default locale, feature toggles |
| Services | `/admin/services` | Umami, GlitchTip, Web Push (VAPID) |
| Integrations | `/admin/integrations` | All integration sub-panels in one view |
| Reminders | `/admin/reminders` | Late / missed thresholds for medication reminders |
| Users | `/admin/users` | Per-user list with role filters and force-logout (v1.4.14+) |
| API tokens | `/admin/api-tokens` | Cross-user view of issued bearer + refresh tokens |
| Login overview | `/admin/login-overview` | Recent logins per user / IP |
| Backups | `/admin/backups` | Weekly backup history + manual run (v1.4.14+) |
| Feedback | `/admin/feedback` | Bug-report inbox, optional escalation |
| Danger zone | `/admin/danger-zone` | Wipe data, decommission instance |

Old anchor-style links (`/admin#section-users`) issue a 301 to the new route, so existing bookmarks keep working.

## General

| Setting | Description | Default |
|---|---|---|
| `registrationEnabled` | Enable or disable registration for new users. The first user can **always** register, regardless of this setting. | `true` |
| `defaultLocale` | Default language for new users: `de` or `en` | `de` |

:::caution
Registration is **enabled** by default. Disable it after creating all desired accounts to prevent unauthorized signups.
:::

## Notifications

Global toggles disable the respective channel for **all** users. Individual user preferences are overridden.

| Setting | Description | Default |
|---|---|---|
| `telegramGlobal` | Enable Telegram notifications globally | `true` |
| `ntfyGlobal` | Enable ntfy notifications globally | `true` |
| `webPushGlobal` | Enable Web Push notifications globally | `true` |

## Web Push (VAPID)

VAPID keys can be set directly in the admin settings. These take precedence over the corresponding environment variables.

| Setting | Description |
|---|---|
| `vapidPublicKey` | VAPID public key |
| `vapidPrivateKey` | VAPID private key (stored encrypted) |
| `vapidSubject` | Contact URI for VAPID (`mailto:...`) |

## Bug Reports

The built-in feedback flow always works (stored in your HealthLog database). Two extra knobs:

| Setting | Description |
|---|---|
| `bugReportEnabled` | Master on/off toggle (v1.4.3+). When off, `/bugreport` and `/api/feedback` both return 503 with a readable error so users see "bug reports are disabled" instead of a broken form. |
| `githubIssueToken` | GitHub Personal Access Token for the optional **Escalate to GitHub** admin action (stored encrypted) |
| `githubIssueRepo` | Target repository in `owner/repo` format |

:::note
The toggle is independent of the GitHub PAT. You can keep the PAT configured for escalation while turning the public bug-report form off, or run the form without ever escalating to GitHub.
:::

:::note
Sensitive values like the VAPID private key and GitHub token are stored encrypted in the database using AES-256-GCM. The encryption key is the `ENCRYPTION_KEY` environment variable.
:::

## Users (v1.4.14)

The **Users** panel at `/admin/users` lists every account on the instance with the role badge, the email Gravatar, the registration date, and the last-seen timestamp. Three filter pills narrow the list:

- **All** — every account.
- **Admins** — accounts with the admin role.
- **Users** — non-admin accounts.

Each row has a **Force logout** action behind a confirmation dialog. It deletes every active session for the target user (web cookies, native Bearer tokens, refresh tokens). The user is signed out immediately on every device and has to re-authenticate. The action writes an `admin.user.force-logout` entry to the audit log so the trail survives.

You cannot force-logout your own account — the button is disabled on your own row.

## Backups (v1.4.14, expanded in v1.4.15)

The **Backups** panel at `/admin/backups` shows the history of weekly snapshots (created Sundays at 03:00 Europe/Berlin by the `data-backup` queue). For every snapshot the panel shows the user, the backup type, the byte size, and the creation timestamp. The encrypted blob itself is **never** rendered — only the metadata.

The **Backup now** button enqueues an ad-hoc `data-backup` job for every user without waiting for the next Sunday. The job runs through the same encryption + S3 upload path the scheduled run uses; a toast confirms success. If the worker process is not running (for example, on a `HEALTHLOG_PROCESS_TYPE=web` container without a sibling worker), the button returns a clear "worker offline" error instead of silently dropping the job.

v1.4.15 turns the panel into the full backup lifecycle: every row carries **Download** (snapshot as `.json`) and **Restore** (re-import that snapshot into the database, behind a triple-confirm gate), and the page itself has a separate **Upload backup** card so you can ingest a snapshot you stored externally. Every operation — run, download, upload, restore (start + outcome) — lands in the audit log with the actor and the target snapshot. See [Backup structure and restore](/admin/backups/) for the file format, the restore confirm flow, and security considerations.

See [Self-Hosting → Scaling](/self-hosting/scaling/) for the off-host S3 upload configuration and the operator-side restore script.

## Overview Page (v1.4.15)

The `/admin` overview was a grid of section status cards through v1.4.14. v1.4.15 replaces it with two more useful blocks:

- **Recent audit-log preview** — the last handful of audit entries with actor, action, and target resource, so the moment you open `/admin` you see what's been happening on the instance. Click through to `/admin/audit-log` for the full history with filters.
- **System-status snapshot** — container, database, queue, and external-service health in one block, so `/admin/system-status` becomes a deep-dive rather than the front door.

The section grid hasn't disappeared — it now lives in the sidebar and only auto-expands while you're actually on an `/admin/*` route, so the sidebar stays quiet when you're elsewhere in the app.

## Host-Load Chart (v1.4.16)

The **System status** panel gains a host-load chart at the top showing host CPU, memory, and disk-IO over the **last 2 hours**, sampled every minute. Coolify Sentinel doesn't expose a clean read endpoint for these numbers, so HealthLog runs its own in-process sampler — a `host-metric-sampler` pg-boss job writes a row to a new `HostMetric` table every minute and the API returns the last 2h on demand. Samples are retained for 7 days, then expired by the same job that writes them.

The chart sits above the existing system-status block, so the moment you open `/admin/system-status` you see whether the host is healthy before you even read the container / DB / queue rows.

## App-Log Preview (v1.4.16)

A new **App logs** panel at `/admin/app-logs` surfaces a tail of the last hour of **structured wide-events** straight from the per-process ring buffer (500-entry FIFO; redacted at API egress). Filters narrow the list by:

- **`trace_id`** — paste a request id from a user-reported bug and you see only that request's events.
- **Level** — `debug` / `info` / `warn` / `error`.
- **Action** — pulldown of every action that's actually been observed in the buffer.
- **Time window** — last 5/15/60 minutes.

Click any row to open a JSON inspector modal with the full event payload (after redaction). Useful for debugging without `docker compose logs` and without shipping every event to Loki — the buffer always has the most recent hour for free.

## AI Quality Preview (v1.4.16)

`/admin/ai-quality` surfaces the daily aggregate of user feedback on AI recommendations. The table is grouped by `severity × provider × prompt-version`, with a helpful-rate column tinted by band (green for ≥ 75%, orange for 50–74%, red for < 50%). A degrading provider or a regression in a new prompt version shows up at a glance.

The aggregator runs once a day at 04:00 Europe/Berlin (`feedback-aggregator` pg-boss queue). The summary is stored in `AppSettings.adminAiInsightsFeedbackSummary` so the page renders from a single read; the per-user feedback rows themselves are never returned to admins.

## Audit Log (v1.4.16)

The audit log gets first-class filtering and export. Filter by **actor**, **action**, **target**, paginate at 25/50/100 rows per page, and click the export button to download the current filtered view as CSV. The action filter is a pulldown populated from a `groupBy` over the audit table itself, so you only ever see actions that actually happened on the instance.

## Auto-Deploy on GHCR Push (v1.4.15)

For self-hosters running Coolify, v1.4.15 wires a webhook so a successful Docker image build on `main` triggers a Coolify deploy automatically. Coolify then pings an internal HealthLog endpoint with the deploy result; success / failure / unknown all land in the audit log under `system.deploy.*`, and persistent failures fan a `SYSTEM_ALERT` to every admin via Telegram (if the channel is configured).

Two GitHub Actions secrets enable the trigger side: `COOLIFY_WEBHOOK` (the Bearer-protected deploy URL Coolify exposes) and `COOLIFY_TOKEN`. The webhook side needs `DEPLOY_WEBHOOK_SECRET` set both in the HealthLog container env (so the endpoint can verify incoming pings) and in Coolify's outgoing-webhook config as the `X-Deploy-Webhook-Secret` header. With those in place, no more manual `docker compose pull` after a release tag.
