HealthLog supports several notification channels that can run in parallel. Three of them — Telegram, ntfy, and Web Push — work with nothing more than the server and a browser. A fourth, **APNs (Apple Push)**, is an optional channel for the native iOS client. The system follows an opt-out model: all event types are enabled by default.

<img src={apnsFlow.src} alt="Push delivery flow: the server raises a notification event; if APNs is configured with a .p8 key it routes through Apple's gateway to the iOS device, otherwise it falls back to Telegram, ntfy or Web Push" />

## Channels

### Telegram

Each user provides their own bot token and chat ID. The bot token is stored AES-256-GCM encrypted in the database.

**Features:**
- Inline buttons in messages: Taken / Snooze / Skipped
- Automatic message deletion after 1 hour (prevents stale buttons)
- Bot commands: `/help`, `/start`, `/add`, `taken <Name>`

:::tip
The free-text command `taken Ibuprofen` lets you confirm an intake directly in the Telegram chat without opening the app.
:::

### ntfy

Self-hosted or public [ntfy](https://docs.ntfy.sh/) instance — a lightweight HTTP-based pub-sub push service you subscribe to by topic. Configurable per user:

- **Server URL** -- e.g., `https://ntfy.example.com`
- **Topic** -- e.g., `healthlog-alice`
- **Authentication** -- Optional (Basic Auth or token)
- **Priority** -- Set automatically based on event type

### Web Push

Browser-based push notifications via the standard [Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API), authenticated with [VAPID](https://datatracker.ietf.org/doc/html/rfc8292) key pairs — the server signs each push so the browser's push service can verify it without a shared secret.

- VAPID keys are generated during setup
- Subscriptions are device-specific (multiple devices per user supported)
- Works even when the browser tab is closed

### APNs (Apple Push)

[Apple Push Notification service](https://developer.apple.com/documentation/usernotifications) (APNs) is the optional channel used by the **native HealthLog iOS app**. It is the only channel that requires an Apple Developer account, and the only one that delivers push to an iPhone or iPad when the app is backgrounded.

APNs is **entirely optional**. If you do not configure it, the server silently skips it and falls back to Telegram, ntfy, and Web Push — the iOS app stays fully functional, you simply won't get native lock-screen pushes. The diagram at the top of this page shows that fall-through.

The server signs each push as a [JWT](https://datatracker.ietf.org/doc/html/rfc7519) (JSON Web Token — a compact, signed credential) using an Apple **`.p8` auth key** and sends it to Apple's gateway. Three identifiers must line up:

| Setting | What it is |
|--------|-----------|
| `APNS_KEY_ID` | The 10-character key ID of the `.p8` auth key |
| `APNS_TEAM_ID` | Your 10-character Apple Developer team ID |
| `APNS_BUNDLE_ID` | The bundle-id of the signed iOS app — this becomes the APNs *topic* |
| `APNS_KEY` / `APNS_KEY_B64` / `APNS_KEY_FILE` | The `.p8` contents (PEM, base64, or a file path) — provide exactly one |

```bash
# Provide all four (one key source). Missing any → APNs is disabled, fallbacks take over.
APNS_KEY_ID="ABCD123456"
APNS_TEAM_ID="S8WDX4W5KX"
APNS_BUNDLE_ID="dev.healthlog.app"
APNS_KEY_B64="LS0tLS1CRUdJTi...="   # base64 of the .p8, no newlines
```

:::caution[Self-hosters: the .p8 is bound to *your* app, not the published one]
An Apple `.p8` key only works with apps signed by the **same Apple Developer team**, and APNs delivers only to the app whose **bundle-id matches the topic**. The published HealthLog app is signed under `dev.healthlog.app`. To push from your own server with your own `.p8`, you must **rebuild and re-sign the iOS app under your own bundle-id and team**, then set `APNS_BUNDLE_ID` to that bundle-id. Reusing the stock bundle-id with a foreign `.p8` is rejected by Apple (`DeviceTokenNotForTopic`). See the [TLS Certificates](/self-hosting/tls-certificates/) guide for the related rebuild story, and the [iOS client repo](https://github.com/MBombeck/healthlog-iOS) for the native implementation.
:::

The iOS app registers its APNs device token through `POST /api/devices`; the server fans one push out per registered device. Implementation details (registration, the `HKMetadataKeyExternalUUID` de-dup, background sync) live in the native client — this server doc only covers the wire contract. See [Native API Clients](/api/native-clients/) and the [iOS repo](https://github.com/MBombeck/healthlog-iOS).

## Event Types

| Event Type | Description |
|-----------|------------|
| `MEDICATION_REMINDER` | Reminder for a due intake (phase-based) |
| `MEASUREMENT_ANOMALY` | Reading outside the normal range |
| `COMPLIANCE_LOW` | Adherence below threshold |
| `WITHINGS_SYNC_FAILED` | Withings sync failed |
| `SYSTEM_ALERT` | System notifications (backup, errors) |

## Configuration

### Opt-Out Model

By default, all event types are active on all channels. Users can selectively disable them:

- Per channel (e.g., Telegram on, ntfy off)
- Per event type per channel (e.g., `SYSTEM_ALERT` on ntfy only)

### Global Settings

Administrators can control notifications system-wide:

- Global toggles per channel
- Quiet hours window (no notifications at night)

:::caution
Global admin settings override individual user preferences. If a channel is globally disabled, no user will receive notifications through it.
:::

## Channel Status

**Settings → Notifications** shows a status card for every channel you have configured. Each card paints:

- **State badge** — connected, error (transient), or auto-disabled
- **Last success** and **last failure** timestamps
- **Consecutive-failure counter** — how many sends in a row failed
- **Disable reason** — e.g. "Web Push subscription returned 410 (gone)" — when HealthLog auto-disabled the channel after a hard reject
- **Re-enable** button (only when auto-disabled) and a **Send test** button

When a channel hits a permanent rejection (e.g. an expired Web Push subscription returning 410, or a Telegram bot the user blocked), HealthLog auto-disables it after a few retries with exponential backoff so it doesn't keep banging on a dead endpoint. Transient errors retry on a `[30s, 5min, 30min, 2h]` schedule before giving up. Re-enable a channel any time after fixing the underlying issue.
