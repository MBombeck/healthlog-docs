HealthLog connects with external services and devices. All integrations are optional and configured per user.

## Withings

Integration with Withings scales, blood pressure monitors, thermometers, and ScanWatch wearables via [OAuth 2.0](https://datatracker.ietf.org/doc/html/rfc6749) — the delegated-authorization standard that lets you grant HealthLog read access to your Withings data without ever sharing your Withings password. Devices live on the Withings ecosystem and pair through the Withings app -- HealthLog reads the data after the user authorises one OAuth connection.

- Marketing site & product range: [withings.com](https://www.withings.com)
- Health Mate app (the Withings companion app you pair devices with): [withings.com/eu/en/health-mate](https://www.withings.com/eu/en/health-mate)
- Developer documentation (for the curious / for setting up the OAuth app): [developer.withings.com](https://developer.withings.com)

:::tip
You do **not** need a Withings+ subscription for any of this. The data sync works with any Withings account that owns the right device. Withings+ adds clinical services and the Withings Intelligence chatbot on top of the free app -- HealthLog provides its own AI Insights surface that doesn't require either.
:::

### Supported Devices and Metrics

| Device Type | Metrics |
|------------|---------|
| Scale (Body+ / Body Comp / Body Scan) | Weight, body fat percentage, total body water (kg), bone mass (kg) |
| Blood Pressure Monitor (BPM Connect / BPM Core / BPM Vision) | Systolic, diastolic, heart rate, SpO2 (BPM Vision) |
| ScanWatch / ScanWatch 2 / ScanWatch Nova | Oxygen saturation (SpO2), VO2 max |
| Thermo | Body temperature (both first- and current-generation) |

### Forward compatibility

When Withings exposes a new metric in the Health Mate app and developer API, HealthLog picks it up as soon as we ship the matching adapter -- usually a one-line addition to the meastype mapping table.

- The current coverage table (every Withings `meastype` code → HealthLog measurement) lives in the main repo under [`src/lib/withings/mapping.md`](https://github.com/MBombeck/HealthLog/blob/main/src/lib/withings/mapping.md).
- The audit of the **full** Withings API surface, with scoring of what's coming next, lives at [`.planning/research/withings-api-coverage.md`](https://github.com/MBombeck/HealthLog/blob/main/.planning/research/withings-api-coverage.md).

If you own a Withings device that produces data HealthLog doesn't ingest yet, open a [GitHub issue](https://github.com/MBombeck/HealthLog/issues) -- additive mappings ship in patch releases.

### Synchronization

Data is synced through two mechanisms:

- **[Webhook](https://en.wikipedia.org/wiki/Webhook)** -- a server-to-server callback Withings POSTs the instant a new reading is recorded, rather than HealthLog polling for it (primary). HealthLog subscribes to the weight + body-composition (`appli=1`), temperature (`appli=2`), and pressure (`appli=4`) categories so blood pressure readings and Thermo measurements arrive within seconds of the device taking them.
- **Polling** -- Hourly fallback fetch (secondary, in case the webhook fails).

### Prerequisites

The Withings integration requires a **Withings Developer Account** with a registered app. The Client ID and Client Secret are entered in the HealthLog settings and stored AES-256-GCM encrypted. The developer app itself is free -- the partner-hub "Basic Biomarker Pack" covers everything HealthLog ingests today.

### Setup

1. Create a Withings Developer App at [developer.withings.com](https://developer.withings.com)
2. Enter the Client ID and Client Secret in the HealthLog settings
3. Connect your Withings account in the HealthLog settings (OAuth 2.0 flow)
4. Grant permission for measurement data
5. The webhook is registered automatically

:::note
If the webhook stops working (e.g., after a server migration), the hourly polling kicks in automatically. The `WITHINGS_SYNC_FAILED` event type notifies you of prolonged outages.
:::

## WHOOP

Integration with [WHOOP](https://www.whoop.com) recovery straps via OAuth 2.0. WHOOP is a per-user **bring-your-own-keys** integration: each self-hoster registers their own WHOOP developer app and pastes the Client ID and Client Secret into HealthLog, stored AES-256-GCM encrypted on the user record.

### Supported metrics

| WHOOP source | HealthLog data |
|---|---|
| Recovery | Resting heart rate, heart-rate variability, oxygen saturation, skin temperature, respiratory rate, and a device-native recovery score |
| Sleep | Per-stage sleep with the shared sleep-stage model |
| Body | Weight, height (height seeds the profile only) |
| Workout | Exercise sessions as workouts (sport type, duration, energy, distance, heart rate) |

WHOOP leads the default source ladder for the recovery-input metrics (sleep, HRV, resting heart rate, respiratory rate) — see [Source priority](/concepts/source-priority/).

### Setup

1. Create a WHOOP developer app at [developer.whoop.com](https://developer.whoop.com)
2. Set the redirect URL to `<your-app-url>/api/whoop/callback` (or the `WHOOP_REDIRECT_URI` env var)
3. Enter the Client ID and Client Secret under **Settings → Integrations → WHOOP**
4. Connect your WHOOP account (OAuth 2.0 flow)

Each connection has a **Test connection** button, a **manual sync** (incremental by default, full history on request), and a **resume** control that recovers a connection after a revoked grant. A signed webhook keeps new data flowing in near-real-time; `WHOOP_WEBHOOK_SECRET` hardens its [HMAC](https://en.wikipedia.org/wiki/HMAC) signature verification so a forged callback can't inject readings.

## Google Health / Fitbit (experimental)

Integration with Fitbit and Pixel wearables through Google's [Health API](https://developers.google.com/health). Like WHOOP, this is a per-user **bring-your-own-keys** integration: each self-hoster registers their own Google Cloud OAuth client and pastes the Client ID and Client Secret into HealthLog, stored AES-256-GCM encrypted.

:::caution
This integration is **experimental**. Google's Health API is young, and several per-type value fields are not yet fully published, so some data types may import nothing until the wire mapping is verified against a live account. Treat imported coverage as provisional and report gaps as [GitHub issues](https://github.com/MBombeck/HealthLog/issues).
:::

### Supported metrics

Server-side sync covers four read bundles:

| Bundle | HealthLog data |
|---|---|
| Activity (daily) | Steps, walking/running distance, active energy burned, floors climbed, VO₂ max |
| Health metrics | Weight, body fat, oxygen saturation, resting heart rate, heart-rate variability, respiratory rate, wrist temperature, spot heart rate (height seeds the profile only) |
| Sleep | Per-stage sleep with the shared sleep-stage model |
| Exercise | Workouts (sport type, duration, energy, distance, heart rate) |

The live coverage table (every Google Health data type → HealthLog measurement) lives in the main repo at [`src/lib/fitbit/mapping.md`](https://github.com/MBombeck/HealthLog/blob/main/src/lib/fitbit/mapping.md).

### Setup

1. Create an OAuth client in a [Google Cloud](https://console.cloud.google.com) project and enable the Health API
2. Set the redirect URI to `<your-app-url>/api/fitbit/callback` (or the `FITBIT_REDIRECT_URI` env var)
3. Enter the Client ID and Client Secret under **Settings → Integrations**
4. Connect your account (Google OAuth consent flow)

The same **Test connection**, **manual sync** (incremental or full history), and **resume** controls as WHOOP apply.

:::note
Every scope HealthLog requests is a Google **Restricted** scope. Before the OAuth client can leave Google's Testing mode and serve more than a handful of test users, the operator's project needs Google brand verification plus an annual CASA security assessment — this is per-OAuth-client, which is why HealthLog cannot ship a single shared app.
:::

## MoodLog

:::caution[Deprecated]
The standalone moodLog.app webhook is deprecated. Mood is now tracked fully inside HealthLog with a five-face capture, a structured tag catalog, and rated factors — see [Mood Tracking](/features/mood-tracking/). The webhook stays functional for existing integrations and is slated for removal in a future major release; do not build new callers against it.
:::

Integration with [moodlog.app](https://moodlog.app) for mood tracking data.

- **Webhook**: MoodLog sends new entries to HealthLog via webhook
- **Polling**: Periodic fetch as a fallback
- **Data**: Mood entries with tags

Mood data feeds into the AI correlation analysis (mood vs. blood pressure, weight, heart rate).

:::note
The moodLog instance URL is validated against an [SSRF](https://owasp.org/www-community/attacks/Server_Side_Request_Forgery) allow-list — Server-Side Request Forgery is when a user-supplied URL tricks the server into calling internal addresses, so internal-network and cloud-metadata addresses are rejected on save and re-checked at fetch time. The webhook secret is stored AES-256-GCM encrypted.
:::

## Test Connection Buttons

Each integration ships with a one-click **Test connection** button under **Settings → Integrations** (Withings, moodLog, Web Push, Glitchtip, Umami, AI provider, Telegram, ntfy). Each test runs server-side, behind its own rate limit, with sanitised error reporting and the same redirect-follow SSRF guard the production fetch uses.

## Connection Status

Each integration card sits above its credentials form and shows the live connection state in a **single status pill** top-right of every card — "Connected · 12 min ago" with locale-aware relative-time bucketing (`just now` / `min` / `h` / `d`), three states (connected / error / disconnected), and `whitespace-nowrap` so it stays on one line down to Pixel-5 width.

Beyond the pill, the card still surfaces:

- **Last error** (if any) — sanitised inline alert above the action row, never leaks the credential
- **Consecutive-failure counter** — `{n}/{threshold}` chip when the upstream is unhappy

When the upstream returns an authentication failure (Withings refresh-token rejection, moodLog 401/403), the card flips to **Reauth required** and scheduled syncs short-circuit instead of hammering the upstream — reconnect with one click and they resume on the next tick. After a configurable threshold of consecutive failures (default 3), HealthLog sends a one-shot Telegram alert to admins (if the channel is enabled) so a quietly-broken integration doesn't slowly rot for weeks.

## External API

HealthLog provides an API for external systems, such as automation tools or IoT devices. Full endpoint reference: [External API](/api/external-ingest/).

### Bearer Token

Tokens are created per medication and use the `hlk_` prefix. They are presented as a [bearer token](https://datatracker.ietf.org/doc/html/rfc6750) in the `Authorization: Bearer …` header.

```bash
curl -X POST https://healthlog.example.com/api/ingest/medication \
  -H "Authorization: Bearer hlk_abc123..." \
  -H "Content-Type: application/json" \
  -d '{"medicationName": "Metoprolol", "idempotencyKey": "unique-key-123"}'
```

**Properties:**
- Per-medication scope (a token can only log intakes for its assigned medication)
- Stored as a keyed HMAC-SHA-256 hash in the database (the `API_TOKEN_HMAC_KEY` env var) — a database dump alone does not let an attacker precompute a rainbow table
- Revocable through the UI

:::tip
The external API is great for [NFC](https://en.wikipedia.org/wiki/Near-field_communication) tags on your medicine cabinet: scan the tag, and the intake is logged automatically. The required `idempotencyKey` means a double-tap still records the dose only once.
:::

## Bug Reports

Users can optionally submit bug reports directly as GitHub issues.

- Requires a GitHub Personal Access Token (PAT) configured by the administrator
- Issues are created in the configured repository
- System info is attached automatically (version, browser, anonymized error data)

:::caution
The GitHub PAT is configured by the administrator. Users do not need their own GitHub account to submit bug reports.
:::
