HealthLog connects with external services and devices. All integrations are optional and configured per user.

## Withings

Integration with Withings scales, blood pressure monitors, thermometers, and ScanWatch wearables via OAuth 2.0. Devices live on the Withings ecosystem and pair through the Withings app -- HealthLog reads the data after the user authorises one OAuth connection.

- Marketing site & product range: [withings.com](https://www.withings.com)
- Health Mate app (the Withings companion app you pair devices with): [withings.com/eu/en/health-mate](https://www.withings.com/eu/en/health-mate)
- Developer documentation (for the curious / for setting up the OAuth app): [developer.withings.com](https://developer.withings.com)

:::tip
You do **not** need a Withings+ subscription for any of this. The data sync works with any Withings account that owns the right device. Withings+ adds clinical services and the Withings Intelligence chatbot on top of the free app -- HealthLog provides its own AI Insights surface that doesn't require either.
:::

### Supported Devices and Metrics

| Device Type | Metrics |
|------------|---------|
| Scale (Body+ / Body Comp / Body Scan) | Weight, body fat percentage, total body water (kg), bone mass (kg) |
| Blood Pressure Monitor (BPM Connect / BPM Core / BPM Vision) | Systolic, diastolic, heart rate, SpO2 (BPM Vision) |
| ScanWatch / ScanWatch 2 / ScanWatch Nova | Oxygen saturation (SpO2), VO2 max |
| Thermo | Body temperature (both first- and current-generation) |

### Forward compatibility

When Withings exposes a new metric in the Health Mate app and developer API, HealthLog picks it up as soon as we ship the matching adapter -- usually a one-line addition to the meastype mapping table.

- The current coverage table (every Withings `meastype` code → HealthLog measurement) lives in the main repo under [`src/lib/withings/mapping.md`](https://github.com/MBombeck/HealthLog/blob/main/src/lib/withings/mapping.md).
- The audit of the **full** Withings API surface, with scoring of what's coming next, lives at [`.planning/research/withings-api-coverage.md`](https://github.com/MBombeck/HealthLog/blob/main/.planning/research/withings-api-coverage.md).

If you own a Withings device that produces data HealthLog doesn't ingest yet, open a [GitHub issue](https://github.com/MBombeck/HealthLog/issues) -- additive mappings ship in patch releases.

### Synchronization

Data is synced through two mechanisms:

- **Webhook** -- Real-time push notification on new readings (primary). HealthLog subscribes to the weight + body-composition (`appli=1`), temperature (`appli=2`), and pressure (`appli=4`) categories so blood pressure readings and Thermo measurements arrive within seconds of the device taking them.
- **Polling** -- Hourly fallback fetch (secondary, in case the webhook fails).

### Prerequisites

The Withings integration requires a **Withings Developer Account** with a registered app. The Client ID and Client Secret are entered in the HealthLog settings and stored AES-256-GCM encrypted. The developer app itself is free -- the partner-hub "Basic Biomarker Pack" covers everything HealthLog ingests today.

### Setup

1. Create a Withings Developer App at [developer.withings.com](https://developer.withings.com)
2. Enter the Client ID and Client Secret in the HealthLog settings
3. Connect your Withings account in the HealthLog settings (OAuth 2.0 flow)
4. Grant permission for measurement data
5. The webhook is registered automatically

:::note
If the webhook stops working (e.g., after a server migration), the hourly polling kicks in automatically. The `WITHINGS_SYNC_FAILED` event type notifies you of prolonged outages.
:::

## MoodLog

Integration with [moodlog.app](https://moodlog.app) for mood tracking data.

- **Webhook**: MoodLog sends new entries to HealthLog via webhook
- **Polling**: Periodic fetch as a fallback
- **Data**: Mood entries with tags

Mood data feeds into the AI correlation analysis (mood vs. blood pressure, weight, heart rate).

:::note
The moodLog instance URL is validated against an SSRF allow-list — internal-network and cloud-metadata addresses are rejected on save and re-checked at fetch time. The webhook secret is stored AES-256-GCM encrypted.
:::

## Test Connection Buttons

Each integration ships with a one-click **Test connection** button under **Settings → Integrations** (Withings, moodLog, Web Push, Glitchtip, Umami, AI provider, Telegram, ntfy). Each test runs server-side, behind its own rate limit, with sanitised error reporting and the same redirect-follow SSRF guard the production fetch uses.

## Connection Status (v1.4.15+, consolidated in v1.4.19)

Each integration card sits above its credentials form (v1.4.15+) and shows the live connection state. v1.4.19 collapses the previous status banner trio (`connected / last successful / last attempted`) and the bottom-of-card "letzter Sync" line into a **single status pill** top-right of every card — "Connected · 12 min ago" with locale-aware relative-time bucketing (`just now` / `min` / `h` / `d`), three states (connected / error / disconnected), and `whitespace-nowrap` so it stays on one line down to Pixel-5 width. Withings and Mood Log now also share the same divider between header and body for visual symmetry.

Beyond the pill, the card still surfaces:

- **Last error** (if any) — sanitised inline alert above the action row, never leaks the credential
- **Consecutive-failure counter** — `{n}/{threshold}` chip when the upstream is unhappy

When the upstream returns an authentication failure (Withings refresh-token rejection, moodLog 401/403), the card flips to **Reauth required** and scheduled syncs short-circuit instead of hammering the upstream — reconnect with one click and they resume on the next tick. After a configurable threshold of consecutive failures (default 3), HealthLog sends a one-shot Telegram alert to admins (if the channel is enabled) so a quietly-broken integration doesn't slowly rot for weeks.

## External API

HealthLog provides an API for external systems, such as automation tools or IoT devices.

### Bearer Token

Tokens are created per medication and use the `hlk_` prefix.

```bash
curl -X POST https://healthlog.example.com/api/ingest/medication \
  -H "Authorization: Bearer hlk_abc123..." \
  -H "Content-Type: application/json" \
  -d '{"medicationName": "Metoprolol", "idempotencyKey": "unique-key-123"}'
```

**Properties:**
- Per-medication scope (a token can only log intakes for its assigned medication)
- Stored as a keyed HMAC-SHA-256 hash in the database (the `API_TOKEN_HMAC_KEY` env var) — a database dump alone does not let an attacker precompute a rainbow table
- Revocable through the UI

:::tip
The external API is great for NFC tags on your medicine cabinet: scan the tag, and the intake is logged automatically.
:::

## Bug Reports

Users can optionally submit bug reports directly as GitHub issues.

- Requires a GitHub Personal Access Token (PAT) configured by the administrator
- Issues are created in the configured repository
- System info is attached automatically (version, browser, anonymized error data)

:::caution
The GitHub PAT is configured by the administrator. Users do not need their own GitHub account to submit bug reports.
:::
