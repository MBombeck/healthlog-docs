HealthLog provides comprehensive export and import capabilities for data backup, sharing with doctors, and migration.

## Settings → Export

Every export — the doctor-report PDF, the per-domain CSVs, and the full JSON backup — lives under one consolidated route at **Settings → Export**. Each export is its own card with a clear title, a one-line description, the relevant filters, and a download button. The cards are:

- **Doctor report (PDF)** — the same client-side jsPDF generator described in [Doctor Report](/features/doctor-report/), but reachable from the Export page now instead of a separate top-level link. Configurable date range and optional practice name.
- **Measurements (CSV)** — every reading you've logged. Time range filter on the card.
- **Medications (CSV)** — your medication list. An optional "include intake history" toggle lets you bundle every recorded intake event into the same CSV.
- **Mood (CSV)** — your mood entries with tags.
- **Full JSON backup** — the entire account snapshot in JSON, importable back into HealthLog.

The mobile layout stacks the cards in one column; on `≥ md` viewports they sit two-up. Every download writes a `user.export.<kind>` entry to your audit log. All four endpoints share a global `export:<userId>` rate-limit bucket of **10 / hour**, and the doctor-report PDF — generated client-side — does not count against that bucket.

## Health-record export (PDF + FHIR R4)

The doctor handover has grown into a selectable **health-record export**, served from `POST /api/export/health-record`. One request can produce three things, chosen with the `format` field:

- **`pdf`** — an enriched clinical PDF: a cover with your patient identity, a deterministic summary, and native sparklines.
- **`fhir`** — a machine-readable [HL7 FHIR R4](https://hl7.org/fhir/R4/) document Bundle (`application/fhir+json`). FHIR R4 is the format used here because it is the interchange standard clinical systems already read — Germany's electronic patient record (ePA) ingests FHIR, so the export drops into a real record rather than being a PDF a practice has to retype.
- **`package`** — both of the above plus a README, zipped together.

<img src={healthRecordExport.src} alt="A health-record export request feeds one shared aggregator read, which becomes an enriched PDF and an HL7 FHIR R4 Bundle. The Bundle carries a Patient resource from the profile identity fields, LOINC-coded Observations including a blood-pressure panel, MedicationStatements, a DiagnosticReport, and an opt-in AI summary marked not clinically validated." />

You choose the **date range** (up to a year) and the **per-domain sections** — vitals (weight, BP, pulse, SpO₂, body composition), cardio fitness (resting HR, HRV, VO₂max), activity, glucose, medications (list, compliance, side effects), mood, and BMI. The FHIR bundle and the PDF read from the **same aggregator**, so both describe identical numbers.

In the FHIR bundle, measurements become [LOINC](https://loinc.org/)-coded `Observation` resources with [UCUM](https://ucum.org/) units (blood pressure groups systolic and diastolic into one panel), medications become `MedicationStatement`s, and a `DiagnosticReport` ties the observations together. The same LOINC/UCUM conventions are used by the iOS client, so records interchange. The `Patient` resource is built from the optional **patient-identity fields** on your profile — full name, insurer, and insurance number (validated and encrypted at rest). Set them under **Account** before exporting if you want them on the record.

:::caution
The AI summary is an **explicit opt-in** section (`includeAiSummary`) and is clearly marked as **not clinically validated**. It is a convenience narrative, not a medical assessment.
:::

The endpoint shares the same `export:<userId>` bucket (**10 / hour**) as the other exports. See the [OpenAPI spec](/api/overview/) for the full request schema.

## Export

### Formats

| Format | Description |
|--------|------------|
| **[JSON](https://en.wikipedia.org/wiki/JSON)** | Structured key–value text format, suitable for backups and re-import |
| **[CSV](https://en.wikipedia.org/wiki/Comma-separated_values)** | Plain-text tabular format (one record per line), compatible with Excel, Google Sheets, etc. |

### Export Types

Data can be exported individually or as a complete package:

- `measurements` -- All health readings
- `medications` -- Medications and schedules
- `intake` -- Intake log
- `mood` -- Mood entries (tracked natively in HealthLog)
- `all` -- Full export of all data

### Rate Limit

```
Maximum exports: 10 per hour per user
```

:::note
The rate limit prevents accidental repeated exports and excessive load. It is more than sufficient for regular use.
:::

## Import

### Format

The import accepts JSON files with the following structure:

```json
{
  "measurements": [
    {
      "type": "WEIGHT",
      "value": 82.5,
      "unit": "kg",
      "measuredAt": "2026-03-01T08:00:00Z"
    }
  ],
  "moodEntries": [
    {
      "date": "2026-03-01",
      "mood": "GUT",
      "score": 4,
      "tags": "relaxed",
      "loggedAt": "2026-03-01T20:00:00Z"
    }
  ]
}
```

Mood is a five-point scale — `mood` is one of `SUPER_GUT`, `GUT`, `OKAY`, `SCHLECHT`, `LAUSIG`, with the matching `score` from 5 (best) down to 1. Each measurement carries its `unit`; values outside a plausible range for the type are rejected.

### Limitations

- **Maximum records**: 10,000 per import
- **Supported data**: `measurements` and `moodEntries`
- **Deduplication**: Duplicates are detected automatically via unique constraints and skipped

:::caution
Imports never overwrite existing data. Duplicates (same type, same timestamp) are silently ignored.
:::

## Automatic Backup

HealthLog creates a weekly encrypted backup:

- **Schedule**: Sundays at 03:00 Europe/Berlin (pg-boss job)
- **Encryption**: [AES-256-GCM](https://en.wikipedia.org/wiki/Galois/Counter_Mode)
- **Storage**: In the database (as an encrypted blob)
- **Content**: All user data (readings, medications, intakes, mood)

```
Schedule: Sunday 03:00 Europe/Berlin
Encryption: AES-256-GCM
Storage: PostgreSQL (encrypted blob)
Job Runner: pg-boss
```

:::caution
The automatic in-app backup is stored **in the same database**. If the database is lost, these backups are lost too. Set up an external PostgreSQL backup as well (e.g., `pg_dump` via cron job). See [Self-Hosting Security](/security/self-hosting/) for details.
:::
