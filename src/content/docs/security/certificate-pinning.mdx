TLS already protects HealthLog traffic, but a standard TLS handshake trusts **any** certificate that chains to a CA in the operating system's trust store. If an attacker can coerce a CA into mis-issuing a certificate for your domain — or slip a rogue root onto the device via a malicious MDM profile or proxy — they can sit in the middle and read everything. Certificate pinning closes that gap by hard-coding *which* key the app is willing to trust.

<img src={tlsFlow.src} alt="TLS trust decision flow on the iOS client: if the host is *.bombeck.io the app validates the SPKI pins and aborts on mismatch, otherwise it falls back to standard CA-validated system-trust TLS with no pin lockout" />

## The threat it stops

A [man-in-the-middle attack](https://en.wikipedia.org/wiki/Man-in-the-middle_attack) on a [TLS](https://en.wikipedia.org/wiki/Transport_Layer_Security) connection works when the attacker presents a certificate the client accepts. Plain TLS accepts any CA-signed cert for the hostname. Pinning narrows acceptance to a specific public key the app shipped with, so a mis-issued-but-valid certificate is rejected before any health data crosses the wire.

## SPKI pinning vs. cert-hash pinning

There are two common ways to pin:

- **Cert-hash pinning** pins the SHA-256 of the entire leaf certificate (the full DER blob). The instant the server rotates to a new certificate — even one carrying the *same* key — the pin breaks.
- **SPKI pinning** pins the SHA-256 of the certificate's **Subject Public Key Info** — the raw public key inside the [X.509](https://en.wikipedia.org/wiki/X.509) certificate. A [public-key fingerprint](https://en.wikipedia.org/wiki/Public_key_fingerprint) survives certificate reissuance as long as the key is reused, which makes operations far less fragile.

HealthLog uses **SPKI pinning**. This is the modern successor to the now-deprecated [HTTP Public Key Pinning](https://en.wikipedia.org/wiki/HTTP_Public_Key_Pinning) header standardised in [RFC 7469](https://datatracker.ietf.org/doc/html/rfc7469) — same idea (pin the public key, not the cert), but enforced inside the native app instead of via an HTTP response header the browser had to remember. Browser-side HPKP is dead: every major browser dropped it because a misconfigured or hijacked pin header could permanently brick a site. We cite RFC 7469 for the SPKI-hash *concept*, not as a live web mechanism — a native app pins client-side, where a bad pin only affects that one app build and can be fixed with an update.

The iOS client extracts the SPKI from each certificate in the presented chain, hashes it with SHA-256, and accepts the connection if **any** hash in its pin set matches **any** certificate in the chain (leaf, intermediate, or root).

## Only `*.bombeck.io` is pinned

This is the part that matters for self-hosters: **the app pins only the managed-cloud domain `*.bombeck.io`.** The decision is made per-host by `isPinnedHost`:

- **Host is `*.bombeck.io`** → the SPKI pin set is enforced. A non-matching chain aborts the connection.
- **Any other host** (including a self-hosted instance on your own domain) → the app falls back to **standard, CA-validated system-trust TLS**. There is no pin to satisfy, so you are never locked out.

In other words, pinning is a hardening measure for the hosted service the maintainer operates; it does not constrain people running their own instance. If you self-host, your TLS works exactly the way it would for any other modern app pointed at your domain. (A self-hoster who rebuilds the app under their own bundle id can opt into pinning their own domain via the `HLPinnedHosts` + `HLPinnedSPKIHashes` build-time keys.)

## CA-level pinning: the rotation-survival strategy

A leaf pin is brittle: the server's certificate auto-renews roughly every 90 days, each renewal mints a new leaf keypair, and a leaf-pinned app breaks on every renewal unless a new build ships first. HealthLog therefore pins **the CA keys, not the leaf**:

| Pin | Role | Typical lifetime |
|-----|------|-----------------|
| **Intermediate** | The issuing CA's key | years |
| **Root** | The trust-anchor key | years |

Because validation accepts a match on *any* certificate in the chain, routine leaf renewals pass with **zero app updates** — the served chain still terminates in the pinned intermediate and root keys. Baseline X.509 evaluation (hostname, validity, revocation) always runs first, so pinning means "valid chain AND pinned key", never "pinned key alone". MITM protection is preserved: an attacker still needs a certificate that chains through the pinned CA keys *and* passes system trust. A release build refuses to launch with fewer than two well-formed pins, so a single-pin configuration cannot ship. A re-pin (and app update) is only needed when the CA rotates its intermediate or root keys, or the server moves to a different CA — rare, multi-year events announced ahead of time.

:::tip[Generating the hashes]
The hashes are produced from the live TLS chain with `scripts/extract-spki.sh <host>` in the iOS repo, which pulls the chain via `openssl s_client -showcerts` and prints the base64 SHA-256 SPKI for each certificate. For the managed cloud that's `scripts/extract-spki.sh healthlog.bombeck.io`.
:::

## Where the implementation lives

Pinning is a **client-side** concern — the server presents a normal certificate; the iOS app decides whether to trust it. The validation logic, the production pin policy (a minimum well-formed pin count enforced at build time), and the rotation runbook all live in the native client:

- `HealthLog/Services/CertificatePinner.swift` — SPKI extraction + chain validation
- `scripts/extract-spki.sh` — hash extraction
- `project.yml` `HLPinnedSPKIHashes` — the pinned hash set

See the [iOS repo](https://github.com/MBombeck/healthlog-iOS) for the source. Self-hosters who want to pin their *own* domain should read the [TLS Certificates](/self-hosting/tls-certificates/) guide.
