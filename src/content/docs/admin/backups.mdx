HealthLog ships its own per-user backup mechanism on top of any database-level dumps you take. The `data-backup` queue (pg-boss) writes a structured JSON snapshot of every user's data to the `DataBackup` table on a weekly schedule, and v1.4.15 added the full lifecycle around it: download, upload, and restore.

This page explains what's inside a snapshot, how the lifecycle works, and the security implications of holding the file outside the database.

## When backups run

| Property | Value |
|----------|-------|
| Schedule | Sundays at 03:00 Europe/Berlin |
| Trigger | pg-boss `data-backup` queue |
| Manual trigger | **Backup now** button on `/admin/backups` |
| Storage location | `DataBackup` table in PostgreSQL (encrypted blob), optionally mirrored to S3 |
| Retention (DB) | The HealthLog worker never deletes rows from `DataBackup` |
| Retention (S3) | Bucket lifecycle policy (the worker has `PutObject` + `GetObject` only — see [Scaling & Operations](/self-hosting/scaling/)) |

The manual **Backup now** action enqueues an ad-hoc job for every user; the regular Sunday run is unchanged.

## What's inside a backup

A backup is a structured JSON document. The top-level shape looks like this:

```json
{
  "schemaVersion": "1",
  "createdAt": "2026-05-09T03:00:00.000Z",
  "user": { "id": "...", "username": "..." },
  "measurements": [ /* ... */ ],
  "medications": [ /* ... */ ],
  "medicationIntakeEvents": [ /* ... */ ],
  "moodEntries": [ /* ... */ ],
  "notificationChannels": [ /* config redacted but referenced */ ],
  "achievements": [ /* ... */ ],
  "userPreferences": { /* dashboard layout, locale, targets, ... */ }
}
```

The `schemaVersion` field is the load-bearing part — it tells the upload / restore endpoint which version of the parser to use. Today only `"1"` is recognised; once a future v2 lands, the upload path will refuse incompatible versions explicitly rather than silently accepting them.

### Which models are included

Every model that's owned by a single user and that contributes to that user's health record:

- **Vitals** — measurements (weight, BP, glucose, SpO₂, sleep, steps, body composition)
- **Mood** — entries with timestamps, scores, tags, free-text notes
- **Medication catalogue** — definitions, schedules, reminder phases
- **Medication intake events** — every confirmed / late / missed / skipped record
- **Notification channels** — Telegram, ntfy, Web Push (see encryption note below)
- **Achievements** — every unlock with its stable `unlockedAt` timestamp
- **User preferences** — dashboard layout, locale, custom health targets, AI provider selection

### What's not in a backup

A few categories are deliberately excluded so the file stays focused on health data:

- **Sessions, passkeys, API tokens, refresh tokens** — these are device-bound credentials. Restoring an old session is a security regression, not a feature.
- **Audit log** — the audit log lives outside the per-user backup boundary and is preserved across restores so the trail survives.
- **Push subscriptions and Telegram message-deletion queue** — re-registered on the next push / on the next reminder.
- **Idempotency keys, rate-limit counters, integration-status snapshots** — operational state, not user data.
- **App-level settings** — admin-managed via `/admin/general`; not the right thing to round-trip through a per-user backup.

## Encryption

Sensitive fields stay encrypted **inside** the JSON.

The `notificationChannels` block, for example, references the channel by id and carries the user's preference flags, but the credentials (Telegram bot token, ntfy auth header, Web Push endpoint with VAPID) are not embedded in plaintext — they remain in the database under `AES-256-GCM` and the backup carries only the metadata needed to wire them back up. The same goes for AI provider keys, Withings OAuth tokens, and the moodLog webhook secret: they are encrypted at rest with a key (`ENCRYPTION_KEY` or a versioned entry from `ENCRYPTION_KEYS`) that **never** leaves the running container.

That said, **the file still contains your full medical history**. Treat it like a password-manager export: fine on encrypted disk under your control, dangerous if it lands on the wrong USB stick.

## Download a backup

Open `/admin/backups`. Each row in the snapshot table has a **Download** action that returns the snapshot as a `backup-<userId>-<timestamp>.json` file.

The download:

- Streams the snapshot directly from the `DataBackup` row — the file you receive is byte-identical to the one the queue wrote.
- Writes an `admin.backups.download` row to the audit log with the actor, the IP address, and the snapshot id.
- Is rate-limited to defend against scripted exfiltration of every backup at once.

If the download fails (e.g. a corrupted blob, a restore mid-transaction holding the row), the audit log records `admin.backups.download.failed` with the underlying error so the trail stays complete.

## Upload a backup

The **Upload backup** card on `/admin/backups` accepts a `.json` file you previously downloaded (or one you crafted yourself, as long as it matches the schema).

The upload path:

1. **Parses** the JSON against `parseBackupPayload()` — fails with `422` on malformed shape.
2. **Checks `schemaVersion`** against `BACKUP_SCHEMA_VERSION = "1"`. Future-version files are rejected with a clear message instead of being silently accepted.
3. **Caps the size** at 10 MB. Production backups today are roughly 2 MB even for accounts with five years of dense history.
4. **Persists** the snapshot as a new `DataBackup` row, marking it as user-uploaded vs. queue-generated.
5. **Audit-logs** the action under `admin.backups.upload` with the snapshot id and the actor.

Uploading a backup does **not** touch your live data — it only stores the snapshot for later download or restore.

## Restore a backup

Restore is the riskiest operation in the panel: it replaces the live data of the target user (or, in the global flow, every user) with the contents of the snapshot. v1.4.15 puts five independent gates in front of it.

### The five gates

1. **Admin only.** `requireAdmin()` enforces the cookie session is an admin's. Bearer tokens cannot trigger a restore.
2. **Confirm string.** The request body must contain `confirm: "RESTORE"`. A missing or different string returns `422` and a meaningful message.
3. **Typed-string UI gate.** The dialog renders a disabled **Restore** button until you type `RESTORE` into the confirmation field by hand.
4. **Idempotency wrap.** The endpoint is wrapped with `withIdempotency()` so an accidental double-click of the network call replays the original outcome rather than running the deletion twice.
5. **Pre-transaction enum validation.** Every value that maps to a Postgres enum is validated **before** the transaction starts. A malformed payload cannot half-wipe the user — either every model in the restore path applies cleanly, or the transaction rolls back without touching the live data.

### What restore does, in order

Inside a single Postgres transaction:

1. **Wipe the live data** for the user. Same scope as the v1.4.14 admin "wipe all data" action plus mood entries: measurements, medications + schedules + reminder phases, intake events, notification channels (and their preferences), push subscriptions, Telegram-scheduled deletions, Withings connections, integration status snapshots, mood entries, achievements, the user's onboarding / report-practice / target / layout preferences.
2. **Re-insert** every model from the snapshot.
3. **Audit-log** `admin.backups.restore.start` at the top of the operation and `admin.backups.restore` (success) or `admin.backups.restore.failed` (rollback) at the end.

The `AuditLog` table itself is **not** wiped — the audit trail survives every restore so you can see who restored what and when, in perpetuity. Sessions, passkeys, and API tokens are also untouched, so the user stays signed in throughout.

### What if the restore fails mid-way?

The whole operation runs inside `prisma.$transaction(...)`. If any insert fails (a referenced foreign key missing, a value outside its allowed enum), the transaction rolls back and the user's live data is exactly what it was before you clicked **Restore**. The audit log shows the start row and the `.failed` row with the underlying error.

### What restore does not do

- It does **not** re-issue notification credentials. The encrypted payload stays put under the user's existing `ENCRYPTION_KEYS` entries; if you restored across an instance with a different key map, run the channel **Test** buttons after restore.
- It does **not** restore push subscriptions. Devices re-subscribe on next visit when granted permission.
- It does **not** alter the `AppSettings` singleton. Admin-managed config never rides along in a per-user backup.

## Security considerations

A backup file is a complete medical history of one user.

- **Treat it like a password-manager export.** Encrypted disk only; never in a shared cloud-sync folder; never in a chat thread.
- **Encryption at rest is your responsibility once the file leaves HealthLog.** Inside the database the snapshot lives in an encrypted column; once you click **Download**, that protection ends — the file is plain JSON.
- **Off-host S3 backups are encrypted** if you wire up the `BACKUP_S3_*` env block ([Scaling & Operations](/self-hosting/scaling/)). The bucket should additionally enable server-side encryption and have a lifecycle policy for retention.
- **Rotate `ENCRYPTION_KEYS`** if you suspect a backup file was exposed alongside the key — see [Scaling & Operations](/self-hosting/scaling/) for the rotation script.
