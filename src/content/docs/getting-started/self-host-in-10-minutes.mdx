This tutorial takes a fresh host from `git clone` to a running instance with a
working first user. Budget about ten minutes if Docker is already installed,
longer if you also want a TLS-fronted public hostname (see
[Reverse proxy](/guides/reverse-proxy/) for that).

## Requirements

- **Docker 24+ with Compose v2.** The image is multi-arch (`linux/amd64` and
  `linux/arm64`), so an x86 VPS, a NAS or a Raspberry Pi 5 with 4 GB or more
  all work unchanged.
- **Memory: 3 GB of RAM, 4 GB recommended.** The app container is capped by
  `APP_MEMORY_LIMIT`, `1536m` by default, which gives Node a heap of about
  792 MB. 1536 MB is the supported floor. Do not lower it to fit a smaller
  host: below it a long-used account or a large import fills the heap, requests
  stall and the app restarts. The app still starts, but the boot log, the
  support report and **Admin → System status** say it runs below the floor. On
  a busy instance, raise it. Postgres and the system need the rest.
- **Disk: 10 GB free to start.** The database grows with your history. An Apple
  Health import streams the uploaded `export.zip` (up to 1.5 GB) and the
  unpacked `export.xml` through `/tmp` in the container, so keep several
  gigabytes free while it runs. Moving to a new Postgres major needs free space
  about the size of the database (see
  [Moving to Postgres 18](/self-hosting/postgres-upgrade/)).
- **CPU.** Any 64-bit CPU runs the app. On x86-64 CPUs without AVX2
  (Celeron and Atom class NAS CPUs) the document renderer switches itself off:
  no thumbnails, and scanned PDFs are read as text only (`NATIVE_CANVAS` in the
  [environment reference](/reference/environment-variables/)).
- **Outbound HTTPS** to `ghcr.io` for image pulls, plus whichever integration
  endpoints you enable later.
- **Optional but recommended:** a reverse proxy that terminates TLS in front of
  `http://localhost:3000`.

## Walkthrough

<Steps>

1. **Clone the repository.**

   ```bash
   git clone https://github.com/MBombeck/HealthLog.git
   cd HealthLog
   cp .env.example .env
   ```

   `.env.example` is a short starter. Every variable the app reads is described
   in `.env.production.example` and in the
   [environment reference](/reference/environment-variables/). Anything you do
   not set falls back to a sane default or leaves the optional feature off.

2. **Generate the three required secrets.** HealthLog refuses to boot without
   them. Generate with `openssl` and append to `.env`:

   ```bash
   echo "POSTGRES_PASSWORD=$(openssl rand -hex 32)" >> .env
   echo "ENCRYPTION_KEY=$(openssl rand -hex 32)"     >> .env
   echo "API_TOKEN_HMAC_KEY=$(openssl rand -hex 32)" >> .env
   ```

   | Variable | Purpose | Rotation cost |
   | --- | --- | --- |
   | `POSTGRES_PASSWORD` | Bundled Postgres password — used by both the `db` service and the derived `DATABASE_URL` | Database restart |
   | `ENCRYPTION_KEY` | AES-256-GCM key for at-rest secrets (provider tokens, AI keys, VAPID secrets) | Coordinated; see [key rotation](/guides/encryption-key-rotation/). Keep a copy outside the server and confirm it under Admin, Encryption ([why](/explanation/encryption-at-rest/#the-recovery-kit)) |
   | `API_TOKEN_HMAC_KEY` | HMAC-SHA256 key for hashing Bearer API tokens **and web session cookies** before storage | Invalidates every issued `hlk_*` token **and signs out every browser session** |

   There is no connection string to edit: the compose file derives
   `DATABASE_URL` from `POSTGRES_PASSWORD` in its `environment:` block, and
   that block overrides anything in `.env`. To use a PostgreSQL you already
   run instead of the bundled one, see [External PostgreSQL](/self-hosting/external-postgres/).

3. **Bring the stack up.**

   ```bash
   docker compose up -d
   ```

   Compose starts `db` (PostgreSQL 18 with a named volume) and `app` (HealthLog
   on `localhost:3000`). A third, short-lived service, `db-upgrade`, checks for a
   Postgres 16 database from an older install and exits at once on a new one.
   The image runs `prisma migrate deploy`
   on boot, so the schema lands automatically; later restarts no-op when the
   database is already current. The first boot pulls a few hundred megabytes;
   once `docker compose logs -f app` shows the Next.js banner, the instance is
   live.

4. **Decide how you will reach the app, then open it.** If you open the
   instance over plain HTTP on anything other than `localhost` (a NAS IP such
   as `http://192.168.1.20:3000`, a hostname on your LAN, a Tailscale address),
   add this line to `.env` before your first login:

   ```env
   SESSION_COOKIE_SECURE=false
   ```

   Without it the session cookie carries the `Secure` flag, the browser drops
   it over HTTP, and login appears to succeed but the next page load sends you
   back to the sign-in form. This is the single most common self-host snag; the
   compose file says the same in its header comment. Leave the variable unset
   when a TLS reverse proxy serves HTTPS, and never set it to `false` on a host
   that serves plain HTTP to the open internet. Passkeys still need HTTPS or
   `localhost` either way. If you added the line, run `docker compose up -d`
   again so the container picks it up.

5. **Create the first user.** Open `http://localhost:3000` (or the address you
   chose above) in a browser and register a username, email, and password.
   **The first user that registers is promoted to admin automatically.** Every
   subsequent registration creates a regular user.

</Steps>

:::caution[Two first-boot decisions worth making now]
**Close public registration if you expose the instance to the internet.**
Registration stays open after the first admin so you can invite the rest of
your household — but on a publicly reachable host that means strangers can
still sign up. Once everyone has an account, turn it off via the `/admin`
registration toggle, or keep it closed and hand out
[invite links](/guides/invites/) instead. Give every household member their own
account rather than one shared login: if somebody needs to see another person's
readings, that is a [shared-access grant](/guides/shared-access/) between two
accounts, which stays revocable and leaves each person's credentials their own.

**Save the admin password in a manager.** No email is configured out of the
box, so password reset has no self-service path until you set up SMTP (see
[reminder channels](/guides/reminder-channels/#email)). Two recovery paths
exist without it. An admin who can still sign in resets any other user from
the admin panel (**Admin → Users**, backed by
`POST /api/admin/users/{id}/reset-password`), which asks you to confirm it is you, sets a new password and
signs that user out everywhere. A locked-out solo admin runs the reset script
that ships in the image, from the host:

```bash
docker compose exec app node scripts/reset-password.mjs <username-or-email>
```

It prompts for the new password without echoing it (minimum 12 characters)
and writes the same Argon2id hash the app would. See
[Sign in and account security](/guides/sign-in-and-security/) for the full
picture of passwords, passkeys, and second factors.
:::

## The bundled compose file

The compose file ships with the repository, and that copy is the one to run.
The shape below is abbreviated for reading: it leaves out log rotation, the
worker service, the one-time `db-upgrade` service and most of the optional
variables, and the comments in the real
file explain every load-bearing line. Copy it from the repository rather than
from this page.

```yaml
services:
  app:
    image: ghcr.io/mbombeck/healthlog${HEALTHLOG_IMAGE_REF:-:latest}
    pull_policy: always          # load-bearing, see note below
    container_name: healthlog-app
    security_opt:
      - no-new-privileges:true
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: "postgresql://healthlog:${POSTGRES_PASSWORD}@db:5432/healthlog?schema=public&connection_limit=${DB_CONNECTION_LIMIT:-20}&pool_timeout=${DB_POOL_TIMEOUT:-20}"
      NODE_ENV: production
      ENCRYPTION_KEY: "${ENCRYPTION_KEY}"
      API_TOKEN_HMAC_KEY: "${API_TOKEN_HMAC_KEY}"
      NEXT_PUBLIC_APP_URL: "${NEXT_PUBLIC_APP_URL:-http://localhost:3000}"
      APP_URL: "${APP_URL:-http://localhost:3000}"
      HEALTHLOG_PROCESS_TYPE: "${HEALTHLOG_PROCESS_TYPE:-all}"
      SESSION_COOKIE_SECURE: "${SESSION_COOKIE_SECURE:-}"
      # … plus the backup, WHOOP, FHIR, deploy-webhook, and TLS-pin vars
    mem_limit: "${APP_MEMORY_LIMIT:-1536m}"
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:18.6-alpine
    container_name: healthlog-db
    security_opt:
      - no-new-privileges:true
    environment:
      POSTGRES_USER: healthlog
      POSTGRES_PASSWORD: "${POSTGRES_PASSWORD}"
      POSTGRES_DB: healthlog
    volumes:
      - postgres-data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U healthlog"]
      interval: 5s
      timeout: 5s
      retries: 5
    restart: unless-stopped

volumes:
  postgres-data:
```

:::note[`pull_policy: always` is load-bearing]
Without it, Docker keeps a stale `:latest` digest cached on the host and skips
the registry round-trip on `compose up`. With it, compose re-checks the GHCR
digest every time and pulls when a fresher manifest exists. The small bandwidth
cost is the price of digest-correctness.
:::

The compose `environment:` block is a **whitelist**: variables not listed there
never reach the container even when `.env` defines them. This is intentional;
when a guide tells you to set a new variable, it also tells you to add it to the
whitelist. `HEALTHLOG_IMAGE_REF` lets you pin a release instead of `:latest`
(`HEALTHLOG_IMAGE_REF=:v1.46.0` or an `@sha256:…` digest), and
`APP_MEMORY_LIMIT` sets the app container's memory cap (`1536m` by default, the
supported floor; see [Requirements](#requirements)).

Out of the box the server makes three small requests of its own, none carrying
health data: a password breach check when a password is set, an update check
for the version badge, and a location lookup for sign-in addresses. Set
`PASSWORD_BREACH_CHECK_DISABLED`, `UPDATE_CHECK_DISABLED` or
`IP_GEO_LOOKUP_DISABLED` to `1` to switch any of them off;
[Security and privacy](/security/overview/#what-leaves-the-instance) says what
each one sends.

## Updates

A new image can bring database migrations, and the container applies them on
the first start of that image. Most are additive, but some rewrite data, and
going back to the previous image does not undo them. The only way back from a
migration that went wrong is a dump taken before it. So take one before every
pull:

```bash
# 1. Dump the database.
docker compose exec -T db pg_dump -U healthlog healthlog \
  | gzip > healthlog-before-update-$(date +%F).sql.gz

# 2. Pull the new image and recreate the app container.
docker compose pull app
docker compose up -d app

# 3. Confirm the running build.
curl -s http://localhost:3000/api/version
```

Keep the dump until the new version has run for a few days, and keep your
encryption key with it: a dump without the key cannot be read.

The start log counts the migrations before it applies them
(`HealthLog: 2 database migrations pending. Back up the database before
updating ...`), or says `HealthLog: Database schema is up to date.` The line
is a reminder and does not pause the start. The
migration ordering for a host that wants the result before the new container
takes traffic, and rollback are on
[Updates and deploy verification](/guides/updates-and-deploy/). Restoring that
dump is under [Restore a database dump](/guides/backups/#restore-a-database-dump).

## Troubleshooting

The recurring operator problems have their own page,
[Troubleshooting & FAQ](/self-hosting/troubleshooting/). First-boot classics:

- **`app` exits with a Prisma migration error.** The Postgres healthcheck can
  race the migration on slow disks. Run `docker compose restart app` once the
  database has stabilised. Migrations are idempotent.
- **Registration shows "registration disabled".** The bundled image ships with
  registration enabled; the toggle lives in
  `app_settings.singleton.registrationEnabled` and the admin panel can flip it.
- **Login succeeds and immediately bounces back to the sign-in form.** You
  opened the app over plain HTTP on a non-`localhost` address without
  `SESSION_COOKIE_SECURE=false`; see step 4 above.
- **Service unreachable on `localhost:3000`.** Check `docker compose ps`. The
  `app` container shows `health: starting` until its first good probe. That is
  usually within 30 seconds, but a boot that waits on a migration can take
  several minutes, and failed probes do not count for the first ten. Tail
  `docker compose logs app db`.
- **OAuth callbacks loop back to localhost.** Set `APP_URL` and
  `NEXT_PUBLIC_APP_URL` to the public hostname and restart `app`.
