Once you have a running instance and a first (admin) user, these are the things
worth doing before you invite anyone or connect a device.

## Answer the setup questions

The first sign-in lands on `/onboarding`. Since v1.38.18 the first run is a
short set of questions that decide what the record shows first, not a
walkthrough: five questions, a sixth about units when one is needed, a
confirm screen, one first result, and a done screen. It takes about two
minutes, and nothing in it is final.

The welcome screen offers **Set up** and **Skip for now**. Both sit behind the
one-time medical disclaimer, which you acknowledge once per version. **Skip
for now** is a real exit: the account is past the first run, the dashboard
opens with the getting-started checklist, the record keeps the default module
map (the ordinary modules on, MCP and nutrients off), and the questions stay
one click away under Settings.

The questions, in order:

1. **Who is this record for?** Me, someone I look after, or both. The one
   question that cannot be skipped.
2. **What do you want to keep an eye on?** Any number of: blood pressure,
   weight and body, blood glucose, sleep and recovery, mood and mental
   wellbeing, cycle, activity and workouts, lab results, illnesses and
   symptoms.
3. **Do you take medication on a schedule?** Yes, no, or sometimes.
4. **Where do your readings come from today?** Any number of: typed in,
   Apple Health on an iPhone, Withings, Oura, WHOOP, Polar, Fitbit, Strava,
   Nightscout, or a file you already have.
5. **Is there a doctor's visit coming up?** Within a month, later, or no.
6. **Which units do you use?** Asked only when an area needs one (blood
   glucose in mg/dL or mmol/L; weight and height in metric or imperial) and
   the account does not hold that preference yet. An account that already
   holds both is never asked.

Every answer is saved the moment it is given, so leaving and coming back
resumes at the same step, and every question but the first can be skipped. The
counter at the top counts questions only.

### The confirm screen

One look before anything is written. It shows what the answers switch on,
read from the same derivation the server applies, so the list you confirm is
the list that lands; the three modules that are always on (insights,
achievements, the document vault) beside the core readings (weight, blood
pressure, pulse); and the units, language and timezone the account holds.
For your own record it also asks for the baseline the clinical surfaces derive
from: height, date of birth, sex and a display name, each refused underneath
its own field rather than silently dropped.

What the answers switch on:

| Answer | Switches on |
| --- | --- |
| Blood pressure, weight and body | Nothing beyond the core readings; the narrative layer (insights) is always on |
| Blood glucose | Glucose |
| Sleep and recovery | Sleep, recovery |
| Mood and mental wellbeing | Mood, mental-health check-ins |
| Cycle | Cycle tracking |
| Activity and workouts | Workouts |
| Lab results, illnesses and symptoms | Labs, illness |
| Medication: yes or sometimes | Medications |
| A visit within a month or later | Doctor report |
| Someone I look after, or both | Vaccinations |

Everything else gets an explicit off and stays one click away under
**Settings → Modules**. A skipped question counts as its conservative answer
(no medication, no visit). The map is derived once: a module you switched on
by hand, or one whose section already holds rows, is never turned off by a
choice here, and the dashboard order is seeded from the answers only while
you have not arranged one yourself.

Answering **someone I look after** changes what the confirm screen asks for.
Instead of your baseline it shows the managed-profile form, and the profile is
created right there, with your second factor; the module map from the answers
is applied to that new record, and your own is left alone. **Finish without
the profile** is allowed: nothing is derived onto your record either, and a
profile you create later under **Settings → Shared access** starts from the
defaults. See [Records with no login of their own](/guides/managed-profiles/).

### The first result

After confirming, the flow ends on one task, chosen by a fixed priority:

- **Connect a source** the browser can finish on its own (Withings, Oura,
  WHOOP, Polar, Fitbit, Strava, Nightscout), if you named one. Apple Health
  needs the phone and a file is an import, so neither is offered here.
- Otherwise **add the first medication** with a reminder, if you said yes to
  a schedule.
- Otherwise **log one reading** for the first area you picked. Blood pressure,
  weight, glucose, sleep and steps open the measurement form inline; mood,
  cycle, labs and illness have their own page, and the screen waits for you to
  come back and mark the entry done.

The task can be skipped. Whatever the priority passed over goes to the
checklist. If you have years of history elsewhere, do not type it in by hand;
use a device sync or an [Apple Health import](/guides/import-apple-health/)
instead. For **someone I look after** there is no first-result screen: the
flow ends at the confirm screen, and the done screen opens the new record so
the first entry lands in the right place.

### The done screen

The dashboard is one click away, already ordered, with the checklist open.
The short tour is offered, not launched. A guardian is offered the record of
the person they look after (or, after **both**, the button that creates it),
and the AI panel shows a labelled sample briefing with the three ways to turn
insights on; setup works without any of them.

The checklist has six rows for every record (profile, first reading, first
medication, a data source, a notification channel, insights), a **prepare the
visit** row when you said a visit is within a month, and a **create the
profile** row after **someone I look after** or **both**. Once the answers are
confirmed the rows are ordered from them; nothing is removed.

### Coming back to it

Under **Settings → Account → Setup**, **Set up again** asks the questions once
more with your old answers prefilled. It resets the steps and the first result
and keeps the module map: a re-run never switches off a module you turned on
by hand. **Show the checklist again** brings back rows this browser hid; the
dismissals live in the browser, not in the account.

## Tour the admin panel

The first user is an admin. Open `/admin` to find the admin console, split
into sections in this order:

- **System Status** (`/admin/system-status`): database connection, user and
  measurement counts, active sessions and API tokens, host load, and the job
  worker (running or stopped, and when it last ran a reminder pass).
- **General**: the registration toggle, default language, and default timezone
  for new accounts.
- **Services**: the global switches for Telegram, ntfy, and the API. These
  settings are stored encrypted in the database, not in `.env`. See
  [Reminder channels](/guides/reminder-channels/).
- **Integrations**: Umami analytics, GlitchTip error reporting and the Web Push
  VAPID keys, beside the instance-wide settings for the device integrations.
- **Coach**: the assistant surface toggles, an optional shared AI key or
  ChatGPT connection for every user, AI provider health, and the feedback
  quality tables for the Coach and AI Insights.
- **Modules**: which optional modules are available on this instance.
- **Reminders**: reminder dispatch and notification health.
- **Users**: the account list, roles, passkeys, and per-user password reset.
- **Invites**: mint expiring invite links when you close open registration.
  See [Invites](/guides/invites/).
- **API Tokens**: every issued token across accounts.
- **Login Overview**: the sign-in history and audit viewer, with IP addresses
  and, when geo data is configured, locations.
- **App Logs**, **Backups**, **Encryption**, **Danger Zone**, and **About**:
  logs, [off-host backups](/guides/backups/), encryption coverage and
  [key rotation](/guides/encryption-key-rotation/), destructive operations,
  and the version and update check.

`requireAdmin()` is **cookie-only** by construction. A Bearer API token, even
with `["*"]` scope, cannot reach any `/api/admin/*` endpoint: admin is a
browser-session boundary, not a token scope.

## Point the instance at a public hostname

Local-only is fine for a single-user trial. For anything more — and to unlock
OAuth callbacks, webhook deliveries, and Web Push — set the public URL pair
before restarting:

```env
NEXT_PUBLIC_APP_URL="https://your-instance.example.com"
APP_URL="https://your-instance.example.com"
```

Both must match. The server reads `NEXT_PUBLIC_APP_URL` at runtime for OAuth
redirects and the other absolute URLs it emits; `APP_URL` is the mirror used by
background jobs that have no request context. Restart the app container after
editing — the pre-built image picks both values up at startup, no rebuild
needed.

```bash
docker compose up -d
```

Then put TLS in front of it: see [Reverse proxy](/guides/reverse-proxy/) for
copy-paste configs for Caddy, Traefik, Nginx Proxy Manager, Coolify, and bare
Nginx.

:::caution[Plain HTTP and the session cookie]
The session cookie carries the `Secure` flag by default under
`NODE_ENV=production`. On a plain-HTTP origin that is not `localhost`, browsers
silently drop a `Secure` cookie, so login appears to succeed but the next page
load 401s. If you deliberately serve HealthLog over HTTP on a trusted LAN or
Tailscale network, set `SESSION_COOKIE_SECURE=false`. Never do this on a
host that serves plain HTTP to the open internet.
:::

## Build-time feature toggles

A few toggles are `NEXT_PUBLIC_*` variables: the framework inlines them into the
client bundle at **build time**, so the pre-built GHCR image cannot read them at
runtime. Setting them in `.env` or the compose `environment:` block has no
effect — they only take hold when you build your own image, which is why they
are intentionally absent from the compose whitelist.

| Variable | Default | Effect when set |
| --- | --- | --- |
| `NEXT_PUBLIC_DASHBOARD_SNAPSHOT` | on | Hydrates every above-the-fold tile from one `GET /api/dashboard/snapshot` cell so the whole strip shares one completion moment. Build with `=false` to fall back to the legacy four-cell path. |
