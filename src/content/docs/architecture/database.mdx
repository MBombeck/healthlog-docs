HealthLog uses [**PostgreSQL 16**](https://www.postgresql.org/docs/) — a relational database — with [**Prisma 7**](https://www.prisma.io/docs) as its [ORM](https://en.wikipedia.org/wiki/Object%E2%80%93relational_mapping) (the layer that maps database rows to typed TypeScript objects so the application never hand-writes SQL for routine reads and writes). The schema is the single source of truth for every persisted entity — **61 models** in total. The tables below group the most important ones by domain; a handful of internal bookkeeping models (OAuth-state scratch rows, slug caches, rate-limit counters) are omitted for readability. Primary keys are `cuid()`s and columns map to `snake_case` names; the generated client lives at `src/generated/prisma`.

## Users and Auth

| Model | Description |
|---|---|
| `User` | Account with username, email, locale, timezone, admin flag, per-user settings, and the optional patient-identity fields used by the [health-record export](/features/export-import/#health-record-export-pdf--fhir-r4) |
| `Passkey` | [WebAuthn](https://www.w3.org/TR/webauthn-2/) credentials (public key, counter, transports) |
| `Session` | Active server-side session with sliding expiry and user reference |
| `RefreshToken` | Per-device one-time-use refresh token with family reuse-detection |
| `AuthChallenge` | Temporary WebAuthn challenges (registration + login), deleted after use |
| `ConsentReceipt` | Recorded consent for processing health data |

A `User` can have multiple `Passkey`s, `Session`s, and `RefreshToken`s.

### Why sessions live in Postgres

Sessions are stored server-side rather than as stateless JWTs, so there is **no
session secret to leak** and any session can be revoked instantly (a password
change invalidates every session; logging out of one device does not require the
others to expire on their own). Expiry slides on use over a 30-day window.
Refresh-token rotation is per-device, and reuse of a spent token revokes the
whole device family — a stolen token is single-use and self-defeating.

## Health Data

| Model | Description |
|---|---|
| `Measurement` | Individual reading with type, value, unit, timestamp, and source |
| `MoodEntry` | Mood entry with level (1–5), optional comment, and tags |
| `Workout` | Workout session (type, duration, energy, distance) |
| `WorkoutRoute` | GPS route geometry attached to a workout |
| `PersonalRecord` | Best-ever value per metric, surfaced in gamification |

The full **measurement type catalogue** (from weight and blood pressure through
the complete HealthKit mobility and audio-exposure family)
is documented on the [Measurements API page](/api/measurements/#measurement-types).
Measurements always reference a `User` and carry a `source` — one of `MANUAL`,
`WITHINGS`, `WHOOP`, `FITBIT`, `APPLE_HEALTH`, `IMPORT`, or `COMPUTED` (the last
is a server-derived score minted by a nightly engine and never ingested from a
client). Values are stored canonically in
SI — display-unit conversion happens at render time, never in the database (see
[source priority](/concepts/source-priority/) for how overlapping sources resolve).

### Soft-delete tombstones

The two measurement delete routes **soft-delete** (set a `deletedAt` tombstone)
rather than hard-delete. An offline client that synced a row before it was deleted
has no other way to learn the row is gone; the [sync delta feed](/api/sync/)
replays tombstones so a native client can mirror the deletion. Tombstones are
pruned past a retention window keyed to the refresh-token lifetime.

## Medications

| Model | Description |
|---|---|
| `Medication` | Medication with name, dosage, route of administration, and status |
| `MedicationSchedule` | Times of day plus a recurrence rule (`rrule` / `rollingIntervalDays` / `intervalWeeks` / `scheduleType` for PRN and cyclic) — see [Medications](/features/medications/#schedules) |
| `MedicationIntakeEvent` | Individual intake (taken/skipped) with timestamp and source |
| `MedicationDoseChange` | Audit trail of dose adjustments over time |
| `MedicationSideEffect` | Logged side effect entries |
| `MedicationInventoryItem` | On-hand stock per medication |
| `MedicationInventoryEvent` | Inventory movements (refill, consumption) |
| `ReminderPhaseConfig` | Phase-based reminder escalation (GREEN, YELLOW, ORANGE, RED) |
| `TelegramReminderMessage` | Sent Telegram messages, tracked for later cleanup |
| `TelegramScheduledDeletion` | Scheduled deletion of Telegram messages |
| `MoodReminderDispatch` | Sent mood-reminder records (dedupe + cleanup) |

A `Medication` has any number of `MedicationSchedule`s (e.g. morning and evening)
and `MedicationIntakeEvent`s. The recurrence engine — not the database — owns
schedule projection; the schema only stores the rule. `ReminderPhaseConfig`
defines per-medication escalation thresholds for the four reminder phases.

## Tokens

| Model | Description |
|---|---|
| `ApiToken` | External API access. The token value is stored as a **keyed HMAC-SHA-256 hash** (using the `API_TOKEN_HMAC_KEY` env var) — the plaintext is not retrievable after creation, and a DB dump alone does not let an attacker precompute matching hashes. |
| `IdempotencyKey` | User-scoped idempotency cache so a retried mutation is not applied twice |

## Rollups (pre-aggregation)

Charts and analytics rarely need every raw row, so HealthLog keeps four **rollup
tables** — `MeasurementRollup`, `MoodEntryRollup`, and
`MedicationComplianceRollup` — holding pre-aggregated `DAY` / `WEEK` / `MONTH` /
`YEAR` buckets (count, min, max, mean, sum). A read tries the rollup first and
falls back to live SQL only when the rollup does not yet cover the requested
window, so the dashboard and `/insights` answer in milliseconds instead of
walking hundreds of thousands of rows. New accounts are backfilled by a boot-time
job; ongoing writes keep the buckets current. This is why a long history loads as
fast as a short one — see [background jobs](/architecture/background-jobs/) for
the maintenance schedule.

## Encryption at rest

Sensitive columns are stored encrypted with
[AES-256-GCM](https://en.wikipedia.org/wiki/Galois/Counter_Mode) — an
authenticated cipher, so a tampered ciphertext fails to decrypt rather than
returning garbage. The encryption layer is **fail-closed**: a missing key,
malformed payload, or unknown key id throws rather than silently writing or
reading plaintext, which guarantees a misconfigured instance never quietly
downgrades your data to cleartext.

Encrypted columns include:

- `User.aiOpenaiKeyEncrypted`, `User.aiAnthropicKeyEncrypted`,
  `User.aiLocalKeyEncrypted` (per-user BYOK AI keys)
- `User.codexAccessTokenEncrypted`, `User.codexRefreshTokenEncrypted`
- `User.telegramBotToken`
- `User.withingsClientIdEncrypted`, `User.withingsClientSecretEncrypted`
- `User.moodLogUrlEncrypted`, `User.moodLogApiKeyEncrypted`
- `User.insuranceNumberEncrypted` (patient-identity field for the FHIR export)
- `WithingsConnection.accessToken`, `WithingsConnection.refreshToken`
- `AppSettings.webPushVapidPrivateKeyEncrypted`,
  `AppSettings.githubIssueTokenEncrypted`, `AppSettings.adminAiKeyEncrypted`
- `NotificationChannel.config` (channel-specific secrets)
- `IntegrationStatus.lastError` (may contain token-fragment metadata)
- `CoachMessage.encryptedContent` (the chat body, stored as `Bytes`)

The active key is supplied as `ENCRYPTION_KEYS` (a `{ "v1": "<hex>", ... }` map)
plus `ENCRYPTION_ACTIVE_KEY_ID`; the legacy single `ENCRYPTION_KEY` env var is
still accepted as `v1`. Keys are versioned so a key can be rotated without
re-encrypting everything at once — keep the old key in the map until the
[rotation script](/configuration/environment-variables/) reports zero remaining
rows on it.
