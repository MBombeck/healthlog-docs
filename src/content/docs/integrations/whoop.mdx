HealthLog connects to a WHOOP strap over [OAuth 2.0](https://datatracker.ietf.org/doc/html/rfc6749). Like every other device connection you bring your own developer app: the WHOOP **Client ID** and **Client Secret** are pasted into Settings (or set as server env vars) and stored AES-256-GCM-encrypted at rest. HealthLog never ships a shared credential, so each instance's data stays under its own WHOOP application.

Once linked, the strap's recovery, sleep, workout and cycle data flow in on a schedule, and — importantly — a WHOOP-native **recovery** percentage becomes the canonical recovery value everywhere HealthLog shows recovery. See [Recovery and readiness](/methodology/recovery/) for why the device's own number wins over the computed proxy.

## What gets synced

The WHOOP client (`src/lib/whoop/client.ts`) maps four collections into HealthLog, each with its own sync cursor so a slow or rejecting collection never holds the others back:

- **Recovery** — the WHOOP recovery percentage, HRV and resting heart rate for the night.
- **Sleep** — per-stage sleep sessions (deep, core/light, REM, awake), efficiency and time in bed.
- **Workouts** — strain-scored exercise sessions.
- **Cycles** — the WHOOP physiological day, carrying day strain.

Imported rows are tagged `source = WHOOP` and pass through the same [source-priority](/concepts/source-priority/) resolver as every other provider.

## OAuth scopes

HealthLog requests the read scopes that cover every collection above, plus `offline` so the connection can refresh without a fresh login:

```
offline read:recovery read:sleep read:workout read:cycles read:profile read:body_measurement
```

`offline` is required — without it WHOOP issues only a short-lived access token and the connection breaks the next day. The remaining scopes are all read-only; HealthLog never writes back to WHOOP.

## 1. Register a WHOOP developer app

1. Sign in at the [WHOOP Developer Dashboard](https://developer.whoop.com/) and **create a new application**.
2. **Redirect URI:** `https://your-instance.example.com/api/whoop/callback`. It must match exactly — scheme, host and the `/api/whoop/callback` path.
3. **Scopes:** select every scope listed above. The user grants once and every sync resource is covered.
4. Save. WHOOP issues a **Client ID** and **Client Secret** — keep the secret out of any chat log.

## 2. Wire the credentials into HealthLog

WHOOP credentials are **per-user bring-your-own-keys**: paste the Client ID and Client Secret under **Settings → Integrations → WHOOP**, where they are stored AES-256-GCM-encrypted on your user record. There is no instance-wide `WHOOP_CLIENT_ID` env var.

Two optional server env vars tune the connection:

```env
# Optional — derived from NEXT_PUBLIC_APP_URL when unset.
WHOOP_REDIRECT_URI="https://your-instance.example.com/api/whoop/callback"
# Optional — hardens the webhook HMAC body-signature check.
WHOOP_WEBHOOK_SECRET="$(openssl rand -hex 32)"
```

Credentials are trimmed on save, so a stray space copied from the portal's copy button does not read as an unknown client. Restart the `app` container after changing an env var.

## 3. Connect from Settings

1. Sign in as the target user and open **Settings → Integrations → WHOOP**.
2. Click **Connect WHOOP** and grant the requested scopes on WHOOP.
3. WHOOP redirects back to `/api/whoop/callback`; HealthLog exchanges the code for a refresh token, stores it encrypted, and runs an initial sync.

Subsequent syncs run on a schedule and on WHOOP change notifications. A full sync can backfill deep history that an incremental tick skips.

## Native recovery authority

When a WHOOP-native recovery score exists for a night, it is the single canonical recovery value on the tile, the chart, the doctor-report, the exports, the coach and the companion app. The server-computed recovery proxy is the fallback only when no native score is present, so a WHOOP user never sees the proxy and the native number competing as two series. The resolver also pins each recovery to the right wake-day so one night reads as exactly one recovery. Full detail in [Recovery and readiness](/methodology/recovery/).

## Troubleshooting

### The connection breaks the next day

The `offline` scope is missing. Re-register the app with `offline` included, re-save the credentials, and reconnect from Settings.

### Recovery shows the proxy, not the WHOOP number

A native recovery row had not yet synced for that night. WHOOP stamps recovery at the morning instant; once the night's recovery lands it takes over the day. A full sync backfills nights an incremental tick missed.

### A workout that synced late went missing

Workout ingest shares the wider overlap window that recovery and sleep use, so a phone that reaches the WHOOP cloud more than an hour after a session is not dropped. The idempotent upsert keeps the widening from duplicating anything.
