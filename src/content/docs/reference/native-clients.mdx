The web PWA uses cookie sessions; native clients (the HealthLog iOS app, n8n, Health Connect bridges, custom shortcuts) authenticate with [bearer tokens](https://datatracker.ietf.org/doc/html/rfc6750) — an opaque credential sent in the `Authorization: Bearer …` header that the server resolves to a user on every request. Both flows share the same handlers, so every protected route accepts either credential.

A Bearer client acts on its owner's own record unless it names another one it holds a [shared-access grant](/guides/shared-access/) on, with an `X-HealthLog-Account: <accountId>` header on each request. Bearer traffic is never fenced, and a token cannot offer a manage grant or change a managed profile, because both need a fresh second factor in a browser; send the person there with copy that says why. The wire rules, including the levels `GET /api/auth/me` reports, are under [Shared access](/reference/api-endpoints/#shared-access).

## Token Issuance

`POST /api/auth/login` and `POST /api/auth/passkey/login-verify` return a bearer token in the response body when the request opts in as a native client.

A request opts in by sending **either**:

- `X-Client-Type: native` header, **or**
- a `User-Agent` starting with `HealthLog-iOS`

Automation (n8n, a Health Connect bridge, a shortcut) sends the `X-Client-Type: native` header; no other `User-Agent` counts. Without one of those signals you get only the session cookie, as a browser does.

When the account has a second factor, sign-in answers `meta.mfaRequired` with an opaque `mfaTicket` instead of tokens. Complete it at `POST /api/auth/mfa/verify` (a TOTP or recovery code) or `POST /api/auth/mfa/webauthn/verify` (a security key, with options from `/api/auth/mfa/webauthn/verify/options`); the answer is the same native bundle.

### Sign-in through the web page

The app can also sign in on the instance's own web login page, which gives a self-hosted domain working password autofill and passkeys. It opens `GET /api/auth/native/login?code_challenge=<S256>` in a system browser sheet; after the person signs in there, the browser returns to `healthlog://login-callback` with a one-time `code`, and the app exchanges it with its PKCE `codeVerifier` at `POST /api/auth/native/token` for the standard native bundle. Only a session created inside that sheet can complete the flow, and the tokens never ride a URL.

### Single sign-on

An instance with OIDC configured offers a third route to the same bundle. The
app opens `GET /api/auth/oidc/login?client=native&code_challenge=<S256>` in a
system browser sheet; the callback returns to the compiled-in scheme
`healthlog://oidc-callback` with a one-time handoff code (or an `mfa_ticket`
when the account carries a second factor), and the app exchanges that code at
`POST /api/auth/oidc/native/token` for the standard native bundle. The
`redirect_uri` is a compile-time constant rather than a parameter, and the
token pair never rides a URL; only the opaque code does. An instance running
`OIDC_ONLY=true` offers this flow alone.

### Response shape (native)

```json
{
  "data": {
    "user": { "id": "clx...", "username": "alice" },
    "token": "hlk_a1b2c3d4...",
    "tokenExpiresAt": "2026-05-10T07:15:00Z",
    "refreshToken": "hlr_z9y8x7w6...",
    "refreshTokenExpiresAt": "2026-07-08T07:15:00Z"
  }
}
```

The raw `hlk_<64-hex>` and `hlr_<64-hex>` values are returned **exactly once**. Default access-token lifetime is 24 hours; refresh tokens rotate.

## Refresh-Token Rotation

Access tokens are short-lived; a long-lived **refresh token** mints new ones without re-prompting for credentials. HealthLog uses [rotating refresh tokens](https://datatracker.ietf.org/doc/html/rfc6749#section-10.4) — each refresh consumes the old token and issues a fresh one, so a leaked token is single-use.

`POST /api/auth/refresh` exchanges a refresh token for a fresh access + refresh pair.

```bash
curl -s -X POST https://your-instance.example.com/api/auth/refresh \
  -H "Content-Type: application/json" \
  -d '{"refreshToken": "hlr_z9y8x7w6..."}'
```

**Reuse-detection**: presenting the same refresh token a second time revokes every refresh token for that device. Only a token issued before per-device families existed, or one presented with a device id that does not match the stored row, escalates to a user-wide revoke. The affected device gets a forced re-login; the attacker holding a stolen token is now locked out. Send `revoke: true` on a normal logout to mark both the refresh row and its paired access token as revoked.

A stable `errorCode` on the refresh response lets a client tell a **revoked family** (the device must re-authenticate) apart from a **transient failure** (retry is safe), so the app doesn't bounce a user to login on a network blip; the codes are listed in [the sync contract](/reference/sync/#authentication-and-token-lifetimes). Every code the server can answer with is enumerated in the `ErrorEnvelope` description of the OpenAPI document; generate the client's enum from there rather than from the codes a test run happened to trigger.

## Sync, idempotency and rate limits

A native client keeps its local copy current through the delta feed in the [offline sync contract](/reference/sync/): domains, identity keys, the opaque cursor, tombstones and conflict rules are there. Retries are made safe by the `Idempotency-Key` header, and a `429` says how long to wait; both are described once, in [Idempotency](/reference/api-overview/#idempotency) and [Rate limits](/reference/api-overview/#rate-limits). In short: one key per write, and an offline queue that meets `record_write.rate_limited` drains slower instead of retrying the same request.

## Background document reads

`POST /api/documents/inbound/{id}/index`, `/summary`, `/suggest`
and `/extract` accept a `Prefer: respond-async` header. With it they answer
`202` with `{ runId, status: "QUEUED", pollAfterMs }`, a `Location` header
pointing at `/api/ai-runs/{id}` and `Preference-Applied: respond-async`.
`GET /api/ai-runs/{id}` returns the run's status (`QUEUED`, `RUNNING`,
`SUCCEEDED`, `FAILED`), on success the `result` the synchronous route would
have answered with, and on failure an `error` with the code and status it would
have answered with, so one error table covers both paths. It may carry
`Retry-After`. A finished run is readable for an hour; after that, like another
account's run, it is a `404` `aiRuns.notFound`. Codes only a run produces are
`aiRuns.workerUnavailable`, `aiRuns.timedOut` and `aiRuns.failed`.

Without the header the four routes answer synchronously.
`POST /api/labs/ocr/extract` always answers `202` with a run id.

## When the server cannot open its data

A server whose encryption key does not match its data answers
`503` with `meta.errorCode` `encryption.key_mismatch` on every route except
`/api/health` and `/api/version`. Show it as a server configuration problem the
operator has to fix, not as offline, and do not retry in a loop. See
[the start-up key check](/explanation/encryption-at-rest/#the-start-up-key-check).

## Device Registration

Native clients register their push-notification handle through `POST /api/devices`.

```bash
curl -X POST https://your-instance.example.com/api/devices \
  -H "Authorization: Bearer hlk_..." \
  -H "Content-Type: application/json" \
  -d '{"platform": "ios", "token": "<APNs-token>"}'
```

If the same APNs / FCM token is already registered to a **different** account, the request is rejected with `409 Conflict` instead of silently transferring ownership. APNs / FCM tokens aren't a secret, so trusting wire input would let anyone who learns a token redirect another user's pushes. The denial is audit-logged.

## Token Storage (Server-Side)

Bearer tokens are stored as **[HMAC](https://en.wikipedia.org/wiki/HMAC)-SHA-256** hashes (keyed by `API_TOKEN_HMAC_KEY`), not plain SHA-256. An HMAC is a keyed hash: without the secret key an attacker who exfiltrates the database cannot precompute the hash of a guessed token, which defeats rainbow-table lookups. The same mechanism is reused for [ingest token](/guides/ingest-token/) verification. Web session cookies use the same storage shape: a random secret in the cookie, only its HMAC in the database.

:::tip[Long-lived tokens are minted per medication]
For long-running automation (n8n, Home Assistant, Health Connect bridges) that logs a medication intake, mint the token from **that medication's own external-integration row** on `/medications` rather than the 24-hour access tokens — same auth header, no refresh dance. The token is scoped to intake for that medication, and every route that does not declare that scope refuses it.

**Settings → API & tokens** has no generic token button; it lists and revokes the tokens the account holds and mints the narrow [measurement, document and workout tokens](/guides/ingest-token/).
:::
