HealthLog exposes a read-only **HL7 FHIR R4** REST API so a clinician system can
pull your record in a standard shape. The routes name a dedicated `fhir:read`
[Bearer token scope](/reference/api-overview/#authentication); see the note
below on which credentials reach them in practice.

## What FHIR is

FHIR (Fast Healthcare Interoperability Resources) is HL7's healthcare-data
interoperability standard. Release 4 (**R4**) is the principal production and
regulatory reference version. It models health data as modular **resources** —
`Patient`, `Observation`, `MedicationStatement`, and so on — each addressable
over a RESTful HTTP endpoint, exchanged as JSON. The pull-based, resource-oriented
design is what lets a third-party EHR request exactly the slice it needs. For
background, see the [FHIR R4 specification](https://hl7.org/fhir/R4/).

HealthLog implements the read side of this contract for the resources it can
populate from your own data.

:::caution[The doctor-report module gates these endpoints]
Since v1.30.19 the FHIR endpoints honour the **doctor-report module switch**
under **Settings → Modules**. With the module off they return `403` rather than
the record. Before that release the switch was ignored here: the export still
returned the full record, the sync feed still sent cycle data, and the dashboard
summary still built glucose and sleep cards regardless. v1.30.23 extended the
same rule to connected assistants over [MCP](/reference/mcp/) and to a shared
clinician link, both of which could previously read a module's data — including
the full doctor summary — with the module off.

**Nothing is deleted by a switch.** Turning a module back on finds the history
complete. A native client pointed at a server where the module is off will see
the `403`; that is the switch working, not a fault.
:::

## Endpoints

The routes check the `fhir:read` scope, but no user-facing mint produces a
token scoped to it — every mint grants a wildcard or an unrelated narrow scope.
In practice the endpoints are reached with a cookie session or a wildcard
Bearer token; the capabilities endpoint reports this as `scopeMintable: false`.

| Method | Endpoint | Returns |
| --- | --- | --- |
| `GET` | `/api/fhir/metadata` | FHIR `CapabilityStatement` |
| `GET` | `/api/fhir/Patient` | The token user's `Patient` resource |
| `GET` | `/api/fhir/Observation` | Vitals + labs as LOINC-coded observations |
| `GET` | `/api/fhir/MedicationStatement` | The medication regimen |
| `GET` | `/api/fhir/MedicationAdministration` | Logged intake events |
| `GET` | `/api/fhir/Coverage` | Insurance coverage |
| `GET` | `/api/fhir/Patient/$everything` | A `Bundle` of every resource above |

Each resource also supports read-by-id (`/api/fhir/<Resource>/{id}`).

`MedicationAdministration` rows in `$everything` are bounded by
`FHIR_MAX_MEDICATION_ADMINISTRATIONS` (default 5000) as a coarse ceiling on the
serialised Bundle size.

## Health-record export

`POST /api/export/health-record` produces a **selectable** export: an enriched
clinical PDF, a machine-readable FHIR R4 document Bundle (LOINC-coded
observations, a BP panel, medication statements, a diagnostic report), or both
packaged as one zip. The selection chooses date range and per-domain sections.
Both formats read the same aggregator, so they describe identical numbers.

Optional patient identity (name, insurer, insurance number) on the account feeds
the report cover and the FHIR `Patient`. An optional AI summary is an explicit
opt-in section, marked as not clinically validated.

## Shareable clinician record

Separately from the FHIR API, a **share link** gives a clinician a scoped,
time-limited, read-only `/c/<token>` view that you revoke after the visit
(`GET` / `POST` / `DELETE /api/share-links`). The share surface publishes
`reportDownload: ["fhir", "pdf"]` in `/api/meta/capabilities`: a
machine-readable FHIR bundle (and a PDF) of exactly the link's frozen selection
is downloadable under the share token, behind the same unlock the page uses.
`/api/fhir/*` itself still refuses a share token. Each surface stands on its
own.

A third way somebody else reads your data is a
[shared-access grant](/guides/shared-access/) to another account on the instance,
and it stands on its own too. A delegate reading your record reaches neither the
FHIR API, nor the export, nor the share-link surface. Those are refused under a
grant rather than hidden, because an export is a copy of everything and a link is
a door that would survive the delegate's own revocation.

:::caution[Read-only and not a clinical record system]
The FHIR API and the export describe your tracked data in a standard shape. They
are for sharing with a clinician, not for use as a system of record or for any
automated clinical decision. The optional AI summary is explicitly not clinically
validated.
:::
