HealthLog exposes a REST API over JSON. Every route, field and error code is
in the generated **OpenAPI 3.1** document; [API endpoints](/reference/api-endpoints/#the-openapi-spec)
links the copy that matches your server's version, says what each kind of
token reaches and maps the endpoint groups to their guides. This page holds the
conventions every route follows.

## Base URL

```
https://your-instance.example.com/api
```

## Authentication

Two methods, with a hard structural boundary between them:

| Method | Used by | Carried as |
| --- | --- | --- |
| **Session cookie** | Browser clients | `__Host-healthlog_session` cookie over HTTPS, `healthlog_session` on plain HTTP (automatic) |
| **Bearer token** | External / native API clients | `Authorization: Bearer hlk_...` |

- **Session cookies** are Postgres-backed with a sliding 30-day expiry,
  HttpOnly + SameSite. The cookie path can elevate to admin via
  `requireAdmin()`. The cookie carries a random 32-byte secret (`hls_<hex>`)
  and only its HMAC-SHA256 hash is stored, so the value in the browser exists
  nowhere on the server.
- **Bearer tokens** are HMAC-SHA256-hashed under `API_TOKEN_HMAC_KEY` before
  storage — there is no plaintext path, and the raw `hlk_<hex>` value is shown
  exactly once at creation. Tokens are scoped. The scopes in use are
  `fhir:read` for the [FHIR API](/reference/fhir-api/), `health:read` and
  `health:write` for the [MCP connector](/guides/mcp-server/),
  `medication:ingest` for one medication's own intake endpoint,
  `measurements:write` for
  [pushing readings from your own hardware](/guides/ingest-token/),
  `documents:write` for [importing documents](/guides/import-documents/), and
  `workouts:write` for [pushing workouts](/guides/ingest-token/#push-workouts).
  No mint produces `fhir:read` yet. Only sign-in (password, passkey and the
  native sign-in handoffs) and refresh mint a wildcard (`["*"]`) token; every
  user-facing mint endpoint hardcodes one narrow scope. The measurement-token,
  document-token and workout-token mints additionally accept the session cookie
  only, so no API token, wildcard included, can mint one.

:::caution[Bearer scope is fail-closed]
A route accepts a narrow-scope token only if it **names** the scope it accepts.
`requireAuth()` with no argument admits a cookie session or a wildcard token
only; a narrow token is refused with `403` (`auth.scope.insufficient`) and an
audit row. Adding a route therefore never widens what an existing token reaches.
:::

:::caution[Admin is cookie-only]
`requireAdmin()` is a cookie-only boundary. A Bearer token — even with `["*"]`
scope — cannot reach any `/api/admin/*` endpoint. This is structural, not a
runtime check future code can soften.
:::

`userId` is never a request-body field. It is always narrowed from the session
or the Bearer token and feeds the Prisma `where` clause directly.

:::note[Acting on a shared record]
A caller that holds a [shared-access grant](/guides/shared-access/) can act on
another account's record, on the routes that declare it. The owner's id then
goes into the `where` clause in place of the caller's. It never comes from the
request body: the caller names the account, and a live grant is checked on
every request. Any other route refuses with `403` rather than falling back to
the caller's own record.
The wire rules are in [Shared access](/reference/api-endpoints/#shared-access),
the model in [What a shared record is](/explanation/record-sharing/).
:::

## Response envelope

Every response is `{ data, error }`, with an optional top-level `meta`:

```json
{ "data": { "...": "..." }, "error": null }
```

On error:

```json
{ "data": null, "error": "Validation failed: password must be at least 12 characters" }
```

On an error, `meta` carries `errorCode`, `requestId` and whatever detail the
code needs. On a success it appears only on a list the server cuts at a
ceiling:

```json
{ "data": ["..."], "error": null, "meta": { "truncated": true, "limit": 100 } }
```

`truncated` is exact: it is true only when a row past `limit` exists. `data`
keeps the shape the route always had, so a client that ignores `meta` still
decodes it, but it must not treat the last row as the oldest one there is.
Such lists take `limit` (each route has its own default and ceiling, in the
spec) and, where the route pages, `offset`. Some older reads instead nest a
pagination block inside `data`:

```json
{
  "data": {
    "measurements": ["..."],
    "meta": { "total": 142, "limit": 20, "offset": 0 }
  },
  "error": null
}
```

Validation failures (422) return all Zod issues in a multi-issue envelope,
sanitised against the echoed input.

## Resolved on the server

Where an answer depends on rules, the server publishes the resolved value and
clients render it rather than working it out again, so the web app and the
native app cannot disagree. Examples: the `ai` block on `GET /api/auth/me`
(whether each AI feature is available, and why not); `courseStatus` and
`intakeActionable` on the medication reads (where today sits in the course, and
whether taken and skip are offered); the trend verdicts on the series and the
dashboard; `appleHealthMirror` on measurement rows; and `cursorExpired` on
`GET /api/sync/changes` (the client's position no longer holds). The OpenAPI
document describes each field.

Text the server writes for a person is written in that person's units: the
health score's labels, the Coach's tables of values and the metric status texts
follow the reader's glucose unit and metric or imperial preference, so a client
shows them as they come rather than converting them.

## Idempotency

Idempotency is opt-in per route, not a property of the method. A route that
declares it accepts an `Idempotency-Key` header of 8 to 128 characters from
`A-Za-z0-9_-:.`, and the OpenAPI document names the header on every route that
honours it. The first request runs and the response is cached; a replay with
the same key returns the cached response with `X-Idempotent-Replay: true`
instead of re-running the mutation.

A key replays only the **same request** within 24 hours: the cache stores a
SHA-256 fingerprint of the method, the path and the body (JSON compared with
its keys sorted, a multipart boundary ignored). A different body under the same
key is executed and saved, not answered with the first one's response. Use
**one key per write**: two halves of one reading sent as two requests need two
keys.

- Keys are **user-scoped** — a composite unique index by
  `userId_key_method_path` means a client cannot replay another user's key.
- `401`, `403`, `408`, `429` and every `5xx` are not cached, so a retry runs
  again. A `422` is cached, so a broken retry does not reach the database
  twice.
- The cache refuses to persist a response body containing secret-shaped patterns
  (`hlk_`, `hlr_`, `sk-`) even if a future caller wraps an auth endpoint by
  mistake.
- A second request arriving while the first is still in flight gets
  `A request with this Idempotency-Key is already in progress`.

This is what makes the native client's retries safe over flaky mobile networks.

## Rate limits

Limits live in Postgres (one atomic upsert per check), so they hold across
several app instances. Authenticated buckets are keyed on the acting account,
anonymous ones on the client IP as the trusted proxy reports it (see
[`TRUST_PROXY_HOPS`](/guides/reverse-proxy/)).

| Surface | Limit | Per |
| --- | --- | --- |
| `POST /api/auth/login` | 5 in 15 minutes | client IP |
| `POST /api/auth/refresh` | 10 in 15 minutes | client IP |
| Every other authenticated write (`POST`, `PUT`, `PATCH`, `DELETE`) | 300 a minute, shared | acting account |
| `POST /api/measurements/batch`, `/api/mood-entries/bulk`, `/api/medications/intake/bulk`, `/api/nutrients/batch`, `/api/cycle/day-logs/bulk` | 60 a minute each | account |
| `POST /api/workouts/batch` | 60 a minute; `workouts:write` tokens share a second 60 | account |
| `POST /api/insights/ecg` | 600 a minute | account |
| `GET /api/sync/changes` | 120 a minute | account |
| The Coach stream (`POST /api/insights/chat`) | 20 messages a minute | account |
| `POST /api/search` | 20 a minute | account |
| `POST /api/ingest/medication` | 60 a minute | token |
| `POST /api/documents/inbound` | 60 an hour; 120 an hour per `documents:write` token (`DOCUMENT_UPLOAD_LIMIT_PER_HOUR`) | account or token |
| Full backup and health-record export | 10 an hour, shared | account |
| `/api/fhir/*` | 120 an hour | account |
| `/mcp` | 120 a minute; writes 60 in 5 minutes | connector token |

The shared write bucket covers every write that is not in a row of its own. It
is charged after authentication and before the body is read, so a client
looping on a `422` spends its allowance too. A delegate spends their own
allowance and cannot collect a fresh one by switching records. If the bucket
cannot be read, the write goes ahead: the bucket stops runaway loops, it does
not decide who may write. Its `429` carries `meta.errorCode:
record_write.rate_limited`, which is how a client tells it from a route's own.

A `429` from one of these buckets on an `/api` route carries four headers:

| Header | Meaning |
| --- | --- |
| `Retry-After` | Whole seconds to wait. Rounded up, never below 1 |
| `X-RateLimit-Limit` | Requests the bucket allows per window |
| `X-RateLimit-Remaining` | Requests left in the current window, `0` on a refusal |
| `X-RateLimit-Reset` | ISO-8601 instant the window rolls over, not epoch seconds |

Back off on `Retry-After` rather than guessing; an offline queue should drain
slower rather than retry the one request. A `429` without these headers did not
come from a bucket: a daily AI budget and a provider's own refusal relayed
onward both look like that, and there is no window to wait out.

## HTTP status codes

| Code | Meaning |
| --- | --- |
| `200` | Success |
| `201` | Resource created |
| `202` | Accepted (async job queued) |
| `204` | Success, no body |
| `400` | Bad request, including a body that is not parseable JSON. `meta.errorCode` is `<surface>.body.invalid_json` on the routes that name it |
| `401` | Not authenticated |
| `403` | Forbidden |
| `404` | Not found |
| `405` | Method not allowed |
| `409` | Conflict, for example a duplicate or a stale shared-record session |
| `410` | The route was retired; see below |
| `413` | Payload too large (per-route body cap) |
| `422` | The body parsed but failed the schema; `details.issues` names every field. One route, `PUT /api/auth/me/health-score-config`, answers a non-JSON body with 422 too, because its published contract promised that |
| `429` | Rate limit exceeded |
| `500` | Internal error |
| `503` | Unavailable, for example `encryption.key_mismatch` or `auth.session.unavailable` |

## Error codes

Every error envelope carries `meta.requestId` (the same value as the
`x-request-id` header; the operator finds the event by it) and
`meta.errorCode`. A route that names no code of its own gets the generic one
for its status, such as `http.not_found` or `http.rate_limited`. Every code the
server emits is enumerated, grouped by surface, in the `ErrorEnvelope`
description of the [OpenAPI document](/reference/api-endpoints/#the-openapi-spec).
The list cannot drift from the server: a code the server can emit is in it, and
a code no longer emitted leaves it. Four spellings coexist (`dot.case`, bare
`snake_case`, a `camelCase` segment, a hyphen) and none is renamed, because a
shipped client branches on the value. Two families are deliberately outside the
list: `assistant.disabled.<surface>` is built from a template, and the
integration probes' classes (`credentials_rejected`, `rate_limited`,
`upstream_error`, `timeout`, `connection_failed`) are enumerated on each `/test`
operation instead.

The generic auth gates, the ones every route passes through before its own body
runs, are the codes every client meets first. Branch on the field: the English
sentence beside it may be reworded or localised at any time.

| Code | Status | Means |
| --- | --- | --- |
| `auth.missing` | `401` | No session cookie and no Bearer header. Send the user to sign in |
| `auth.token.expired` | `401` | The Bearer token's lifetime has passed. Refresh and retry |
| `auth.token.invalid` | `401` | Unknown, revoked, or the owning account is gone. Discard the credential; retrying will not help |
| `auth.mfa.code_invalid` | `401` | A second factor presented on a step-up flow did not verify. Re-prompt for a code and keep the session |
| `auth.stepup.required` | `401` | The route needs a fresh factor. Re-prove and retry |
| `auth.reproof.required` | `401` | The route needs a recent sign-in or confirmation. `meta.methods` lists what the account can use; confirm at `POST /api/auth/reproof` and retry |
| `auth.reproof.too_weak` | `422` | The method offered at `POST /api/auth/reproof` does not count for this account (a password on an account with a second factor) |
| `auth.reproof.failed` | `401` | The confirmation did not verify. Re-prompt; attempts share the step-up budget |
| `auth.scope.insufficient` | `403` | The credential is valid but its scope does not reach this route, which includes any Bearer token against an admin surface |
| `auth.admin.required` | `403` | A cookie session that is not an admin's |

Further codes can meet a client before any route body runs. A server whose
encryption key cannot open its data answers every route except
`/api/health` and `/api/version` with `503` `encryption.key_mismatch`; show it
as a server configuration problem, not as offline. And the browser sign-in
routes refuse with `409` `auth.session.insecure_transport` when the web client
reports a plain `http://` page while the server sets `Secure` cookies. A
session that could not be checked because the session store was unreachable
answers `503` `auth.session.unavailable`: keep the credential and retry.

A route that checks a credential of its own, meaning sign-in, the MFA challenge
exchange or a password confirmation, answers `401` with the generic
`http.unauthenticated`: the route refused the credential it was handed.

## Retired and deprecated routes

A route that was published and then removed answers every method with `410`
and `meta.errorCode: route.retired`, plus `meta.removedIn` (the release) and
`meta.replacedBy` (the path to use instead, or `null`). Stop calling it; a
retry will not help. A deprecated route still answers, and says so with a
`Deprecation` header, a `Sunset` header with the first date it may stop
answering, and a `Link` to its successor. The OpenAPI document marks both
kinds.
