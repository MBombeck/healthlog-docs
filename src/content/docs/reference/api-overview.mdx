HealthLog exposes a REST API over JSON. The machine-readable **OpenAPI 3.1**
contract lives at
[`docs/api/openapi.yaml`](https://github.com/MBombeck/HealthLog/blob/main/docs/api/openapi.yaml)
in the main repository — it is the source of truth for any client codegen
(Swift, Kotlin, OpenAPI Generator) and the contract the native iOS client speaks
against. The spec carries the version of the release it ships with; CI fails the
build on drift between the Zod schemas and the YAML, so the contract stays
honest.

This page documents the cross-cutting conventions. For the endpoint groups, see
[Endpoints](/reference/api-endpoints/).

## Base URL

```
https://your-instance.example.com/api
```

## Authentication

Two methods, with a hard structural boundary between them:

| Method | Used by | Carried as |
| --- | --- | --- |
| **Session cookie** | Browser clients | `healthlog_session` cookie (automatic) |
| **Bearer token** | External / native API clients | `Authorization: Bearer hlk_...` |

- **Session cookies** are Postgres-backed with a sliding 30-day expiry,
  HttpOnly + SameSite. The cookie path can elevate to admin via
  `requireAdmin()`. Since v1.30.33 the cookie carries a purpose-generated
  32-byte random secret (`hls_<hex>`) and only its HMAC-SHA256 hash is stored,
  so the value in the browser exists nowhere on the server. It used to be the
  session row's own primary key — an identifier built for collision resistance,
  not for unguessability, and one that appeared wherever that row was
  referenced. Sessions created before that release keep working and are simply
  not renewed, so they run out their normal 30 days: the change signs nobody
  out.
- **Bearer tokens** are HMAC-SHA256-hashed under `API_TOKEN_HMAC_KEY` before
  storage — there is no plaintext path, and the raw `hlk_<hex>` value is shown
  exactly once at creation. Tokens are scoped. The scopes in use are
  `fhir:read` for the [FHIR API](/reference/fhir-api/), `health:read` and
  `health:write` for the [MCP connector](/guides/mcp-server/),
  `medication:ingest` for one medication's own intake endpoint, and
  `measurements:write` for
  [pushing readings from your own hardware](/guides/ingest-token/). Only the
  login, passkey and refresh paths mint a wildcard (`["*"]`) token; every
  user-facing mint endpoint hardcodes one narrow scope. The measurement-token
  mint additionally accepts the session cookie only, so no API token, wildcard
  included, can mint one.

:::caution[Bearer scope is fail-closed since v1.30.17]
A route accepts a narrow-scope token only if it **names** the scope it accepts.
`requireAuth()` with no argument admits a cookie session or a wildcard token
only; a narrow token is refused with `403` and an audit row. Before v1.30.17 a
token minted for one purpose reached every Bearer-accepting endpoint, including
the full backup export. **Revoke and re-issue any token you handed to a third
party**, and treat it as having had that reach for its whole lifetime.
:::

:::caution[Admin is cookie-only]
`requireAdmin()` is a cookie-only boundary. A Bearer token — even with `["*"]`
scope — cannot reach any `/api/admin/*` endpoint. This is structural, not a
runtime check future code can soften.
:::

`userId` is never a request-body field. It is always narrowed from the session
or the Bearer token and feeds the Prisma `where` clause directly.

:::note[Acting on a shared record since v1.36.0]
A caller can hold access to another account's record, and on the routes that
allow it the `userId` in the `where` clause is then the record owner's rather
than the caller's. That substitution never comes from the request body either.
It comes from an account selector the caller names, checked against a live grant
row on **every** request, and it only happens on a route that has declared which
mode it serves under a grant. Both declared sets are frozen by a structural
test; every other route refuses with `403`
(`meta.errorCode: sharing.not_permitted`) rather than falling back to the
caller's own record, because answering with the wrong person's health record is
worse than refusing.

Since v1.36.1 a grant carries a level, so the substitution can apply to a write
as well as a read. Twelve route modules declare write, out of 131 that serve a
shared record at all, and at write level every one of them creates a row rather
than changing one. Since v1.37.0 a third declared set serves `MANAGE`-level
grants, which do edit and delete entries (see
[Shared access](/reference/api-endpoints/#shared-access) for the level and
scope model). The row belongs to the record owner exactly as if they had
entered it themselves; authorship of the write rides the audit row, not the
data row. An
unsafe method on a route that declared itself readable counts as a write
whatever the route intended, so a read-level grant refuses it (`403`,
`meta.errorCode: sharing.access.denied`) and a route cannot widen itself by
gaining a verb.

Cookie clients name the account with `POST /api/account/switch`; Bearer clients
send the `X-HealthLog-Account` header per request and are refused by the switch
endpoint, because a token must keep meaning one person for as long as it exists.
See [Shared access](/reference/api-endpoints/#shared-access) and
[What a shared record is](/explanation/record-sharing/).
:::

## Response envelope

Every response is `{ data, error }`, with an optional `meta` on the error path:

```json
{ "data": { "...": "..." }, "error": null }
```

On error:

```json
{ "data": null, "error": "Validation failed: password must be at least 12 characters" }
```

Paginated reads nest their pagination block inside `data`; a top-level `meta`
appears on error responses only (carrying `errorCode` and similar):

```json
{
  "data": {
    "measurements": ["..."],
    "meta": { "total": 142, "limit": 20, "offset": 0 }
  },
  "error": null
}
```

Validation failures (422) return all Zod issues in a multi-issue envelope,
sanitised against the echoed input.

## Idempotency

Idempotency is opt-in per route, not a property of the method. A route that
declares it accepts an `Idempotency-Key` header of 8 to 128 characters from
`A-Za-z0-9_-:.`, and the OpenAPI document names the header on every route that
honours it. The first request runs and the response is cached; a replay with
the same key returns the cached response with `X-Idempotent-Replay: true`
instead of re-running the mutation.

- Keys are **user-scoped** — a composite unique index by
  `userId_key_method_path` means a client cannot replay another user's key.
- The cache refuses to persist a response body containing secret-shaped patterns
  (`hlk_`, `hlr_`, `sk-`) even if a future caller wraps an auth endpoint by
  mistake.
- A second request arriving while the first is still in flight gets
  `A request with this Idempotency-Key is already in progress`.

This is what makes the native client's retries safe over flaky mobile networks.

## Rate limits

A `429` the rate limiter produced carries four headers:

| Header | Meaning |
| --- | --- |
| `Retry-After` | Whole seconds to wait. Rounded up, never below 1 |
| `X-RateLimit-Limit` | Requests the bucket allows per window |
| `X-RateLimit-Remaining` | Requests left in the current window, `0` on a refusal |
| `X-RateLimit-Reset` | ISO-8601 instant the window rolls over, not epoch seconds |

Back off on `Retry-After` rather than guessing, which is what an offline queue
that tripped a cap needs. Every limited route carries the four, the batch
endpoints, `/api/sync/changes` and `/api/auth/refresh` among them. A `429` that
did not come from one of these buckets carries none of them, because there is no
bucket to describe: a daily AI budget and a provider's own refusal relayed
onward both look like that.

Limits live in Postgres (a single atomic SQL
upsert), so multi-instance correctness is structural. The bucket key is
`<surface>:<identifier>` — `userId` for authenticated routes, the trusted-proxy
IP for anonymous ones (see [`TRUST_PROXY_HOPS`](/guides/reverse-proxy/)).

## HTTP status codes

| Code | Meaning |
| --- | --- |
| `200` | Success |
| `201` | Resource created |
| `202` | Accepted (async job queued) |
| `204` | Success, no body |
| `400` | Bad request |
| `401` | Not authenticated |
| `403` | Forbidden |
| `404` | Not found |
| `413` | Payload too large (per-route body cap) |
| `422` | Validation error (multi-issue Zod envelope) |
| `429` | Rate limit exceeded |
| `500` | Internal error |

## Auth error codes

The generic auth gates, the ones every route passes through before its own body
runs, name their reason in `meta.errorCode`. Branch on that field: the English
sentence beside it may be reworded or localised at any time.

| Code | Status | Means |
| --- | --- | --- |
| `auth.missing` | `401` | No session cookie and no Bearer header. Send the user to sign in |
| `auth.token.expired` | `401` | The Bearer token's lifetime has passed. Refresh and retry |
| `auth.token.invalid` | `401` | Unknown, revoked, or the owning account is gone. Discard the credential; retrying will not help |
| `auth.mfa.code_invalid` | `401` | A second factor presented on a step-up flow did not verify. Re-prompt for a code and keep the session |
| `auth.stepup.required` | `401` | The route needs a fresh factor. Re-prove and retry |
| `auth.scope.insufficient` | `403` | The credential is valid but its scope does not reach this route, which includes any Bearer token against an admin surface |
| `auth.admin.required` | `403` | A cookie session that is not an admin's |

A route that checks a credential of its own, meaning sign-in, the MFA challenge
exchange or a password confirmation, may still answer `401` with prose and no
code. A missing `meta.errorCode` there means the route refused the credential it
was handed, not that the response is malformed.
