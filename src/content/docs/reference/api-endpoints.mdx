The API has more than 400 routes. This page does not list them. It says where
the full contract is, what each kind of credential reaches, the few rules a
schema cannot express, and which guide describes each area. The conventions
every route follows (authentication, the envelope, paging, idempotency, rate
limits, error codes, retired routes) are on [API overview](/reference/api-overview/).

## The OpenAPI spec

The contract is the OpenAPI 3.1 document `docs/api/openapi.yaml` in the app
repository. It is generated from the server's own request and response
schemas, and CI fails a build where the two drift, so it is the reference for
every route, field and error code, and the source for generated clients. Every
route the server answers is in it, apart from a few internal ones the
repository names with a reason. Each operation declares its security, so a
generated client sends the session cookie or the Bearer token.

Read the spec at the release tag that matches your server. `GET /api/version`
returns the running `version`; for 1.46.0 the file is:

- [openapi.yaml at v1.46.0](https://github.com/MBombeck/HealthLog/blob/v1.46.0/docs/api/openapi.yaml), to read on GitHub
- [the raw file](https://raw.githubusercontent.com/MBombeck/HealthLog/v1.46.0/docs/api/openapi.yaml), for a client generator or a viewer such as Swagger UI

For another release, replace `v1.46.0` in the link with `v` and your
version. The copy on `main` can describe routes your server does not have yet.

## What each credential reaches

| Credential | Reaches |
| --- | --- |
| Browser session cookie | Everything the account may do. Admin routes too, for an admin account |
| Full-access Bearer token (`["*"]`) | Every route except `/api/admin/*` and the few acts that need a browser session (token mints, a manage invitation, managed-profile changes). Minted only by sign-in, passkey sign-in, refresh and the native sign-in handoffs; see [Native API clients](/reference/native-clients/) |
| `measurements:write` | `POST /api/measurements` and `POST /api/measurements/batch` on its owner's own record. Rows are attributed `EXTERNAL`; a body that names a `source` is refused with `422` |
| `workouts:write` | `POST /api/workouts/batch`, rows attributed `EXTERNAL` |
| `documents:write` | `POST /api/documents/inbound` and `GET /api/documents/inbound/source` |
| `medication:ingest` | `POST /api/ingest/medication` for the one medication it was minted for |
| `health:read`, `health:write` | `/mcp` only; see the [MCP server reference](/reference/mcp/) |
| `fhir:read` | `/api/fhir/*`, but no mint produces it yet; use a session or a full-access token |

A narrow token sent anywhere else gets `403` with `auth.scope.insufficient`.
The measurement, document and workout tokens are minted at
`POST /api/tokens/measurements`, `/documents` and `/workouts`: cookie only,
with fresh proof (below), ten mints a minute, 365 days unless a shorter
`expiresInDays` is given, and the raw `hlk_` value in that one response only.
A measurement token also takes `mirrorToAppleHealth` (default `false`), which
lets the iPhone app write its readings into Apple Health; change it later with
`PATCH /api/tokens/{id}` (cookie only; any other kind of token answers `422`
`tokens.mirror.not_measurement_token`). `GET /api/tokens` lists the account's
tokens and `DELETE /api/tokens/{id}` revokes one. Setup for each is in
[Push readings from your own hardware](/guides/ingest-token/) and
[Import documents](/guides/import-documents/).

## Fresh proof on the web

Acts that copy the whole record out or leave a standing way into it ask a
browser session for a sign-in or a re-proof within the last five minutes: the
exports (full backup, encrypted export, JSON export, health-record export,
FHIR `Patient/$everything`), minting a token or a share link, approving an MCP
connection, offering shared access, and the admin backup, restore, wipe and
password-reset routes. Without it they answer `401` `auth.reproof.required`
with `meta.methods`, the methods the account can use. Confirm at
`POST /api/auth/reproof` (same body as `POST /api/auth/step-up`) and retry;
`GET /api/auth/reproof` answers `200` while the proof is fresh. On an account
with a second factor only a sign-in or proof that included it counts. Bearer
callers follow the rules each route's spec entry names.

## Batch writes

`POST /api/measurements/batch` takes up to 500 entries and answers a status
per entry: `inserted`, `updated`, `duplicate`, `skipped` (with a reason) or
`failed`.

- An `externalId` that starts with `stats:` (for example
  `stats:HKQuantityTypeIdentifierStepCount:2026-10-01`) is a running total and
  is **overwritten** by a re-post: value, unit, `measuredAt`,
  `externalSourceVersion`, `deviceType` and `sleepStage` are replaced, and the
  entry answers `updated`.
- Every other `externalId` is first-write-wins: a re-post answers `duplicate`,
  because a sample is a recorded fact.
- A batch refused as a whole names the reason in `meta.errorCode`
  (`measurement.batch.invalid`, `measurement.batch.too_large`,
  `measurement.batch.source_not_permitted`). All three are permanent for the
  batch as sent.

Every instant a request sends must carry seconds (`2026-10-16T06:15:00Z`);
`2026-10-16T06:15Z` is refused with `422`. How a client keeps a local copy in
step is the [offline sync contract](/reference/sync/).

## Shared access

A caller that holds a [shared-access grant](/guides/shared-access/) can act on
another account's record, on the routes that declare it. The model is in
[What a shared record is](/explanation/record-sharing/); the wire rules are
these.

- A browser session switches with
  `POST /api/account/switch` (`accountId: null` goes back to its own). A
  Bearer client sends `X-HealthLog-Account: <accountId>` on each request
  instead; the switch refuses it with `400` `sharing.switch.wrong_transport`,
  and the header next to a cookie is refused. The grant is read again on every
  request, so a revocation applies to the next call.
- `GET /api/auth/me` reports the active record and
  each entry of `accountAccess` with `level` (`read`, `write`, `manage`; branch
  on this), `canWrite`, `sections` (`null` is the whole record, `[]` is
  nothing) and `recordKind`. The older `access` field reports a manage grant
  as `write`. `modules` describe the active record and are masked to the
  grant; `moduleAccess` says why a module is off (`disabled`, `not_granted`,
  `unavailable`).
- An unknown account, an account that granted nothing, a
  grant whose sections do not reach the route and a read grant on a write all
  answer the same `403` `sharing.access.denied`, so the answer reveals nothing
  about other accounts. A route that serves no shared record answers `403`
  `sharing.not_permitted`, and so do the grant-management routes, the FHIR
  API, share links and the whole-record exports (full backup, encrypted and
  JSON export) while the caller acts on another record. The health-record
  export is the one export a manage-level grant reaches.
- A switched browser session sends
  `X-HealthLog-Record-Epoch` and `X-HealthLog-Record-Scope`, adopted from
  `recordSession` on `GET /api/auth/me` or the switch. A stale epoch answers
  `409` `sharing.session.changed`: re-read `/api/auth/me`, adopt the new
  `recordSession`, retry once. Bearer traffic is never fenced.
- Offering a manage grant and every change to a
  [managed profile](/guides/managed-profiles/) need a fresh second factor,
  which only a browser session can give. A token gets `403`; send the person
  to the browser.

On `GET /api/integrations/status`, read `health` on each entry: it is the one
resolved connection state. The older fields beside it (`state`, `lastError`,
`syncHealth`, `needsReauth`, `planUnavailable`, `scopeReconnect` and others)
are deprecated in the spec and still served; no removal release is set.
