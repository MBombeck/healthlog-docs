The API has over 400 routes. Rather than hand-maintain every one here (which
would drift), this page documents the **groups** with representative endpoints
and examples. The authoritative, machine-readable contract is
[`docs/api/openapi.yaml`](https://github.com/MBombeck/HealthLog/blob/main/docs/api/openapi.yaml)
— generate clients from it, and treat it as canonical when this page and the spec
disagree.

Since v1.37.25 the spec is complete in a way it was not before. Every route the
application serves is either published there or listed in the repository with a
reason for its absence, and a test fails the build if a new route is neither.
Before that release the spec described 262 paths while the application answered
on 410: the drift check compared the spec against the schemas and never against
the routes, so a route that was never registered raised no complaint. The same
release added the `security` declaration the spec had always been missing, so a
generated client now wires the Bearer token or the session cookie instead of
treating every operation as public.

All mutations require [authentication](/reference/api-overview/); responses use
the `{ data, error }` envelope.

## Measurements & health data

The core ingest and read surface. Batch endpoints power the native client.

| Method | Endpoint | Notes |
| --- | --- | --- |
| `GET` | `/api/measurements` | List (paginated, filterable by type / source / date) |
| `POST` | `/api/measurements` | Create one measurement, or up to five in an array. Also accepts a `measurements:write` token |
| `POST` | `/api/measurements/batch` | Bulk ingest, up to 500 entries; see the overwrite note below. Also accepts a `measurements:write` token |
| `DELETE` | `/api/measurements/by-external-ids` | Soft-delete rows by external id (HealthKit deletion reconciliation) |
| `POST` | `/api/measurements/bulk-delete` | Tombstoned bulk delete |
| `GET` | `/api/analytics/range` | Trend summaries over a window |
| `GET` | `/api/sleep/night` · `/api/workouts` | Sleep nights, workouts (with `/batch`) |
| `GET` | `/api/devices` | Registered device list |

:::note[Batch overwrite contract]
`POST /api/measurements/batch` recognises `externalId` values starting with
`stats:` (e.g. `stats:HKQuantityTypeIdentifierStepCount:YYYY-MM-DD`) as
**overwrites** — a re-post replaces value / unit / measuredAt / deviceType. Every
other externalId prefix keeps first-write-wins immutability, because each sample
is a canonical reading. The per-entry status is `"updated"` for an overwrite vs
`"inserted"` for a fresh row.
:::

The two `POST` endpoints are the only routes a `measurements:write` token can
reach. Such a token writes on its owner's own record only (a request carrying
the account selector is refused with `403` before any sharing grant is read),
its rows are attributed `MANUAL`, an entry naming `APPLE_HEALTH` is refused
with `422`, and a batch from it does not move the phone's sync checkpoint. See
[Push readings from your own hardware](/guides/ingest-token/).

## Shared access

One account's standing permission on another's record, at `READ`, `WRITE` or
`MANAGE`, over the whole record or over named sections. See
[Give another account access to your record](/guides/shared-access/).

| Method | Endpoint | Notes |
| --- | --- | --- |
| `GET` / `POST` | `/api/account/grants` | List grants in both directions / invite by username or e-mail |
| `POST` | `/api/account/grants/{id}/accept` | The delegate accepts. Until this lands, the grant confers nothing |
| `POST` | `/api/account/grants/{id}/renounce` | The delegate hands the access back |
| `DELETE` | `/api/account/grants/{id}` | The owner withdraws. Stamps the row, never deletes it |
| `GET` | `/api/account/activity` | Day-coalesced record of who opened the caller's record, and what they did in it. Owner-only, never served under a grant |
| `POST` | `/api/account/switch` | Point this browser session at a record, or back at its own with `accountId: null`. Cookie transport only |

`POST /api/account/grants` takes `identifier` (the invitee's username or e-mail,
matched case-insensitively, the same identifier they sign in with), an optional
`access` of `READ`, `WRITE` or `MANAGE` defaulting to `READ`, an optional
`scope`, and an optional `expiresAt`. Omitted or `null` `expiresAt` means the
grant runs until somebody ends it.

### Levels

`access` is fixed at the invitation. No endpoint raises, lowers or otherwise
edits a live grant's level, and none is planned: anything above read is two
consents meeting once at acceptance, so moving somebody between levels means
ending their grant and inviting them again at the level you mean.

- `READ` reads the record and changes nothing.
- `WRITE` additionally **adds** entries: readings, results, observations, a
  medication, a marked dose. It still edits and deletes nothing, including its
  own.
- `MANAGE` additionally changes and removes entries, including ones the owner
  wrote, reads the generated insights, and records the record's own health
  background (allergies, family history).

The boundary is record content against account configuration. `MANAGE` never
reaches login, the second factor, provider connections, API tokens, notification
routing, module and threshold configuration, or who else has access.

Offering `MANAGE` is step-up gated and the step-up resolves through the session
cookie, so a Bearer caller is refused `403`
(`meta.errorCode: sharing.invite.manage_browser_only`) before anything else
happens. Accepting one carries no transport restriction.

### Scope

`scope` narrows a `READ` or `WRITE` grant to named sections. Omitted or `null`
is the entire record, which is what every grant written before v1.37.0 carries.
The vocabulary is closed: `measurements`, `medications`, `labs`, `profile`,
`illness`, `mind`, `cycle`, `documents`.

An empty array, an unknown key, and any `scope` at all beside `access: MANAGE`
are each `422`. Management is whole-record by construction.

A stored scope never grows by release. A grant opens the sections it named at
the moment it was written and nothing added afterwards, because the scope is
stored as the keys the owner ticked.

### What the account payload reports

`/api/auth/me` reports the active record and every entry in `accountAccess`
with:

| Field | Values | Meaning |
| --- | --- | --- |
| `access` | `read` \| `write` | The legacy union, unchanged. A `MANAGE` grant serialises here as `write` |
| `level` | `read` \| `write` \| `manage` | The canonical level. Branch on this |
| `canWrite` | boolean | Always equals `level !== "read"` |
| `sections` | `null`, or an array of section keys | `null` is the entire record. `[]` is **nothing**: the stored scope could not be parsed and the server failed closed |
| `recordKind` | `self` \| `shared` \| `managed` | Presentation metadata, resolved server-side, never an authorization input |

`access` keeps two members on purpose. A client compiled against v1.36.0 decodes
it as a closed set and would fail on a third case, so `MANAGE` does not go
there. `GET /api/account/grants` reports the level on every row.

### One refusal, everywhere

Every one of these answers `403` with `meta.errorCode: sharing.access.denied`,
byte for byte:

- a selector naming an account that does not exist;
- a selector naming an account that granted nothing;
- a grant whose sections do not reach this surface;
- a read grant on a request that writes;
- a fenced browser session sending no record assertion.

A distinguishable refusal would be an account-enumeration oracle for anybody
with a login on the instance. The reason reaches the record owner's activity
feed and the operator's audit trail instead. On this code: stop using the
selector, re-read `/api/auth/me`, render what it now says.

A route that declared nothing refuses outright with `403`
(`meta.errorCode: sharing.not_permitted`), and so do the six grant-management
operations, which are never delegable. The canonical intake route carries two
further refusals that are not level failures at all: deferring a reminder, and
overturning a dose decision that is already recorded, are the owner's whatever
the grant says. Both file an audit row under the owner, so a refused attempt is
visible to them rather than silent. Re-sending an identical dose decision is
admitted, because a retry and a second tap look exactly like that.

### Activity

`GET /api/account/activity` carries two fields beside the entries, and a client
should show both.

- `retentionDays` is how far back the feed can see, resolved from the instance's
  audit retention setting rather than a constant. The query is bounded to it, so
  it is the real limit of the list. `GET /api/account/grants` carries it too, so
  a client ending an access can state the window in the same breath. See
  [Audit-trail retention](/reference/environment-variables/#audit-trail-retention).
- `truncated` is true when the read reached its row ceiling, meaning `entries`
  is the most recent activity inside the window rather than all of it.

Per entry, `actor` is `null` when that account has since been deleted; render
that as a deleted account rather than as a blank, which would read as the owner
having done it themselves. `accesses` is a per-day count on a coalesced read row
and `null` on everything else, so the numbers are not additive.

Neither endpoint is delegable. A grant is not an introduction to the other
people in the household.

:::note[Naming the record on each transport]
`POST /api/account/switch` is a browser-session feature. A Bearer caller gets
`400` (`meta.errorCode: sharing.switch.wrong_transport`) and instead sends
`X-HealthLog-Account: <accountId>` on each request it wants scoped to that
record. A token never accumulates switch state, because the credential has to
keep meaning "this person" for as long as it exists. That header is Bearer only;
sending it alongside a cookie is refused rather than ignored, and `/api/auth/me`
refuses it outright with `403` (`meta.errorCode: sharing.not_permitted`).

A browser session that has entered another record also asserts it on every
request, through `X-HealthLog-Record-Epoch` and `X-HealthLog-Record-Scope`. Both
are adopted from the `recordSession` object in the body of exactly two
responses, `GET /api/auth/me` and `POST /api/account/switch`. A mismatching
epoch answers `409` with `meta.errorCode: sharing.session.changed`, which is a
reconciliation signal rather than a refusal of access: re-read `/api/auth/me`,
adopt the `recordSession` it returns, retry once. A session that has never
entered another record is served without either header and is unaffected.
Bearer traffic is never fenced and `recordSession` is `null` for it.

Every endpoint in this group except the switch refuses while the caller is
already acting on another account (`403`,
`meta.errorCode: sharing.not_permitted`). A delegate cannot invite, widen,
transfer or end anybody's access from inside a record they were given. The
switch endpoint stays reachable because it is the way back out.
:::

## Managed profiles

A health record for somebody with no login of their own. A guardian relationship
is a `MANAGE` grant with the profile as the grantor. See
[Records with no login of their own](/guides/managed-profiles/).

| Method | Endpoint | Notes |
| --- | --- | --- |
| `POST` | `/api/managed-profiles` | Create a profile and become its first guardian, in one transaction. Cookie only, unconditional fresh second factor, ten an hour |
| `GET` | `/api/managed-profiles/{id}/guardians` | Who looks after this record now. Cookie only, no step-up. An actor surface: it answers from a guardian's own account |
| `POST` | `/api/managed-profiles/{id}/guardians` | Invite another guardian. Ten an hour per caller |
| `DELETE` | `/api/managed-profiles/{id}/guardians/{grantId}` | End somebody else's guardianship |

There is deliberately no list endpoint. The profiles a guardian looks after are
the `recordKind: "managed"` entries of `accountAccess.accounts` on
`/api/auth/me`, so re-read the account payload after any change in this family.

`POST /api/managed-profiles` answers with
`{ id, displayName, dateOfBirth | null, locale, timezone, recordKind }`.
`locale` and `timezone` belong to the record rather than to the guardian reading
it: they decide how the profile's own reminders are worded and when its day
starts. `dateOfBirth` is an optional `YYYY-MM-DD` and is never synthesised from
a year.

A guardian row carries five fields and no more: `grantId`, `account`
(`{ id, username, displayName }`, never an e-mail address), `state`
(`PENDING` or `ACTIVE`), `invitedAt`, and `acceptedAt`. There is no `access` or
`scope`, because both are constants for a guardian grant, and no `expiresAt`,
because an expiry bounds one invitation rather than describing who looks after
the record. Ended grants are absent rather than listed with a state. The `201`
from the invitation answers with the same shape, which is why it echoes no
`expiresAt` even when the caller supplied one.

**Count the `ACTIVE` rows to know whether a removal is possible.** The
last-guardian floor counts accepted, unexpired `MANAGE` grants, so a `PENDING`
row does not satisfy it.

`DELETE .../guardians/{grantId}` answers `{ grantId, revokedAt }`. Nothing is
deleted; the row survives as the consent record. Its `404` covers four
situations the caller cannot tell apart, including **the target grant being the
caller's own**, so do not offer that control on the caller's own row. A guardian
leaves through `POST /api/account/grants/{id}/renounce`, which is where the
floor refusal (`409`, `meta.errorCode: managed_profile.guardian.required`)
actually arrives, along with the owner's revoke, guardian account deletion and a
data wipe.

:::caution[Resolve `meta.errorCode` before the status here]
`POST /api/managed-profiles/{id}/guardians` answers five ways, and one status
appears twice:

| Status | `meta.errorCode` | Means |
| --- | --- | --- |
| `429` | none | Rate limit, ten invitations an hour per caller |
| `404` | none | No account on this instance carries that identifier |
| `404` | `managed_profile.not_found` | No such profile, or the caller is not one of its guardians |
| `409` | `managed_profile.guardian.duplicate` | That account already holds a live grant |
| `422` | `managed_profile.guardian.managed_invitee` | A record with no self cannot look after another one |

A client branching on the status first tells somebody to check a spelling when
the real answer is that they no longer administer the record. Rate-limit
refusals carry no `errorCode` anywhere in this application, and
`POST /api/account/grants` answers an unknown identifier with a bare `404` too,
so the two codeless arms match their siblings rather than their neighbours.

Inviting yourself lands on the duplicate `409`, because a guardian grant's
grantor is the profile and never the caller, so naming yourself names an account
that already has access.
:::

## Export, FHIR & clinician links

| Method | Endpoint | Notes |
| --- | --- | --- |
| `POST` | `/api/export/health-record` | PDF + FHIR R4 bundle, selectable |
| `GET` | `/api/fhir/{Patient,Observation,MedicationStatement,...}` | Read-only FHIR R4, `fhir:read` scope |
| `GET` / `POST` / `DELETE` | `/api/share-links` · `/{id}` | Scoped clinician share links |

See the [FHIR read API](/reference/fhir-api/). These are for handing a record to
somebody with no account on the instance. Giving another *account* read access is
[Shared access](#shared-access), a separate surface. None of the three endpoints
above is reachable while acting on a shared record: a delegate can neither export
nor mint a link, because a link would be a door that survives their own
revocation.

## Sync (offline clients)

`GET /api/sync/state` and `GET /api/sync/changes` provide a paginated,
opaque-cursor delta feed with measurement tombstones so native and offline
clients reconcile incrementally.

## Admin (cookie-only)

User management, invites, notification diagnostics, backup test, audit log,
shared AI config. Bearer tokens cannot reach any of these.

| Method | Endpoint | Notes |
| --- | --- | --- |

| `GET` | `/api/admin/notifications/diagnostic` | Masked tokens + last 20 attempts |
| `POST` | `/api/admin/backup/test` | S3 round-trip probe |
