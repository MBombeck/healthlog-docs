HealthLog requires HTTPS in production — session cookies are `secure: true` and passkeys (WebAuthn) only work over [TLS](https://en.wikipedia.org/wiki/Transport_Layer_Security) or `localhost`. The one supported exception: on a trusted-network plain-HTTP deploy (LAN, Tailscale, VPN), `SESSION_COOKIE_SECURE=false` lifts the Secure flag so sign-in works, though passkeys still need TLS or `localhost`. This page covers how a self-hoster gets a valid [X.509 certificate](https://en.wikipedia.org/wiki/X.509) and clears up a common worry: **certificate pinning in the iOS app does not affect your self-hosted domain.**

## Get a valid certificate

You almost never deal with certificates by hand. The reverse proxy in front of HealthLog terminates TLS and provisions a certificate automatically over the [ACME protocol](https://letsencrypt.org/how-it-works/) — the automated challenge-response flow [Let's Encrypt](https://letsencrypt.org/how-it-works/) uses to issue browser-trusted certificates for free, with no human in the loop:

- **Caddy** — issues and renews Let's Encrypt certificates with zero configuration.
- **Traefik** — set a `certresolver` (e.g. `letsencrypt`) on the router label.
- **nginx** — pair with `certbot` for issuance and renewal.

The [Reverse Proxy](/guides/reverse-proxy/) guide has copy-paste examples for all three. Make sure `APP_URL` matches the public HTTPS domain you terminate on — passkey registration and OAuth redirects depend on it.

```bash
APP_URL=https://health.example.com
```

That is the entire TLS story for the vast majority of self-hosters: point a reverse proxy at port 3000, let it fetch a Let's Encrypt cert, done.

## Self-hosted domains are never pin-locked

Nothing to do here. A normal Let's Encrypt (or any CA-issued) certificate on your own domain is all the iOS app needs: the app pins only the managed-cloud domain, and every other host gets standard, CA-validated system-trust TLS, so there is no pin to satisfy and no lockout. Why the app pins at all, why only that one domain, and how the pin set survives certificate renewals is explained under [Only the managed-cloud domain is pinned](/security/certificate-pinning/#only-bombeckio-is-pinned).

## Optional: pin your own domain (advanced)

If you are security-conscious and want the same MITM hardening that the managed cloud gets, you can pin your own domain — but this requires rebuilding the iOS app, so it is strictly optional and only worthwhile if you are already re-signing the client under your own bundle-id (for example because you also configured [APNs push](/guides/reminder-channels/)).

The pinning host list is a build configuration in the iOS project:

1. Extract the SPKI hashes for your domain from its live TLS chain:

   ```bash
   scripts/extract-spki.sh yourdomain.example.com
   ```

   This prints the base64 SHA-256 SPKI for each certificate in the chain —
   leaf, intermediate, and root.

2. Set the build config in the iOS project:

   - **`HLPinnedHosts`** — your host (e.g. `health.example.com`)
   - **`HLPinnedSPKIHashes`** — the **intermediate + root** hashes from step 1

3. Rebuild and re-sign the app, then distribute it to your devices.

:::caution[Pin the CA keys, not the leaf]
Pin the **intermediate and root** keys and leave the leaf out of the set. The
leaf auto-renews roughly every 90 days and each renewal mints a new keypair —
a leaf pin buys nothing (validation accepts a match on any certificate in the
chain, so the CA pins already pass every renewal) and only becomes a stale
entry to maintain. This mirrors the managed cloud's own
[rotation-survival strategy](/security/certificate-pinning/#ca-level-pinning-the-rotation-survival-strategy).
A release build requires at least two well-formed pins. The implementation
lives in the [iOS repo](https://github.com/MBombeck/healthlog-iOS).
:::
