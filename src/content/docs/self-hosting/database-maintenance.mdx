This page is for operators: the maintenance run you start yourself, how to
see which queries take the time, and two database settings.

## After passing through v1.42

An install that updates through v1.42 runs two background jobs by itself,
once per account: a repair of hourly and daily means that an older fold
computed from part of a day, then a cleanup of the folded Apple Health samples
older releases kept as deleted rows. Neither needs anything from you, and
neither should be hurried by hand: a mean the repair has not seen keeps its
wrong value once its samples are gone. On an instance that synced Apple Health
for a while the measurements table shrinks a lot, and the rebuild below gives
the space back.

## After a large heart-rate fold

Heart rate from Google Health and Oura that is older than 90 days is folded
into one mean per hour, as Apple Health's is. On an account with years of
minute-by-minute heart rate the first fold works through the backlog over a
few nights, one day per transaction, and leaves the account alone until its
summaries are rebuilt. The folded rows leave the same empty index pages
behind, so run the rebuild below once the backlog is through. See
[Large accounts](/self-hosting/scaling/#large-accounts).

## Rebuild the table afterwards

The cleanup leaves the indexes full of empty pages, and only a rebuild gives
that space back. That step is yours to start, once the cleanup has finished:
in the admin area under **System Status**, or with a signed-in admin session:

```sh
curl -X POST https://<your-instance>/api/admin/maintenance/measurements \
  -H 'content-type: application/json' \
  --cookie '__Host-healthlog_session=<session>' \
  -d '{"vacuum": true, "reindex": true}'
```

It runs `VACUUM (ANALYZE)` on the measurements table and then
`REINDEX INDEX CONCURRENTLY` for each of its indexes, largest first. Reads and
writes keep working while it runs. Either step can be left out
(`"reindex": false` runs only the vacuum). The route is cookie-only like every
admin route and answers `503` without a background worker.

Before you start:

- Pick a quiet time. Each rebuild reads the whole table and writes a new copy
  of the index.
- Have at least twice the size of the largest index free on the database
  volume:

  ```sql
  SELECT c.relname, pg_size_pretty(pg_relation_size(c.oid))
  FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
  WHERE i.indrelid = 'measurements'::regclass
  ORDER BY pg_relation_size(c.oid) DESC
  LIMIT 3;
  ```

- Take a [backup](/guides/backups/).

The run refuses to start while the cleanup is still queued or running, and
the admin card says so. If a rebuild fails, most likely for lack of disk, it
drops its half-built copy and stops; the remaining indexes keep working as they
are. Free some space and start it again. It never retries by itself.

`VACUUM FULL` is not needed. After the cleanup the remaining table is small and
new rows reuse the space inside it.

## Query statistics

The bundled database loads the `pg_stat_statements` library through the
`command:` of the `db` service in `docker-compose.yml`. Loading it only
collects statistics in the database's shared memory; nothing is sent
anywhere.

To read the statistics, create the extension once:

```sh
docker compose exec db psql -U healthlog -d healthlog \
  -c "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"
```

The slowest query shapes by total time:

```sh
docker compose exec db psql -U healthlog -d healthlog -c "SELECT calls, round(total_exec_time) AS total_ms, round(mean_exec_time, 1) AS mean_ms, left(query, 120) AS query FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 15;"
```

Statements are stored with their parameters replaced by placeholders, so no
value from anyone's record appears there. `SELECT pg_stat_statements_reset();`
starts the counts over.

On your [own PostgreSQL](/self-hosting/external-postgres/), add
`pg_stat_statements` to `shared_preload_libraries` in its configuration and
restart it before creating the extension. The step is optional; HealthLog does
not need it.

## Session settings: work_mem and PgBouncer

Every app connection sets three things when it opens: the statement timeout
(`DATABASE_STATEMENT_TIMEOUT_MS`, 60 seconds by default; see
[Large accounts](/self-hosting/scaling/#large-accounts) before raising it), `work_mem` from
`DATABASE_WORK_MEM` (16MB by default), and the time zone, `TimeZone=UTC`. Sorts and aggregates
larger than `work_mem` spill to disk; each sort step of each pooled connection
may use that much memory, so raise it with the pool size in mind.

Both travel to Postgres in the libpq `options` startup parameter. PgBouncer
refuses that parameter ("unsupported startup parameter: options") unless it is
listed in its `ignore_startup_parameters`. Behind such a pooler, set
`DATABASE_SESSION_OPTIONS_DISABLED=1` (or `true`, `yes`) and the app sends no
session settings at all; the pooler's or the database's own defaults then
apply. Set the timeout and `work_mem` on the database role instead
(`ALTER ROLE healthlog SET work_mem = '16MB'`) if you still want them.
The time zone is the exception: with the options off the app pins it with
`SET TIME ZONE 'UTC'` on each new connection, and warns at startup if a
connection still reports another zone. See
[External PostgreSQL](/self-hosting/external-postgres/#what-the-database-has-to-provide).

The measurement maintenance run then applies its own settings with `SET` after
it connects. Its `REINDEX INDEX CONCURRENTLY` needs a whole session, so run it
through a session-mode pool or a direct connection to Postgres; a
transaction-mode pool cannot carry it. All three variables are on the compose whitelist. See
[Environment variables](/reference/environment-variables/).
