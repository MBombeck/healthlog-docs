For a single Docker box that only you and your household need to reach,
`tailscale serve` can stand in for the [reverse proxy](/guides/reverse-proxy/)
entirely. [Tailscale](https://tailscale.com/) terminates HTTPS with a
certificate every device on your tailnet already trusts, there is no extra
container to run and nothing to renew, and the free plan covers all of it. The
trade is scope: the instance is reachable only from devices signed into your
tailnet, which for a personal health record is usually the point.

Two modes exist, and the difference matters more here than for most apps:

- **`tailscale serve`** publishes HealthLog inside your tailnet only. Every
  device that should reach it runs the Tailscale client and signs into the same
  tailnet, including the iPhone if you use the iOS app. The instance is
  invisible from the public internet. This is the right default for a personal
  health record.
- **`tailscale funnel`** publishes the same HTTPS endpoint to the public
  internet. No client is needed on the phone, but anyone on the internet can
  reach the sign-in page, so the instance becomes a public deployment and needs
  to be treated like one. Funnel is the deliberate opt-in, not the default.

## Set up `tailscale serve`

1. Install Tailscale on the Docker host and sign in. On macOS, the standalone
   app from tailscale.com is more full-featured than the App Store build;
   either works for this page.

2. With the compose stack running on `localhost:3000`, run:

   ```bash
   tailscale serve --bg localhost:3000
   ```

3. If HTTPS certificates are not yet enabled for your tailnet, the CLI says so
   and prints the admin-console link that enables them. Follow that link once;
   it is a one-time, per-tailnet step.

4. The CLI prints the HTTPS URL it now serves, of the form
   `https://<machine>.<tailnet>.ts.net`. `--bg` persists the configuration
   across restarts, so this is a run-once command, not something to add to a
   boot script.

## Or run Tailscale as a container next to HealthLog

`tailscale serve` on the host shares whatever answers on `localhost:3000`. If
you stop HealthLog and start something else on that port, a hobby project for
example, your tailnet now reaches that instead. Running Tailscale as its own
container in the compose stack avoids this: the tailnet share starts and stops
with HealthLog, and nothing else on the host is exposed.

1. In the Tailscale admin console, under **Settings → Keys**, generate an auth
   key. The container needs it only for its first sign-in; after that the
   state volume below keeps the node's identity.

2. Next to `docker-compose.yml`, create `tailscale/serve.json`:

   ```json
   {
     "TCP": {
       "443": { "HTTPS": true }
     },
     "Web": {
       "${TS_CERT_DOMAIN}:443": {
         "Handlers": {
           "/": { "Proxy": "http://127.0.0.1:3000" }
         }
       }
     },
     "AllowFunnel": {
       "${TS_CERT_DOMAIN}:443": false
     }
   }
   ```

   Keep `${TS_CERT_DOMAIN}` exactly as written; the container fills in its own
   tailnet name.

3. Create `docker-compose.override.yml` in the same directory:

   ```yaml
   services:
     tailscale:
       image: tailscale/tailscale:latest
       hostname: healthlog
       environment:
         TS_AUTHKEY: "${TS_AUTHKEY}"
         TS_STATE_DIR: /var/lib/tailscale
         TS_SERVE_CONFIG: /config/serve.json
       volumes:
         - tailscale-state:/var/lib/tailscale
         - ./tailscale:/config:ro
       devices:
         - /dev/net/tun:/dev/net/tun
       cap_add:
         - net_admin
         - sys_module
       restart: unless-stopped

     app:
       network_mode: service:tailscale
       ports: !reset []
       depends_on:
         tailscale:
           condition: service_started

   volumes:
     tailscale-state:
   ```

   `network_mode: service:tailscale` puts the app into the Tailscale
   container's network, which is how `127.0.0.1:3000` in `serve.json` reaches
   it. The app can no longer publish its own port in that mode, so
   `ports: !reset []` removes the `3000:3000` mapping from the main file (this
   needs Docker Compose 2.24 or newer). The app still reaches the database
   under its usual name, because the Tailscale container sits on the same
   compose network.

4. Put the key into `.env` as `TS_AUTHKEY=tskey-auth-...` and start the stack
   with `docker compose up -d`. The instance appears in your tailnet as
   `https://healthlog.<tailnet>.ts.net`; use that URL in the next step.

Keep the `tailscale-state` volume. Without it every restart signs in as a new
machine, with a new name and a new certificate.

## Point HealthLog at the tailnet URL

Set the URL pair in `.env` to the exact HTTPS URL the CLI printed:

```bash
NEXT_PUBLIC_APP_URL="https://your-machine.your-tailnet.ts.net"
APP_URL="https://your-machine.your-tailnet.ts.net"
```

Both variables are on the bundled compose `environment:` whitelist, so values
in `.env` reach the container. Restart to pick them up:

```bash
docker compose up -d
```

## Cookies and TLS

`tailscale serve` terminates real HTTPS, so the session cookie's `Secure` flag
works exactly as it does behind any TLS-terminating proxy. Leave
`SESSION_COOKIE_SECURE` unset. The `SESSION_COOKIE_SECURE=false` escape hatch
described on the [TLS certificates](/self-hosting/tls-certificates/) page
exists for serving the raw `http://host:3000` surface across a trusted network
without a TLS front; once `serve` fronts the app you do not need it.

Prefer `serve` over exposing the raw port even on a network you trust, because
the certificate buys back more than the cookie flag. Browsers keep passkey
sign-in, web-push notifications, and home-screen installation for HTTPS pages
only, and a plain-HTTP origin loses all three however the server is
configured. Real HTTPS on the tailnet gives you all of them.

`serve` is a single proxy hop in front of the app, which is the topology the
default `TRUST_PROXY_HOPS=1` assumes. If the log shows a null client IP after
the switch, or every caller lands in one shared rate-limit bucket, the
"Verify the chain" section of the [reverse proxy](/guides/reverse-proxy/)
guide shows how to read the mismatch warning and adjust.

## The iOS app and Apple Health

With `serve`, the iPhone reaches the instance the same way every other device
does: install Tailscale from the App Store on the phone, sign into the same
tailnet, then [connect the iOS app](/getting-started/connect-ios-app/) using
the `https://<machine>.<tailnet>.ts.net` URL. Apple Health sync works over
this path; from the app's perspective the tailnet URL is an ordinary HTTPS
origin with a trusted certificate, and
[self-hosted domains are never pin-locked](/self-hosting/tls-certificates/).

## Public exposure with `tailscale funnel`

If the instance must be reachable without the Tailscale client, for example
for someone outside your household's tailnet, `tailscale funnel` publishes the
endpoint to the public internet. The command shape mirrors `serve`; follow the
CLI's own output, which walks through any admin-console enablement funnel
needs on your tailnet.

:::caution[Funnel makes the instance public]
The sign-in page is now internet-facing. Close public registration once every
household member has an account (see
[the self-hosting walkthrough](/getting-started/self-host-in-10-minutes/)),
and keep the image current with
`pull_policy: always`. Everything the other guides say about publicly
reachable hosts applies unchanged.
:::
