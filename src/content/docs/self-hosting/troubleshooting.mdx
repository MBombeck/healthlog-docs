The recurring problems from real deployments, with the fix and the reason.
Each entry links the page that covers the subsystem in depth.

## Login succeeds, next page load is signed out (plain HTTP)

**Symptom.** Registration or login appears to work, but the very next request
behaves as if you were never signed in.

**Cause.** Under `NODE_ENV=production` the session cookie carries the `Secure`
flag, and browsers silently drop `Secure` cookies on a plain-HTTP origin that
is not `localhost`.

**Fix.** Either put TLS in front of the instance (see
[reverse proxy](/guides/reverse-proxy/)) or — only for a trusted LAN, Tailscale,
or VPN-only deployment — set `SESSION_COOKIE_SECURE=false` in `.env` **and**
make sure it is listed in the compose `environment:` whitelist. Never disable it
on a host that serves plain HTTP to the open internet.

## `docker compose up` "updates" but the version does not change

**Symptom.** You pull an update, restart, and `/api/version` still reports the
old build.

**Cause.** Without `pull_policy: always`, Docker re-uses the stale `:latest`
digest it has cached and never asks the registry whether a newer manifest
exists.

**Fix.** Keep the `pull_policy: always` line from the bundled
`docker-compose.yml` — it is load-bearing, not a nicety. After any deploy,
verify with `curl -s localhost:3000/api/version`: it returns `version`,
`buildSha`, and `builtAt`, which is the only trustworthy signal that the new
image is actually running. See [updates and deploy](/guides/updates-and-deploy/).

## A variable is set in `.env` but the app ignores it

**Cause.** The compose `environment:` block is a **whitelist**. Compose reads
`.env` for `${VAR}` substitution, but does not forward arbitrary variables into
the container.

**Fix.** Add the variable to the `environment:` block of the `app` service,
then `docker compose up -d`. The
[environment-variable reference](/reference/environment-variables/) marks which
variables ship on the whitelist.

Related: `NEXT_PUBLIC_*` toggles are inlined at **build time** — setting them at
runtime against the pre-built GHCR image has no effect at all.

## Decryption errors after rotating encryption keys

**Symptom.** After a key rotation, some rows fail to decrypt or the app throws
on boot.

**Cause.** A key was removed from the `ENCRYPTION_KEYS` map while rows encrypted
under it still existed. HealthLog fails closed on an unknown key id — it will
never silently return plaintext or garbage.

**Fix.** Restore the legacy key entry to the map (its id is embedded in each
encrypted value), then run the rotation script until it reports **zero
remaining rows** on the old key. Only then remove the entry. The full playbook
is in [encryption key rotation](/guides/encryption-key-rotation/).

## iOS push notifications never arrive

Work through these in order:

1. **All-or-none env set.** APNs needs `APNS_KEY_ID`, `APNS_TEAM_ID`,
   `APNS_BUNDLE_ID`, and the key itself. Missing any one disables APNs
   silently.
2. **Use `APNS_KEY_B64`.** Paste the `.p8` as base64, not as a raw PEM body —
   deployment panels that write `env_file` entries mangle literal newlines, and
   a mangled key fails in non-obvious ways.
3. **Key scope.** The `.p8` must be scoped **"Sandbox & Production"** in the
   Apple Developer Portal. A Sandbox-only key fails with
   `BadEnvironmentKeyInToken` on production builds.
4. **Delivery ledger.** The admin notification diagnostic
   (`/api/admin/notifications/diagnostic`) shows the channel state and the last
   20 delivery attempts for the calling user, with masked tokens — the
   fastest way to see whether APNs is rejecting or simply not attempting.

## OAuth callbacks land on `localhost` or the wrong host

**Cause.** `NEXT_PUBLIC_APP_URL` / `APP_URL` still point at
`http://localhost:3000`, so every derived redirect URI does too.

**Fix.** Set both to the public origin, restart, and make sure the redirect URI
registered at the provider matches the app's callback path **exactly** — e.g.
`/api/google-health/callback` for
[Google Health](/guides/connect-google-health/), `/api/withings/callback` for
[Withings](/guides/connect-withings/). A single trailing slash or an `http`
scheme mismatch is enough for the provider to refuse the flow.

Since v1.38.1 the integration cards under **Settings → Integrations** show a
warning when the origin of the callback address differs from the address in the
browser, and each setup guide on those cards shows the full callback address.
Both values are the ones the server registers with the provider, resolved from
`NEXT_PUBLIC_APP_URL` or the matching `*_REDIRECT_URI` override at request
time. In v1.38.0 the check read the app address from the browser bundle, which
the published image is built without, so on that version the warning never
appeared and the guide showed only a path.

## The dashboard briefing / insights are empty

The daily briefing and the comprehensive insight are **pre-generated
overnight** by a budget-gated job — never on page visit. On a brand-new account
(or before the first nightly run) the page shows a *preparing* state; that is
by design, not a failure. Configure a provider under **Settings → AI** and give
the nightly job one cycle, or use the explicit generate button where offered.
See [how AI insights work](/insights/how-it-works/).

## The app shows the wrong language

The display language resolves in a fixed order: an explicit choice you made
(**Settings → Account → Language**) wins everywhere and sticks permanently —
it is persisted on your profile and in a server-set, year-long cookie. If you
never chose, the app is in **automatic** mode and follows the browser/system
language. If the app used to revert to another language after about a week,
that was a pre-v1.27.11 cookie-lifetime bug — update, pick the language once,
and it holds.

## Postgres migration errors on first boot

The Postgres healthcheck can race the migration on slow disks. Migrations are
idempotent — run `docker compose restart app` once the database has settled.

## Someone I invited to my record still cannot see it

**Symptom.** You sent an invitation from **Settings → Shared access** and the
other person says nothing appeared, or that they can see the invitation but not
the record.

**Cause.** An invitation confers nothing until the person named on it accepts,
and accepting is theirs to do. There is no way for you to accept on their
behalf, by design.

**Fix.** Ask them to open **Settings → Shared access** on their own account and
choose **Accept** under "Records I can open". After that the record appears in
their user menu under **Open a record**. If the invitation never arrived at all,
check the name you typed: it has to be the username or e-mail they sign in with,
and an account has to exist on this instance already. See
[Give another account access to your record](/guides/shared-access/).

## Pages refuse while I am inside somebody else's record

**Symptom.** You are in a record that was shared with you and parts of the app
say they are not part of shared access.

**Cause.** Not a bug and not a rendering fault. Sharing covers the health record
itself. The account around it stays with the person who owns it, so credentials,
connected services, notification channels, exports, clinician share links and
grant management are refused by the server rather than merely hidden. The full
list and the reasoning are in
[What a shared record is](/explanation/record-sharing/).

**Fix.** Use the button in the banner at the top, or **My own record** in the
user menu, to go back to your own account. Those surfaces work there.

## Buttons I expect are missing inside a shared record

**Symptom.** You are in somebody else's record and there is no edit button, no
delete button, or no way to add anything at all.

**Cause.** By design, and the same design at every level. A control the record
will not accept is not drawn rather than drawn and then refused, so nobody fills
in a form that was always going to be turned down. At the read level nothing can
be added. At the write level a short, closed list of entries can be added, and
nothing already in the record can be changed or removed, including an entry the
delegate added a minute ago. Only the manage level changes and removes what is
already there. The banner across the top of every page says which one applies.

An invitation can also open part of a record rather than all of it, so a
destination that is missing altogether is a section that was never shared rather
than a broken page.

**Fix.** Nothing to fix if the banner says the record cannot be changed. If the
missing control is an edit or a delete and the grant is read or write, that one
belongs to the owner and no setting moves it. Moving somebody up a level means
ending the grant they have and inviting them again at the level meant, which
they accept again. See
[What each level may do](/guides/shared-access/#what-each-level-may-do).

## Sharing shows a 409 in the logs

**Symptom.** Your app logs carry `409` responses with
`meta.errorCode: sharing.session.changed` on accounts that use shared records.
Nobody has reported a problem.

**Cause.** Not an error, and not something to report upstream. A browser session
that has entered somebody else's record asserts which record it is in on every
request. When a person switches records with more than one tab open, the tabs
that have not caught up yet name the record they were in a moment ago, and the
server refuses those rather than serving the wrong record. The tab re-reads who
it is and re-renders, which needs no interaction and shows nothing to the user.

**Fix.** Nothing. Treat these the way you treat a conditional-request `304`: a
protocol answer rather than a failure. A session that has never opened another
account's record is never fenced and never produces this, and neither is the
phone app or any other client authenticating with a token.

What is worth looking at is a `403` with `meta.errorCode: sharing.access.denied`
arriving in a burst from one account, since that is a delegate whose access
ended or was narrowed while they were using it. It is still not a fault, but it
is the shape of somebody having a confusing minute. The record owner sees the
reason in their own activity view, which is where the reason deliberately goes.

## Where to look when something else breaks

- `docker compose logs -f app` — the app logs structured wide events; errors
  carry a request id.
- `/api/version` — confirms exactly which build is serving.
- The **admin panel** — worker status shows whether the pg-boss job worker is
  alive; the audit log shows sensitive operations.
- [GitHub issues](https://github.com/MBombeck/HealthLog/issues) — search first;
  the classics above account for most reports.
