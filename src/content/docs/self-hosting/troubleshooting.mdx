The recurring problems from real deployments, with the fix and the reason.
Each entry links the page that covers the subsystem in depth.

## Login succeeds, next page load is signed out (plain HTTP)

**Symptom.** Registration or login appears to work, but the very next request
behaves as if you were never signed in.

**Cause.** Under `NODE_ENV=production` the session cookie carries the `Secure`
flag, and browsers silently drop `Secure` cookies on a plain-HTTP origin that
is not `localhost`.

**Fix.** Either put TLS in front of the instance (see
[reverse proxy](/guides/reverse-proxy/)) or, only for a trusted LAN, Tailscale
or VPN-only deployment, set `SESSION_COOKIE_SECURE=false` in `.env` **and**
make sure it is listed in the compose `environment:` whitelist. Never disable it
on a host that serves plain HTTP to the open internet.

## Signing in cannot complete on this page

**Symptom.** The login page shows "Signing in cannot complete on this page"
before you type anything, and a sign-in attempt is refused.

**Cause.** The same as above, caught earlier. The server sets its session
cookie with the `Secure` flag and the page was opened over `http://`, where the
browser would drop it. The server refuses such a sign-in with `409` and
`meta.errorCode` `auth.session.insecure_transport` before it checks a password
or uses up a code, passkey challenge or ticket.

**Fix.** Open the `https://` address (behind a TLS proxy, make sure it forwards
`X-Forwarded-Proto: https`), or set `SESSION_COOKIE_SECURE=false` for a server
you only reach over plain HTTP on your own network, and restart it. On
`http://localhost` most browsers accept the cookie anyway, so the page only
warns there.

## HealthLog cannot open its data

**Symptom.** Every page shows "HealthLog cannot open its data", API requests
answer `503` with `meta.errorCode` `encryption.key_mismatch`, and
`/api/health` answers `503` with `reason: "encryption_key_mismatch"`.

**Cause.** At start the app checks that its encryption key opens
the data already in the database. This server was started with a different key
than the one its data was written with, typically after a reinstall or a move
that generated a fresh `ENCRYPTION_KEY`. Nothing is served and no background
job runs, so nothing is written under the wrong key.

**Fix.** Put the original key back, point `DATABASE_URL` at the database that
belongs to this key, or start with an empty database; then restart. How the
check decides, how to reset it when you are certain the key is right, and the
`ENCRYPTION_KEY_CHECK=warn` last resort are in
[the start-up key check](/explanation/encryption-at-rest/#the-start-up-key-check).

## `docker compose up` "updates" but the version does not change

**Symptom.** You pull an update, restart, and `/api/version` still reports the
old build.

**Cause.** Without `pull_policy: always`, Docker re-uses the stale `:latest`
digest it has cached and never asks the registry whether a newer manifest
exists.

**Fix.** Keep the `pull_policy: always` line from the bundled
`docker-compose.yml`; it is load-bearing. After any deploy,
verify with `curl -s localhost:3000/api/version`: it returns `version`,
`buildSha`, and `builtAt`, which is the only trustworthy signal that the new
image is actually running. See [updates and deploy](/guides/updates-and-deploy/).

## A variable is set in `.env` but the app ignores it

**Cause.** The compose `environment:` block is a **whitelist**. Compose reads
`.env` for `${VAR}` substitution, but does not forward arbitrary variables into
the container.

**Fix.** Add the variable to the `environment:` block of the `app` service,
then `docker compose up -d`. The
[environment-variable reference](/reference/environment-variables/) marks which
variables ship on the whitelist.

Related: `NEXT_PUBLIC_*` toggles are inlined at **build time**; setting them at
runtime against the pre-built GHCR image has no effect at all.

## Decryption errors after rotating encryption keys

**Symptom.** After a key rotation, some rows fail to decrypt or the app throws
on boot.

**Cause.** A key was removed from the `ENCRYPTION_KEYS` map while rows encrypted
under it still existed. HealthLog fails closed on an unknown key id: it will
never silently return plaintext or garbage.

**Fix.** Restore the legacy key entry to the map (its id is embedded in each
encrypted value), then rotate again (**Admin → Encryption → Rotate now**, or
the rotation script) until it reports **zero remaining rows** on the old key
and **Keys the backups still need** no longer lists it. Only then remove the
entry. The full playbook
is in [encryption key rotation](/guides/encryption-key-rotation/).

## iOS push notifications never arrive

Work through these in order:

1. **All-or-none env set.** APNs needs `APNS_KEY_ID`, `APNS_TEAM_ID`,
   `APNS_BUNDLE_ID`, and the key itself. Missing any one disables APNs
   silently.
2. **Use `APNS_KEY_B64`.** Paste the `.p8` as base64, not as a raw PEM body:
   deployment panels that write `env_file` entries mangle literal newlines, and
   a mangled key fails in non-obvious ways.
3. **Key scope.** The `.p8` must be scoped **"Sandbox & Production"** in the
   Apple Developer Portal. A Sandbox-only key fails with
   `BadEnvironmentKeyInToken` on production builds.
4. **Delivery ledger.** The admin notification diagnostic
   (`/api/admin/notifications/diagnostic`) shows the channel state and the last
   20 delivery attempts for the calling user, with masked tokens. It is the
   fastest way to see whether APNs is rejecting or simply not attempting.

## OAuth callbacks land on `localhost` or the wrong host

**Cause.** `NEXT_PUBLIC_APP_URL` / `APP_URL` still point at
`http://localhost:3000`, so every derived redirect URI does too.

**Fix.** Set both to the public origin, restart, and make sure the redirect URI
registered at the provider matches the app's callback path **exactly**, for example
`/api/google-health/callback` for
[Google Health](/guides/connect-google-health/), `/api/withings/callback` for
[Withings](/guides/connect-withings/). A single trailing slash or an `http`
scheme mismatch is enough for the provider to refuse the flow.

The integration cards under **Settings → Integrations** warn when the origin
of the callback address differs from the address in the browser, and each
setup guide on those cards shows the full callback address the server
registers with the provider.

Leave `WITHINGS_REDIRECT_URI`, `FITBIT_REDIRECT_URI`,
`GOOGLE_HEALTH_REDIRECT_URI`, `POLAR_REDIRECT_URI`, `OURA_REDIRECT_URI`,
`WHOOP_REDIRECT_URI` and `STRAVA_REDIRECT_URI` unset unless the callback lives
on a different address than `NEXT_PUBLIC_APP_URL`. An empty value counts as
unset.

## The dashboard briefing / insights are empty

The daily briefing and the comprehensive insight are **pre-generated
overnight** by a budget-gated job, never on page visit. On a brand-new account
(or before the first nightly run) the page shows a *preparing* state; that is
by design, not a failure. Configure a provider under **Settings → AI provider** and give
the nightly job one cycle, or use the explicit generate button where offered.
See [how AI insights work](/insights/how-it-works/).

## The app shows the wrong language

The display language resolves in a fixed order: an explicit choice you made
(**Settings → Account → Language**) wins everywhere and sticks permanently:
it is saved on your profile and in a year-long cookie. If you
never chose, the app is in **automatic** mode and follows the browser/system
language.

## Sharing does not show what I expect

An invitation confers nothing until the person named on it accepts it under
**Settings → Shared access** on their own account. Inside somebody else's
record, account surfaces (credentials, connected services, notification
channels, exports, clinician share links, grant management) are refused by
design, and controls the access level does not allow are not drawn at all.
The banner across the top says which level applies. See
[Give another account access to your record](/guides/shared-access/) and
[What a shared record is](/explanation/record-sharing/).

## Sharing shows a 409 in the logs

**Symptom.** Your app logs carry `409` responses with
`meta.errorCode: sharing.session.changed` on accounts that use shared records.
Nobody has reported a problem.

**Cause.** Not an error. A browser tab that has entered somebody else's record
names that record on every request. After a person switches records with
several tabs open, the tabs that have not caught up are refused rather than
served the wrong record; they re-read and re-render without any interaction.

**Fix.** Nothing. A burst of `403` with `meta.errorCode: sharing.access.denied`
from one account is a delegate whose access ended or was narrowed while they
used it; the record owner sees the reason in their own activity view.

## Background jobs fail with "job timed out"

**Symptom.** The admin status page lists failing jobs, such as the nightly
clean-up or the backup, with "job timed out", usually on an account with a
large imported history.

**Cause.** A job ran longer than its time limit, or the app restarted while it
ran, often because the container ran out of memory.

**Fix.** Check the container's restart count and that its memory limit is at
least the [supported floor](/getting-started/self-host-in-10-minutes/#requirements).
The admin page says what the job's limit was, and the log names long, expired
and cut-off jobs by queue; see [App logs](/guides/admin-overview/#app-logs).
A full-history import of a connected service may run for up to sixteen hours;
a second start of the same import for the same account stops at once and says
so in the log.

## Dashboard cards stay empty on a very large account

**Symptom.** On an account with years of minute-by-minute heart rate the
dashboard cards stay empty or reads answer `500`, the log shows
`rollup-full-backfill` failing with Postgres error `57014` (`canceling
statement due to statement timeout`), and the admins get a push that the job
keeps failing.

**Cause.** The summary tier for that account is incomplete, and the reads that
fall back to the raw readings run into the 60 second statement limit.

**Fix.** Usually nothing: the backfill works through the history one year at a
time with a longer limit of its own and hands what is left to a follow-up run.
Do not raise `DATABASE_STATEMENT_TIMEOUT_MS` first; see
[Large accounts](/self-hosting/scaling/#large-accounts) for when that helps.

## Admin says the server runs below the supported memory floor

**Cause.** The app container's memory limit is below 1536 MB, usually a 1 GB
limit from an older compose file. Node then gets a heap of about 524 MB, which
a long-used account fills.

**Fix.** Set `APP_MEMORY_LIMIT=1536m` (or more) in `.env` and run
`docker compose up -d`. On a platform without the compose file, raise the
container's memory limit there. See
[Requirements](/getting-started/self-host-in-10-minutes/#requirements).

## The app restarts with "JavaScript heap out of memory"

**Symptom.** The app log shows `FATAL ERROR: Reached heap limit Allocation
failed - JavaScript heap out of memory` and the container restarts.
`docker inspect` reports `OOMKilled` as `false`: the app hit its own heap
limit before Docker stepped in.

**Fix.** First check the memory limit as in the entry above. If it is at the
floor or higher and the error comes back, collect what the process logs before
it dies: it writes `runtime.heap.sampled` lines, a `runtime.heap.pressure`
report naming the work in flight at 85 % of the heap, and Node's own report
with `"trigger": "OOMError"`:

```bash
docker compose logs app --since 2h | grep -E '"runtime.heap.|"trigger": "OOMError"'
```

To capture what the heap is made of, set `HEALTHLOG_HEAP_SNAPSHOT=1` (and
optionally `HEALTHLOG_DIAG_DIR`, default `/tmp`); the app then writes one heap
snapshot at the first pressure report. A snapshot contains decrypted health
data and keys: never attach it to an issue, and delete it when you are done.
Turn the switch off again afterwards. Open an issue with the log lines.

## A restore waits and does not start

A restore never runs beside a backup or another large job, such as an import
or a nightly pass. The admin backups page says which one it waits for; the
restore starts about a minute after that job finishes.

## AI features stop for a while after errors

A provider that keeps failing is paused: after three failures in a row it is
skipped for five minutes, and from five on for half an hour, doubling with
each further failure up to a day. Background jobs leave it out while it is
paused; interactive requests such as the Coach still try it last. Fix the cause (key, model, address) and save the AI settings, which
ends the pause. See [When a provider keeps failing](/guides/ai-providers/#when-a-provider-keeps-failing).

## A backup fails with a message naming `BACKUP_MAX_STORED_MB`

**Symptom.** One account's row on the admin backups page keeps an old date, or
an upload is refused with `413` and `backup.upload.too_large`. The app log's
`job.data_backup` line has a warning for that account containing
`Backup stopped after`.

**Cause.** The account's encrypted copy is larger than the storage limit for
one stored backup, 2048 MB unless you changed it. This is a storage limit, not
a memory problem.

**Fix.** Set `BACKUP_MAX_STORED_MB` in `.env` to a larger number of megabytes
and run `docker compose up -d`. Make sure the database volume has room for two
copies of that size, since the old copy stays until the new one is complete.
The previous copy is still there in the meantime. See
[Backups kept in the database](/guides/backups/#backups-kept-in-the-database).

## A restore fails and everything was rolled back

**Symptom.** A restore on the admin backups page ends as failed, and the page
says the restore ran longer than the database allowed, waited on records
another process was changing, hit a record the database rejected, ran out of
disk space or memory, or lost its connection to the database.

**Cause.** The database refused the restore transaction, so nothing was
changed.

**Fix.** Act on the cause the page names: start again when the database host is quieter, free up disk space on
it, or check that the database is running. For a rejected record, the server
log names the table and the rule. The audit log records the cause and the
database's error code. See
[When the database refuses a restore](/guides/backups/#when-the-database-refuses-a-restore)
and [How long a restore may take](/guides/backups/#how-long-a-restore-may-take).

## The reading count drops a day after an Apple Health import

**Symptom.** An import reports millions of readings, and a day later the
account, the admin status page or a fresh export shows far fewer.

**Cause.** Expected. The nightly clean-up folds heart-rate, HRV and
blood-oxygen samples older than 90 days into hourly means, and other
high-frequency types into daily values. Heart rate from Google Health and Oura
is folded into hourly means the same way.

**Fix.** Nothing. See
[why the reading count drops](/guides/import-apple-health/#why-the-reading-count-drops-after-an-import).

## An update stops at migration 0409

**Symptom.** The update to v1.43 exits during the migration step with
`HealthLog migration 0409 stopped: … still stored in plaintext`, and every
later start refuses with `P3009`.

**Cause.** The v1.42 encryption backfill has not sealed every stored location
yet, usually because the host skipped v1.42 or stopped soon after updating to
it. Nothing was dropped.

**Fix.** Mark the failed attempt as rolled back, run v1.42.4 until the
backfill reports zero rows, then upgrade again. The commands are in
[Migration 0409 stops the upgrade](/guides/updates-and-deploy/#migration-0409-stops-the-upgrade).

## Report a problem with an error id

HealthLog sends nothing home, and only the operator can read an instance's
logs. Three things make a bug report findable without exposing anything
personal.

**The error id.** When the server fails (a 5xx answer), the
message shows **Error ID** with eight characters, for example `3f9a2c1b`, and
a button that copies the full id. A page that fails to render shows one when
the server has one to give. The id is the request id of the failing call;
every error answer of the API carries it as `meta.requestId` and in the
`x-request-id` header. A 4xx answer, such as a refused input or a missing
permission, shows no id: its message says what to change. An incoming
`x-request-id` is only adopted when it is 8 to 64 letters, digits and
hyphens; anything else is replaced with a fresh id.

**Support info, for everyone.** **Settings, About this app, Copy support
info** puts together in the browser the server version and build, the
browser, language, time zone and switched-on modules, the AI state (whether a
provider is set up, the usage level, which AI features are available and why
not), each connected source's health state, reason, last success, newest data
and recent sync attempts, and the last five error ids of this browser session.
It never contains a username, email address, name, server address, token,
recorded value or record id. Nothing is sent; the text goes to the clipboard.

**Support report, for the operator.** **Admin, System status, Support report**
summarises the instance: build and runtime, the database version, size and
last migration, which features are configured (as yes or no only), job
failures of the last 72 hours by queue and error class, connections per health
state, AI usage levels and provider state, notification delivery over 7 days,
backup freshness, and the 20 most frequent warning and error actions of the
process. Accounts appear as `Account 1`, `Account 2`. As a second layer the
finished text is scrubbed for the instance's own usernames, emails, names and
ids, and for tokens, URLs, IP addresses and host names, before it is shown.

To find the event behind an error id, type the id into **Error ID** under
**Admin, App logs**; see [App logs](/guides/admin-overview/#app-logs). The
same search works on the API:

```
GET /api/admin/app-logs?requestId=3f9a2c1b&ring=problems
```

`ring=problems` reads the buffer of the last 1,000 warnings and errors.
`docker compose logs app` and Loki carry the same events as JSON lines with
`request_id`, so an error id finds its line there too.

Read both texts before you post them, add the error id, and attach them to the
[bug report](https://github.com/MBombeck/HealthLog/issues/new?template=bug_report.yml).
They are built to contain nothing personal, but you are the one publishing
them.

## Where to look when something else breaks

- `docker compose logs -f app`: the app logs structured events; errors carry a
  request id, the same id the web shows as **Error ID**.
- `/api/version` confirms which build is serving.
- The **admin panel**: worker status shows whether the job worker is alive; the
  audit log shows sensitive operations.
- [GitHub issues](https://github.com/MBombeck/HealthLog/issues): search first.
