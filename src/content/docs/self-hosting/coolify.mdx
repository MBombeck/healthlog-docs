[Coolify](https://coolify.io/) is the deploy stack HealthLog itself ships on, so the moving parts are well-trodden. This page covers what bites first-time operators: the stale-digest pull, the host-side retag fallback when a deploy refuses to pull, and pinning a release.

## Why Coolify

Coolify gives you Docker-Compose-shaped self-hosting with a UI in front. For HealthLog that means you get the same `docker-compose.yml` the repository ships, plus a deploy webhook, image-watch on a GHCR tag, environment-variable management, and one-click rollback to a previous deploy. The trade-off is that Coolify does its own caching of pull manifests, which is where the stale-digest gotcha lives.

## Initial setup

1. **Create the application** in Coolify as a Docker Compose app. Point it at the public repo (`MBombeck/HealthLog`) or a clone you maintain.
2. **Pick the branch.** `main` is the single release trunk and is always deployable. Production should track `main`, or a pinned release tag to be more conservative.
3. **Compose file.** Use the repo's `docker-compose.yml` unchanged. The entrypoint already waits for Postgres, runs migrations, and starts the server.
4. **Environment variables.** Paste the required three secrets (`POSTGRES_PASSWORD`, `ENCRYPTION_KEY`, `API_TOKEN_HMAC_KEY`) plus any integrations you plan to enable. `DATABASE_URL` is derived from `POSTGRES_PASSWORD` inside the compose file's `environment:` block, so there is no connection string to manage. Every variable is described in the repo's `.env.production.example` and in the [environment reference](/reference/environment-variables/).
5. **Domain and TLS.** Coolify ships [Traefik](https://doc.traefik.io/traefik/) by default; set your domain and toggle the auto-TLS switch.

## The `pull_policy: always` requirement

HealthLog's `docker-compose.yml` ships with:

```yaml
services:
  app:
    image: ghcr.io/mbombeck/healthlog${HEALTHLOG_IMAGE_REF:-:latest}
    pull_policy: always
```

This is **load-bearing** for Coolify deploys. Without `pull_policy: always`, Coolify will happily restart the same image [digest](https://docs.docker.com/dhi/core-concepts/digests/) it had last time even after you've published a fresh tag. The explicit `always` policy ships in the repo's compose file; confirm the line is present after every compose-file edit.

## When a deploy refuses to pull: the host-side retag fallback

Coolify can hit a cache bug where a new image is published to GHCR but the deploy webhook fires against a stale manifest. The reproducible workaround is a host-side retag:

```bash
# SSH to the host
docker pull ghcr.io/mbombeck/healthlog:<version>
docker tag ghcr.io/mbombeck/healthlog:<version> ghcr.io/mbombeck/healthlog:latest
# Restart from the Coolify UI
```

The retag forces Coolify's next compose-up to use the freshly-pulled digest as the canonical `:latest`. Less elegant than autodeploy but reliable when the cache misbehaves.

The cleaner long-term fix needs no compose-file edit: the shipped image line reads `ghcr.io/mbombeck/healthlog${HEALTHLOG_IMAGE_REF:-:latest}`, so setting `HEALTHLOG_IMAGE_REF` in `.env` or in Coolify's environment UI pins the deploy to an explicit `:vX.Y.Z` tag or `@sha256:<digest>` and removes Coolify's cache from the path entirely.

## Worker-process split

To run the job worker in its own container, follow [Scaling](/self-hosting/scaling/) and uncomment the `app-worker` service in the shipped compose file rather than writing a new one: it merges the same environment block as `app` (`<<: *healthlog_env`), and a worker that misses part of that environment cannot send notifications or run the AI jobs.

## Postgres 18

From v1.46 the compose file runs Postgres 18 and moves an older Postgres 16 database across on the first deploy with the new compose file, through a short-lived `db-upgrade` service. It has `restart: "no"`, so Coolify shows it as exited, not failed. The deploy needs free disk about the size of the database; see [Moving to Postgres 18](/self-hosting/postgres-upgrade/).

## Resource sizing

`APP_MEMORY_LIMIT` (default `1536m`, the supported floor) caps the app container, and the worker example carries a matching `WORKER_MEMORY_LIMIT`. Raise it on a busy instance and never lower it; see [Requirements](/getting-started/self-host-in-10-minutes/#requirements). The Postgres service deliberately carries no `mem_limit`, so under memory pressure the app is killed before the database. A large Apple Health import needs disk rather than memory: the archive and the `export.xml` unpacked from it are streamed to `/tmp` in the container that runs the worker.

## Backups

The app dumps the whole database every night into its `backups` volume. Set up the optional off-host bucket so a copy of each dump, and of every account, leaves the host. [Which backup covers what](/guides/backups/#which-backup-covers-what) says what each one protects against.

## Logs and observability

Coolify proxies container logs through its UI. For longer-term retention, point the app at a Loki endpoint via `LOKI_ENDPOINT` (with `LOKI_USERNAME` / `LOKI_PASSWORD` for basic auth). The structured log lines are pre-formatted for Loki's structured-log path. The endpoint can be the base URL or the full push URL, and a Loki on the same Docker network or your LAN works. If a push fails, the container log gets one line with the Loki address and the reason, at most every five minutes. All three `LOKI_*` variables are on the shipped compose whitelist, so a value in `.env` or in Coolify's per-service environment UI reaches the container.

Glitchtip and Umami land in the admin-panel monitoring section; both honour the SSRF guard and only emit when explicitly configured.

## Common Coolify gotchas

- **An import in flight during a deploy fails.** An Apple Health import streams through `/tmp` inside the container, and a redeploy replaces the container. Start the import again after the deploy.
- **The deploy URL is a secret.** Coolify's deploy URL carries the application UUID as a query parameter. Do not commit it.
- **No source clone needed.** The published image is self-contained; the compose file pulls it from GHCR and never references a source directory, so a wiped checkout on the host cannot break a deploy.
