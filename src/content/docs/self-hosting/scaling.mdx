For single-user self-hosts, the bundled `docker-compose.yml` is enough — a single container runs the web app and the pg-boss worker side by side. Once you grow past that, the worker / web split below lets each scale independently. Two related operations tasks have their own runbooks: [encrypted off-host backups](/guides/backups/) and [encryption-key rotation](/guides/encryption-key-rotation/).

## Worker / Web Split

The optional `HEALTHLOG_PROCESS_TYPE` env var splits HTTP traffic and pg-boss background jobs into separate containers, so you can scale each independently.

| Value | Behaviour |
|-------|-----------|
| `all` (default) | Single container — HTTP + pg-boss in the same process. |
| `web` | HTTP only. No background job runs here; the container opens a send-only pg-boss connection to hand jobs (imports, document reads, lab scans) to the worker. Reminders, insight caching, and the nightly off-host backup run only on the worker. |
| `worker` | pg-boss only. The proxy refuses HTTP traffic with `503 Service Unavailable` and an `X-HealthLog-Process-Type: worker` header so a misrouted request fails loudly. |

Run **one** worker per database. pg-boss claims jobs atomically via row-level locking (`FOR UPDATE SKIP LOCKED`), so a second worker replica is safe — no job runs twice — but it doubles the DB load and muddies telemetry without adding throughput a personal instance needs. Scale the web containers instead.

```yaml title="docker-compose.scale.yml"
services:
  app-web:
    image: ghcr.io/mbombeck/healthlog:latest
    environment:
      HEALTHLOG_PROCESS_TYPE: web
      # ... rest of env

  app-worker:
    image: ghcr.io/mbombeck/healthlog:latest
    environment:
      HEALTHLOG_PROCESS_TYPE: worker
      # ... rest of env
```

Pin both services to the same explicit version tag in production so a deploy can never split the two across releases. See [Updates and deploy](/guides/updates-and-deploy/) for the full process-type matrix and the post-deploy version check.

A startup gate refuses to boot the reminder worker when
`HEALTHLOG_PROCESS_TYPE=web`, so an accidental cross-mode invocation aborts
immediately instead of silently doubling cron load. The off-host backup job
runs in the worker only, while the admin backup smoke test runs in the web
container — set the `BACKUP_*` vars on **both** (see
[Backups](/guides/backups/)).

## Document and lab-scan reads run on the worker

Since v1.40.0 the AI read of a document or a lab report runs as a background
job: reading a document for search, a document summary, filing suggestions,
extracting facts from a stored document, and a lab scan. The request only
queues the read and answers `202`, and the client polls the run until it ends,
so a slow model is not cut off by a proxy timeout. When the enqueue itself
fails, the request answers `503` straight away and nothing is charged.

"Waiting for the background worker" is what the app shows when a read has sat
in the queue for more than 30 seconds. On a single `all` container that is rare
and short. If it does not go away, no worker is consuming the queue: the worker
container is stopped, crashing on boot, or pointed at another database. A run
that no worker picks up within 15 minutes fails as `aiRuns.workerUnavailable`
and its AI budget reservation is handed back. That sweep is itself a worker
job, so with no worker running at all the run stays queued until one starts.

**In a web/worker split, the worker must run the same version as the web
containers.** Only a worker that knows the document read queue can execute it.
A worker left on a pre-v1.40 image never takes these jobs, so every document
read and lab scan waits and then fails, while everything else looks healthy.
Deploy both from the same image tag and restart them together.

## Healthchecks and liveness

- The **web** container's healthcheck polls `/api/health` every 30 seconds
  (`/api/version` is the deploy-verification endpoint, not the liveness probe).
- The **worker** exposes no port, and its liveness is in-process state only:
  the reminder worker updates an in-memory status that `/api/admin/status`
  (and the admin panel's worker-status card) reads from the same process. In a
  web/worker split the web container cannot see the worker's in-memory state,
  so the worker-status card is only meaningful in single-container (`all`)
  mode. Monitor a split worker through its container logs and pg-boss job
  activity instead; the failing-queues readout on the admin status page does
  span containers, because it asks the queue tables in Postgres.

Neither container depends on the other, so startup cannot deadlock; both wait
only on Postgres being healthy.

## Postgres connection-pool sizing

Every container that boots the image opens its own pool against
`DATABASE_URL`, with a ceiling of **20 connections per container** by default,
shared between Prisma and pg-boss. The operator knob is `DB_CONNECTION_LIMIT`:
the bundled compose file substitutes it into `DATABASE_URL` as
`connection_limit`, so setting it in `.env` reaches the container.
(`DATABASE_POOL_MAX` still works as a legacy explicit override, but it is not
on the compose environment whitelist.) Plan total Postgres slots as
**container count × connection limit** — a stock Postgres 16 ships with
`max_connections = 100`, so four web replicas plus one worker at the default
ceiling consume all 100 slots and starve every other client (`psql`, backups,
the Prisma CLI during a migration deploy).

In the default single-container setup (`HEALTHLOG_PROCESS_TYPE=all`) the web
requests and the background worker run in one process. Since v1.40.1 that
process holds one database client instead of one per server bundle (three
before, about 55 MB more memory and three pools each sized to the whole
budget), so web pages and background jobs share the one pool of
`DB_CONNECTION_LIMIT` connections. A limit sized for the web traffic alone
leaves the worker's jobs queueing for the same connections; keep the default of
20 unless you have a reason to lower it.

Rules of thumb:

- Set `DB_CONNECTION_LIMIT` on every container that needs a non-default
  ceiling; web and worker read the same variable.
- Keep the limit at 8 or above on web replicas — the analytics fan-out holds
  up to 4 concurrent slots per request.
- Worker replicas mostly use one connection per active job; `8` is plenty.
- If the sum approaches `max_connections`, raise the Postgres ceiling, lower
  the per-container pool, or front the database with PgBouncer in
  transaction-pooling mode.

## Memory

The compose file caps the app container with `mem_limit: ${APP_MEMORY_LIMIT:-1536m}`.
Node sizes its heap from that cap: `1536m` gives about 792 MB, `1g` about
524 MB. Before v1.40.1 the default was `1g`, and a long-used account filled
that heap in normal operation, so garbage collection stalled requests for
seconds and a weekly backup could end the process.

- **A host with 2 GB of memory or less.** Set `APP_MEMORY_LIMIT=1g` in `.env`,
  so Postgres and the system keep enough room. Do not go below 1 GB (see
  [Large accounts and memory](/guides/backups/#large-accounts-and-memory)).
- **A busy instance.** Raise it.
- **A split worker.** The worker example in the compose file carries its own
  `WORKER_MEMORY_LIMIT`, with the same `1536m` default.

If you set `APP_MEMORY_LIMIT` yourself already, the update to v1.40.1 changes
nothing. The Unraid Community Applications template and the TrueNAS app set no
memory limit, so this does not apply to them. The Portainer app template and
Unraid's Compose Manager deploy the project's `docker-compose.yml` and get the
same default; set `APP_MEMORY_LIMIT` as a stack environment variable there.

The Postgres service deliberately carries no `mem_limit`, so under memory
pressure the app is stopped before the database.
