If you run an Apple Watch plus a Withings ScanWatch plus the iPhone Health app, three different sensors are writing your step count for the same day. Without a resolver, the dashboard would triple-count and the AI Coach would talk about 30 000 steps in a day you spent on the couch. HealthLog's source-priority resolver picks **one canonical row per (user, day, metric)**, keeps the losing rows in the audit trail, and never silently merges values.

This is the classic [data fusion](https://en.wikipedia.org/wiki/Data_fusion) problem — also called [sensor fusion](https://en.wikipedia.org/wiki/Sensor_fusion): combining several imperfect sensors into a single, more reliable estimate. Rather than averaging readings blindly — which would let a noisy wrist estimate drag down a precise dedicated device — HealthLog ranks sources per metric by how trustworthy each is for that measurement, and takes the best available one. HealthLog uses the simplest, most explainable variant: a deterministic per-metric ranking, not a statistical blend, so the canonical value is always traceable to exactly one source row.

## The two-axis ladder

The resolver runs a different ladder depending on whether the metric is **cumulative** (a daily total that grows with activity) or a **point measurement** (a single sensor reading at a moment in time):

| Axis | Ladder | Why |
| ---- | ------ | --- |
| Cumulative activity — steps, active energy, distance, flights | **APPLE_HEALTH ≻ WITHINGS ≻ FITBIT ≻ MANUAL** | iOS HealthKit folds every contributing sensor (Apple Watch motion, iPhone motion, Withings ScanWatch via Health Mate) into one canonical daily aggregate. That aggregate is more complete than any single device's stream. |
| Recovery inputs — sleep, [HRV](https://en.wikipedia.org/wiki/Heart_rate_variability), [resting HR](https://en.wikipedia.org/wiki/Heart_rate), [respiratory rate](https://en.wikipedia.org/wiki/Respiratory_rate) | **WHOOP ≻ FITBIT ≻ APPLE_HEALTH ≻ WITHINGS** | A dedicated recovery strap is the primary sensor for nightly recovery signals, so it leads these ladders ahead of a general aggregator. |
| Point — weight, BP, [body fat](https://en.wikipedia.org/wiki/Body_fat_percentage), body temperature, [SpO₂](https://en.wikipedia.org/wiki/Pulse_oximetry), [VO₂ max](https://en.wikipedia.org/wiki/VO2_max) | **WITHINGS ≻ APPLE_HEALTH ≻ MANUAL ≻ …** | A dedicated Withings device is the primary sensor; the Apple Health row for the same reading is a second-hand copy received via the Health Mate iOS app, and a wrist estimate (WHOOP/Fitbit) ranks below both. Trusting the primary sensor avoids round-trip rounding and timezone-shift artefacts. |

The exact per-metric ladders are encoded in `src/lib/validations/source-priority.ts` and ship with the app — a few metrics tune the order (the ScanWatch pulse-ox leads SpO₂, for example). They're conservative — they minimise surprises for users who turn on a second source after months of running just one.

## The audit trail

The resolver never deletes the losing rows. Every `Measurement` lands in Postgres tagged with its `source` enum value (`MANUAL`, `WITHINGS`, `APPLE_HEALTH`, `WHOOP`, `FITBIT`, `IMPORT`, plus the server-derived `COMPUTED`); only the **aggregation pipeline** filters them through the ladder. Practically:

- The `/measurements` list view shows all rows. Filter by source to see what each integration contributed.
- The dashboard tiles, trend charts, Insights cards, and Coach answers all read the resolved aggregate.
- The doctor-report PDF prints the resolved aggregate, with an optional appendix listing per-source breakdowns.
- If you change your mind about a source ranking, the historic rows are still there — the next aggregation read picks the new winner without a backfill.

## Per-user override

The ladder is a default, not a rule. Per-user overrides live in `User.sourcePriorityJson` and edit through the **Sources** section of `/settings/thresholds`. Use cases:

- **You trust your Withings step count more than the iPhone aggregate.** Override the cumulative ladder to put `WITHINGS` ahead of `APPLE_HEALTH` for `STEPS` only.
- **You ran a multi-month period with manual weigh-ins before adding the Withings scale.** Override the point ladder to put `MANUAL` ahead of `APPLE_HEALTH` so the gap days don't lose the manual entries to a HealthKit echo.
- **You disabled an integration entirely.** Drop it from the chain; rows still arrive but the resolver skips them.

The override is a JSON document of the shape `{ "STEPS": ["WITHINGS", "APPLE_HEALTH", "MANUAL"] }`. Malformed JSON falls back to the default rather than 500-ing.

## What "winner per day" actually means

The resolver runs at the **day granularity** the metric uses. For cumulative metrics that's the user-local day (`Europe/Berlin` by default, configurable per user). For point measurements it's "per row" — there is no daily aggregate to pick, so the winner is decided per reading by source ranking, then time-of-day for tied sources.

The day boundary respects the user's timezone preference end-to-end. A Withings scale weighing at 23:55 local time and an Apple Health echo of the same reading at 23:58 UTC the next day resolve to the same canonical user-local day because the Apple Health row carries its own local timestamp from the export.

## Source-priority + Apple Health import

The [Apple Health import](/integrations/apple-health/) page covers the upload mechanics. Worth knowing once you've imported:

- A 10-year history import adds rows back to the start of your iCloud-synced history. The resolver runs at read time, not import time, so older days with no competing source see the imported rows immediately.
- Days that overlap with existing Withings data resolve via the point or cumulative ladder above — no double-counting, no manual deduplication required.
- The `result.recordsInserted` and `result.recordsUpdated` counts on the `ImportJob` row tell you how many days landed cleanly versus updated an existing row.

## Source-priority + comparison overlays

The [comparison overlay](/dashboard/comparison/) (vs. last month / vs. last year) reads from the same resolved aggregate. The prior-period mean is computed over the resolved daily series, not the raw multi-source row stream — flipping the toggle does not expose the audit-trail rows.

## When to override

A short rule of thumb: trust the device that produced the reading, not the system that re-syndicates it. Apple Health is a near-perfect aggregator for cumulative activity. Withings devices are the primary sensor for the point measurements they take. Manual entries are the gap-filler. The defaults reflect this; touch the override only when your hardware reality diverges.

## Wide-event observability

Every resolve runs through the `measurements.aggregate.resolve` wide-event log line with the ladder used, the source counts, and the winner per metric. Tail the structured logs (or query the Loki endpoint if you configured one) to see exactly which source backed each tile on a given day — useful when a user reports "the number on the dashboard doesn't match the number my watch shows".
