This page walks through what actually happens between the moment you open the **Insights** page and the moment you read a generated sentence. It complements the [feature catalogue's AI section](/features/#ai-coach--insights), which lists what's there; this page explains how the pieces fit together.

The diagram above is the bird's-eye view of the flow: your question (or a scheduled generation) goes through a snapshot builder, then a prompt assembler that bolts the system prompt, your locale, and the JSON response contract onto the snapshot, then a per-user provider chain that walks ChatGPT OAuth → BYOK OpenAI → BYOK Anthropic → local → admin-shared. The provider behind every step is a [large language model](https://en.wikipedia.org/wiki/Large_language_model) (LLM), a text-prediction model that is constrained here to emit structured JSON rather than free prose. The response parser validates the payload and sends one corrective retry if it is malformed. The sections below zoom in on each stage.

## What the Insights page shows

The `/insights` page is mostly **computed, not generated**. It renders a hero strip (greeting plus health score), the daily briefing, a trends row, per-metric status assessments, the derived readiness and recovery scores, rhythm events, the [ECG section](/insights/ecg-recordings/), and the Coach. Of those, only two pieces come from a language model: the **daily briefing** and the **comprehensive insight**. Everything else is server-side arithmetic over your own readings, and stays available with no AI provider configured at all.

The two generated pieces are warmed **overnight** by a budget-gated background job, so opening the page is a cache read instead of a synchronous model call. If the cache is cold (a brand-new account, or before the first nightly run), the page shows a *preparing* state rather than blocking the request.

## The daily briefing

The briefing is a short narrative paragraph plus up to five **key findings**: one-liners that each summarise a single trend with a tone (good / watch / info), an optional delta string ("↓ 4 mmHg"), and the metric and time window the finding was drawn from. The findings list is hard-capped at five so a runaway model cannot pad the surface with filler, and the prompt instructs the model to derive every finding from a number visible in the snapshot.

## What the response contract actually requires

The comprehensive insight parses against a Zod schema, and it is worth being precise about what that schema does and does not enforce.

**Required on every response:**

- A `summary` string.
- A five-step `classification` of the overall picture.
- A `findings` array and a `correlations` array.
- A `dataQuality` block describing how much data the generation had to work with.
- A `disclaimer` string.

**Optional on each recommendation:** a recommendation can be a plain string or a structured object. On the structured shape only the `text` is required; `severity` (info / suggestion / important / urgent), a stable `id`, a `rationale` (a data window from `last7days` / `last30days` / `last90days` / `allTime`, plus `comparedTo` and `deviation` strings), a `metricSource` naming the snapshot field the recommendation rests on, a `referenceId`, and a `confidence` value are all optional metadata the model may or may not emit.

Two of those optional fields are still bounded when present:

- `referenceId` must resolve to the curated medical-reference bundle (ids such as `esh-2023-bp-adults`, `who-2024-bmi-classification`, `aha-2023-resting-heart-rate`). A fabricated id fails parse.
- `confidence` must be an integer between 0 and 100. It is the **model's own estimate**, nothing more: there is no server-side confidence computation. A deterministic server-side score was designed at one point but never ran in production and was removed rather than wired in.

**When a response is malformed**, the generation gets exactly one corrective retry: a message that names the live contract field by field and embeds a minimal valid example payload. That example is validated against the schema by a test, so the corrective prompt and the validator cannot drift apart without the suite going red. If the retry still fails, the surface shows its error or preparing state rather than a half-formed result.

## Per-metric assessments interpret, they don't enumerate

Since v1.27.13 the per-metric assessment answers "where does this sit?" rather
than listing numbers back at you. For metrics with an established general
reference — resting heart rate, SpO₂, respiratory rate, body temperature,
sleep duration, waist, pulse-wave velocity, BMI, visceral-fat rating — the
assessment states which **guideline band** the current value falls in, each
band drawn from a **cited primary source**, plus what that band means in plain
words. The trend is judged by position: a shift near a band boundary leads the
text; movement deep inside a healthy band is a footnote, not a headline.

Two rules keep this honest:

- **The band position is computed server-side** and handed to the model as
  context. The model states it; it never computes it.
- **Metrics without an established general band say so** and are interpreted
  against your own baseline instead of a fabricated norm.

And, as everywhere else, a band is a description, not a verdict — the
[non-diagnostic standard](/explanation/non-diagnostic-standard/) applies to
every assessment sentence.

## How the multi-provider fallback chain works

Most users configure one provider — that's fine, the chain just has one entry. When you configure two or more under **Settings → AI**, the wrapper tries them in order. A provider is considered **hard-failed** if it returns:

- `401` / `403` — auth or scope problem.
- `429` — rate limit.
- `5xx` — vendor server error.
- Transport-level error — network refused, DNS failed, TLS handshake bad.

On hard fail the wrapper cascades to the next provider in your chain.

**A malformed body does not cascade.** If a provider answered but the body failed the contract, retrying against another provider just wastes another paid request, so the corrective retry runs against the same provider instead.

The **last provider that successfully answered** is cached for an hour per user. So after a vendor outage, the cascade only runs once — the next generation goes straight to the working provider. The "active provider" badge in **Settings → AI** shows which entry actually served the most recent generation, so you can see at a glance whether the fallback kicked in.

## Feedback

Feedback lives on the **Coach**: every settled Coach reply carries a small per-message thumbs pair, stored against the message. A separate recommendation-feedback endpoint (`/api/insights/feedback`) stores a helpful / not-helpful verdict per user and recommendation; rating the same recommendation twice is refused rather than double-counted.

Today, feedback affects two things:

1. **Admin observability.** A daily aggregator (`feedback-aggregator`, runs at 04:00 Europe/Berlin) writes a per-(severity × provider × prompt-version) helpful-rate summary into `AppSettings.adminAiInsightsFeedbackSummary`. The admin can see at `/admin/ai-quality` whether one provider is producing output users find useful and another isn't, or whether a new prompt version is regressing.
2. **Per-user learning** *(not yet enabled)*. The cross-user prompt ratchet — feeding aggregate helpful-rate data back into the system prompt — is intentionally deferred until enough feedback has been collected to be statistically meaningful.

Feedback is **not** used as a soft-block filter. Output isn't hidden because previous similar output got down-voted; that would create a feedback loop where the model only ever surfaces what's already popular and never tells you the thing you need to hear.

## Privacy: feedback is per-user only

Your individual thumbs-up / thumbs-down votes are stored against your user id and **never leave your instance** in any form an admin can read back. The `/admin/ai-quality` aggregate is only counts, grouped by severity and provider. The per-user feedback rows are admin-invisible: there is no admin route that returns them, and the daily aggregator is the only consumer of the table.

The aggregator runs **on the same Postgres** that holds the rest of your data. Cross-user feedback data is never exfiltrated to the cloud, and the daily summary only writes counts (number of up-votes / down-votes per group), not text.

If you delete your account, your feedback rows cascade-delete with the rest of your data via the standard GDPR cascade — there is no orphan row left behind to feed an aggregate after you're gone.
