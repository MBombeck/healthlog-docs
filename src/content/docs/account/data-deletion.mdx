HealthLog has three distinct deletion paths, and they affect different sets of data. This page enumerates every model touched by each path so you can pick the right one with confidence — and so you know what you've still got after.

## Three deletion paths

| Path | Scope | Triggered by | Confirm string | What stays |
|------|-------|--------------|----------------|------------|
| **Delete all data** | Every row one account owns, across 99 user-scoped models | `/settings/advanced` → "Delete all data" | `DELETE` | The account and the credentials that sign into it |
| **Delete account** | One user, including the account itself | `/settings/account` → "Delete account" | `DELETE_ACCOUNT` | Audit-log entries that reference other users still survive (the row's `userId` is purged but the audit row itself remains for the rest of the audit trail) |
| **Wipe all data** (admin only) | Every account's health data, instance-wide: 98 tables (the per-account plan minus one exemption), derived from the wipe plan since v1.37.1 | `/admin/danger-zone` → "Wipe all data" | `DELETE ALL` | Accounts and their sign-in credentials, instance configuration, and shared-access grants |

The two per-account paths are the ones a user runs themselves under [GDPR Art. 17](https://gdpr-info.eu/art-17-gdpr/) (right to erasure), and they are the ones held against `prisma/schema.prisma` by a test. The instance-wide wipe was meant for refurbishing a self-hosted box; since v1.37.1 it derives from the same plan and is held by the same test.

## What "Delete all data" deletes

`DELETE /api/settings/data` with body `{ "confirm": "DELETE" }` removes every row the calling account owns, keeping only what the account needs to sign in again. An account with a second factor enrolled has to pass a fresh step-up first.

The list of models is not written in the route. It is declared once in `src/lib/data-wipe/wipe-plan.ts`, and `src/__tests__/data-wipe-completeness.test.ts` enumerates the Prisma schema and fails when a model belongs to neither the wipe list nor one of the two exemption lists. That test is why the number is 99 rather than the thirteen the route deleted while telling people it had deleted everything.

Covered, in the order the plan declares (children before parents, so the per-model counts in the audit row are truthful): measurements and every derived tier built from them, medications and their schedules and intake history, mood, the clinical record, activity, context and engagement, documents, the AI surfaces including Coach messages, sharing grants, integrations, notification transports, and the API surface with its operational trails.

Everything runs in one transaction with a 120-second budget, because a half-applied wipe is worse than none: the person is told it succeeded either way. Soft-deleted rows go too — the delete carries no `deletedAt` filter, so the tombstone goes with the record. The personal columns carried on the account row itself are reset in the same transaction, and the reset is held to the `User` model's columns by the same test.

### What "Delete all data" preserves

Only the sign-in layer, and each entry carries its reason in the plan file: passkeys, second-factor credentials and recovery codes, trusted-device grants, the session performing the wipe, per-device refresh tokens, and the in-flight challenges that expire on their own within seconds. Removing those would not be data deletion, it would be account deletion, and that has its own path.

A single `user.data.clear` audit row is written **after** the transaction commits, so it survives the deletion of the person's own audit history and stands as the receipt for the erasure they asked for.

## What "Wipe all data" deletes

The admin "Wipe all data" action at `/admin/danger-zone` runs `DELETE /api/admin/data` with body `{ "confirm": "DELETE ALL" }`. It's rate-limited (5/min/IP and 5/min/admin), requires the admin role, and audit-logs the intent **before** the transaction starts — so the trail describing "an admin is about to wipe data" survives even if the operation crashes mid-way.

:::note[Derived from the wipe plan since v1.37.1]
The route no longer carries its own list. It clears the models the per-account wipe plan declares, minus one deliberate exemption, and a build-time rule fails if the route ever names a table inline again. On builds before v1.37.1 the route held an inline list written years earlier and cleared nine tables of the 122 in the schema, reporting the same success line however much was cleared; labs, documents, cycle and journal entries, mood, workouts, sleep, Coach conversations and achievements all survived that wipe. On those builds, run the per-account "Delete all data" on each account instead, or clear the database.
:::

Inside a single Postgres transaction, for every account at once: 98 tables, the per-account plan minus the single `AccountGrant` exemption. That is the per-account "Delete all data" scope applied instance-wide, so the enumeration above applies here too: measurements and every derived tier, medications with their schedules and intake history, mood, the clinical record, activity, context and engagement, documents, the AI surfaces including Coach messages, integrations, notification transports, and the API surface with its operational trails. The per-user columns on each `User` row are reset in the same transaction, held to the model's columns by the same completeness test.

Two consequences of the wider scope are worth knowing before pressing the button:

- **The audit history goes with it.** Audit rows are part of the operational trail and are wiped. The `admin.data.clear.start` row written before the transaction survives a crash or rollback; on success, a fresh `admin.data.clear` row written after the commit restarts the trail with the receipt for the wipe itself.
- **In-database backups go with it.** `DataBackup` rows are in the wipe scope, so `/admin/backups` cannot undo an admin wipe. Objects already written to an off-host bucket are untouched, and restoring one of those is the recovery path.

### What "Wipe all data" preserves

Every survivor is one of three things:

- **The sign-in layer**: accounts, passkeys, second-factor credentials and recovery codes, trusted devices, sessions, per-device refresh tokens, and the in-flight challenges that expire on their own. Nobody is locked out by the button.
- **Instance configuration**: the `AppSettings` singleton (registration flag, notification globals, VAPID keys, etc.), rate-limit buckets, host telemetry, the seeded symptom catalogues, and the invite ledger.
- **Shared-access grants.** `AccountGrant` rows are the one deliberate exemption from the per-account plan, for the same reason accounts and passkeys survive: the wipe clears health data and leaves the identity and authorization layer standing. If you are refurbishing a box for somebody else, check **Settings → Shared access** on each account, or clear `account_grants` on the database, before handing it over. A wiped instance still knows who could open whose record. See [Give another account access to your record](/guides/shared-access/).
- **Managed profiles hold a floor that a wipe respects.** A record with no login of its own may never be left with nobody looking after it, so an operation that would strip the last guardian is refused rather than silently orphaning the record. That holds on a data wipe and on a guardian deleting their own account, not only on the button that looks like it would. The way to end such a record is to delete the profile. See [Records with no login of their own](/guides/managed-profiles/).

## What "Delete account" deletes

A user-initiated `DELETE /api/settings/account` with body `{ "confirm": "DELETE_ACCOUNT" }` removes the user's account and everything attached to it.

The handler:

1. **Refuses last-admin deletion.** If the user is the only admin on the instance, the request fails with `400 The last admin account cannot be deleted` so you can never lock the instance out of its own admin panel.
2. **Audit-logs the intent** as `user.account.delete` before doing anything destructive, so the trail predates the deletion.
3. **Destroys every active session** for the user — the device that initiated the delete is signed out; every other browser, tab, and native client is signed out on the next request.
4. **Explicitly purges the user's `AuditLog` rows** (IP addresses, login geo), which schema-level `onDelete: SetNull` would otherwise keep with a nulled `userId`.
5. **Deletes the `User` row.** Postgres `ON DELETE CASCADE` then takes care of every model that holds a foreign key back to the user:
   - Passkeys, sessions, auth challenges
   - Measurements, mood entries
   - Medications, medication schedules, reminder phase configs, intake events, Telegram reminder messages
   - API tokens, refresh tokens
   - Withings connections, integration status snapshots
   - Notification channels (and their per-channel preferences via the channel FK)
   - Push subscriptions, Telegram scheduled deletions
   - Data backups (own snapshots are wiped so a recovered DB doesn't leak the user's history through a rebuild)
   - Idempotency keys, devices, achievements
   - Shared-access grants **in both directions**: every `AccountGrant` naming the deleted account as the owner *or* as the delegate, whatever its state. Anyone who could open this user's record loses that access, and this user loses access to any record that was shared with them.

### Why GDPR-clean and what it means

`AuditLog` uses `onDelete: SetNull` rather than `Cascade` because the rows themselves are operationally useful even after the user is gone — admin tooling, security forensics. Without an extra purge step, the row would survive with `userId = null` but still carry the user's IP address and login city. An explicit `deleteMany({ where: { userId } })` runs on account deletion so it is genuinely complete erasure (right to erasure) and not just disconnection.

After the transaction commits, the deleting request's own wide event is annotated `settings.account.delete`, so the operational telemetry records that the deletion happened. The audit log itself keeps nothing for the deleted account.

### What "Delete account" preserves

- **App settings** — never user-bound to begin with.
- **Other users' audit-log entries** — the deleted user's `AuditLog` rows are purged, but rows that mention them as a *target* (e.g. "Admin X force-logged-out user Y") stay because they belong to the actor's audit trail, not the deleted user's.
- **The instance itself** — deleting the last non-admin doesn't tear anything down; the app keeps running.
- **Audit rows recording that this account opened somebody else's record.** They belong to the *other* person's record, and they render as "a deleted account" rather than being nulled. Turning "your daughter opened your record" into "you opened your record" would be worse than an unresolvable id.

## Backups and the right to be forgotten

If your instance has off-host S3 backups configured ([Scaling & Operations](/self-hosting/scaling/)), the user's data still exists in those snapshots until the bucket lifecycle policy expires them. That is by design — backups are the floor against accidental deletion — but if a user invokes Art. 17, you may also need to:

1. Identify any in-database `DataBackup` rows for that user — `onDelete: Cascade` on the FK takes care of those automatically when the user is deleted.
2. Purge the equivalent objects from S3 (the worker holds `PutObject` + `GetObject` only, so this is an operator action, not an in-app one).
3. Note in your records that the bucket-side purge happened, so the next audit shows the steps were taken.

The HealthLog code never auto-prunes off-host backups — that's intentional ([Scaling & Operations](/self-hosting/scaling/) explains why a compromised worker must not be able to wipe your backup history).

## Public Privacy Policy page

Every HealthLog instance serves a public Privacy Policy at `/privacy` — reachable without an account so app-store reviewers, prospective users, and self-hosted-instance visitors can read it before signing up. The page was added so the iOS build could clear App Store Connect submission, but it doubles as the canonical DSGVO / GDPR transparency surface for every deployment:

- **EU GDPR / DSGVO data-subject rights** are enumerated explicitly — right of access (Art. 15), rectification (Art. 16), erasure / "right to be forgotten" (Art. 17), restriction (Art. 18), data portability (Art. 20), and objection (Art. 21) — each cross-linked to the in-app surface that fulfils it.
- **Apple HealthKit quantity-type list** is disclosed in full so reviewers and users see exactly which HealthKit categories the upcoming iOS app reads — body mass, blood pressure systolic + diastolic, blood glucose, heart rate, oxygen saturation, body fat percentage, lean body mass, BMI, HRV SDNN, sleep analysis, resting heart rate, step count, active energy burned, flights climbed, walking + running distance, VO₂ max, and body temperature.
- The page renders from `/privacy` on every instance (self-hosted + demo), is public, and contains zero per-user data.
