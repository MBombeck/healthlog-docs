The AI Insights wrapper supports five provider types. **Settings → AI** is the one place you configure all of them, plus the order in which the [multi-provider fallback chain](/insights/how-it-works/#how-the-multi-provider-fallback-chain-works) tries them.

This page covers the setup paths for each provider, the fallback-chain editor, and the **Test connection** button.

## The Settings → AI page

The panel is **dropdown-driven**: one provider dropdown sits at the top, and the configuration form below switch-renders for whichever provider you pick. Below the form sits the fallback-chain editor.

The dropdown is the **only** source of truth for which provider you're editing. Switch from Codex to OpenAI direct and the Codex token isn't lost — it's parked in the encrypted config table; switching back later re-hydrates the form. So you can keep a long-tail OpenAI key around as a backup without losing it just because Codex is your daily driver.

## Connect with ChatGPT (Codex)

The headline path. If you already pay for ChatGPT Plus or ChatGPT Pro, this is the cheapest way to power Insights — it uses the same `chatgpt.com/backend-api/codex/responses` endpoint the official Codex CLI uses, against your ChatGPT account, with no separate API plan.

1. Pick **ChatGPT (Codex)** in the provider dropdown.
2. Click **Connect with ChatGPT**.
3. HealthLog displays a short user code (e.g. `RGRP-N5F7U`) and opens `https://auth.openai.com/codex/device` in a new tab.
4. Enter the code on that page and confirm the access prompt with your ChatGPT account.
5. The Settings panel polls in the background and switches to **ChatGPT connected** — done.

There is no redirect URL to whitelist, so the flow works on any HealthLog instance, including hosted self-hosts behind a domain. The OAuth refresh token is stored AES-256-GCM encrypted; HealthLog rotates the access token transparently before each request.

The default model is `gpt-5.3-codex` — the codex-optimised slug that ChatGPT Plus and Pro tiers can call. Operators can pin a different default for their plan tier via the `CODEX_MODEL` environment variable.

To **disconnect**, click the *Disconnect* button next to the badge — that revokes the stored token. Reconnect any time.

:::note
If you connected before v1.4.14, click **Disconnect** and reconnect once. Earlier storage forms didn't carry the `chatgpt_account_id` claim that the Codex backend now requires.
:::

:::note
The **Connect with ChatGPT** button is hidden on instances where the operator has not configured `CODEX_OAUTH_CLIENT_ID`. On those instances, the OpenAI-direct path below is the only OpenAI option.
:::

## OpenAI direct

The classic path: bring your own OpenAI API key.

1. Pick **OpenAI** in the provider dropdown.
2. Paste your API key (the form takes both `sk-…` and project-scoped `sk-proj-…` keys).
3. Pick a model from the dropdown — `gpt-4o`, `gpt-4o-mini`, `gpt-5`, etc. — or type a custom model slug into the override field if your account has access to a model that isn't in the preset list yet.
4. Click **Test connection** to verify the key + model combination before saving (see below).
5. **Save**.

The key is stored AES-256-GCM encrypted in the database. Switching providers does not delete the key; it stays in the config table for whenever you switch back.

If your admin has set a shared OpenAI key (for the whole instance), a checkbox above the API-key field lets you opt into the shared key. You can switch back to your own key at any time.

## Anthropic Claude

1. Pick **Anthropic** in the provider dropdown.
2. Paste your Anthropic API key.
3. Pick a model — `claude-3-5-haiku`, `claude-3-5-sonnet`, etc.
4. **Test connection**, then **Save**.

Same encryption-at-rest as OpenAI direct.

## Local / OpenAI-compatible

For [Ollama](https://ollama.com/), LM Studio, vLLM, LiteLLM, or any other endpoint that speaks the OpenAI Chat Completions API. This is the fully self-contained path — your health data never leaves your network, since the model runs on hardware you control.

1. Pick **Local / OpenAI-compatible** in the provider dropdown.
2. Enter the **base URL** of your local endpoint (e.g. `http://192.168.1.10:11434/v1` for an Ollama box on your LAN).
3. If your endpoint requires an API key, enter it; many local endpoints accept a placeholder string.
4. Enter the **model slug** your local endpoint exposes (e.g. `llama3.1:70b-instruct-q5_K_M`).
5. **Test connection**, then **Save**.

This path is the one that keeps your data on your network end-to-end. The base URL is treated as a per-user secret and is encrypted at rest, the same way API keys are — switching providers cannot leak a saved local URL to OpenAI / Anthropic on the next request.

## Admin-shared OpenAI

If your admin has configured a shared OpenAI key on this instance, you can opt into it without ever pasting a personal key. Pick **OpenAI** and tick the *Use admin-shared key* checkbox; the form hides the API-key field and uses the instance-level key for your generations. You can opt out and provide your own key at any time.

The admin can set this from `/admin/integrations` → AI section.

## The fallback chain

Below the per-provider form sits the **fallback chain editor**. It lists every provider you've configured, in the order the wrapper will try them on hard failures. Each row carries:

- An **arrow up / arrow down** pair to reorder.
- A **toggle** to disable an entry without removing it (useful when you want to test a single provider in isolation).
- A **remove** button to delete the entry from the chain (the saved credentials stick around).
- An **active** badge on the entry that served the most recent generation.

The hard-failure cascade is `401 / 403 / 429 / 5xx / transport`. Schema 422 still bubbles — re-trying a malformed body against a different provider just wastes another request. See [How the fallback chain works](/insights/how-it-works/#how-the-multi-provider-fallback-chain-works) for the full policy.

The chain is **per user**. You can have one user on Codex with OpenAI fallback, another user on a local Ollama with no fallback, a third user on the admin-shared OpenAI key — all on the same instance.

## Test connection

The **Test connection** button next to each provider form fires a single low-cost request against the configured provider + model + endpoint and surfaces the result inline:

- **Green check** — the provider answered. The model slug is on the allow-list, the key works, the endpoint is reachable.
- **Red error** with a clear message — the credential, the model slug, or the URL is wrong. The exact upstream error message is shown (after redaction of the key in transit). For Codex, model slugs that aren't in the allow-list for your ChatGPT plan tier are rejected with a clear "model not available on your plan" message.

Test connection does **not** generate a real insight — it does not consume your rate-limit budget, and it does not write to the audit log. It also does not save the form; you still need to click **Save** after a green check.

## Where credentials live

| Item | Storage |
|------|---------|
| OpenAI API key (per user) | `User.aiOpenAiApiKey` — AES-256-GCM |
| Anthropic API key (per user) | `User.aiAnthropicApiKey` — AES-256-GCM |
| Local base URL (per user) | `User.aiLocalBaseUrl` — AES-256-GCM |
| Local API key (per user) | `User.aiLocalApiKey` — AES-256-GCM |
| Codex OAuth refresh token | `User.codexRefreshToken` — AES-256-GCM |
| Provider chain config | `User.aiProviderChain` — JSON, with embedded keys also AES-256-GCM where present |
| Admin-shared OpenAI key | `AppSettings.adminOpenAiKey` — AES-256-GCM |

All values are encrypted using `ENCRYPTION_KEYS` (versioned). Online key rotation is supported via `pnpm tsx scripts/rotate-encryption-key.ts <id>` — see [Self-Hosting → Scaling](/self-hosting/scaling/#encryption-key-rotation).

## When does each provider get used?

A generation request flows like this:

1. The wrapper reads your provider chain.
2. It tries the first **enabled** entry. If a provider successfully answers, it's cached as the "last working" provider for an hour.
3. On hard failure, the wrapper cascades to the next enabled entry. Schema 422 bubbles.
4. If every entry hard-fails, the wrapper surfaces a clean error and writes the cascade trail to the audit log — so the admin can see at `/admin/ai-quality` and `/admin/app-logs` exactly which providers failed in which order.

The "last working" cache is **in-process** and **per user** — it's an hour-long preference that lets the cascade re-stabilise after a vendor outage without re-running the full chain on every generation.
