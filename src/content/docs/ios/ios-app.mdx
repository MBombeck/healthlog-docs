HealthLog ships a native [SwiftUI](https://developer.apple.com/xcode/swiftui/) iOS client alongside the web PWA. It is on the **[App Store](https://apps.apple.com/app/id6769501341)**, with [TestFlight](https://testflight.apple.com/join/bucuTBpa) carrying the newest builds for free, and it talks to the same `/api` surfaces as the browser — same server, same data, same source of truth. The phone is a view plus a write-ahead log; your self-hosted instance remains the database.

The iOS source lives in its own repository: [github.com/MBombeck/healthlog-iOS](https://github.com/MBombeck/healthlog-iOS).

## Requirements

- **iOS 18 or newer** for the app itself, **watchOS 11 or newer** for the Apple Watch app.
- **iOS 26 or newer** on an Apple-Intelligence-eligible iPhone for the on-device AI coach.
- A reachable HealthLog instance served over HTTPS. Passkeys and the secure-cookie path require a valid TLS certificate — see [TLS certificates](/self-hosting/tls-certificates/).
- The app, either from the [App Store](https://apps.apple.com/app/id6769501341) or from the free [TestFlight](https://testflight.apple.com/join/bucuTBpa) beta, which runs ahead of the store.

## Install and pair

**HealthLog - Companion App** on the [App Store](https://apps.apple.com/app/id6769501341) is a one-time purchase with no subscription; the free [TestFlight](https://testflight.apple.com/join/bucuTBpa) beta carries newer builds first. The app is available in English and German, and the [iOS repository CHANGELOG](https://github.com/MBombeck/healthlog-iOS/blob/main/CHANGELOG.md) tracks what landed in each build.

The app signs in against your own server; there is no central HealthLog account service. Installing, entering your instance's address and signing in are covered step by step in [Connect the iOS app](/getting-started/connect-ios-app/). The token exchange behind it is documented under [Native API clients](/reference/native-clients/).

## Apple Health (HealthKit) live two-way sync

The headline feature: the iPhone reads from and writes to [Apple Health](https://en.wikipedia.org/wiki/Apple_Health) ([HealthKit](https://developer.apple.com/documentation/healthkit)) and keeps it in step with your server in near real time. This is distinct from the one-shot `export.zip` import — that path is described under [Apple Health import](/guides/import-apple-health/) and remains available for backfilling historical data from any device.

On first sync the app requests HealthKit read permission for the metric types it supports. iOS shows its standard per-type consent sheet; you can grant or deny each type. Typical metrics the app reads and forwards to your server include:

- **Steps**, active energy, and walking/running distance (aggregated to one row per local day).
- **Weight** and [body-composition](https://en.wikipedia.org/wiki/Body_composition) values.
- **Blood pressure** (systolic and diastolic) and resting/heart-rate readings.
- **Blood glucose** ([blood sugar level](https://en.wikipedia.org/wiki/Blood_sugar_level)).
- **Sleep** analysis and heart-rate variability.
- Exercise and stand minutes, stand hours, mindful minutes, State of Mind and
  AFib burden, with an app build that sends them.

Grant only the types you want synced — denied types simply never leave the phone.

On iOS and watchOS 27 the app can also read the newer RMSSD heart-rate
variability. The server stores it as HRV RMSSD, next to SDNN and never
averaged with it, and the HRV page charts each measure on its own.

The other direction: readings you type into HealthLog, Withings readings and
imported readings are written to Apple Health by the app. Readings from a
[measurement token](/guides/ingest-token/#write-readings-to-apple-health) (a
scale or Home Assistant) are written only when that token's **Write readings
to Apple Health** switch is on, which needs an app build that reads it.

The Apple Health card under **Settings → Integrations** lists, per type
(**By data type**, in the card's collapsed
[details](/guides/integrations/#details-for-a-bug-report)), when the server
last received it and how: in the background, when the app came to the front,
or from a manual **Sync all**. Medication doses have their own entry. When a
later arrival came from opening the app, the entry adds "Last in background"
with its own time, so you can see whether the phone still delivers by
itself.

### How the round-trip stays clean

Live reads use HealthKit's observer and anchored-query APIs, and a background-processing task gives delivery a second chance when the app is not in the foreground. Every iOS-side write carries a stable external identifier so the server and Apple Health do not echo each other's writes back and forth. Day-aggregated cumulative metrics (steps, energy, distance) use the same `stats:<HKType>:<YYYY-MM-DD>` external-ID convention the bulk importer uses, so a phone sync and a later `export.zip` import resolve to the same rows rather than duplicating. See [Source priority](/explanation/source-priority/) for how readings from the phone, a Withings device, and manual entry collapse to one canonical value per day.

### Workouts backfill their heart-rate curve

A workout recorded before the phone learned to send heart-rate detail can pick
that detail up afterwards. When the app sends a session the
server already holds and the payload this time carries the reading-by-reading
heart rate, the server attaches the curve to the workout that is already there
and it shows on the workout's detail page. The session itself is untouched:
duration, calories, the average and maximum heart rate and the times all stay as
first recorded. A workout that already has its curve is left alone, so the phone
can walk back through years of history as often as it likes without writing
anything twice. If one session's readings arrive unusable, that session alone is
reported back and the rest of the batch still lands.

## What the home screen can show

The app's home screen renders the summary the server computes; it never recomputes a figure of its own.

## Reminders and push

The app schedules **local notifications** for medication doses, with action buttons (taken, snooze, skipped) that mark an intake through the server without opening the app. It tells the server that it handles these reminders, so the server does not push the same reminder to the phone a second time.

The **pen list** shows a container's manufacturer and printed strength, which you fill in on the medication's **Supply** tab.

A self-hosted server cannot send [APNs](https://en.wikipedia.org/wiki/Apple_Push_Notification_service) push to the App Store or TestFlight build. Apple binds a push to the developer team, bundle id and signing key of the app, and only the publisher holds that key. For reminders and alerts from the server itself, use [Web Push](/guides/reminder-channels/) (install the web app on the home screen), ntfy or Telegram; the app's own local reminders work regardless. Server-side APNs works only for a copy of the open iOS client that you build and sign under your own Apple identity, with the `APNS_*` [environment variables](/reference/environment-variables/) set.

## On-device AI coach

On iOS 26+ Apple-Intelligence-eligible iPhones, the app offers a conversational coach built on Apple's [Foundation Models framework](https://developer.apple.com/documentation/foundationmodels). The prompt and the response are generated on the device and never leave it. This is separate from the server-side, multi-provider [AI Insights](/insights/how-it-works/) the web client uses; on iOS you can use either path.

## Doctor-report export

The iPhone can generate a doctor-report PDF from the device, mirroring the [health-record export](/reference/fhir-api/) the web client produces. The export bundles vital signs and medication compliance using the same [HL7 FHIR R4](https://hl7.org/fhir/R4/) / [LOINC](https://loinc.org/) mappings the server uses, so records interchange between the two clients.

## Security on the device

- **Passkey-first sign-in** via Face ID or Touch ID ([WebAuthn](https://en.wikipedia.org/wiki/WebAuthn)).
- **Keychain storage** for tokens, scoped to the device and available only after first unlock.
- **Public-key (SPKI) [certificate pinning](https://en.wikipedia.org/wiki/Public_key_pinning)** on authenticated requests — see [Certificate pinning](/security/certificate-pinning/) for how to configure a pin for a self-hosted certificate.
- A log sanitiser that strips tokens and hostnames from every log line.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Sign-in fails immediately | The instance is not served over HTTPS, or the certificate is not trusted by the device | Serve over valid TLS; see [TLS certificates](/self-hosting/tls-certificates/). For a private CA, configure a [pin](/security/certificate-pinning/). |
| No HealthKit data appears | Read permission was denied for those types | Re-grant in iOS **Settings → Privacy & Security → Health → HealthLog**. |
| Duplicate steps after an `export.zip` import | None — the external-ID convention dedupes phone syncs against the importer | If you still see duplicates, check [Source priority](/explanation/source-priority/). |
| Older ECG recordings are missing | A server before 1.39.8 refused some recordings | Update the server; recordings refused earlier arrive once the app sends them again, or right away by uploading the Apple Health `export.zip` under Import. See [ECG recordings](/insights/ecg-recordings/#how-recordings-arrive). |
| Every request fails although the server is up | A server whose encryption key does not match its data answers every request with `503` `encryption.key_mismatch` | The operator restores the original key; see [the start-up key check](/explanation/encryption-at-rest/#the-start-up-key-check). |
